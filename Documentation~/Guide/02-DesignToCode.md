# 02. 기획을 코드 구조로

기획서를 받으면 코드를 쓰기 전에 "이 문장은 무엇으로 만드는가"를 먼저 정한다. Momoi Project에서는 같은 기획 요소라도 플레이어 데이터·인스턴스·이벤트·행동·키워드·도감 종류·MonoBehaviour 중 어디에 두느냐에 따라 Undo·저장·멀티플레이·기획자 편집이 저절로 되거나 안 된다. 이 장은 그 판단표를 주고, 카드 던전 기획 한 장을 실제 클래스 목록으로 옮기는 과정을 처음부터 끝까지 보여 준다.

이 장에서 쓰는 말:

| 말 | 뜻 |
|---|---|
| 플레이어 데이터 | 게임 중에 바뀌는 값을 담는 칸. 평범한 `[Serializable]` 클래스를 쓰고, 필드는 그냥 고친다. |
| Sync | 시스템이 플레이어 데이터의 사본(Mirror)과 지금 값을 비교해 바뀐 곳만 기록하는 동작. 이 기록이 Undo·저장·멀티플레이 전송의 바탕이다. |
| 구역 | 플레이어 데이터가 들어가는 저장 파일. 세션 구역(이번 판, `Session`)과 메타 구역(프로필, `Meta`) 둘뿐이다. |
| 인스턴스 | 클래스의 원본 값 하나(타격 카드, 고블린 …)를 도감에 채워 둔 항목. 게임은 원본을 읽기만 하고(`session.Instances`), 바뀌는 값은 판 데이터에 따로 둔다. 통째로 고칠 사본이 필요하면 `CopyInstance`로 깊은 사본을 만든다. |
| 이벤트 | "방금 일어난 일"을 값과 함께 담은 클래스. 게임 코드가 쏘고(`Publish`), 로그·도전과제·화면이 받는다. |
| 행동 | 플레이어 입력 하나를 담은 데이터 클래스(`GameAction`). 행동 하나 = Undo 한 단위 = 네트워크 한 묶음. |
| 키워드 | 등급·속성처럼 정해진 목록에서 고르는 글자 값. |
| Block | 기획자가 도감에서 골라 조립하는 로직 단위. 대상 Block(누구에게)·효과 Block(무엇을)·조건 Block(언제만)·코딩한 결과가 있다. |
| Trigger · Outcome | 도감 항목의 "언제(Trigger) → 무엇을(Outcome, 결과)" 두 칸. 로그·도전과제·능력·사용 기능이 같은 칸을 쓴다. |

---

## 1. 이 단계의 목표

기획서의 문장마다 "무엇으로 만들지"를 판단표로 정하고, 그 결과를 클래스 목록(데이터·인스턴스·이벤트·행동·키워드·Block·도감 종류)과 도감 항목 목록으로 적는다. 이 목록이 이후 모든 장의 설계도다.

## 2. 할 일 순서

1. 기획서를 한 장으로 요약한다(규칙 문장마다 번호).
2. **명사**를 뽑아 "게임 중에 바뀌는가 / 기획자가 채우는 원본인가 / 화면만의 것인가"로 나눈다. 한 명사 안에서도 고정 값(원본)과 바뀌는 값(판 데이터)을 가른다.
3. **동사**를 뽑아 플레이어 입력과 규칙의 한 걸음을 행동으로 만든다.
4. **"~하면 / ~할 때"** 를 뽑아 이벤트로 만든다.
5. **고르는 값**(등급·종류·태그)을 키워드로 만든다.
6. **남는 것 / 버리는 것**을 나눠 구역을 정한다.
7. **기획자가 계속 더할 것**을 찾는다: 같은 모양의 원본이면 인스턴스, "언제 → 무엇"을 항목마다 조립하면 도전과제·로그·사용 기능, 그 어디에도 맞지 않는 새 종류면 도감 종류.
8. 조립할 동작 단위를 Block으로, 한 항목만의 예외를 `[BindTo]`로 적는다.
9. 객체마다 `id`가 필요한지 정하고, 객체 사이의 연결을 id로 적는다.
10. 클래스 목록과 도감 항목 목록을 적어 팀과 맞춘다.

## 3. 판단 기준

### 3-1. 무엇으로 만들까 — 판단표

위에서부터 읽어 처음 맞는 줄을 고른다.

| 기획에서 이런 것이 보이면 | 이것으로 만든다 | 카드 던전 예 |
|---|---|---|
| 기획자가 수치를 채우는 원본이 여러 개(같은 모양, 다른 값) | 클래스 + 인스턴스(도감 › 인스턴스) | 카드·몬스터·물약 원본 |
| 게임 중에 바뀌고, 되돌리거나·저장하거나·조건으로 검사할 값 | 플레이어 데이터(`[Serializable]` 클래스 + 도감 › 플레이어 데이터). 원본에 있는 고정 값은 복사하지 않고 원본 ID만 둔다 | 판 `run`, 프로필 `profile`, 덱의 한 장 `DeckCard` |
| 다른 값에서 계산되는 값 | 저장하지 않는다(읽기 속성이나 함수) | `Fighter.IsDead` |
| 매 프레임 바뀌는 값, 화면 상태(위치·애니메이션·끌고 있는 카드·열린 창) | MonoBehaviour 필드 | 카드를 끄는 손 위치 |
| 플레이어 입력 하나, 또는 규칙이 한 걸음 나아가는 단위 | 행동(`SimpleAction`·`GameAction<T>`) | 카드 내기, 턴 끝 |
| "~하면 / ~할 때" 다른 기능(로그·도전과제·유물·연출)이 반응하는 순간 | 이벤트(`[GameEvent]`) | 턴 끝, 전투 승리 |
| 정해진 목록에서 고르는 글자 값 | 키워드(`[KeywordGroup]` + `[Keyword]`) | 등급·속성·카드 종류·상태 |
| 한 번 이루면 끝나는 목표 | 도전과제(도감, 코드 없음 또는 `[BindTo]`) | 첫 승리, 한 턴 30 피해 |
| 이벤트를 받을 때마다 쌓는 숫자 | 로그(도감) | 처치 수, 한 턴 최대 피해 |
| 쓰는 순간 효과가 나는 원본 | 클래스에 사용 기능 필드(`Usable`) | 카드·물약 |
| 항목마다 "언제 → 무엇"을 기획자가 조립하고, 위 기능과 규칙(한 번·숫자·사용)이 다른 새 종류 | 도감 종류(`GameData` + `[Database]`) + Trigger 감시 | 유물 |
| 기획자가 조립할 동작 하나(누구에게 / 무엇을 / 언제만) | Block(`TargetSelector<T>`·`Effect<T>`·`SimpleCondition`·`Reward`) | 피해, 모든 적 |
| 그 항목 하나에만 있는 예외 로직 | `[BindTo]` 함수 | 연쇄 번개 카드 |
| 여러 행동·Block이 같이 쓰는 게임 규칙 계산 | 평범한 static 함수 | 피해 계산, 덱 섞기 |

이 표 전체를 꿰는 핵심 기준이 하나 있다.

> **판 데이터에는 ID와 바뀌는 값만 둔다. 고정 값(이름·비용·그림·사용 기능·몬스터 공격 순서)은 원본에서 읽는다.**

덱에 든 카드 한 장이 카드의 이름·비용·그림·효과까지 들고 있으면, 같은 값이 덱의 장 수만큼 판 데이터에 복사된다. 그 복사본이 모두 Sync 대상이 되고, 판 저장 파일에 들어가고, 멀티플레이에서는 처음 맞출 때 통째로 전송된다. 그림 같은 에셋 참조는 판 저장에 담기지도 않는다. 원본 ID와 이 장만의 바뀌는 값(강화 여부)만 들면 저장·동기화가 작아지고, 기획자가 원본의 비용을 고치면 이미 덱에 든 카드에도 바로 반영된다. 원본은 `session.Instances`로 복사 없이 읽는다. 게임이 켜질 때 만든 표에서 찾으므로 자주 읽어도 빠르다. 원본은 모든 판이 같이 쓰는 값이라 게임 중에 고치지 않는다.

헷갈리기 쉬운 경계 몇 가지:

- **원본과 판 데이터.** "고블린"이라는 몬스터 정의는 바뀌지 않으므로 인스턴스다. 전투에 나온 고블린 한 마리의 지금 체력은 바뀌므로 플레이어 데이터다. 같은 개념이 두 클래스로 갈라지는 것이 정상이다(`MonsterData` 원본 → 전투 중 `Enemy`, `Card` 원본 → 덱의 `DeckCard`). 판 데이터 쪽은 원본 ID로 원본을 가리킨다.
- **이벤트와 행동.** 행동은 "하라"(입력), 이벤트는 "했다"(결과)다. `PlayCard` 행동이 실행되면 그 안에서 `CardPlayed` 이벤트를 쏜다. 로그·도전과제는 행동이 아니라 이벤트를 받는다.
- **매번 일어나는 규칙과 항목마다 다른 규칙.** "적이 쓰러지면 전투에서 뺀다"처럼 늘 같은 규칙은 행동·규칙 함수에 바로 쓴다. "이 유물은 첫 턴에 방어도"처럼 항목마다 다르고 기획자가 바꾸고 싶은 것만 Trigger·결과로 둔다.
- **키워드와 enum.** 기획자가 목록을 늘리고 이름을 고르는 값은 키워드다. 저장 값이 글자라 목록 순서가 바뀌어도 저장이 깨지지 않는다.

### 3-2. 어느 구역에 둘까

| 판이 끝나면 | 구역 | 저장 파일 | 카드 던전 |
|---|---|---|---|
| 버린다 | 세션(`Session`) | `run.json`(이어 하기) | 층·골드·주인공·덱·전투·유물·물약 |
| 남긴다 | 메타(`Meta`) | `profile.json` | 최고 층·누적 골드·해금 카드 |

- 판 데이터와 프로필 데이터를 한 클래스에 섞지 않는다. 플레이어 데이터 하나는 구역 하나에만 들어간다.
- 판이 끝날 때 남길 값은 판을 끝내는 행동이 프로필로 옮긴다(카드 던전의 `EndRun`).
- 로그는 범위(이번 판 / 누적)를 따로 고르고, 도전과제 달성은 늘 메타 구역이다. 이 둘은 클래스로 만들지 않는다.

### 3-3. 클래스 하나 = 개념 하나, 기능은 필드

- 카드를 "공격 카드 / 스킬 카드" 자식 클래스로 나누지 않는다. 카드라는 개념은 `Card` 하나이고, 종류는 키워드 필드(`tags`), 쓰는 효과는 사용 기능 필드(`usable`)가 맡는다. 새 종류가 생겨도 클래스가 늘지 않고, 기획자는 도감에서 값만 고른다.
- 붙었다 떨어지는 기능은 비어 있을 수 있는 `[SerializeReference]` 필드 하나로 둔다. `null`이면 그 기능이 없다.
- 상속은 "서로 다른 개념이 같은 부분을 나누고, 그 부분에 대해 같은 규칙(Block)이 돌아야 할 때"만 쓴다. 주인공(`Hero`)과 적(`Enemy`)은 다른 개념이지만 둘 다 피해·방어도·상태를 받으므로 공통 부분 `Fighter`를 두고, 효과 Block은 `Effect<Fighter>` 하나로 둘 다에 쓴다.
- 이벤트는 상속하지 않는다. 이벤트 받기와 `Subscribe<T>`는 형식이 정확히 같을 때만 받는다. 종류를 나누려면 필드를 두고 값 조건으로 거른다.
- 다른 값에서 계산되는 값은 필드로 두지 않는다. 필드로 두면 두 값이 어긋날 수 있고 Sync할 것이 는다.

### 3-4. `id`를 둘 객체와 연결 방법

`public string id;`를 두는 객체:

| 이럴 때 | 왜 |
|---|---|
| `Game.Find<T>(id)`로 다시 찾는다 | `Find`는 `id` 필드로 찾는다. |
| 행동의 대상이다(`GameAction<T>`) | 행동은 대상을 객체가 아니라 `target`(id)으로 실어 나른다. |
| `Game.Use`의 사용자·대상이다 | 사용 행동은 id만 담고, 끝날 때 최종 대상의 id로 `능력 사용` 이벤트를 쏜다. `id`가 없으면 예외로 사용 전체가 취소된다. |
| 같은 원본을 가리키는 판 데이터가 여러 개다(같은 카드 여러 장) | 원본 ID로는 장을 구별할 수 없다. `Game.NewId("접두어")`로 장마다 새 id를 준다. |

`id`가 필요 없는 객체: 플레이어 데이터 하나에 하나뿐인 뿌리 객체(`RunState`·`Profile`, `Game.Data()`로 꺼낸다), 한 객체 안에 하나뿐인 하위 객체(`Battle`), 인스턴스 원본(도감 항목 ID가 곧 이름이다).

연결은 객체 참조가 아니라 **id 글자**로 한다. 손패는 카드 객체 리스트가 아니라 카드 id 리스트이고, 가진 유물은 유물 ID 리스트다. 행동·이벤트의 필드도 id다. 이렇게 두면 저장·리플레이·네트워크에 그대로 실리고, Undo·불러오기 뒤에 객체가 바뀌어도 `Find`로 지금 객체를 다시 찾는다. 스프라이트 같은 에셋은 플레이어 데이터에 두지 않고 원본(인스턴스) 쪽에 둔다(3-1의 핵심 기준). 판 저장에는 도감 항목 참조만 ID로 담기고, 그 밖의 에셋 참조는 "저장할 수 없는 참조입니다" 경고와 함께 빠진다. 도감 항목 ID를 담는 글자 필드에는 `[DataRef(typeof(종류))]`를 붙인다. 도감에서 목록으로 고르는 칸이 되고, ID를 바꾸면 값도 따라 바뀐다.

## 4. 카드 던전에서 실제로

### 4-1. 기획 한 장

기획자에게 받은 문서를 규칙 문장 하나에 번호 하나로 줄였다.

> **카드 던전**
> 1. 플레이어는 주인공 '모모이'로 던전을 오른다. 한 판(런)은 1층에서 시작하고, 주인공이 쓰러지면 끝난다.
> 2. 판을 시작하면 체력 70, 골드 99, 시작 덱(타격 5장·수비 4장·화염구 1장), 시작 유물 '불타는 피', 회복 물약 1개를 받는다.
> 3. 층마다 전투가 있다. 적은 고블린·슬라임·드래곤 같은 몬스터이고, 몬스터마다 턴별 공격 순서가 정해져 있다.
> 4. 턴이 시작되면 에너지 3을 받고 카드 5장을 뽑는다. 뽑을 카드가 없으면 버린 카드를 섞어 다시 쓴다.
> 5. 카드에는 비용·등급·속성·종류(공격·스킬·파워)와 그림이 있다. 카드를 내면 에너지를 쓰고 효과가 난다(피해, 방어도, 회복, 화상 같은 상태). 일부 카드는 강화하면 다른 카드가 된다.
> 6. 방어도는 그 턴 동안 피해를 먼저 막는다.
> 7. 턴을 끝내면 적들이 공격하고, 손패를 버리고, 다음 턴이 시작된다.
> 8. 적을 모두 쓰러뜨리면 골드 10~20을 얻고 다음 층으로 간다.
> 9. 상점에서 골드로 카드를 산다. 물약은 3칸까지 들고 다니며 마시면 효과가 난다.
> 10. 유물은 가지고 있으면 어떤 순간에 저절로 효과를 낸다(닻: 전투 첫 턴에 방어도, 불타는 피: 전투에 이기면 체력 회복). 기획자가 유물을 계속 더한다.
> 11. 판이 끝나도 가장 높이 오른 층, 모은 골드 합계, 해금한 카드가 남는다. 처음 전투에 이기면 '연쇄 번개' 카드가 해금된다. 연쇄 번개는 적마다 차례로 3, 4, 5 … 피해를 준다.
> 12. 처치 수·한 턴 최대 피해·얻은 골드 합계를 기록하고, 한 턴에 30 이상 피해를 주면 도전과제를 달성한다.
> 13. 잘못 낸 카드는 되돌릴 수 있다.

### 4-2. 명사: 바뀌는 것 / 원본 / 화면

명사를 뽑아 세 칸에 나눈다.

| 게임 중에 바뀐다(플레이어 데이터) | 기획자가 채우는 원본(인스턴스) | 화면만의 것(MonoBehaviour) |
|---|---|---|
| 주인공의 체력·방어도·상태, 적의 체력·공격 차례, 층, 골드, 덱(어느 카드가 몇 장, 강화 여부), 손패·뽑을 더미·버린 더미, 에너지, 턴, 가진 유물, 물약 칸, 최고 층, 누적 골드, 해금 카드 | 카드(이름·비용·등급·그림·효과), 몬스터(이름·최대 체력·공격 순서·초상화), 물약(이름·겹치는 수·효과) | 카드를 끄는 위치, 공격 애니메이션 |

"카드"는 두 칸에 걸친다. 카드의 이름·비용·효과는 바뀌지 않으므로 원본에, "내 덱에 타격이 5장 있고 그중 한 장은 강화했다"는 판마다 다르므로 판 데이터에 둔다. 적도 같다. 이렇게 한 명사 안에서 고정 값과 바뀌는 값을 가르는 것이 3-1의 핵심 기준이다.

바뀌는 값을 개념별로 묶으면 클래스가 나온다. 주인공과 적은 체력·방어도·상태를 함께 가지므로 공통 부분을 하나로 둔다.

```csharp
[Serializable]
public class Fighter
{
    public string id;                 // Game.Find로 찾는 id(판 안에서 유일)
    public string name;
    public int hp;
    public int maxHp;
    public int block;                 // 이번 턴 방어도
    [Keyword(typeof(Status))] public List<string> statuses = new List<string>();

    public bool IsDead => hp <= 0;
}

[Serializable]
public class Hero : Fighter
{
    public int energyPerTurn = 3;
    public int drawPerTurn = 5;
}

[Serializable]
public class Enemy : Fighter
{
    public string monster;            // 원본 인스턴스 ID(예: "goblin")
    public int intentIndex;           // 공격 패턴에서 이번 턴 차례
}
```

`IsDead`는 체력에서 계산되므로 필드가 아니라 속성이다. 적은 원본 몬스터의 ID(`monster`)와 공격 순서의 지금 차례(`intentIndex`)만 더 가진다. 공격 순서 자체는 바뀌지 않으므로 원본에서 읽는다(3-1의 핵심 기준). 체력은 전투 중에 바뀌므로 전투를 시작할 때 원본의 최대 체력으로 채워 판 데이터에 둔다.

전투 중에만 있는 값은 `Battle`로 묶고, 판 전체를 `RunState` 하나로 묶는다(01장 4-3). 전투 밖이면 `battle`은 `null`이다. 손패·더미는 카드 id 리스트다.

```csharp
[Serializable]
public class Battle
{
    public int turn;
    public int energy;
    public List<Enemy> enemies = new List<Enemy>();
    public List<string> drawPile = new List<string>();   // 덱 카드(DeckCard) id
    public List<string> hand = new List<string>();
    public List<string> discard = new List<string>();
    public int damageThisTurn;                            // 로그·도전과제용 집계
}
```

`damageThisTurn`은 기획 12번(한 턴 최대 피해)을 위해 둔 값이다. 턴 끝 이벤트에 실어 보내려면 턴 동안 모아 둘 곳이 필요하다.

원본 쪽은 기획자가 채울 칸만 둔다. 몬스터는 이름·최대 체력·턴별 공격 순서·속성·초상화, 물약은 이름·겹치는 수·사용 기능이다. 카드도 원본은 고정 값만 가진다. `id` 필드가 없는 것에 주의한다. 원본은 도감 항목 ID로 부르고, 게임 중에 `Find`로 찾을 일이 없다.

```csharp
[Serializable]
public class Card
{
    public string title;
    public int cost = 1;
    [Keyword(typeof(Rarity))] public string rarity = Rarity.Common;
    [Keyword(typeof(CardTag))] public List<string> tags = new List<string>();
    public Sprite art;
    public bool upgradable;
    [ShowIf(nameof(upgradable)), DataRef(typeof(InstanceData))] public string upgradeTo;
    [Hide] public int balanceScore;   // 밸런스 도구가 채우는 값(기획자 화면에서는 숨긴다)
    [SerializeReference] public Usable usable;   // 기능 = 필드 하나
}
```

(발췌다. 실제 클래스에는 속성 필드도 있다.) 강화 대상은 `[ShowIf]`로 강화 가능할 때만 보이고, `[DataRef]` 덕분에 인스턴스 목록에서 고르는 칸이 된다. 도구가 채우는 값은 `[Hide]`로 기획자 화면에서 숨긴다. 기획자 화면을 이렇게 다듬는 일은 [05장](05-WorkingWithDesigners.md)에서 더 다룬다.

덱에 든 카드 한 장은 다른 클래스다. 같은 카드를 여러 장 가지면 장마다 강화 여부가 따로 바뀔 수 있으므로, 장마다 id와 바뀌는 값을 두고 원본은 ID로만 가리킨다.

```csharp
[Serializable]
public class DeckCard
{
    public string id;                                           // 장마다 다른 id(Game.NewId("card"))
    [DataRef(typeof(InstanceData))] public string card;         // 원본 인스턴스 ID(능력 이름으로도 쓴다)
    public bool upgraded;
}
```

카드의 비용이 필요하면 원본을 읽는다. 규칙 도우미에 "원본 ID → 원본" 함수를 두면 행동·Block·화면이 같은 방법으로 읽는다.

```csharp
public static Card CardData(GameApi game, string card) => game.Session.Instances?.Invoke(card) as Card;
```

몬스터(`MonsterOf`)·물약(`PotionOf`)도 같은 모양이다. 돌려받은 원본은 읽기만 한다.

### 4-3. 동사: 행동

기획의 동사 중 플레이어가 고르는 것과 규칙이 한 걸음 나아가는 것을 행동으로 만든다.

| 기획 | 행동 | 대상 |
|---|---|---|
| 판을 시작한다(2) | `StartRun` | 없음 → `SimpleAction` |
| 전투를 연다(3) | `StartBattle` | 없음(몬스터 ID 리스트를 필드로) |
| 카드를 뽑는다(4) | `DrawCards` | 없음(장 수를 필드로) |
| 카드를 낸다(5) | `PlayCard` | 덱 카드 한 장 → `GameAction<DeckCard>`, 고른 적은 `targetId` 필드 |
| 턴을 끝낸다(7) | `EndTurn` | 없음 |
| 전투에 이긴다(8) | `WinBattle` | 없음 |
| 카드를 산다(9) | `BuyCard` | 없음(원본 ID·가격을 필드로) |
| 물약을 마신다(9) | `DrinkPotion` | 없음(물약 ID·대상 id를 필드로) |
| 판을 끝낸다(1) | `EndRun` | 없음(승리 여부를 필드로) |

행동의 필드는 id와 숫자 같은 값만 둔다. 행동은 저장·리플레이·서버 전송에 그대로 실리는 데이터이기 때문이다.

```csharp
[Serializable, BlockInfo("카드 내기")]
public class PlayCard : GameAction<DeckCard>
{
    public string targetId;

    protected override void Run(DeckCard card)
    {
        // … 본문은 03장에서 본다
    }
}
```

덱 카드의 id는 `GameAction<DeckCard>`가 물려주는 `target` 필드에, 고른 적의 id는 `targetId`에 담긴다. 시스템이 `target`으로 판 데이터에서 그 장을 찾아 `Run`에 넘겨 준다.

`StartBattle`·`DrawCards`·`WinBattle`·`EndRun`은 플레이어가 직접 누르지 않아도 행동으로 만든다. 다른 행동 안에서 불리면(`Game.Do`) 바깥 행동의 일부로 그 자리에서 실행되므로, 혼자 쓸 때(디버그 명령·모니터)와 다른 행동 안에서 쓸 때 모두 같은 코드다. 행동이 어떻게 이어지는지는 [03장](03-GameLoop.md).

### 4-4. "~하면 / ~할 때": 이벤트

기획에서 다른 기능이 반응하는 순간을 찾는다. 반응하는 쪽이 하나라도 있으면 이벤트로 만든다.

| 순간 | 받는 쪽 | 이벤트 | 실어 나르는 값 |
|---|---|---|---|
| 적이 쓰러지면(12) | 로그 처치 수 | `EnemyKilled` "적 처치" | 처치한 쪽 id, 적 id, 몬스터 ID |
| 턴이 시작되면(10) | 유물 닻 | `TurnStarted` "턴 시작" | 턴 번호 |
| 턴이 끝나면(12) | 로그 한 턴 최대 피해 | `TurnEnded` "턴 끝" | 턴 번호, 이번 턴 피해 합 |
| 전투에 이기면(10, 11) | 유물 불타는 피, 도전과제 첫 승리 | `BattleWon` "전투 승리" | 층, 걸린 턴 수 |
| 골드를 얻으면(12) | 로그 얻은 골드 합계 | `GoldGained` "골드 획득" | 양 |
| 카드를 내면 · 피해를 주면 · 판이 끝나면 | 연출, 앞으로 생길 로그·도전과제 | `CardPlayed` · `DamageDealt` · `RunEnded` | id·수치 |

이벤트에는 조건·로그가 읽을 값을 필드로 둔다. 로그의 "반영할 값"과 Trigger의 값 조건은 이벤트 필드 목록에서 고르기 때문이다. 기획 12번의 "한 턴 최대 피해"가 `TurnEnded`에 `damage` 필드를 두는 이유다.

```csharp
[GameEvent("턴 끝")]
public class TurnEnded
{
    public int turn;
    public int damage;        // 이번 턴에 준 피해 합(로그 "한 턴 최대 피해"가 읽는다)
}
```

`[GameEvent("표시 이름")]`을 붙이면 도감·모니터 목록에 이 이름으로 나오고, 컴파일할 때 값 읽기 코드가 생겨 조건·로그가 실행 중 리플렉션 없이 값을 읽는다. 객체를 통째로 넣지 않고 id를 넣는다.

### 4-5. 고르는 값: 키워드

등급·속성·카드 종류·상태는 기획자가 목록에서 고르는 값이다. 키워드 그룹 하나 = static class 하나, 키워드 하나 = `const string` 하나다.

```csharp
[KeywordGroup("등급")]
public static class Rarity
{
    public const string Common = "common";
    public const string Rare = "rare";
    public const string Legendary = "legendary";
}
```

필드에는 `[Keyword(typeof(Rarity))]`를 붙인다. `string` 필드는 하나, `List<string>`은 여러 개를 고른다(카드 종류가 여러 개일 수 있으므로 `tags`는 리스트). 코드가 곧 키워드 목록이고, 도감 › 키워드 탭에서 더해도 이 파일이 고쳐진다. 게임 코드는 상수로 비교한다(`card.rarity == Rarity.Legendary`).

### 4-6. 남는 것과 버리는 것: 구역

기획 11번이 구역을 정한다. 최고 층·누적 골드·해금 카드만 남고 나머지는 판과 함께 버린다. 그래서 플레이어 데이터는 둘이다.

| ID | 구역 | 값 형식 |
|---|---|---|
| `run` | Session | `RunState` |
| `profile` | Meta | `Profile` |

판이 끝날 때 남길 값은 `EndRun` 행동이 판에서 프로필로 옮긴다.

```csharp
var run = Game.Data().Run;
var profile = Game.Data().Profile;
profile.bestFloor = Math.Max(profile.bestFloor, run.floor);
profile.totalGold += run.gold;
```

판이 끝났다는 사실도 판 데이터에 남긴다. `EndRun`이 층을 0으로 돌리고, `RunState`의 읽기 속성 `IsActive`(층이 0보다 큰가)가 "진행 중인 판이 있는가"를 답한다. 따로 플래그를 두지 않고 이미 있는 값에서 계산한다(3-1의 "계산되는 값"). 이어 하기는 이 속성을 보고 끝난 판을 다시 열지 않는다([03장](03-GameLoop.md) 4-2).

### 4-7. 기획자가 계속 더할 것: 인스턴스 · 기본 기능 · 도감 종류

기획에서 "계속 늘어난다"고 할 만한 것을 찾고, 늘어나는 모양에 따라 나눈다.

- **같은 모양의 원본** — 카드·몬스터·물약. 클래스만 만들어 두면 기획자가 도감 › 인스턴스에서 항목을 더한다. 프로그래머 일은 없다.
- **쓰는 순간 효과가 나는 원본** — 카드와 물약. 클래스에 `[SerializeReference] public Usable usable;` 필드를 둔다. 사용 기능이 붙은 인스턴스는 게임이 켜질 때 인스턴스 ID로 등록되어 `Game.Use(인스턴스 ID, 사용자, 대상들)`로 쓴다. 효과는 기획자가 Block으로 조립한다.
- **한 번 이루는 목표, 쌓는 숫자** — 기획 11·12번의 첫 승리·한 턴 30 피해는 도전과제, 처치 수·한 턴 최대 피해·얻은 골드는 로그다. 이미 있는 도감 기능이라 클래스를 만들지 않는다. 필요한 것은 이벤트(4-4)뿐이다.
- **그 어디에도 맞지 않는 새 종류** — 유물(10번). "가지고 있는 동안, 어떤 순간마다(반복), 무언가 한다". 도전과제는 한 번이라 맞지 않고, 로그는 숫자만 쌓고, 사용 기능은 쓰는 순간에만 발동한다. 그래서 도감 종류를 새로 만든다: `GameData`를 상속한 `RelicData`에 Trigger 칸과 결과 칸을 두면 도감에 '유물' 탭이 생기고 기본 기능과 같은 편집 화면을 쓴다. 런타임에서 감시하고 결과를 실행하는 코드는 프로젝트가 쓴다([04장](04-AddingContent.md) 4-10).

### 4-8. 조립할 동작과 예외: Block · `[BindTo]` · 규칙 함수

카드·물약·유물의 효과(5·9·10번)를 동작 단위로 쪼개면 Block 목록이 나온다.

| 종류 | Block | 기획 |
|---|---|---|
| 효과(무엇을) | 피해 `DealDamage`, 방어도 `GainBlock`, 회복 `Heal`, 상태 걸기 `AddStatus` | 5번의 효과 넷 |
| 대상(누구에게) | 모든 적 `AllEnemies`, 무작위 적 `RandomEnemy` | 범위 공격, 무작위 공격 |

대상을 고르지 않으면 플레이어가 고른 대상(카드를 끌어 놓은 적)이 그대로 쓰이고, 기본 제공 `사용자 자신`은 카드를 낸 주인공을 고른다. 그래서 타격(고른 적에게 피해)·수비(나에게 방어도)·화염구(고른 적에게 피해 + 화상)는 코드 없이 조립된다.

"적마다 차례로 3, 4, 5 … 피해"(연쇄 번개, 11번)는 Block 조합으로 나타내기 어렵다. 대상마다 수치가 달라지는 동작은 그 카드에만 있으므로 Block을 만들지 않고 `[BindTo]`로 그 인스턴스의 결과를 함수 하나로 쓴다. "처음 전투에 이기면 해금"(11번)도 첫 승리 도전과제의 결과를 `[BindTo]`로 쓴다. 불타는 피 유물도 같다.

피해 계산(방어도가 먼저 깎임, 적이 쓰러지면 빼고 이벤트를 쏨)과 덱 섞기는 행동·Block·`[BindTo]` 함수가 모두 쓰므로 평범한 static 함수로 한곳에 모은다(`Rules.Damage`, `Rules.Shuffle`). 래퍼나 특별한 문법 없이 그냥 C#이다.

### 4-9. id와 연결

3-4의 기준으로 정한다.

| 객체 | id | 이유 · 만드는 법 |
|---|---|---|
| `Hero` | 있음 | `Game.Use`의 사용자, 피해 이벤트의 출처. 판마다 `"hero"` |
| `Enemy` | 있음 | 카드의 고른 대상, `Find`. `Game.NewId("enemy")` |
| `DeckCard` | 있음 | `PlayCard`의 대상, 손패·더미가 가리킨다. 같은 카드 여러 장을 구별한다. `Game.NewId("card")` |
| `RunState`·`Profile` | 없음 | 플레이어 데이터의 뿌리. `Game.Data().Run`·`.Profile` |
| `Battle` | 없음 | `RunState` 안에 하나 |
| `Card`·`MonsterData`·`Potion` | 없음 | 원본은 인스턴스 ID로 부르고 복사 없이 읽는다. 판 데이터에는 원본 ID만 든다(덱은 `DeckCard.card`, 적은 `Enemy.monster`, 물약은 가방 칸) |

`Game.NewId`의 번호는 메타 구역에 있어 판이 바뀌어도 이어서 늘어난다. 그래서 새 판의 카드 id가 지난 판과 겹치지 않는다. 연결은 모두 글자다: `DeckCard.card`·`Enemy.monster`(원본 ID), `Battle.hand`(덱 카드 id), `RunState.relics`(유물 ID), 가방 칸(물약 ID).

## 5. 다른 장르라면

> **다른 장르라면** — 턴제 전술 게임은 전장(`Board`)과 유닛 리스트가 플레이어 데이터, 유닛 종류(검사·궁수)가 인스턴스, 이동·공격·턴 넘기기가 행동이다. 유닛의 칸 좌표는 턴마다 한 번 바뀌므로 플레이어 데이터에 두지만, 이동 애니메이션 중의 화면 위치는 MonoBehaviour에 둔다.

> **다른 장르라면** — 실시간 액션 게임은 매 프레임 바뀌는 위치·속도를 플레이어 데이터에 넣지 않는다(매 프레임 기록이 쌓인다). 체력·쿨다운 시각·인벤토리처럼 사건으로 바뀌는 값만 플레이어 데이터에 두고, 쿨다운은 `Time.time`이 아니라 게임 시계(`session.Clock.Time`) 기준 시각으로 적는다. [07장](07-GenreRecipes.md).

> **다른 장르라면** — 수집형 게임은 메타 구역이 주인공이다. 보유 캐릭터·재화·강화 단계가 프로필(Meta)이고, 한 번의 전투가 세션 구역이다. 퀘스트·일일 미션처럼 "언제 → 보상"을 기획자가 계속 더하는 것은 유물처럼 도감 종류로 만든다([17. 프로젝트 고유 기능](../Manual/17-Custom-Features.md)).

## 6. 체크리스트

- [ ] 기획 문장마다 판단표의 어느 줄인지 적었다.
- [ ] 바뀌는 값은 모두 `[Serializable]` 클래스 안에 있고, 판 데이터와 프로필 데이터가 다른 플레이어 데이터로 나뉘어 있다.
- [ ] 계산되는 값을 필드로 두지 않았다.
- [ ] 매 프레임 바뀌는 값·화면 상태는 MonoBehaviour 쪽이다.
- [ ] 같은 모양의 원본은 클래스 + 인스턴스이고, 원본과 게임 중에 바뀌는 쪽(덱의 한 장, 전투 중의 적)은 클래스를 나눴다.
- [ ] 판 데이터에는 원본 ID와 바뀌는 값만 있고, 이름·비용·그림·사용 기능·패턴 같은 고정 값은 원본에서 읽는다.
- [ ] 종류를 자식 클래스가 아니라 키워드 필드·기능 필드로 나타냈다.
- [ ] 플레이어 입력과 규칙의 한 걸음이 모두 행동이고, 행동 필드는 id와 값뿐이다.
- [ ] 다른 기능이 반응할 순간이 모두 `[GameEvent]` 이벤트이고, 조건·로그가 읽을 값이 필드에 있다.
- [ ] 찾거나 가리킬 객체에 `public string id;`가 있고, 연결은 id 글자다. 에셋 참조를 플레이어 데이터에 두지 않았다.
- [ ] 효과는 Block 목록, 예외는 `[BindTo]` 목록, 새 종류는 도감 종류로 적었다.
- [ ] 클래스 목록과 도감 항목 목록을 팀과 맞췄다.
