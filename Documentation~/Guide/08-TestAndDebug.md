# 08. 시험과 디버깅

## 1. 이 단계의 목표

매일 쓰는 디버깅 흐름을 갖춘다. 버그를 보면 같은 판을 다시 만들고(고정 시드·판 저장), 모니터에서 무엇이 왜 바뀌었는지 거슬러 올라가고, Undo로 앞뒤를 오가며 고친다. 잘 바뀌지 않아야 할 게임 규칙은 EditMode 테스트로 묶어 둔다.

이 장에서 쓰는 말:

| 말 | 뜻 |
|---|---|
| 모니터 | `MomoiProject → 모니터`. 플레이 중인 세션을 들여다보고 조작하는 창. 탭은 타임라인 · 데이터 · 도전과제 · 로그 · 이벤트 · 행동 · 명령. |
| 통합 기록(Journal) | 세션에서 일어난 모든 일(행동·이벤트·값 변경·달성·경고)을 원인과 함께 한 줄씩 남긴 기록. 모니터의 타임라인 탭이 보여 준다. |
| 행동 | 플레이어 입력 하나를 담은 클래스. 하나가 Undo 한 단위다. |
| Undo | 마지막 행동이 바꾼 값을 행동 전으로 되돌리는 것. 난수도 함께 돌아간다. |
| 이벤트 호출 | 모니터 이벤트 탭에서 이벤트 값을 채워 직접 쏘는 도구. |
| 시뮬레이션 | 값을 덮어쓰지 않고 실제 이벤트를 쏴서 게임과 같은 경로(이벤트 → 로그 → 도전과제 → 보상)로 움직이는 것. 쏜 이벤트 묶음은 행동 하나로 기록된다. |
| 시드 | 결정론 난수의 씨앗. 같은 시드에서 같은 행동을 하면 같은 결과가 나온다. |

## 2. 할 일 순서

1. **개발 빌드는 시드를 고정한다.** `Configuring`에서 `options.Seed`를 정해 두면 같은 순서로 하면 같은 판이 나온다.
2. **자주 쓰는 조작을 디버그 명령으로 만든다.** 골드 넣기·적 모두 처치·시드 기록처럼 시험 준비를 버튼 하나로(`session.Debug.Register`).
3. **버그를 보면 판을 저장한다.** 모니터 › 명령 › **판 저장**은 판 데이터·난수 상태·게임 시계를 `run.json`에 쓴다. 이 파일을 불러오면 다음 난수까지 같은 상태로 돌아온다.
4. **타임라인으로 원인을 찾는다.** 값 하나를 골라 그 값이 바뀐 기록만 보고, 줄을 골라 인과 관계(어떤 행동 → 어떤 이벤트 → 어떤 변경)를 따라간다.
5. **Undo로 앞뒤를 오간다.** 고친 코드로 같은 행동을 다시 해 보고, 결과가 다르면 Undo하고 또 해 본다.
6. **이벤트 호출·시뮬레이션으로 반응을 본다.** 도전과제·로그·유물이 실제 게임 경로로 반응하는지 이벤트를 쏴서 확인한다.
7. **규칙을 테스트로 묶는다.** 카드 내기·실패 취소·Undo처럼 지켜야 할 규칙은 EditMode 테스트로 쓴다.
8. **경고를 0으로 유지한다.** 타임라인·콘솔의 `[MomoiProject]` 경고는 쌓아 두지 않고 그때그때 아래 대응표로 고친다.

## 3. 판단 기준

| 알고 싶은 것 | 볼 곳 |
|---|---|
| 이 값이 왜 바뀌었나 | 타임라인 › **모든 값 ▾**에서 값 고르기 → **묶어 보기** → 줄 고르기 → 오른쪽 **인과 관계** |
| 지금 값이 무엇인가, 값을 바꿔 보고 싶다 | 데이터 탭(**판 데이터**·**프로필 데이터**). 고친 값은 개발자 행동 하나로 기록되어 Undo된다 |
| 내 행동이 실행됐나, 왜 실패했나 | 행동 탭(상태 **실행** · **Undo됨** · **실패**, 실패 줄에 마우스를 올리면 오류) |
| 이 이벤트를 받으면 무엇이 반응하나 | 이벤트 탭(**이벤트 호출**, 아래 "반응하는 로그") |
| 도전과제가 제대로 달성되나 | 도전과제 탭 **트리거로 달성**(실제 이벤트로), 안 되면 **강제 달성** |
| 로그가 제대로 쌓이나 | 로그 탭 **이벤트로 더하기**·**이벤트로 기록**(실제 이벤트로) / **직접 수정**(값만) |
| 몇 판을 해야 나오는 상황을 지금 보고 싶다 | 명령 탭의 프로젝트 디버그 명령 |

| 이럴 때 | 이것 |
|---|---|
| 같은 버그를 다시 보고 싶다 | 고정 시드로 같은 순서를 반복하거나, 버그 직전에 저장한 판을 불러온다 |
| 시험 준비로 값을 바꾼다 | 데이터 탭에서 고치거나, `DeveloperEditAction`을 쓰는 디버그 명령(Undo된다) |
| 반응을 시험한다 | 값을 덮어쓰지 말고 이벤트를 쏜다(`SimulateEvents`, 이벤트 호출). 같은 이벤트를 받는 다른 기능도 함께 반응한다 |
| 규칙이 바뀌지 않았는지 늘 확인한다 | EditMode 테스트 |
| 라이브러리 코어가 깨지지 않았는지 Unity 없이 확인한다 | 프로젝트 루트의 `Tools/RunCoreTests.ps1`(라이브러리의 코어 테스트만 돈다) |

## 4. 카드 던전에서 실제로

### 고정 시드와 디버그 명령

카드 던전의 시작 설정은 개발 빌드에서 시드를 고정하고(07장), 세션이 만들어지면 디버그 명령 둘을 등록한다. 모니터 › **명령** 탭의 "카드 던전" 묶음에 버튼으로 보인다.

```csharp
session.Debug.Register("카드 던전", "골드 +100", () => session.Do(new DeveloperEditAction { label = "골드 +100", Edit = () => session.Game.Data().Run.gold += 100 }));
```

`DeveloperEditAction`은 넘긴 함수를 행동 하나 안에서 실행한다. 그래서 디버그 명령으로 바꾼 값도 기록(행동 탭의 "[개발] 골드 +100", 공개 범위 "개발자")에 남고 Undo로 되돌릴 수 있다. 디버그 명령 안에서 값을 그냥 고치면 행동 밖 변경이 되어 Undo되지 않으므로 이 형태를 쓴다. 명령은 세션마다 등록되므로 `GBibleRuntime.Started`에서 등록하고, `Debug.isDebugBuild`로 출시 빌드에서는 빼 둔다.

버그 보고에 붙일 정보를 남기는 명령도 하나 둔다. 타임라인에 시드와 층을 한 줄 남긴다.

```csharp
session.Debug.Register("카드 던전", "시드 기록", () =>
    session.Journal.Append(JournalKind.System, "CardDungeon", $"시드 {session.Random.MasterSeed} · 층 {session.Game.Data().Run.floor}"),
    "지금 시드와 층을 타임라인에 남긴다(버그 보고에 붙인다).");
```

`Journal.Append`는 게임 코드 어디서든 기록에 한 줄을 남긴다. `JournalKind.Warning`·`Error`로 남기면 콘솔에도 `[MomoiProject] …`로 나간다.

### 같은 판 다시 만들기

버그를 재현하는 방법은 두 가지다.

- **고정 시드로 처음부터.** 개발 빌드는 시드가 `20261003`으로 고정이라, 같은 카드를 같은 순서로 내면 덱 섞기·전리품·무작위 대상이 같게 나온다. 난수를 용도별 흐름(`deck`·`loot`·`cardTarget`)으로 나눠 두었으므로, 그 사이에 코드를 고쳐 한 흐름의 뽑는 횟수가 달라져도 다른 흐름은 그대로다.
- **판 저장에서.** 버그 직전에 모니터 › 명령 › **판 저장**을 누르면 `GBibleRuntime.RunSavePath`(`…/MomoiProject/run.json`)에 판 데이터·난수 상태·게임 시계가 저장된다. 다음 플레이에서 **판 불러오기**를 누르거나 런 스크립트가 시작할 때 `GBibleRuntime.LoadRun`으로 이어 하면, 저장한 순간과 다음 난수까지 같다. 이 파일을 버그 보고에 붙이면 다른 사람도 같은 상태에서 시작한다.

개발 중에 데이터 구조(플레이어 데이터의 필드 이름·형식)를 바꾸면, 다음 플레이를 시작할 때 맞지 않는 저장이 지워지고 "개발 중 데이터 구조가 바뀌어 저장을 초기화했습니다" 경고가 남는다. 필드를 더하기만 했으면 그대로 이어 간다.

### 모니터로 원인 찾기

"턴을 넘겼더니 체력이 생각보다 많이 줄었다"를 예로 든다.

1. 타임라인 탭의 **모든 값 ▾**에서 `run`을 고르고 **묶어 보기**를 켠다. 맨 위 행동 줄 "턴 끝"을 펼치면 그 행동이 쏜 이벤트(턴 끝, 피해 ×2, 턴 시작)와 바뀐 값(`hero.hp`, `hand` …)이 차례로 보인다.
2. `hero.hp`가 바뀐 줄을 고르면 오른쪽 **인과 관계**에 뿌리 행동부터 그 줄까지가 보인다. 피해 이벤트를 열면(**열기**) `sourceId`·`amount`로 어느 적이 얼마를 줬는지 나온다.
3. 데이터 탭 › **판 데이터**에서 그 적의 `intentIndex`를 보고, 몬스터 원본의 `attackPattern`과 비교한다.
4. 행동 탭에서 실패한 행동이 있었는지 본다. 실패한 행동은 바꾼 것이 모두 취소되었으므로, 화면에 보인 연출과 값이 다르다면 여기부터 의심한다.

**Alt**를 누르고 있으면 타임라인 문장이 코드식으로 바뀌어 필드 경로를 정확히 볼 수 있다.

### Undo로 앞뒤 보기

모니터 머리의 **Undo** 버튼은 마지막 행동을 되돌린다(런 스크립트의 Undo 버튼과 같은 `session.Undo()`). 되돌리면 난수 상태도 행동 전으로 돌아가므로, 같은 카드를 다시 내면 같은 결과가 나온다. 그래서 "카드를 낸다 → 결과를 본다 → Undo → 데이터 탭에서 값을 바꾸거나 다른 대상으로 다시 낸다"를 반복해 같은 난수 조건에서 결과를 비교할 수 있다. 다시 하기(Redo)는 없으므로, 앞으로 가려면 같은 행동을 다시 한다.

Undo해도 도전과제 달성과 그 보상은 남는다. 첫 승리 도전과제를 다시 시험하려면 데이터 탭 › **도전과제 달성**에서 거짓으로 바꾸거나 도전과제 탭의 **초기화**를 쓴다.

### 이벤트 호출과 시뮬레이션

도전과제 `bigTurn`은 "로그 `maxTurnDamage`가 30 이상"일 때 달성된다. 한 턴에 30 피해를 내는 덱을 만들지 않고도 확인할 수 있다.

- 모니터 › **이벤트** 탭에서 "턴 끝"을 고르고 `damage`에 30을 넣고 **이벤트 호출**을 누른다. 로그 `maxTurnDamage`가 30이 되고 `bigTurn`이 달성된다. 아래 "반응하는 로그"에 이 이벤트를 받는 로그가 미리 보인다.
- 도전과제 탭에서 `bigTurn` 카드를 누르고 **트리거로 달성**을 누른다. 모자란 로그를 채울 이벤트를 계획해 쏜다.

자주 하는 시험은 디버그 명령으로 만들어 둔다. 코드로는 `session.SimulateEvents`(이벤트 목록을 행동 하나로 쏜다)와 `session.TrySimulateAchievement`(트리거로 달성)를 쓴다.

```csharp
session.Debug.Register("카드 던전", "한 턴 30 피해", () =>
    session.SimulateEvents(new object[] { new TurnEnded { turn = 1, damage = 30 } }, "한 턴 30 피해"),
    "로그 maxTurnDamage와 도전과제 bigTurn이 반응하는지 본다.");

session.Debug.Register("카드 던전", "bigTurn 트리거로 달성", () =>
{
    if (!session.TrySimulateAchievement(GameIds.Achievement.BigTurn, out var error)) Debug.LogWarning(error);
});
```

시뮬레이션으로 쏜 이벤트는 행동 하나("[테스트] …")로 기록되어 Undo하면 로그는 돌아가고 달성은 남는다. 같은 이벤트를 받는 유물·다른 로그도 실제 게임처럼 함께 반응하므로, "턴 끝을 받는 유물이 엉뚱하게 발동한다" 같은 문제도 여기서 드러난다. 모니터에서 이벤트를 쏘려면 이벤트 클래스에 매개변수 없는 생성자가 있어야 한다(카드 던전의 이벤트는 모두 필드만 있는 클래스라 된다).

### EditMode 테스트로 규칙 묶기

규칙 테스트는 `GBibleRuntime`과 도감 없이 세션을 직접 만든다. 플레이어 데이터는 `Define`으로, 카드·몬스터 원본은 `session.Instances`에 함수로, 카드의 사용 기능은 같은 ID의 능력(`AbilityDefinition`)으로 넣는다. 게임 코드는 덱의 한 장(`DeckCard`)이 든 원본 ID로 `Rules.CardData`·`MonsterOf`·`PotionOf`를 거쳐 이 원본을 읽으므로, 테스트에 필요한 수치만 넣으면 기획자가 도감 수치를 바꿔도 테스트가 흔들리지 않는다.

```csharp
_session = new GameSession(new SessionOptions { Seed = 7 });
_session.Data.Define(GameIds.PlayerData.Run.Id, DataZone.Session, new RunState(), "판");
_session.Data.Define(GameIds.PlayerData.Profile.Id, DataZone.Meta, new Profile(), "프로필");

// 도감 › 인스턴스 대신 원본을 코드로 넣는다(시험에 필요한 수치만).
var originals = new Dictionary<string, object>
{
    [GameIds.Instance.Strike] = new Card { title = "타격", cost = 1 },
    [GameIds.Instance.Goblin] = new MonsterData { title = "고블린", maxHp = 20, attackPattern = new List<int> { 6 } },
    // … 수비·화염구·슬라임·회복 물약
};
_session.Instances = id => originals.TryGetValue(id, out var value) ? value : null;
```

그다음 테스트는 게임과 똑같이 행동을 실행하고 값을 확인한다. 예를 들어 "에너지가 모자라면 아무것도 바뀌지 않는다"는 이렇게 쓴다.

```csharp
Game.Do(new StartRun());
var battle = Game.Data().Run.battle;
battle.energy = 0;                                   // 시험 준비(행동 밖 변경)
var hand = new List<string>(battle.hand);
Assert.Throws<InvalidOperationException>(() => Game.Do(new PlayCard { target = hand[0] }));
CollectionAssert.AreEqual(hand, Game.Data().Run.battle.hand);
```

이 밖에 "같은 시드면 첫 손패가 같다"(세션 둘을 같은 시드로 만들어 비교), "카드를 내고 Undo하면 에너지·적 체력·손패가 모두 돌아온다"를 같은 방식으로 쓴다. 테스트 파일은 에디터 전용 테스트 asmdef에 둔다. 라이브러리의 `GBible.Tests.Editor.asmdef`와 같이 참조에 게임 로직 asmdef·`GBible.Core`·`GBible.Unity`·`UnityEngine.TestRunner`·`UnityEditor.TestRunner`를, 미리 컴파일된 참조에 `nunit.framework.dll`을 넣고, 플랫폼은 Editor, `defineConstraints`에 `UNITY_INCLUDE_TESTS`를 둔다. Unity의 Test Runner 창(EditMode)에서 돈다. `GBibleRuntime` 없이 세션을 직접 만든 테스트는 프레임이 흐르지 않으므로, 프레임 끝 처리가 필요하면 `session.EndFrame(0.016)`을 직접 부른다.

프로젝트 루트의 `Tools/RunCoreTests.ps1`은 라이브러리 저장소의 코어 테스트(`Tests/Editor`의 정해진 파일들)를 Unity 없이 돌리는 스크립트다. 라이브러리를 고쳤을 때 코어가 깨지지 않았는지 보는 용도이고, 프로젝트의 게임 규칙 테스트는 넣지 않는다. 카드 던전의 규칙 코드는 `UnityEngine` 형식(스프라이트, `RuntimeInitializeOnLoadMethod`)을 함께 쓰므로 위의 EditMode 테스트로 돌린다.

## 5. 다른 장르라면

> **다른 장르라면** 실시간 액션은 행동 단위가 아니라 스냅샷 단위로 되감는다. 모니터 머리에 "되감기 스냅샷 n (n초 간격)"이 보이고, **Undo**는 마지막 스냅샷으로 되감는다. 버그 직전으로 돌아가 다시 보려면 그 순간 근처에서 `CaptureSnapshot`을 부르는 디버그 명령을 만들어 둔다. 모니터의 **일시정지**·**1프레임**·배속(0.25× …)으로 빠른 장면을 늦춰 본다.

> **다른 장르라면** 턴제 전술의 AI처럼 판단이 복잡한 코드는 AI가 고른 행동을 `Describe()`로 행동 탭에 읽기 쉽게 남기면("오크1 → 영웅 공격"), 타임라인만으로 AI의 선택을 따라갈 수 있다.

> **다른 장르라면** 수집형·방치형처럼 프로필이 오래 쌓이는 게임은 모니터 › 명령 › **프로필 삭제**(다음 플레이부터 적용)와 **새 판**으로 처음 상태를 자주 시험하고, 오래된 프로필 파일을 몇 개 보관해 두었다가 출시 전 저장 변환을 시험한다.

## 6. 체크리스트

- [ ] 개발 빌드는 시드가 고정되어 있다.
- [ ] 시험 준비용 디버그 명령이 있고, 값을 바꾸는 명령은 `DeveloperEditAction`으로 Undo된다.
- [ ] 버그를 보면 판을 저장하고, 저장 파일과 시드를 보고에 붙인다.
- [ ] 타임라인에서 값 하나의 변경 원인을 따라갈 수 있다.
- [ ] 도전과제·로그·유물의 반응을 이벤트 호출·트리거로 달성으로 확인했다.
- [ ] 지켜야 할 규칙(실패 취소, Undo, 같은 시드 같은 결과)이 EditMode 테스트로 있다.
- [ ] 타임라인·콘솔에 `[MomoiProject]` 경고가 남아 있지 않다.
