# 전체 점검 (2026-10-01)

플레이어 데이터 클래스(위빙)까지 반영한 뒤, 기획자·프로그래머가 실제로 밟는 흐름을 처음부터 끝까지 따라가며 점검한 결과.
각 흐름은 **지금 하는 법 → 점검에서 나온 것**. 맨 아래에 결정이 필요한 것과 Unity에서 확인할 것을 모았다.

---

## A. DB (기획자)

### A-1. 키워드
**지금 하는 법**
1. DB › 키워드 → `+ 새 그룹`(예: `grade`) → 그룹 줄의 `+ 키워드`로 `common`·`rare`·`legendary`.
2. 연결: 그 키워드를 고를 필드를 정한다. 두 곳에서 같은 화면이 열린다.
   - DB › 클래스 → 클래스를 눌러 상세 → 필드의 '키워드 그룹' (개발자가 만든 클래스)
   - 각 DB 종류 탭 머리의 `필드 연결` (아이템·장소 같은 시스템·기능 클래스)
3. 연결된 필드는 어디서든(DB 상세, 템플릿, 보상 값, 조건 값) 칸이 드롭다운이 된다. 키워드 그룹 줄 아래에 연결된 필드가 칩으로 보이고, 누르면 그 클래스 상세로 간다.

**점검**
- 이상 없음. 키워드 탭의 그룹 줄은 클래스 탭과 달리 제목을 누르면 그룹 편집이 열린다(제목 줄 전체로 접기는 클래스·이벤트 탭만). 같은 동작으로 맞출지는 결정 필요(아래 D-6).

### A-2. 클래스
**지금 하는 법**
1. DB › 클래스. 맨 위 `Code`가 `Assets/MomoiProject/Code` 폴더이고 그 아래 그룹이 하위 폴더다(`+ 하위 그룹`으로 중첩). 줄에 마우스를 올리면 버튼이 보이고, 버튼 밖을 누르면 접고 펼친다. `↗`는 그 그룹만 새 창에.
2. `+ 데이터 클래스`(값을 담는 클래스: 유닛·인벤토리·버프) 또는 `+ DB 종류`(DB에 항목을 만드는 클래스: 아이템).
3. 상세에서 `+ 필드` → 이름·형식·하나/리스트. 데이터 클래스는 **플레이어 데이터 클래스**로 만들어져(`[PlayerData]`) 리스트는 `GameList`가 된다.
4. Ctrl+S → 스크립트 파일·폴더에 쓰고 다시 컴파일. 그룹을 바꾸면 파일이 그 폴더로 옮겨진다(GUID 유지).

**점검**
- 예전에 만든 데이터 클래스(사용자의 `TestClasss` 같은)는 상세에 '플레이어 데이터 클래스로 바꾸기'가 뜬다. `TestClasss`는 이번에 직접 옮겼다.
- DB 종류(GameData)는 정의 데이터라 플레이어 데이터 클래스가 아니다(정상). 그 안의 리스트는 일반 `List` 그대로.
- 저장 직후 Unity가 멈췄던 문제는 추정 원인(가져오는 중인 스크립트 에셋 불러오기)을 없앴지만 재현 확인 전.

### A-3. 플레이어 데이터
**지금 하는 법**: DB › 플레이어 데이터 → ID(예: `player.gold`), 구역(메타: 판이 바뀌어도 남음 / 세션: 이번 판만), 값 형식(숫자·글자·enum 또는 데이터 클래스), 단순 값이면 기본값.

**점검**
- 값 형식이 플레이어 데이터 클래스가 아니면(일반 `List`가 섞인 클래스 등) 검증이 경고한다 — 동작은 하지만 느린 비교 방식.
- 코드에서는 `Game.Data().PlayerGold += 100`처럼 이름으로 쓴다(식별자 코드 생성 때 함께 생김).

### A-4. 로그
**지금 하는 법**: DB › 로그 → 반영 규칙 `[이벤트] [반영할 값(필드 또는 횟수)] × 배수`, 필요하면 이벤트 조건식으로 거르기(예: 태그에 boss 포함). 범위 이번 판/누적, 집계 합계/최대.

**점검**
- 조건 블럭 이름이 아직 **"수치 비교"**다(탭 이름은 로그). 표현 방침으로 이름을 유지해 왔지만, 보상 "획득"을 없앤 지금은 "로그 비교"로 바꾸는 게 덜 헷갈린다(D-1).
- 로그는 이벤트로만 쌓인다(보상으로 늘리지 않음 — 확정 규칙).

### A-5. 이벤트
**지금 하는 법**: DB › 이벤트 → `+ 이벤트`로 클래스를 만들고 필드에 함께 알릴 값(처치한 적, 태그, 콤보 …). 이벤트를 내는 것은 게임 코드(`Game.Events.Publish(new EnemyKilled { … })`). 라이브러리가 내는 이벤트(도전과제 달성, 능력 사용)는 '기본' 그룹에 잠겨 보인다.

**점검**: 이상 없음. 이벤트 클래스는 순간 메시지라 플레이어 데이터 클래스가 아니다(정상).

### A-6. 도전과제
**지금 하는 법**
1. 조건: 블럭 · 논리 연산자 · 괄호. 블럭 손잡이(⠿)로 끌어 순서를 바꾸거나 괄호 안팎으로 옮긴다.
2. 보상: `+ 보상 추가` → 플레이어 데이터 필드 → 형식에 맞는 값(숫자 증감 / 글자·enum 값 / 클래스는 템플릿 / 리스트는 요소). 이미 고른 필드는 다시 안 나온다.

**점검**
- 보상은 플레이어 데이터 기준이라 "누구에게"가 없다(전역). 개체 대상은 능력의 몫(A-8).
- 딕셔너리 필드는 보상 목록에 안 나온다(D-3).

### A-7. 템플릿
**지금 하는 법**: DB › 템플릿 → 형식(데이터 클래스) 고르기 → 값을 탐색기로 채움(아이템 A, B …). 보상·능력이 넣을 때는 사본이 들어간다.

**점검**: 템플릿 값 편집은 에셋 편집이라 기록 대상이 아니다(정상).

### A-8. 능력 (새로 생김)
**지금 하는 법**: DB › 능력 → `대상` Block(위에서부터 차례로, 비어 있으면 고른 대상 그대로) + `효과` Block(대상마다). 게임에서 `Game.Use("능력 ID", 사용자, 대상들)`.

**점검**
- **사용 조건이 없다**(예: 체력이 가득이면 못 씀). 지금의 조건 Block은 "누가 쓰는지"를 모른다(D-2).
- **아이템과의 연결 방식이 정해지지 않았다.** 인벤토리 모듈의 아이템은 '기능 조립'(`ItemFeature`)을 쓰는데, 사용 효과는 능력으로 만들었으니 둘을 잇는 기본 기능이 필요하다(D-4).
- DB에서 Block을 고르고 저장하는 화면은 Unity에서 확인 전.

## B. 프로그래머

### B-1. 클래스
- DB에서 만드는 게 기본(A-2). 코드로 직접 쓸 때:
```csharp
[Serializable, PlayerData]
public class Unit { public string id; public int hp; public GameList<string> buffs = new GameList<string>(); }
```
- 필드에 `=`를 쓰면 그 순간 기록된다(어디서 쓰든). 리스트는 `GameList`, 딕셔너리는 `GameDictionary`. 개체로 찾을 클래스는 `public string id;`.
- 기록되지 않는 것: 지역 변수, 구조체 필드 제자리 수정, 리플렉션, 미리 컴파일된 DLL(개발 빌드가 다음 행동 때 경고).

### B-2. 조건 로직
```csharp
[Serializable, BlockInfo("적 전멸", Category = "전투")]
public class AllEnemiesDown : SimpleCondition
{
    public string team = "enemy";                       // 에디터 칸
    protected override bool Check() => Game.All<Unit>().Where(u => u.team == team).All(u => u.hp <= 0);
}
```
- 무엇을 보는지 선언하지 않아도 읽은 플레이어 데이터가 바뀔 때 다시 평가된다. 값은 바꾸지 않는다.
- 진행도 표시·시간 조건이 필요하면 `Condition`을 직접 상속(`TryGetProgress`·`PollInterval`).

### B-3. 보상·효과 로직
- **보상**은 대부분 기본 블럭('플레이어 데이터에 주기')으로 끝난다. 그 밖(결제 지급·플랫폼 연동)만 `Reward`를 상속(`Grant`·`Effect`).
- **효과**(능력용):
```csharp
[Serializable, BlockInfo("피해", Category = "전투")]
public class Damage : Effect<Unit>
{
    public int amount = 10;
    protected override void Apply(Unit target) => target.hp -= amount + Game.Random("damage").Range(0, 3);
}
```
- 대상 고르기는 `TargetSelector<T>`, 사용자는 `User<Unit>()`, 이번 사용 정보는 `Use`.

### B-4. MonoBehaviour에서
```csharp
public class RunManager : MonoBehaviour
{
    string _selected;                                   // 객체 대신 id
    GameApi Game => GBibleRuntime.Game;

    void Start() => GBibleRuntime.Start();         // 보통 자동(씬 로드 전)
    public void OnClickTile(int x, int y) => Game.Do(new MoveUnit { target = _selected, x = x, y = y });
    public void OnClickSkill(Unit t) => Game.Use("ability.splash", _selected, t);
    void OnEnable() => _hit = Game.Events.Subscribe<UnitDamaged>(e => PlayHit(e));   // 연출은 이벤트를 보고
    void Update() { foreach (var u in Game.All<Unit>()) Draw(u); }
    System.IDisposable _hit;
}
```
- 플레이어 입력은 행동(`Game.Do`·`Game.Use`) — Undo 한 단위, 서버 전송·리플레이.
- 씬 코드에서 플레이어 데이터 클래스를 고쳐도 기록은 되지만 되돌릴 단위가 없다. 읽기·그리기 위주로.

**점검**
- `GBibleRuntime.Game`만 정적이고 나머지는 세션 단위라, 서버(판 여러 개)에서는 `session.Game`을 쓴다(문서화됨).
- 이벤트 클래스(`UnitDamaged` 등)는 DB › 이벤트에서 만들고 효과 Block 안에서 `Game.Events.Publish`로 낸다.

## C. 이번 점검에서 고친 것

- **Modify 안의 리플렉션 쓰기 누락**: 플레이어 데이터 클래스 값을 `Modify`로 고치면서 리플렉션으로 쓰는 경로(모니터 창의 값 편집, 보상 블록 '플레이어 데이터에 주기')가 기록되지 않았다. `Modify`는 이제 그 순간 이전 모습과 비교해 한 번에 기록한다(테스트 추가).
- README의 옛 설명(클래스 폴더 `Assets/Scripts/Data`, 보상 '획득') 갱신.

## E. Unity에서 처음 열고 확인할 것

1. 컴파일 오류 없이 열리는지, 콘솔에 `[MomoiProject] 플레이어 데이터 위빙 실패`가 없는지.
2. Test Runner로 EditMode 테스트 전체(특히 `PlayerDataTests` · `ClassCodeTests` · `EditorToolTests`). 코어 테스트 127개는 Unity 밖에서 통과(같은 위빙 적용).
3. 클래스 탭: 폴더 만들기·지우기, 클래스·폴더를 끌어 다른 폴더에 놓기 후 Ctrl+S(디스크 폴더가 그대로 바뀌는지), 줄 마우스 올리기·누르기 동작, `↗` 새 창.
3-1. 다른 DB 탭(로그·도전과제·템플릿·능력·플레이어 데이터 …): 폴더 만들기·이름 바꾸기·지우기, 항목·폴더 끌어 놓기, Ctrl+S 뒤 다시 열어도 그대로인지. 키워드 탭: 그룹을 다른 그룹 위에 놓아 하위 그룹 만들기, 그룹 ⋯ › 그룹 편집.
4. 클래스 만들고 필드 둘 넣고 저장 → **멈추지 않는지**(지난번 멈춤).
5. 창 탭 막대: 열려 있던 창을 닫고 다시 열면 유틸리티 창(탭 막대 없음)으로 뜨는지.
6. 도전과제 보상 `+ 보상 추가` 흐름, 능력 탭에서 대상·효과 Block 고르기·저장.
7. 툴팁이 긴 글을 다 보여 주는지.
