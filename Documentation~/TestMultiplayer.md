# 테스트용 멀티플레이 환경 설계 (2026-10-06 구현 — 기록)

> **2026-10-06 구현됨**: 지금 쓰는 법은 매뉴얼 [40장](Manual/40-Multiplayer.md). 서버 프로그램은 .NET이 아니라 **Unity 서버 빌드**로 정했다(2026-10-06 — 테스트용 멀티는 게임 빌드를 `-momoi-server`·`-momoi-host`로 켜면 된다). 직접 접속은 WebSocket을 TCP 위에 직접 구현했고(HttpListener를 쓰지 않음 — 관리자 권한 불필요), 시험 모드(한 프로그램 안 4블록)·형식 번호표 교환이 더해졌다. 아래는 2026-10-02 설계 기록이다(코드 이름은 구현과 다를 수 있다).

## 1. 사용자 조건과 판정

| 조건 | 판정 | 방법 |
|---|---|---|
| 1. 랜이 아닌, 인터넷으로 떨어진 두 컴퓨터가 멀티 | 가능 | 한 컴퓨터(또는 빌린 서버)에서 서버 프로그램을 돌리고, 다른 컴퓨터들이 주소로 접속. 접속 경로는 3절의 셋 중 하나 |
| 2. 개별 설정이 좀 필요해도 됨, 수치 입력만으로 되면 좋음 | 가능 | 서버 쪽: 실행 파일 + 포트 하나. 클라이언트 쪽: 접속 창에 주소·포트·이름만 입력 |
| 3. 보안 불필요 | 반영 | 인증·암호화·치팅 방지 없음. 이름만 입력하면 입장 |
| 4. 게임 코드 문법이 AWS 버전과 같을 것 | 가능 | 게임 코드는 "어디에 어떻게 붙는지"를 모른다. 바뀌는 것은 접속 방식(테스트: 주소 직접 입력 / AWS: 매칭 → 서버 주소·입장권)뿐이고, 그 부분은 설정 하나로 갈아 끼운다 |

## 2. 구조 (유형 A 기준: 서버 권한)

HANDOVER 1.11의 유형 A(자체 서버, AWS)와 **같은 서버 프로그램**을 쓴다. 다른 점은 그 프로그램이 AWS가 아니라 테스터의 컴퓨터에서 돈다는 것뿐이다.

흐름:
1. 서버 프로그램(.NET, Unity 없이 코어만 — 코어는 이미 엔진 무관으로 컴파일·실행 검증됨)을 실행한다. 정의 데이터는 빌드 때 내보낸 JSON을 읽는다(내보내기 도구는 아직 없음 → 착수 시 같이 만든다).
2. 클라이언트가 접속(WebSocket — AWS 설계와 같은 전송)하면 서버가 플레이어 데이터 전체를 한 번 보낸다(`session.Data.Snapshot(key)` — 값 전체 + 객체 번호, 2만 유닛 기준 약 1.6MB). 클라이언트는 `MirrorReceiver.Load`로 받는다.
3. 플레이어 입력은 `GameAction`(데이터)으로만 서버에 간다. 서버가 실행하고, 행동 끝의 Sync가 만든 ChangeSet(바뀐 곳만, 공격 한 번 수십 바이트)을 모든 클라이언트에 보낸다. 같은 행동에서 쏜 이벤트(연출용)도 함께 보낸다.
4. 클라이언트는 ChangeSet을 `MirrorReceiver.Apply`로 적용하고(두 곳에서 가리키는 객체도 같은 인스턴스로 이어진다), 받은 이벤트를 자기 쪽에서 다시 쏜다(UI·연출이 받는다).
5. 실시간 게임은 행동마다가 아니라 서버 틱(예: 초당 20번)마다 ChangeSet을 모아 보낸다.

게임 코드가 쓰는 문법(테스트·AWS 공통, 가칭):
- 입력: `Game.Do(new 공격 { … })` — 싱글에서는 그 자리에서 실행, 멀티에서는 서버로 보내진다(같은 문법).
- 결과 받기: 지금처럼 이벤트를 받는다 / 플레이어 데이터를 읽는다.
- 접속: `Multiplayer.Connect(접속 정보)` — 접속 정보는 접속 방식이 만들어 준다.
  - 테스트: 주소 직접 입력 방식(주소·포트·이름)
  - AWS: 매칭 방식(FlexMatch 매칭 → 서버 주소 + 입장권, Steam 인증)
  - 둘은 같은 인터페이스를 구현하고, 프로젝트 설정에서 어느 쪽을 쓸지 고른다.
- 서버 쪽 진입(가칭 서버 호스트): 테스트는 실행하자마자 대기, AWS는 매칭 결과 알림을 받아 매치를 만든다. 매치 안의 게임 로직(행동 처리·Sync·이벤트)은 같은 코드.

## 3. 인터넷으로 서로 닿게 하는 방법 (게임 코드와 무관, 셋 중 편한 것)

1. **포트 포워딩**: 서버를 돌리는 컴퓨터의 공유기에서 포트(예: 7777)를 그 컴퓨터로 넘기고 Windows 방화벽에서 허용. 다른 사람은 그 집의 공인 IP로 접속. 공유기 설정 권한이 필요하고, 통신사가 공인 IP를 여러 집이 나눠 쓰게 하는 경우(CGNAT — 공유기의 WAN IP와 "내 IP 확인" 사이트의 IP가 다르면 해당)에는 안 된다.
2. **가상 랜 도구**(Tailscale, ZeroTier, Radmin VPN 등, 무료): 모두 같은 가상 네트워크에 들어가면 서로 가상 IP로 닿는다. 공유기 설정이 필요 없고 CGNAT에서도 된다. 가장 간편해 기본 추천.
3. **작은 서버 임대**(아무 VPS): 서버 프로그램을 거기서 돌린다. 실제 AWS 환경과 가장 비슷하다(모두가 외부 서버에 붙는다).

편의 기능(착수 시): 접속 창(주소·포트·이름 입력, 최근 주소 기억, 연결 확인 버튼), 서버 실행 파일의 명령줄 인자(`--port 7777`), 서버 창에 "다른 사람이 입력할 주소" 표시(로컬·가상 랜·공인 IP 후보).

## 4. 유형 B(실시간 친구 방, 방장 권한)

출시 설계는 Steam 로비 + Steam Datagram Relay. 테스트에서는 Steam 대신 방장 컴퓨터에 직접 접속(3절의 방법 그대로)하는 전송을 쓴다. 게임 코드는 같고 전송 계층만 바뀐다(어댑터). 실시간이라 UDP 전송(예: LiteNetLib — 단일 소스, MIT)을 후보로 둔다.

## 5. 착수할 때 할 일 (순서)

1. 정의 데이터 JSON 내보내기(서버가 읽음).
2. `GameAction` 직렬화 — Mirror 생성기가 플레이어 데이터처럼 행동 클래스도 쓰기·읽기 코드를 만든다.
3. 메시지 규격: 입장, 행동, ChangeSet(+이벤트), 전체 데이터, 핑.
4. 서버 프로그램(.NET 콘솔 → 이후 AWS에서는 ASP.NET Core로 감싸기), 테스트 접속 방식, 클라이언트 접속 창.
5. 두 컴퓨터 실제 접속 확인(가상 랜 도구로).

## 6. 정할 것 (착수 시 사용자 확인)

- 위 가칭들의 이름.
- 유형 B 테스트 전송 라이브러리(LiteNetLib / Unity Transport).
- 멀티플레이 되돌리기 규칙(HANDOVER 7.2).
