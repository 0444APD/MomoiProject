# 프로젝트 관례 (Momoi Project / GBible)

GBible로 만드는 모든 프로젝트에서 AI가 지키는 규칙이다. 장르와 상관없이 같다. 장르·게임마다 다른 것(규칙 함수의 동사, 데이터 모양, 켤 선택 기능 …)은 그 프로젝트의 **기획 명세서**가 정한다. GBible에 무엇이 있고 어떻게 쓰는지는 **GBible 참조 문서**가 맡는다. 이 문서는 "어떻게 쓰나"만 정한다.

세 가지는 어떤 경우에도 지킨다(넘어야 하면 먼저 사람에게 말한다):
1. 프로그래머의 코딩이 어려워지지 않는다(감싸는 형식 금지, 어트리뷰트는 괜찮다).
2. 모든 게임 상태 변경은 행동(Action)으로 — 그래야 Undo·저장·리플레이·멀티플레이가 따라온다.
3. 실행 중 리플렉션 금지(게임이 켜질 때의 무거운 준비는 괜찮다).

---

## 0. 무엇을 쓸지 고르는 순서

- 만들기 전에 GBible 참조 문서에서 같은 일을 하는 기능을 먼저 찾는다(도전과제·로그·조건·보상·능력·상태 효과·예약·선택 대기·가중치 표·밸런스 값·설정·슬롯 …). 있으면 그것을 쓰고, 비슷한 것을 새로 만들지 않는다.
- 없으면 이 순서로 만든다. 앞쪽일수록 기획자가 DB에서 직접 고칠 수 있다.
  1. **DB Block 조합**(트리거·조건·결과·효과·대상 Block을 DB 항목에서 조립)
  2. **재사용 Block 하나 추가**(효과·대상·조건·결과 클래스. 다른 항목도 쓸 수 있게 일반적으로)
  3. **그 항목 전용 `[BindTo]` 코드**(한 항목만의 특수한 결과)
  4. **중간층 확장**(규칙 함수·의도 필드·새 가로채기 자리)
- GBible 자체에 없는 범용 기능이 필요하면(라이브러리를 고쳐야 하면) 고치지 않고 사람에게 알린다. 프로젝트 코드로 우회할 수 있으면 우회하고 그 사실을 보고한다.

## 1. 폴더·어셈블리, 데이터와 코드

- `Assets/Code/Rules`(어셈블리 `MomoiProject.Rules`): 게임 규칙 전부 — 데이터 클래스(RunState·Profile·원본 클래스), 행동, 규칙 함수(`Rules`), 이벤트·의도, Block, `[BindTo]` 함수. **화면 API(MonoBehaviour·GameObject·씬·입력)를 쓰지 않는다.** 서버·테스트에서도 같은 코드가 돈다.
- `Assets/Code/Client`: 화면·입력·연출·사운드. 규칙은 바꾸지 않고 행동만 보낸다.
- `Assets/Code/Editor`: 에디터 도구만. `Assets/Code/Tests`: 규칙 테스트(Rules만 참조).
- `Assets/MomoiProjectGenerated/`(`GameIds.cs`)는 손대지 않는다(DB를 저장하면 다시 만들어진다).
- 파일 하나에 주제 하나: `Actions/BattleActions.cs`, `Rules/Rules.cs`, `Events/Events.cs`, `Events/Intents.cs`, `Cards/CardBlocks.cs` …
- **데이터는 DB, 동작은 코드.**
  - 같은 모양의 원본(카드·몬스터·아이템·스킬)은 코드에 클래스만 두고, 하나하나는 DB › 인스턴스(또는 능력·상태 효과 같은 전용 종류)에서 만든다.
  - 기획자가 바꿀 숫자는 DB › 밸런스 값, 확률 표는 DB › 가중치 표, 플레이어에게 보일 글은 텍스트 표.
  - 판 데이터(RunState)에는 원본 ID와 **바뀌는 값**만 둔다(`DeckCard { id, card, upgraded }`). 원본은 게임 중에 고치지 않는다.
  - 코드가 필요 없는 설정(세션 옵션·판 저장·씬 흐름·고정 틱·Steam)은 DB에서 정한다(코드로 같은 값을 정하지 않는다).

## 2. 이름

- DB ID: lowerCamelCase, 점으로 묶을 수 있다(`fireball`, `startHp`, `boss.dragon`). 코드에서는 늘 `GameIds.종류.이름` 상수로 쓴다(글자로 적지 않는다).
- 클래스·필드: C# 기본(클래스 PascalCase, 데이터 클래스는 public 필드 lowerCamelCase).
- 이벤트: 일어난 일을 과거형으로 — `TurnEnded`, `EnemyKilled`, `CardPlayed` + `[Serializable, GameEvent("표시 이름")]`.
- 의도: 곧 일어날 일 + `Intent` — `DamageIntent`, `HealIntent` + `[Serializable, Intent("표시 이름")]`.
- 행동: 동사구 — `PlayCard`, `EndTurn`, `StartRun` + `[Serializable, BlockInfo("표시 이름")]`.
- Block: 효과는 동사(`DealDamage`), 대상은 명사구(`AllEnemies`), 조건은 서술(`HasLowHp`) + `[BlockInfo("표시 이름", Category = …, Description = …)]`. Description은 꼭 적는다(기획자가 목록에서 읽는다).
- 텍스트 키: `fail.*`(행동 실패), `hint.*`(미리보기 글), `hud.*`, `popup.*`, `menu.*`, DB 항목 이름은 `<id>.name`.
- 난수 흐름 이름: 쓰임 하나에 하나(`"deck"`, `"loot"`, `"ai"`).
- 기획 명세서에 없는 **새 개념**(새 DB 종류·새 시스템)의 이름만 사람에게 확인한다. 이벤트·의도·행동·Block 같은 나머지는 이 규칙대로 짓고 보고만 한다.

## 3. 규칙과 화면의 경계

- 플레이어 데이터를 바꾸는 코드는 **행동의 `Run`과 그 안에서 부르는 규칙 함수·Block·`[BindTo]`에만** 있다. 화면 코드는 읽기만 하고, 바꿀 때는 `Game.Do(new 행동 { … })`.
- 규칙 함수는 `public static class Rules`의 static 함수다(첫 인자 `GameApi game`). 행동·Block·`[BindTo]`가 같은 함수를 불러서 계산이 한 곳에만 있다.
- 행동 필드에는 객체를 넣는다(`new PlayCard { card = deckCard, target = enemy }`). 기록·전송에는 id만 남고 실행 직전에 지금 객체로 다시 찾는다. 행동 안에서 새 개체를 만들면 id는 `Game.NewId("접두어")`.
- 행동은 실패하면 바꾼 것이 모두 취소된다. 그러니 검사를 미리 다 하려고 애쓰지 말고, 안 되는 순간 던진다(플레이어용이면 `Game.Fail`, 5절). 행동 안에서 다른 행동을 불러도 된다(바깥 행동의 일부가 된다).
- 행동은 빨리 끝난다. 기다리지 않는다(애니메이션·플레이어 선택·시간 경과를 행동 안에서 기다리지 않는다 → 6·10·11절).
- 난수는 `Game.Random("흐름 이름")`만 쓴다. `UnityEngine.Random`·`System.Random`·`DateTime`·`Time`은 규칙에서 쓰지 않는다(재현·Undo·멀티가 깨진다).
- static 전역 상태를 규칙에 두지 않는다(세션마다 따로 돌아야 한다). 필요한 값은 플레이어 데이터에.
- 실행 중 리플렉션 금지: 데이터 클래스는 그 클래스·부모·안쪽 클래스·리스트 요소까지 모두 `[Serializable]`, 이벤트는 `[GameEvent]`, 의도는 `[Intent]`. 컬렉션은 `List<T>`·`T[]`·`Dictionary<K, V>`(키는 글자·정수·enum).

## 4. 가로채기 자리

- 장르의 **핵심 규칙 함수**(기획 명세서의 기본 동사: 피해·회복·죽음·사용·비용·뽑기·이동·획득 …)는 일을 하기 직전에 의도를 만들어 `Game.Intercept`에 통과시킨다. 막혔으면(`cancelled`) 아무것도 하지 않는다.
  ```csharp
  var hit = game.Intercept(new DamageIntent { sourceId = source?.id, targetId = target.id, amount = amount, kind = kind });
  if (hit.cancelled || hit.amount <= 0) return;
  ```
- 의도의 필드는 기믹이 고칠 만한 것 전부: 주체·대상 id, 양, 종류, 횟수, `cancelled`. 나중에 필드를 더해도 기존 가로채기는 그대로 돈다.
- 이벤트는 일이 끝난 뒤(가로채기 다음, 실제로 바뀐 값으로) 쏜다. 함수 하나에 의도 하나·이벤트 하나.
- 비용은 직접 빼지 않고 `Game.Pay`(비용 의도를 이미 거친다, 5절).
- 이렇게 해 두면 기획 단계에서 몰랐던 기믹(반사·면역·두 배·대신 맞기)이 이 자리에 붙는다.

## 5. 숫자·비용·실패

- 기획자가 바꿀 숫자(시작 값·보상·확률·성장)는 코드에 적지 않고 DB › 밸런스 값에서 읽는다: `Game.Balance(GameIds.Balance.X)`, 층·레벨마다 변하면 곡선 + `Game.Balance(id, 단계)`. 규칙 자체의 상수(덱 섞기 알고리즘 같은 것)는 코드에 둔다.
- 무게 있는 뽑기(드롭·보상·조우)는 DB › 가중치 표 + `Game.Roll`.
- 능력치(공격력 등)는 숫자 필드 + Modifier(`Game.AddModifier`·`Game.Attribute`). 장비·버프의 보정을 필드에 직접 더하지 않는다(벗을 때 되돌릴 수 없다).
- 비용: `Game.Pay(키, 경로, 양, what: "energy.name")`. 모자라면 플레이어용 실패가 난다. 화면 미리 확인은 `Game.CanPay`·`Game.CanDo`.
- 실패:
  - 플레이어에게 보일 것(모자람·조건 안 맞음·지금 못 함) → `throw Game.Fail("fail.키", "기본 문장 {값}", ("값", x))`. 텍스트 표에 키를 넣으면 번역된다.
  - 프로그래머 실수(없는 ID·잘못된 상태) → `throw new InvalidOperationException("…")`. 플레이어에게 보이지 않는다.
  - 능력·아이템의 사용 조건이 안 맞을 때 플레이어에게 보일 글은 그 항목의 **쓸 수 없을 때 글**(DB 칸 `failText`, 텍스트 키)에 둔다. 비우면 라이브러리 기본 글({condition}이 DB 조건 문장 그대로)이 보인다.

## 6. 화면·연출

- 화면은 데이터를 그린다: `GameView.Redraw(그리기, 키…)`, 목록은 `ViewList`, 단순한 값 하나는 컴포넌트 '데이터 연결'. 값이 바뀔 때마다 그리지 말고 이 도구가 프레임 끝에 한 번 그리게 한다.
- 연출(피해 숫자·카드 이동·쓰러짐)은 규칙이 끝난 뒤의 일이다: `session.Events.SubscribeAfterAction<이벤트>(e => GameView.Present(연출(e)))`. 실패한 행동의 이벤트는 오지 않는다. 연출 코드는 데이터를 바꾸지 않는다.
- 연출 안의 시간은 `GameView.Wait`·`GameView.DeltaTime`(속도·건너뛰기를 따른다). `done()` 콜백 연출은 반드시 `done`을 부른다.
- 입력은 `GameView.Busy`(연출 중이거나 선택을 기다림)일 때 막는다.
- 예상 값(예상 피해·"낼 수 없음" 이유)은 화면에서 따로 계산하지 않고 `Game.Preview(행동, g => 읽기)`·`Game.CanDo(행동, out 이유)`.
- 화면 오브젝트를 데이터 id로 찾을 때는 `GameView.Find<T>(id)`(ViewList가 등록한다).
- 씬 전환은 화면이 직접 하지 않는다: 판 데이터의 씬 필드를 행동이 바꾸고 씬 흐름(DB › Bootstrap)이 연다.

## 7. 글·다국어

- 플레이어에게 보일 글은 코드·UXML에 적지 않고 텍스트 키로: `Texts.Get("hud.energy", ("energy", n))`. DB 항목 이름은 `<id>.name`(값에 ID를 넣으면 그 이름으로 바뀐다).
- 원문 언어(기본 한국어) 표에 키를 채우고, 다른 언어는 시트로 번역한다.
- 실패 글은 5절의 `Game.Fail`.

## 8. 데이터 구역·저장

- 판(한 번의 플레이)에만 있는 것은 **Session** 구역(기본 `run` = RunState), 판이 끝나도 남는 것은 **Meta** 구역(기본 `profile` = Profile). 새 플레이어 데이터는 DB › 플레이어 데이터에 만들고 구역을 고른다.
- 저장은 DB › Bootstrap의 판 저장 설정대로 저절로 된다. 저장 코드를 따로 쓰지 않는다. 세이브 칸이 여럿이면 슬롯(`GBibleRuntime.UseSlot`).
- 플레이어 데이터에 에셋(스프라이트·프리팹·ScriptableObject) 참조를 넣지 않고 DB ID를 넣는다. DB 항목 ID가 든 글자 필드에는 `[DataRef(typeof(종류))]`를 붙인다(ID를 바꾸면 따라간다).
- 출시 뒤 저장 구조를 바꾸면 DB › 개발 › 저장 변환에 줄을 더한다(필드 이름을 바꾸기 전에 확인).
- 기기마다 하나인 것(음량·언어·화면·키)은 DB › 설정(`GameSettings`). 판 규칙에 영향을 주는 값은 설정에 두지 않는다.

## 9. 이벤트·트리거로 잇기

- 다른 기능이 반응할 만한 일(처치·획득·턴 끝·판 끝)은 이벤트로 쏜다. 반응하는 쪽(도전과제·로그·유물·상태 효과)은 이벤트를 받는 트리거로 만든다(DB에서 조립 우선). 쏘는 쪽이 받는 쪽을 직접 부르지 않는다.
- 이벤트 필드에는 받는 쪽이 거를 수 있게 주체·대상 id와 양을 넣는다(가진 쪽 필드·이벤트 조건이 이것을 본다).
- 결과가 다시 이벤트를 쏘아 끝없이 도는 고리를 만들지 않는다(사슬 한도 16에서 끊기고 경고가 남는다).

## 10. 시간·턴

- 턴제: 턴은 행동(`EndTurn`)과 이벤트(`TurnEnded`)로 흐른다. "N턴 동안/N턴 뒤"는 상태 효과(이벤트 횟수 지속·끝날 때 결과)로, 코드에서 나중에 할 일은 `Game.ScheduleOn<이벤트>(횟수, 행동)`.
- 실시간: DB › Bootstrap의 고정 틱을 켠다. 시간 지속은 상태 효과(게임 시간), 나중 일은 `Game.ScheduleAfter(초, 행동)`. 틱마다의 가벼운 규칙은 `session.Ticked`에서 `Game.Do`로. 이동·물리는 화면 쪽 자유 영역이고, 규칙에 필요한 결과(맞음·주움)만 행동으로 보낸다.
- `Update`에서 플레이어 데이터를 바꾸지 않는다.

## 11. 플레이어 선택

- 행동 도중 플레이어가 골라야 하면(카드 1장 버리기·보상 3개 중 1개) 기다리지 않고 `Game.Ask(안내, 후보, new 이어서할행동())`. 고른 뒤 할 일은 모두 이어서 할 행동(`[Chosen]` 필드)에 쓴다. DB에서는 결과 '선택 요구'(판에 있는 것에서)·'가중치 표에서 고르기'(DB 원본에서).
- 뽑기의 후보(풀)는 저장하지 않고 뽑을 때 만든다: 진행·해금은 가중치 표 줄의 조건, 판에서 만들어진 것은 목록 줄, 가진 것은 뺄 목록, 규칙이 계산한 후보는 `Game.Roll(풀, …, stream: "쓰는 곳 이름")`.
- 화면은 `Game.Choice`를 보여 주고 `Game.Answer`로 답한다. 기다리는 동안 입력은 `GameView.Busy`로 막힌다.

## 12. 테스트·검증·보고

- 규칙(행동·규칙 함수·Block)을 만들거나 고치면 `Tests`에 테스트를 하나 이상 둔다. 세션을 손으로 만든다: 플레이어 데이터 `Define`, 밸런스 값 `session.Balance.Define`, 상태 효과 `session.Statuses.Define`, 원본 `session.Instances`.
- 테스트는 게임처럼 행동을 실행하고 값을 본다. 플레이어용 실패는 `Assert.Throws<GameFailure>`(NUnit은 정확한 형식만 잡는다). Undo가 맞는지(`session.Undo()` 뒤 값)도 본다.
- 코드를 고친 뒤에는 컴파일이 되는지 확인하고, Unity가 열려 있으면 콘솔 오류·DB 검증("검증 통과")을 본다.
- 사람에게 보고할 것: DB에 만들어야 하는 항목(종류·ID·값), Unity에서 직접 봐야 확인되는 것, 정한 이름, 기획 명세서와 달라진 점. 작업량·테스트 수는 말하지 않는다.
- 기획 명세서와 코드가 다르면 코드를 맞추거나, 명세서가 틀렸으면 사람에게 묻는다(몰래 바꾸지 않는다).

## 13. 문법 밖 기믹

- 효과는 "언제(즉시·발동·지연·지속) + 누구에게(대상 고르기) + 무엇을(데이터 바꾸기·만들기/없애기·가로채기·선택 요구·비용) + 안전장치(연쇄 제한)"로 쪼갠다. 쪼개지면 0절 순서로 만든다.
- 쪼개지지 않는 것(실시간 물리 규칙, 게임 전체를 과거로 되감기, 규칙 밖의 연출 의존 판정 …)은 만들기 전에 표시하고 묻는다: 무엇이 문법 밖인지, 어떻게 만들 수 있는지(화면 쪽·별도 시스템·근사), 각각의 비용.
- 기획 명세서의 "문법에 안 맞는 기믹" 칸에 적힌 것은 그 답을 따른다.

## 14. 하지 않는 것

- GBible 라이브러리(`Packages/com.momoi.gbible`) 코드를 고치지 않는다.
- 생성 파일(`Assets/MomoiProjectGenerated/`)을 고치지 않는다.
- DB 에셋 파일(.asset)을 텍스트로 직접 쓰지 않는다(15절의 방법으로 만든다).
- 행동 밖에서 플레이어 데이터를 바꾸지 않는다(개발용 명령도 DB › 개발 명령이나 행동으로).
- 화면 코드에 규칙 계산을 복사하지 않는다(미리보기를 쓴다).

## 15. DB 항목 만들기

AI는 Unity 창을 누를 수 없으므로, DB 항목은 사람이 확인하고 저장하는 형태로 만든다. 어느 쪽이든 만든 항목은 DB에 **적용 전**으로 들어가고, 사람이 DB에서 보고 Ctrl+S로 적용한다.

- **값이 많은 것**(밸런스 값·카드 수치·몬스터 수치·가중치 표의 항목 줄처럼 숫자·글자·enum과 그 목록): CSV 파일을 써 두고, 사람이 그 DB 종류 탭의 **CSV › CSV 가져오기**로 넣는다. 첫 칸 `id`, 나머지 칸 이름 = 필드 이름(묶음 필드는 `curve.step`, 목록은 `entries[0].weight`처럼). 인스턴스는 값의 클래스마다 한 파일. Block 칸(트리거·조건·결과)은 CSV에 없다.
- **트리거·조건·결과 Block이 든 것**(도전과제·능력·상태 효과·로그·가중치 표의 조건 …): `Assets/Code/Editor`에 메뉴 하나짜리 DB 추가 메뉴 스크립트를 쓴다. 사람이 메뉴를 한 번 누르면 항목이 적용 전으로 생긴다.
  ```csharp
  // Assets/Code/Editor/AddAchievements.cs — 메뉴: MomoiProject › DB 추가 › 도전과제(예: 가이드 예시의 Editor/AddBalanceValues.cs)
  using GBible; using GBible.Data; using GBible.EditorTools; using UnityEditor;

  static class AddAchievements
  {
      [MenuItem("MomoiProject/DB 추가/도전과제")]
      static void Run()
      {
          var db = EditorDatabase.Instance;
          if (db.FindById("firstWin") == null)
          {
              var a = (AchievementData)EditorDatabase.Staging.Add(typeof(AchievementData), "firstWin");
              a.trigger = new EventTrigger { eventType = typeof(BattleWon).FullName };
              // a.outcomes.Add(…);
          }
          EditorDatabase.Staging.Touch();   // DB 화면 갱신. 적용은 사람이 Ctrl+S
      }
  }
  ```
  이미 있는 ID는 건너뛴다(사람이 고친 값을 덮지 않는다). 고쳐야 하면 `EditorDatabase.Staging.Work(항목)`으로 작업본을 받아 고친다.
- 사람에게 보고할 때: 누를 메뉴, 넣을 CSV 파일과 그 탭, 만들어질 항목 목록, 적용(Ctrl+S) 뒤 확인할 것(DB 아래 "검증 통과").
- 플레이어 데이터 키·필드처럼 시작 설정이 만드는 것은 시작 설정에, 화면 에셋(프리팹·스프라이트·UXML)은 사람이 Unity에서 만들거나 지정한다(AI는 필요한 목록과 연결할 필드를 적는다).

## 16. 기본 진행 순서(시스템층)

1. 기획 명세서를 읽고(`PlanningSpecGuide.md`의 칸 → GBible 표와 질문 규칙) 시스템 목록을 만든다: 데이터(판·프로필), 원본 종류(카드·몬스터 …), 핵심 동사(규칙 함수), 이벤트, 진행 흐름(판 → 전투 → 턴 …), 켤 선택 기능, DB 설정(Bootstrap·설정·Steam).
2. 데이터 클래스(RunState·Profile·원본 클래스)와 플레이어 데이터.
3. 규칙 함수(핵심 동사마다 의도·가로채기 자리·이벤트)와 의도·이벤트 클래스.
4. 행동(진행 흐름: 판 시작·전투 시작·턴 끝·판 끝 …)과 재사용 Block(효과·대상·조건).
5. 프로젝트 고유 기능(유물·축복처럼 DB에서 조립할 종류)이 필요하면 DB 종류 클래스 + 감시 등록.
6. DB 항목(15절: DB 추가 메뉴·CSV)과 밸런스 값 이름.
7. 테스트(12절) — 흐름 하나(판 시작부터 전투 승리까지)가 행동만으로 끝까지 도는지.
8. 화면(Client): 데이터를 그리는 화면 → 입력 → 연출. 처음에는 모니터(명령 탭·데이터 탭)로 시험하고 화면은 나중에.
9. 보고(12절).

레벨 디자인(개별 카드·몬스터·기믹·수치)은 이 단계의 범위가 아니다. 시스템층은 그것을 0절 순서로 쉽게 더할 수 있게 해 두는 데까지다.

## 17. 질문

- 기획 명세서에 답이 있으면 묻지 않는다. 명세서와 이 관례로 정해지지 않고, 틀리면 나중에 크게 바꿔야 하는 것만 묻는다(데이터 구조·진행 흐름·핵심 동사·멀티 여부·문법 밖 기믹).
- 물을 때는 한 번에 모아서, 질문마다 추천 기본값과 이유를 붙인다. 사람이 답하지 않으면 추천값으로 가도 되는 것은 그렇게 표시한다.
- 되돌리기 쉬운 것(이름·수치·화면 배치)은 묻지 않고 정한 뒤 보고한다.
