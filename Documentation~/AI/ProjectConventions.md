# 프로젝트 관례 (Momoi Project / GBible)

GBible로 만드는 모든 프로젝트에서 AI가 지키는 규칙이다. 장르와 상관없이 같다. 장르·게임마다 다른 것(규칙 함수의 동사, 데이터 모양, 켤 선택 기능 …)은 그 프로젝트의 **기획 명세서**가 정한다. GBible에 무엇이 있고 어떻게 쓰는지는 **GBible 참조 문서**(`Reference.md`)가 맡는다. 이 문서는 "어떻게 쓰나"만 정한다.

**누가 무엇을 하나**: 로직·데이터·DB 항목·화면·테스트 도구는 AI가 코드와 DB 반영 스크립트로 만든다. 개발자는 에디터에서 읽고, 밸런싱 값을 바꾸고, 다이얼로그 그래프를 만들고, 레벨을 배치하고, 에셋을 가져오고, 테스트한다. 진행 순서와 질문은 `ProjectFlow.md`(진행 매뉴얼)가 정한다.

세 가지는 어떤 경우에도 지킨다(넘어야 하면 먼저 사람에게 말한다):
1. 틀리지 않고, 되돌아가지 않고, 예외가 생기지 않는다 — 틀에 맞지 않는 것은 예외 코드로 덧붙이지 않고 틀을 고친다(그래서 첫 단계에서 예외를 다 끌어낸다). 감싸는 형식·고유 문법은 피한다(어트리뷰트는 괜찮다).
2. 모든 게임 상태 변경은 행동(Action)으로 — 그래야 Undo·저장·리플레이·멀티플레이가 따라온다.
3. 실행 중 리플렉션 금지(게임이 켜질 때의 무거운 준비는 괜찮다).

---

## 0. 무엇을 쓸지 고르는 순서

- 만들기 전에 GBible 참조 문서에서 같은 일을 하는 기능을 먼저 찾는다(도전과제·로그·조건·보상·능력·상태 효과·패시브·예약·선택 대기·가중치 표·밸런스 값·설정·슬롯·격자·화면 …). 있으면 그것을 쓰고, 비슷한 것을 새로 만들지 않는다.
  - "가지고 있으면 발동"(유물·특성·패시브 스킬·장비 효과·조커·참)은 DB › 패시브, "걸려 있는 동안·N턴 동안"은 상태 효과, 쿨다운은 상태 효과 + 조건 '상태 효과 검사'. 프로젝트 DB 종류(17장)는 이것들로 안 될 때만.
  - 놓인 순서대로 발동하는 조각(조커 칸·보드)은 패시브 '놓인 것마다', 가진 동안 +N은 패시브의 '가진 동안 능력치 보정'(트리거 없이도 된다, 조건부면 `modifierWhen`). 한 조각이 순간마다 다른 결과(쌓기·빼기·내기)는 패시브 하나의 `rules`(발동 더), N초마다는 `pulse`.
  - 효과 문장은 `GimmickCatalog.md`(기믹 목록)의 갈래로 쪼개고, 갈래에 적힌 부품으로 만든다.
- 없으면 이 순서로 만든다. 앞쪽일수록 개발자가 DB에서 읽고 값을 바꿀 수 있다.
  1. **DB Block 조합**(트리거·조건·결과·효과·대상 Block을 DB 항목에서 조립)
  2. **재사용 Block 하나 추가**(효과·대상·조건·결과 클래스. 다른 항목도 쓸 수 있게 일반적으로)
  3. **그 항목 전용 `[BindTo]` 코드**(한 항목만의 특수한 결과)
  4. **중간층 확장**(규칙 함수·의도 필드·새 가로채기 자리)
- GBible 자체에 없는 범용 기능이 필요하면(라이브러리를 고쳐야 하면) 고치지 않고 사람에게 알린다. 단 화면 쪽 도구(UI·입력·카메라·이동)는 알리지 않고 프로젝트에 만든다(21절). 프로젝트 코드로 우회할 수 있으면 우회하고 그 사실을 보고한다.

## 1. 폴더·어셈블리, 데이터와 코드

- `Assets/MomoiProject/Code/Rules`(어셈블리 `MomoiProject.Rules`): 게임 규칙 전부 — 데이터 클래스(RunState·Profile·원본 클래스), 행동, 규칙 함수(`Rules`), 이벤트·의도, Block, `[BindTo]` 함수. **화면 API(MonoBehaviour·GameObject·씬·입력)를 쓰지 않는다.** 서버·테스트에서도 같은 코드가 돈다.
- `Assets/MomoiProject/Code/Client`: 화면·입력·연출·사운드. 규칙은 바꾸지 않고 행동만 보낸다.
- `Assets/MomoiProject/Code/Editor`: 에디터 도구만. `Assets/MomoiProject/Code/Tests`: 규칙 테스트(Rules만 참조).
- `Assets/MomoiProject/Generated/`(`GameIds.cs`)는 손대지 않는다(DB를 저장하면 다시 만들어진다).
- 파일 하나에 주제 하나: `Actions/BattleActions.cs`, `Rules/Rules.cs`, `Events/Events.cs`, `Events/Intents.cs`, `Cards/CardBlocks.cs` …
- **데이터는 DB, 동작은 코드.**
  - 같은 모양의 원본(카드·몬스터·아이템·스킬)은 코드에 클래스만 두고, 하나하나는 DB › 인스턴스(또는 능력·상태 효과 같은 전용 종류)에서 만든다.
  - 개발자가 바꿀 숫자는 DB › 밸런스 값, 확률 표는 DB › 가중치 표, 플레이어에게 보일 글은 텍스트 표.
  - 판 데이터(RunState)에는 원본 ID와 **바뀌는 값**만 둔다(`DeckCard { id, card, upgraded }`). 원본은 게임 중에 고치지 않는다.
  - 코드가 필요 없는 설정(세션 옵션·판 저장·씬 흐름·고정 틱·Steam)은 DB에서 정한다(코드로 같은 값을 정하지 않는다).

## 2. 이름

- DB ID: lowerCamelCase, 점으로 묶을 수 있다(`fireball`, `startHp`, `boss.dragon`). 코드에서는 늘 `GameIds.종류.이름` 상수로 쓴다(글자로 적지 않는다).
- 클래스·필드: C# 기본(클래스 PascalCase, 데이터 클래스는 public 필드 lowerCamelCase).
- 이벤트: 일어난 일을 과거형으로 — `TurnEnded`, `EnemyKilled`, `CardPlayed` + `[Serializable, GameEvent("표시 이름")]`.
- 의도: 곧 일어날 일 + `Intent` — `DamageIntent`, `HealIntent` + `[Serializable, Intent("표시 이름")]`.
- 행동: 동사구 — `PlayCard`, `EndTurn`, `StartRun` + `[Serializable, BlockInfo("표시 이름")]`.
- Block: 효과는 동사(`DealDamage`), 대상은 명사구(`AllEnemies`), 조건은 서술(`HasLowHp`) + `[BlockInfo("표시 이름", Category = …, Description = …)]`. Description은 꼭 적는다(기획자가 목록에서 읽는다).
- 텍스트 키: `fail.*`(행동 실패), `hint.*`(미리보기 글), `hud.*`, `popup.*`, `menu.*`, DB 항목 이름은 `<id>.name`.
- 난수 흐름 이름: 쓰임 하나에 하나(`"deck"`, `"loot"`, `"ai"`).
- 폴더·파일 이름(만드는 것 모두 — `Assets/MomoiProject/Code`·`Assets/MomoiProject/UI`·`Assets/Dev/Art` …)은 영어. 한글은 쓰지 않는다.
- `Assets/Dev`는 개발자 폴더다(안의 폴더 = DB 'Dev' 탭). 요청받을 때만 만들거나 바꾼다. 예외: 넣을 에셋 자리(`AssetRequests`)는 `Assets/Dev/Art`·`Dev/Audio`·`Dev/Fonts` … — 개발자가 진짜 파일을 넣는 곳이다.
- AI가 쓰는 것은 모두 `Assets/MomoiProject/` 아래: 코드 `Code/`(Rules·Client·Editor·Tests·Keywords), 화면 `UI/`. `Assets` 바로 아래에 새 폴더를 만들지 않는다.
- 기획 명세서에 없는 **새 개념**(새 DB 종류·새 시스템)의 이름만 사람에게 확인한다. 이벤트·의도·행동·Block 같은 나머지는 이 규칙대로 짓고 보고만 한다.

## 3. 규칙과 화면의 경계

- 플레이어 데이터를 바꾸는 코드는 **행동의 `Run`과 그 안에서 부르는 규칙 함수·Block·`[BindTo]`에만** 있다. 화면 코드는 읽기만 하고, 바꿀 때는 `Game.Do(new 행동 { … })`.
- 규칙 함수는 `public static class Rules`의 static 함수다(첫 인자 `GameApi game`). 행동·Block·`[BindTo]`가 같은 함수를 불러서 계산이 한 곳에만 있다.
- 행동 필드에는 객체를 넣는다(`new PlayCard { card = deckCard, target = enemy }`). 기록·전송에는 id만 남고 실행 직전에 지금 객체로 다시 찾는다. 행동 안에서 새 개체를 만들면 id는 `Game.NewId("접두어")`(여럿이면 `Game.NewIds`). id는 플레이어 데이터 전체에서 하나다(형식이 달라도 겹치지 않게 — 접두어로).
- 한 행동 안에서 같은 객체를 `Game.Find`로 여러 번 찾지 않는다(찾을 때마다 데이터 전체를 훑는다). 한 번 찾아 변수로.
- 행동은 실패하면 바꾼 것이 모두 취소된다. 그러니 검사를 미리 다 하려고 애쓰지 말고, 안 되는 순간 던진다(플레이어용이면 `Game.Fail`, 5절). 행동 안에서 다른 행동을 불러도 된다(바깥 행동의 일부가 된다). 행동 안에서 쏜 이벤트를 받은 규칙·트리거 결과가 던져도 그 행동 전체가 취소된다.
- **메인 룰**(조각이 자리에 놓이고 정해진 순서로 발동하는 게임의 뼈대)은 기믹 목록 1절의 모양으로 만든다: 조각 = 판 데이터의 객체 목록(고유 `id` + 원본 ID 필드), 자리 = 목록 + 줄 길이(`Placement`), 순서 = 메인 룰 행동이 단계마다 이벤트를 쏘거나 자리 순서로 돌며 `Game.TryUse`. 조각 하나하나의 효과는 DB(패시브·능력)에 두고 메인 룰 코드에 쓰지 않는다. 메인 룰이 갖는 것은 단계·순서·공식(능력치 변환 단계 같은 계산식)이고, 조각은 공식이 읽는 값(비율 능력치·필드)에 보정을 더할 뿐이다. 반응을 발동이 끝난 뒤로 미루는 대기열도 메인 룰이다(기믹 목록 3절).
- 행동은 빨리 끝난다. 기다리지 않는다(애니메이션·플레이어 선택·시간 경과를 행동 안에서 기다리지 않는다 → 6·10·11절).
- 난수는 `Game.Random("흐름 이름")`만 쓴다. `UnityEngine.Random`·`System.Random`·`DateTime`·`Time`은 규칙에서 쓰지 않는다(재현·Undo·멀티가 깨진다). 현실 시각은 `Game.Now`(행동에 기록된다)·날짜 번호 `Game.Day(초기화 시각)`, 게임 시간은 `session.Clock`.
- **판정 보고 행동**: 물리·충돌·투사체·미니게임처럼 화면이 정하는 판정은 화면(Client)이 하고, 그 결과(누가 누구를 맞혔나·잡았나·성공)를 행동 하나로 보낸다(실시간이면 틱마다 묶어 `Strike { hits }`). 규칙은 결과로만 데이터를 바꾼다. 위치·속도는 화면 쪽이고, 한 번 정해지는 값(폭발 지점)은 행동 필드로 넘긴다.
- static 전역 상태를 규칙에 두지 않는다(세션마다 따로 돌아야 한다). 필요한 값은 플레이어 데이터에.
- 실행 중 리플렉션 금지: 데이터 클래스는 그 클래스·부모·안쪽 클래스·리스트 요소까지 모두 `[Serializable]`, 이벤트는 `[GameEvent]`, 의도는 `[Intent]`. 컬렉션은 `List<T>`·`T[]`·`Dictionary<K, V>`(키는 글자·정수·enum).

## 4. 가로채기 자리

- 장르의 **핵심 규칙 함수**(기획 명세서의 기본 동사: 피해·회복·죽음·사용·비용·뽑기·이동·획득 …)는 일을 하기 직전에 의도를 만들어 `Game.Intercept`에 통과시킨다. 막혔으면(`cancelled`) 아무것도 하지 않는다.
  ```csharp
  var hit = game.Intercept(new DamageIntent { sourceId = source?.id, targetId = target.id, amount = amount, kind = kind });
  if (hit.cancelled || hit.amount <= 0) return;
  ```
- 의도의 필드는 기믹이 고칠 만한 것 전부: 주체·대상 id, 양, 종류, 횟수, `cancelled`. 나중에 필드를 더해도 기존 가로채기는 그대로 돈다.
- 이벤트는 일이 끝난 뒤(가로채기 다음, 실제로 바뀐 값으로) 쏜다. 함수 하나에 의도 하나·이벤트 하나.
- 비용은 직접 빼지 않고 `Game.Pay`(비용 의도를 이미 거친다, 5절).
- 이렇게 해 두면 기획 단계에서 몰랐던 기믹(반사·면역·두 배·대신 맞기)이 이 자리에 붙는다.
- GBible이 이미 가로채기 자리를 둔 동작: **사용**(`Game.Use`·`TryUse` — 횟수·막기), **효과 배율**(능력을 쓸 때·패시브가 발동할 때 — 기본 효과 Block이 곱하고, 프로젝트 효과 Block은 수치에 `Use.Context.Power`를 곱한다), **비용 지불**(`Game.Pay`·`TryPay` — 양·공짜·하한(빚)·낼 곳, `forId`·`userId`로 거름), **상태 효과 걸기**(`Game.ApplyStatus`·효과 '상태 효과 걸기' — 바꾸기·중첩·길이·최대 중첩·주기·막기), **확률**(`Game.Chance`·조건 '확률' — 확률 배율). 이 동작은 이 함수로만 한다: 확률을 `Game.Random(…).Chance`로 직접 굴리거나 상태 효과 목록을 직접 고치면 가로채기가 붙지 않는다.

## 5. 숫자·비용·실패

- 개발자가 바꿀 숫자(시작 값·보상·확률·성장)는 코드에 적지 않고 DB › 밸런스 값에서 읽는다: `Game.Balance(GameIds.Balance.X)`, 층·레벨마다 변하면 곡선 + `Game.Balance(id, 단계)`. 규칙 자체의 상수(덱 섞기 알고리즘 같은 것)는 코드에 둔다.
- 무게 있는 뽑기(드롭·보상·조우)는 DB › 가중치 표 + `Game.Roll`.
- 능력치(공격력 등)는 숫자 필드 + Modifier(`Game.AddModifier`·`Game.Attribute`). 장비·버프의 보정을 필드에 직접 더하지 않는다(벗을 때 되돌릴 수 없다).
- 비용: `Game.Pay(키, 경로, 양, what: "energy.name", forId: 무엇을 위한, user: 내는 쪽)`. 모자라면 플레이어용 실패가 난다. 틱 묶음 행동 안에서 "되면 낸다"(연계 MP·카드마다 비용)는 `Game.TryPay`(모자라면 바꾸지 않고 거짓). 화면 미리 확인은 `Game.CanPay`·`Game.CanDo`(`CanPay`는 가로채기 전 값이라 규칙 판정에 쓰지 않는다).
- 실패:
  - 플레이어에게 보일 것(모자람·조건 안 맞음·지금 못 함) → `throw Game.Fail("fail.키", "기본 문장 {값}", ("값", x))`. 텍스트 표에 키를 넣으면 번역된다.
  - 프로그래머 실수(없는 ID·잘못된 상태) → `throw new InvalidOperationException("…")`. 플레이어에게 보이지 않는다.
  - 능력·아이템의 사용 조건이 안 맞을 때 플레이어에게 보일 글은 그 항목의 **쓸 수 없을 때 글**(DB 칸 `failText`, 텍스트 키)에 둔다. 비우면 라이브러리 기본 글({condition}이 DB 조건 문장 그대로)이 보인다.

## 6. 화면·연출

- **UI(HUD·메뉴·팝업)는 UI Toolkit 화면**(매뉴얼 35장): 화면 하나 = `Assets/MomoiProject/UI/Screens/<이름>.uxml`(+ `.uss`) + DB › 화면 항목(층·뒤로로 닫기·열 씬) + 필요하면 `Assets/MomoiProject/Code/Client/Screens/<이름>.cs`(`[BindTo(GameIds.Screen.X)] : GameScreen`). UXML·USS·화면 코드는 AI가 쓰고, 프리팹·인스펙터 연결은 쓰지 않는다.
  - 값을 보이기만 하는 칸은 UXML의 `binding-path`(`run:gold`, `run:gold@hud.gold`, `@hud.endTurn`). 화면 코드에 같은 일을 쓰지 않는다.
  - 버튼 → 행동은 `OnClick("이름", () => new 행동())`(Busy면 무시, 플레이어용 실패는 알림). 화면을 여는 버튼은 `OnClick("이름", () => GameScreens.Open(…))`.
  - 데이터 목록은 `List<T>("컨테이너", Item("칸 UXML"), …)`(목록 칸 UXML은 `Assets/MomoiProject/UI/Items/`, 화면 UXML에 `<ui:Template>`로 적는다).
  - 고르기 창·확인·설정·슬롯·일시정지·알림은 **기본 화면**을 쓰고 새로 만들지 않는다. 모양은 `Assets/MomoiProject/UI/Theme.uss`의 `--momoi-…` 변수로 맞추고, 프로젝트 화면의 USS도 그 변수를 쓴다.
  - 1920×1080 기준 px. 그림(스프라이트·아이콘)·글꼴은 사람이 넣는다: 그 자리는 색 상자로 두고 보고에 "넣을 에셋(경로·크기·쓰는 곳)"을 적는다.
- 씬에 놓이는 것(캐릭터·카드 오브젝트)은 `GameView.Redraw(그리기, 키…)`·`ViewList`·컴포넌트 '데이터 연결'. 값이 바뀔 때마다 그리지 말고 이 도구가 프레임 끝에 한 번 그리게 한다.
- 연출(피해 숫자·카드 이동·쓰러짐)은 규칙이 끝난 뒤의 일이다: `session.Events.SubscribeAfterAction<이벤트>(e => GameView.Present(연출(e)))`. 실패한 행동의 이벤트는 오지 않는다. 연출 코드는 데이터를 바꾸지 않는다.
- 연출 안의 시간은 `GameView.Wait`·`GameView.DeltaTime`(속도·건너뛰기를 따른다). `done()` 콜백 연출은 반드시 `done`을 부른다.
- 입력은 `GameView.Busy`(연출 중이거나 선택을 기다림)일 때 막는다.
- 예상 값(예상 피해·"낼 수 없음" 이유)은 화면에서 따로 계산하지 않고 `Game.Preview(행동, g => 읽기)`·`Game.CanDo(행동, out 이유)`.
- 화면 오브젝트를 데이터 id로 찾을 때는 `GameView.Find<T>(id)`(ViewList가 등록한다), UI Toolkit 칸은 `GameView.FindElement(id)`(ElementList가 등록한다). 화면 위에 잠깐 띄우는 요소(피해 숫자)는 `GameScreens.Overlay`에.
- 씬 전환은 화면이 직접 하지 않는다: 판 데이터의 씬 필드를 행동이 바꾸고 씬 흐름(DB › Bootstrap)이 연다.

## 7. 글·다국어

- 플레이어에게 보일 글은 코드·UXML에 적지 않고 텍스트 키로: `Texts.Get("hud.energy", ("energy", n))`. DB 항목 이름은 `<id>.name`(값에 ID를 넣으면 그 이름으로 바뀐다).
- 원문 언어(기본 한국어) 표에 키를 채우고, 다른 언어는 시트로 번역한다.
- 실패 글은 5절의 `Game.Fail`.

## 8. 데이터 구역·저장

- 판(한 번의 플레이)에만 있는 것은 **Session** 구역(기본 `run` = RunState), 판이 끝나도 남는 것은 **Meta** 구역(기본 `profile` = Profile). 새 플레이어 데이터는 DB › 플레이어 데이터에 만들고 구역을 고른다.
- 저장은 DB › Bootstrap의 판 저장 설정대로 저절로 된다. 저장 코드를 따로 쓰지 않는다. 세이브 칸이 여럿이면 슬롯(`GBibleRuntime.UseSlot`).
- 플레이어 데이터에 에셋(스프라이트·프리팹·ScriptableObject) 참조를 넣지 않고 DB ID를 넣는다. DB 항목 ID가 든 글자 필드에는 `[DataRef(typeof(종류))]`를 붙인다(ID를 바꾸면 따라간다).
- 출시 뒤 저장 구조를 바꾸면 DB › 개발 › 저장 변환에 줄을 더한다(필드 이름을 바꾸기 전에 확인).
- 기기마다 하나인 것(음량·언어·화면·키)은 DB › 설정(`GameSettings`). 판 규칙에 영향을 주는 값은 설정에 두지 않는다.

## 9. 이벤트·트리거로 잇기

- 다른 기능이 반응할 만한 일(처치·획득·턴 끝·판 끝)은 이벤트로 쏜다. 반응하는 쪽(도전과제·로그·유물·상태 효과)은 이벤트를 받는 트리거로 만든다(DB에서 조립 우선). 쏘는 쪽이 받는 쪽을 직접 부르지 않는다.
- 이벤트 필드에는 받는 쪽이 거를 수 있게 주체·대상 id와 양을 넣는다(가진 쪽 필드·이벤트 조건이 이것을 본다).
- 결과가 다시 이벤트를 쏘아 끝없이 도는 고리를 만들지 않는다(사슬 한도 16에서 끊기고 경고가 남는다).

## 10. 시간·턴

- 턴제: 턴은 행동(`EndTurn`)과 이벤트(`TurnEnded`)로 흐른다. "N턴 동안/N턴 뒤"는 상태 효과(이벤트 횟수 지속·끝날 때 결과)로, 코드에서 나중에 할 일은 `Game.ScheduleOn<이벤트>(횟수, 행동)`.
- 실시간: DB › Bootstrap의 고정 틱을 켠다. 시간 지속은 상태 효과(게임 시간, 주기(초)로 N초마다 결과), 가진 동안 N초마다는 패시브 `pulse`(멈추기·앞당기기·리셋이 있는 카운터는 조각 필드 + 틱 행동), 나중 일은 `Game.ScheduleAfter(초, 행동)`. 틱마다의 가벼운 규칙은 `session.Ticked`에서 `Game.Do`로. 이동·물리는 화면 쪽 자유 영역이고, 규칙에 필요한 결과(맞음·주움)만 행동으로 보낸다(3절 판정 보고 행동).
  - 실시간 예산(매뉴얼 33장): 판 저장은 '행동마다' 대신 'N초마다', 연출은 `GameView.Play`(대기열 밖, 입력을 막지 않음), 개체 수백(투사체·보석)은 화면 쪽 오브젝트 풀로 두고 규칙에는 수와 결과만.
- 부가 기능(현실 시간·게임 안 달력·칸 단위 맵·큰 수·되감기·시드 …)은 명세서 6절에 표시된 것만 붙인다(참조 문서 2-6). 현실 시각은 규칙에서 `Game.Now`·`Game.Day`만 쓴다.
- 조각의 자리(한 줄·격자·보드)는 `Placement`(목록 + 줄 길이). 목록 순서 = 발동 순서이므로, 순서가 열 우선인 보드(와일드프로스트)는 목록을 열 우선으로 담는다. 칸 단위로 움직이는 맵은 `Grid`.
- 조각 자리는 '칸'이라 부른다('슬롯'은 세이브 슬롯).
- `Update`에서 플레이어 데이터를 바꾸지 않는다.

## 11. 플레이어 선택

- 행동 도중 플레이어가 골라야 하면(카드 1장 버리기·보상 3개 중 1개) 기다리지 않고 `Game.Ask(안내, 후보, new 이어서할행동())`. 고른 뒤 할 일은 모두 이어서 할 행동(`[Chosen]` 필드)에 쓴다. DB에서는 결과 '선택 요구'(판에 있는 것에서)·'가중치 표에서 고르기'(DB 원본에서).
- 뽑기의 후보(풀)는 저장하지 않고 뽑을 때 만든다: 진행·해금은 가중치 표 줄의 조건, 판에서 만들어진 것은 목록 줄, 가진 것은 뺄 목록, 규칙이 계산한 후보는 `Game.Roll(풀, …, stream: "쓰는 곳 이름")`.
- 화면은 `Game.Choice`를 보여 주고 `Game.Answer`로 답한다. 기다리는 동안 입력은 `GameView.Busy`로 막힌다.
- 다시 뽑기는 행동 하나(비용·남은 횟수를 내고 `Game.RerollChoice(선택 id)`). 후보 수를 늘리는 기믹은 '가중치 표에서 고르기'의 '후보 수에 더할 숫자'.

## 12. 테스트·검증·보고

- 규칙(행동·규칙 함수·Block)을 만들거나 고치면 `Tests`에 테스트를 하나 이상 둔다. 세션을 손으로 만든다: 플레이어 데이터 `Define`, 밸런스 값 `session.Balance.Define`, 상태 효과 `session.Statuses.Define`, 원본 `session.Instances`.
- 테스트는 게임처럼 행동을 실행하고 값을 본다. 플레이어용 실패는 `Assert.Throws<GameFailure>`(NUnit은 정확한 형식만 잡는다). Undo가 맞는지(`session.Undo()` 뒤 값)도 본다.
- 코드를 고친 뒤에는 컴파일이 되는지 확인하고, Unity가 열려 있으면 콘솔 오류·DB 검증("검증 통과")을 본다.
- 응답을 끝낼 때 컴파일 검사 훅(`.claude/hooks/compile-check.ps1`, 매뉴얼 20장 11절)이 돈다. 오류가 나오면 고친 뒤 끝낸다. 세 번 막힌 뒤에도 남은 오류는 보고에 적는다.
- 사람에게 보고할 것(진행 매뉴얼 13절): 적용(Ctrl+S)할 DB 항목, 넣을 에셋, 돌려 볼 테스트 상황·명령, Unity에서 직접 봐야 확인되는 것, 기록한 결정(D-n), 기획 명세서와 달라진 점. 작업량·테스트 수는 말하지 않는다.
- 기획 명세서와 코드가 다르면 코드를 맞추거나, 명세서가 틀렸으면 사람에게 묻는다(몰래 바꾸지 않는다).

## 13. 문법 밖 기믹

- 효과는 "언제(즉시·발동·지연·지속) + 누구에게(대상 고르기) + 무엇을(데이터 바꾸기·만들기/없애기·가로채기·선택 요구·비용) + 안전장치(연쇄 제한)"로 쪼갠다. 쪼개지면 0절 순서로 만든다.
- 문법 안으로 보는 것: 화면이 판정하고 결과를 행동으로 보내는 것(물리 충돌·투사체 반사·벽에 부딪힘·미니게임 — 3절 판정 보고 행동), 같은 세션 안의 되감기(`session.UndoTo(지점)`), 현실 시각(`Game.Now`), 큰 수(`BigNumber`).
- 쪼개지지 않는 것(저장을 넘어 과거로 되감기, 되감은 뒤 난수를 다시 굴리기, 규칙이 화면의 결과 없이 물리 결과를 알아야 하는 것 …)은 만들기 전에 표시하고 묻는다: 무엇이 문법 밖인지, 어떻게 만들 수 있는지(화면 쪽·별도 시스템·근사), 각각의 비용.
- 기획 명세서의 "문법에 안 맞는 기믹" 칸에 적힌 것은 그 답을 따른다.

## 15. DB 항목 만들기 — DB 반영 스크립트

AI는 Unity 창을 누를 수 없다. DB 항목은 **DB 반영 스크립트**로 만든다: `Assets/MomoiProject/Code/Editor`의 static 함수에 `[DbSeed("버전")]`을 붙이면 컴파일이 끝난 뒤 GBible이 저절로 한 번 돌린다. 만든 항목은 DB에 **적용 전**으로 들어가고, 개발자가 읽어 보고 Ctrl+S로 적용한다(적용했을 때만 "이 버전은 돌았다"로 기록 — 버리면 다음 컴파일 뒤 다시 돈다).

```csharp
// Assets/MomoiProject/Code/Editor/Seeds/AchievementSeeds.cs
using GBible; using GBible.Data; using GBible.EditorTools;

static class AchievementSeeds
{
    [DbSeed("1")]   // 내용을 바꾸면 "2"로 — 바뀐 버전만 다시 돈다
    static void FirstWin()
    {
        var db = EditorDatabase.Instance;
        if (db.FindById("firstWin") == null)   // 이미 있으면 건너뛴다(개발자가 맞춘 값을 덮지 않는다)
        {
            var a = (AchievementData)EditorDatabase.Staging.Add(typeof(AchievementData), "firstWin");
            a.trigger = new EventTrigger { eventType = typeof(BattleWon).FullName };
            // a.outcomes.Add(…);
        }
    }
}
```

- 함수 하나 = 주제 하나(종류 하나·콘텐츠 묶음 하나). 파일은 `Assets/MomoiProject/Code/Editor/Seeds/<주제>Seeds.cs`.
- **이미 있는 항목은 건너뛴다.** 개발자가 밸런싱한 값을 덮지 않는다. 구조(Block·참조 칸의 종류)를 고쳐야 하면 버전을 올리고 `EditorDatabase.Staging.Work(항목)`으로 작업본을 받아 그 칸만 고친다(숫자 칸은 건드리지 않는다).
- **지우기**는 버전을 올리고 `EditorDatabase.Staging.Remove(항목)`. 그 ID를 쓰는 코드(`GameIds` 상수)도 같이 지운다.
- **값이 많은 것**(밸런스 값·카드 수치·몬스터 수치·가중치 표 줄 — 숫자·글자·enum과 그 목록)은 CSV도 된다: 첫 칸 `id`, 나머지 칸 이름 = 필드 이름(묶음 필드는 `curve.step`, 목록은 `entries[0].weight`). 개발자가 그 DB 종류 탭의 **CSV › CSV 가져오기**로 넣는다. Block 칸(트리거·조건·결과)은 CSV에 없다.
- 메뉴 `MomoiProject › DB 반영 스크립트 › 모두 다시 돌리기`가 모든 스크립트를 다시 돌린다(이미 있는 항목은 건너뛰므로 안전하다).
- 예전 방식(`[MenuItem("MomoiProject/DB 추가/…")]`을 사람이 누름)도 돈다. 새로 쓸 때는 `[DbSeed]`.
- 보고할 때: 적용 전으로 들어갈 항목 목록, 적용(Ctrl+S) 뒤 확인할 것(DB 아래 "검증 통과").
- 플레이어 데이터 키·필드처럼 시작 설정이 만드는 것은 시작 설정에. 화면은 반영 스크립트에서 `ScreenSetup.Ensure()`(Panel Settings·테마·DB › 화면 설정)를 먼저 부르고, 화면 항목의 `layout`을 `AssetDatabase.LoadAssetAtPath<VisualTreeAsset>("Assets/MomoiProject/UI/Screens/….uxml")`로 넣는다(매뉴얼 35장 5-6). 그림·글꼴·소리 에셋은 개발자가 가져온다(AI는 넣을 목록과 자리를 만든다 — 18절).

## 16. 기본 진행 순서(단계 1 시스템층)

## 18. 개발자가 읽고 바꿀 수 있는 모양으로

개발자는 코드를 읽지 않는다. 에디터(DB·모니터)에서 읽고, 밸런싱 값을 바꾸고, 테스트한다. 그래서 AI가 만드는 것은 이 모양이어야 한다.

- **숫자는 에디터에.** 개발자가 바꿀 만한 숫자(체력·피해·비용·확률·보상 양·성장·시간)는 코드에 적지 않는다: 밸런스 값(`Game.Balance`), DB 항목의 칸, 원본 인스턴스의 필드. 규칙 자체의 상수(덱 섞기 방식)만 코드에.
- **고르는 값은 enum·키워드, 가리키는 것은 참조.** "보상으로 줄 아이템", "소환할 적", "걸 상태 효과"는 글자 ID 칸이 아니라 `[DataRef(typeof(…))]` 칸으로 둔다 — DB에서 드롭다운으로 고를 수 있다. 인스턴스를 가리키면 `[DataRef(typeof(원본 클래스))]`(그 클래스의 인스턴스만 나온다).
- **효과는 DB에서 문장으로 읽히게.** 가능하면 Block으로 조립한다(DB에 문장으로 보이고, 문장 안의 숫자·참조를 개발자가 바꾼다). 프로젝트 Block에는 `[BlockInfo("표시 이름", Sentence = "…{필드}…")]`를 붙여 문장에 칸이 드러나게 한다. `[BindTo]` 코드는 DB에서 이름·설명만 보이므로, 그 안의 숫자는 그 항목의 칸이나 밸런스 값에서 읽는다.
- **이름은 개발자 화면용으로.** 플레이어 데이터·DB 칸에는 `[FieldLabel("한글")]`, Block·이벤트·의도에는 한글 표시 이름. 코드 이름(클래스·필드·함수)은 영어로, 뜻이 드러나게, 같은 일은 같은 접두어로.
- **지켜보기 좋게.** 판의 상태는 플레이어 데이터에 있어야 모니터에 보인다(규칙이 쓰는 값을 static이나 화면 쪽에 숨기지 않는다). 다른 기능이 반응할 만한 일은 이벤트로 쏜다(모니터 타임라인에 남는다).
- **개발자 몫은 개발자 도구로.** 레벨 배치·다이얼로그 그래프·에셋은 개발자가 하므로, AI는 그 데이터 모양과 연결을 만들고 직접 채우지 않는다(요청받으면 예시 하나만).
  - **레벨 데이터**: DB에서 배치하게 하려면 프로젝트 DB 종류에 `[Database("층", Group = "레벨", DeveloperAuthored = true)]`를 붙인다 — 이 종류만 개발자가 추가·삭제·ID 바꾸기를 할 수 있다(DB는 로직 쪽 종류의 추가·삭제를 잠근다, 매뉴얼 21장 3-1). 인스턴스(DB › 인스턴스)는 잠겨 있으므로 레벨 배치에 쓰지 않는다. 맵 모양은 Unity 씬·타일맵에 두고, 스폰 지점·사건 칸은 컴포넌트로 만들어 규칙 데이터로 읽힌다.
  - **에셋**: 그림·소리가 필요한 곳은 반영 스크립트에서 `AssetRequests.Sprite(경로, 너비, 높이, 쓰는 곳, 느낌)`·`Audio(경로, 쓰는 곳, 초)`·`Request(경로, 쓰는 곳)`로 임시 에셋과 넣을 것 목록을 만든다. 화면·DB는 그 경로의 에셋을 바로 쓴다 — 개발자가 에셋 관리에서 진짜 파일을 넣으면(같은 자리·GUID 유지) 다시 연결할 필요가 없다(매뉴얼 39장). 경로는 종류별 폴더(그림 `Assets/Dev/Art` · 소리 `Assets/Dev/Audio` · 글꼴 `Assets/Dev/Fonts` …).

## 19. 테스트할 수 있게

개발자는 런타임에 원하는 상황을 만들어 기믹·밸런스·버그를 시험한다. AI는 프로젝트마다 그 환경을 만든다.

- **테스트 씬**: 단계 1에서 반영 스크립트로 `TestSceneSetup.Ensure(copyFrom: "Assets/Scenes/게임씬.unity", scenario: "")`를 부른다 — 게임 씬을 복사해 `Assets/Scenes/Test.unity`를 만들고 컴포넌트 `TestScene`(시작할 테스트 상황 · 시드 · 따로 슬롯 · 시간 배속 · 테스트 패널)을 붙인다(이미 있으면 건너뛴다). 플레이하면 그 상황으로 바로 시작하고, 게임 화면 위에 테스트 패널(테스트 명령 버튼 · 상황 저장·불러오기 · 시간 · Undo)이 뜬다(개발 빌드·에디터에서만).
- **테스트 명령** = DB › 개발 명령(`DebugCommandData`) 항목: 주입(인스턴스를 목록에 넣기 · 자원 주기 · 패시브 얻기 · 상태 효과 걸기 · 적 만들기)과 발동(이벤트 쏘기 · 행동 실행)을 결과 Block으로 조립한다. 문장 안의 값(어느 인스턴스·몇 개·어느 대상)은 개발자가 드롭다운으로 바꾼다. Block으로 안 되는 것만 `[BindTo]`. 모두 행동으로 돌아 Undo·기록이 남는다. 반영 스크립트로 만들고 분류(`category`)로 묶는다(예: "판", "조각", "적", "상황").
- **테스트 상황** = 지금 플레이어 데이터·시드·게임 시각을 이름 붙여 저장한 파일(`TestScenarios`, `Assets/MomoiProject/Data/Tests/`). 개발자가 패널이나 모니터에서 저장하고, AI는 명세서 13절·버그 보고의 상황을 테스트 명령으로 만들어 두고 저장 방법을 알린다. 규칙 테스트는 같은 상황을 코드로 다시 만든다.
- **단계 2의 조각마다** 얻기·쓰기·걸기 테스트 명령을 만든다. 버그 보고를 받으면 같은 상황을 테스트 상황·규칙 테스트로 재현한 뒤 고친다.
- 테스트 도구는 출시 빌드에 들어가지 않는다(`session.Debug.Enabled`가 거짓이면 명령이 생기지 않고, `TestScene`은 개발 빌드에서만 패널을 띄운다).

## 20. 멀티플레이(명세서 0절이 '있음'일 때)

구조는 4블록 하나다(매뉴얼 40장): 화면은 행동만 보내고, 판정하는 쪽(매칭큐 = 서버, 친구 방 = 방장)이 실행해 바뀐 곳·이벤트를 돌려준다. 게임 코드는 싱글과 같게 짜되 아래를 처음부터 지킨다(나중에 고치면 데이터 구조부터 바뀐다).

- **판정은 행동 안에서만.** 화면·연출 코드는 플레이어 데이터를 바꾸지 않는다(클라이언트에서 바꾸면 어긋난다). 화면은 `Do` 직후 결과를 읽지 않고 바뀐 곳 알림·`SubscribeAfterAction`으로 그린다. 실패는 `GameScreens.Do`가 알림으로 띄운다(멀티 거절도 같다).
- **플레이어마다 칸.** 플레이어 데이터에 플레이어 번호(`actorId`·`session.LocalPlayer`와 같은 번호)를 담는다: 목록 `players[]` 또는 키 `hand:1`·`hand:2`. 남에게 숨길 것은 **플레이어별 키 + `Data.SetVisibility(키, DataVisibility.Owner, 번호)`**(키 단위로만 숨긴다). 숨길 이벤트(카드를 뽑음)는 `IOwnedEvent`(주인만 받음), 서버 규칙끼리만 쓰는 이벤트는 `[GameEvent(ServerOnly = true)]`.
- **서버 규칙은 서버가 준비될 때 건다.** 친구 방·시험 모드: `GameNet.ServerStarted += server => …`, 매칭큐: `GameNet.RoomStarting += room => …`(플레이어별 키 정의·공개 범위·`Validate`), 첫 턴은 `GameNet.RoomReady`. `Validate`는 차례·주인(남의 유닛을 움직이려 함)을 거절 글로 막는다. `actorId`는 서버가 보낸 사람 번호로 덮으므로 규칙은 `actorId`를 믿고 쓴다.
- **매칭큐 결과**: 승패를 정한 규칙이 `GameNet.Hub.EndMatch(room, NetMatchResult[])`를 부른다(다음 틱에 점수·전적 저장 후 로비로). 재화·해금 같은 계정 값은 서버 저장소(`NetAccount.values`)에 두고 클라이언트 값을 믿지 않는다.
- **실시간 협동의 움직임**: 내 캐릭터·탄환처럼 매 순간 움직이는 것은 규칙 데이터가 아니라 `NetTransformSync`(entityId를 모든 프로그램에서 같게, owner = 플레이어 번호). 맞힘·피해는 방장의 규칙이 판정한다(클라이언트는 판정 보고 행동, 방장이 확인).
- **친구 방 화면**: 방 만들기·초대·참가 버튼은 `GameNet.CreateRoom`·`InviteToRoom`·`JoinRoom`만 부른다(Steam이 준비되면 Steam 로비, 아니면 직접 접속 — 화면 코드는 같다). 방장이 나가면 판이 끝난다(이어받기 없음) — `GameNet.Closed`에서 메뉴로 돌아간다.
- **끊김**: 다시 접속은 저절로 된다(`GameNet.AutoReconnect`). 화면은 `GameNet.Reconnecting`에서 '다시 접속하는 중'을 보이고 `Reconnected`에서 거둔다. `Joined`는 처음 한 번만 온다 — 다시 들어온 뒤에도 화면은 바뀐 곳 알림으로 저절로 맞는다.
- **되감기 기믹**: 턴 시작 행동에서 `Game.MarkRewind()`, 기믹은 `Game.Rewind`·`RewindKey`·`RewindEntity`(행동 안). 멀티에서 플레이어의 일반 무르기는 없다.
- **주고받는 클래스**: `[Serializable]`(생성 코드), `#if UNITY_EDITOR` 필드를 두지 않는다. 이벤트는 `[GameEvent]` 클래스(구조체 이벤트는 보낼 수 없다).
- **시험**: 단계 1에서 테스트 씬의 멀티플레이를 '시험 모드'로 한 번 돌려 본다(지연 0.1 이상 — 화면이 결과를 기다리는지). 매칭큐는 `GameNet.StartMatchServer` + 테스트 패널의 매칭 찾기로 로컬에서 끝까지(줄 → 수락 → 방 → `EndMatch` → 로비) 확인한다. 규칙 테스트는 코어에서 `NetServer`·`NetClient`·`MemoryNetwork`(Manual)로 서버 하나·클라이언트 둘을 띄워 단언할 수 있다(`Tests/Editor/NetTests.cs`가 본보기).

## 21. 화면 쪽 도구는 프로젝트에 만든다(UI·입력·카메라·이동)

GBible에는 넣지 않는다(2026-10-06 결정 — 장르마다 달라 미리 만들어 두면 맞지 않는다). 필요하면 AI가 그 프로젝트의 `Assets/MomoiProject/Code/Client`에 만든다. 3절(규칙과 화면의 경계)·6절(화면)을 그대로 따르고, 아래를 더 지킨다.

- **입력은 행동까지만.** 입력 코드가 하는 일은 "무엇을 하려는가"를 행동 하나로 바꿔 `Game.Do`(화면 버튼이면 `GameScreens.Do`)에 넘기는 것까지다. 키·패드는 Input System의 동작(선택 기능 '입력'을 켰으면 `GameInput.Use(동작 에셋)` — 키 바꾸기가 따라온다), 화면 버튼은 UI Toolkit(6절). `GameView.Busy`일 때는 받지 않는다.
- **월드를 누르기 전에 화면 칸 위인지 본다.** 화면(UI Toolkit) 칸 위에서 누른 것은 월드로 보내지 않는다.
  ```csharp
  // screen: Pointer.current.position(왼쪽 아래가 원점)
  public static bool OverScreen(Vector2 screen)
  {
      var root = GameScreens.Overlay?.parent;   // 화면 층들을 담은 뿌리
      if (root?.panel == null) return false;
      var picked = root.panel.Pick(RuntimePanelUtils.ScreenToPanel(root.panel, new Vector2(screen.x, Screen.height - screen.y)));
      return picked != null && picked != root && root.Contains(picked);
  }
  ```
- **누른 오브젝트 → 데이터.** 3D는 `Physics.Raycast(camera.ScreenPointToRay(screen), out var hit)`, 2D는 `Physics2D.OverlapPoint(camera.ScreenToWorldPoint(screen))`. 오브젝트를 만들 때(`ViewList`의 bind) 데이터 id를 담는 프로젝트 컴포넌트(`Client/DataTag.cs` — `public string id`)를 채워 두고, 맞은 것에서 `GetComponentInParent<DataTag>()` → `Game.Find<T>(id)`로 찾은 객체를 행동 필드에 넣는다.
- **좌표 변환은 한 곳에.** 칸 단위 게임은 칸 좌표가 데이터다(매뉴얼 36장 격자). 칸 ↔ 월드 위치 변환은 Client의 함수 한 쌍(`Board.ToWorld(칸)`·`ToCell(위치)`)에만 두고 화면 코드가 모두 그것을 쓴다.
- **이동.** 위치가 규칙 데이터인 게임(칸·턴제)은 행동이 칸을 바꾸고 화면은 그 변화를 연출로 옮긴다(Transform 보간 — `GameView.Present`). 실시간 액션은 위치가 화면 쪽이다: 방식(Transform·Rigidbody·CharacterController·NavMesh)은 명세서의 장르·조작으로 고르고, 규칙에는 판정 보고 행동만 보낸다(3절). 멀티면 움직이는 것에 `NetTransformSync`(20절).
- **카메라.** Client의 컴포넌트 하나가 맡는다(따라가기·경계·확대). 흔들기·확대 같은 연출은 `GameView.Present`·`Play`의 연출 안에서 부른다. 새 패키지(Cinemachine 등)를 들여야 하면 먼저 사람에게 묻는다(내려받기).
- **인벤토리·슬롯 UI.** 데이터는 인벤토리(매뉴얼 25장)·자리(37장 — 칸 옮기기 예제), UI는 6절의 `List<T>` 칸. 옮기기(끌어 놓기·두 번 누르기)는 놓는 순간 행동 하나이고, 끄는 동안에는 화면만 움직인다. 놓을 수 있는지는 `Game.CanDo`로 미리 보이고, 칸 수·겹치기·장비 칸 규칙은 규칙 함수에 둔다. 명세서에 칸 수·겹치기·장비 칸·옮기는 법이 없으면 묻는다(데이터 모양이라 뒤집기 비용이 크다).
- **생김새·배치는 묻지 않는다.** 명세서에 없으면 기본 화면·테마 변수(6절)로 만들고 결정 기록에 남긴다(17절 — 되돌리기 쉬운 것). 다른 UI 방식(UGUI 프리팹·UI 에셋)은 들이지 않는다.
