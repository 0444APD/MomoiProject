# 기획 명세서를 읽는 법 (AI용)

기획 명세서(`PlanningSpec.md` 양식, 채운 예시 `PlanningSpec-CardDungeon.md`)의 칸을 GBible로 옮기는 표와, 단계 0(흡수)·단계 1(시스템층)의 세부다. 전체 진행·질문 규칙·결정 기록은 `ProjectFlow.md`(진행 매뉴얼)가 정하고, 이 문서는 그 안에서 칸 → GBible을 맡는다. 목표는 단계 0에서 예외를 다 끌어내고, 기반을 하루(약 12시간) 안에 닦는 것이다.

- 어떻게 쓰나는 `ProjectConventions.md`(프로젝트 관례), 무엇이 있나는 `Reference.md`(GBible 참조 문서)를 따른다.
- 기믹을 무엇으로 만드나는 `GimmickCatalog.md`(기믹 목록)를 따른다.

---

## 1. 순서(진행 매뉴얼 단계 0·1)

1. `Docs/Decisions.md`(결정 기록)를 읽는다. 이미 정한 것은 다시 묻지 않는다.
2. 자료(`Docs/Source/`)·명세서·`GimmickCatalog.md`를 끝까지 읽는다. 모르는 말은 질문에 넣지 말고 문맥으로 먼저 푼다.
3. 자료로 명세서를 채운다(칸마다 출처 `(자료)`·`(답 D-n)`·`(추천 승인 D-n)`). **넘겨짚지 않는다** — 자료·답이 없는 칸은 추천으로 채우지 않고 `(확인 전: 추천 …)`으로 둔 채 질문에 넣는다(진행 매뉴얼 1·5-2절). 이 게임에 해당하지 않는 칸(전투가 없는 게임의 피해 공식 …)은 `해당 없음 — 이유`로 채우고 묻지 않는다(진행 매뉴얼 5-2).
4. **질문 목록**을 만든다(진행 매뉴얼 3절 형식). 넣는 것:
   - 빈 칸 — [필수]·[선택] 모두(추천을 붙여서. [선택] 칸은 추천 승인 목록으로 묶어도 된다)
   - 자료를 해석해 채운 칸(두 가지로 읽히는 것)의 확인
   - 칸끼리 모순
   - 메인 룰(4-1)이 기믹 목록 1절의 모양(조각·자리·순서)으로 풀리지 않는 곳
   - 자료의 효과 문장·4-3의 이상한 효과 중 갈래로 쪼개지지 않는 것
   - 예외 잡기 표(진행 매뉴얼 5-3) 중 자료로 답이 나오지 않은 줄
   - 개발자 몫(12절: 밸런싱 범위·레벨 배치·대사)
   - 5절의 문법 밖 기믹

   질문은 한 번에 보낸다.
5. 답을 결정 기록·명세서에 적고, **시스템 목록**(5절)을 만들어 한 번 보여 준다(확인 질문 하나). 진행 매뉴얼 5-5의 나가는 조건이 모두 참이면 단계 1.
6. 관례 16절 순서로 만든다. 만드는 동안 새로 생긴 기획 사항은 되돌리기 쉬우면 가안으로 넣고 '확인 기다리는 것'에 올려 승인받고, 어려우면 만들기 전에 모아서 묻는다(진행 매뉴얼 1절). 구현 방식(코드 이름·내부 구조)은 AI가 정한다.

## 2. 칸 → GBible

'비었을 때' 칸은 **질문에 붙일 추천**이다. 그 값으로 칸을 채우지 않는다 — 개발자가 답하거나 승인해야 확정이다(진행 매뉴얼 1절).

| 명세서 칸 | 정하는 것 | GBible에서 | 비었을 때 |
|---|---|---|---|
| 0-1 자료 | 흡수할 원본 | 끝까지 읽는다(시트는 모든 효과 문장). `Docs/Source/`에 두게 한다 | 한 문단 아이디어라도 질문으로 채운다 |
| 0 장르·한 판 길이 | 추천값의 줄 | 구현 가이드(BuildGuide) 07장 1절 표에서 가장 가까운 장르 줄을 고른다(Undo 방식·판 저장·구역·난수 흐름). 한 판이 길면(1시간 이상) 판 저장은 행동마다 | 질문 |
| 0 멀티플레이 | 세션 구조 · 멀티 종류 | 없음: 세션 하나(`GBibleRuntime.Session`). 있음: 4블록(매뉴얼 40장) — 화면 코드는 싱글과 같고 서버·방장이 판정한다. 친구 방 → 사설 호스트(`GameNet.CreateRoom` — Steam이 준비되면 Steam 로비, 방장 권한, 실시간 움직임은 `NetTransformSync`), 경쟁 → 매칭큐(`NetHub`, 서버 권한·로비·점수). 처음부터: 모든 변경을 행동으로, 플레이어마다 데이터 칸(`players[]` 또는 키 `hand:1`처럼 — 숨길 것은 플레이어별 키 + `DataVisibility.Owner`), 조각에 주인 id, 고르기는 답할 플레이어(`Game.Ask(…, player:)`), 서버 규칙 `Validate`(차례·주인), 연출은 `SubscribeAfterAction`. 인원·숨길 정보·차례 방식·끊김(매칭큐는 재접속, 방장이 나가면 판 끝, 돌아오지 않는 플레이어의 기권 — 턴 시간 초과 몇 번)·결과(등수)를 묻는다. 친구 방이고 숨길 정보가 있으면 "방장이 모든 데이터를 본다 — 친구 대전도 매칭큐 서버(친구 코드)로 할까"를 묻는다(`Multiplayer.md`). 기본 일시정지 창은 게임 시간을 멈추므로 실시간 협동이면 멈추지 않는 메뉴가 필요한지 묻는다. **비동기**(고스트 — 다른 플레이어가 남긴 덱 · 보드와 겨룸)는 실시간 접속이 없어 4블록 규칙(`Multiplayer.md` — 실시간 멀티용)을 쓰지 않는다: 세션 하나에서 상대 데이터를 **독립 모양**(내 판 데이터와 섞이지 않는 `[Serializable]` 클래스 — 원본 ID와 값만)으로 판 데이터에 넣고 규칙이 그것과 싸운다. 상대를 받는 곳은 **바꿔 끼우는 함수 한 곳**(기기 안 기록 · DB 기본 고스트 · 나중의 서버)으로 둔다 — 지금 GBible에는 고스트를 올리고 받는 저장소가 없다(`INetPlayerStore`는 계정 · 매치만, Steam 리더보드 · UGC 없음). 공정성(조작한 고스트 · 버전이 다른 데이터)을 어디까지 막을지는 질문 | 질문 |
| 1 시간 | 시계·Undo 방식 | 턴제: 고정 틱 0, Undo 행동 단위. 실시간: 고정 틱 30(DB › Bootstrap), Undo 스냅샷 또는 쓰지 않음(위치는 화면 쪽이라 되감으면 어긋남). 섞임: 고정 틱은 실시간 쪽에 맞춘다. Undo는 턴제 쪽만 쓰면 행동 단위, 아니면 쓰지 않음. **예외 — 방치형**(꺼 둔 시간 정산이 핵심): 고정 틱 0, Undo 쓰지 않음, 시간은 게임 시계가 아니라 `Game.Now`로 잰다(구현 가이드 07장 1절 방치형 줄). 묻는 것은 턴제/실시간이고, 고정 틱 수는 기획 질문이 아니라 추천 승인 목록에 올린다(진행 매뉴얼 3절) | 질문 |
| 1 한 판 | 행동 목록·씬 흐름 | 판 시작·단계마다 행동(`StartRun`·`StartBattle`·`EndRun` …), 판 끝 이벤트(Bootstrap '판 끝 이벤트'), 씬 흐름(판 데이터의 씬 필드). 캠페인처럼 전투가 이어지면 한 판 = 무엇인지(전투 하나·세이브 전체) 정한다: 캠페인 진행은 프로필(메타), 전투 중 값은 판(세션) | 질문 |
| 1 반복 단위 | 턴 행동·이벤트 | `EndTurn` 같은 행동 + `TurnEnded` 같은 이벤트. 상태 효과의 '셀 이벤트'가 된다. 실시간: 웨이브(웨이브 행동 + `WaveStarted` 같은 이벤트, 다음 웨이브 시각은 판 데이터 — 매뉴얼 33장 5-1) / N초마다(시각 필드 + 틱 규칙) / 끊김 없음(지속은 게임 시간 초) | 질문 |
| 1 판이 끝나는 때 | 승패 행동 | 승리·패배 행동과 판 끝 이벤트. 패배를 막는 기믹이 있으면 패배를 동사로(행동 직전 이벤트). 시간 승리(N분 버티기)는 끝 시각(밸런싱 값)을 판 데이터에 두고 틱 규칙이나 `Game.ScheduleAfter`가 승리 행동을 부른다 | 질문 |
| 1 남는 것 · 2-5 프로필 | 프로필 | `profile`(Meta 구역) 필드. 해금은 프로필 목록 또는 도전과제 보상 | 질문 |
| 1 거점과 판 | 들고 들어감 · 가져옴 · 잃음 | 거점(창고 · 마을)은 프로필, 판은 판 데이터. 판 시작 행동이 들고 들어갈 것을 프로필 목록에서 빼 판 목록에 넣고, 탈출 · 승리 행동이 가져올 것을 판 → 프로필로, 실패 행동이 잃을 것을 지운다 — 같은 객체를 id 그대로 옮긴다(관례 3절 옮기기). 묻는 것: 무엇을 들고 들어가나 · 무엇을 가져오나 · 실패하면 무엇을 잃나(모두 · 일부 · 보험) · 판 중간에 끄면(판 저장으로 이어 하기 / 실패로 침). 저장 추천은 구현 가이드 07장 1절 '거점 + 판' | 질문(해당 없으면 `해당 없음`) |
| 1 되돌리기 | Undo 범위 | 마음대로: 행동 단위·보관 200. 이번 턴만: Undo 끊는 이벤트 = 턴 끝 이벤트. 없음: Undo 방식 '쓰지 않음' | 장르 추천값(3절) |
| 1 이어 하기 | 판 저장 | 행동마다(턴제) / N초마다(실시간) / 이벤트를 받을 때(체크포인트·방 클리어) / 끌 때 / 저장하지 않음(Bootstrap '판 저장'). 타이틀이 없으면 '시작할 때 이어 하기' | 장르 추천값 |
| 2-1 유닛 · 등장인물 | 데이터 클래스·스탯 | `id`가 있는 `[Serializable]` 클래스, 숫자 필드 = 스탯(Modifier 대상, `Game.Attribute`). 카운터처럼 규칙이 줄이는 값도 숫자 필드. 공략 대상 · 마을 사람: 고정 값(생일 · 좋아하는 것)은 원본(DB › 인스턴스), 바뀌는 값(호감도 · 만난 횟수)은 판 데이터의 객체(고유 id + 원본 ID). 호감도처럼 효과가 고칠 값은 핵심 동사(3절 — 행동 직전 이벤트를 거친다)로 두고, 다이얼로그 · DB 결과도 그 동사를 부르는 프로젝트 결과 Block으로 바꾼다(참조 2-2). 화자 그림(스탠딩 프로필)은 다른 DB 종류라 ID는 명명 가이드라인 1-1(`seoa` · `seoa.profile`) | 질문(숫자 목록) |
| 2-1 피해 공식 | 규칙 함수 안 계산 | `Rules.Damage`: 스탯 → 계수 → 증폭 합 → 추가 피해, 방어 100/(100+방어), 행동 직전 이벤트 자리(관례 4절). 다른 스탯에서 끌어오는 값·변환(기믹 2-4)이 있으면 스탯 함수(`Rules.Stat`) 한 곳 | 기본 공식. 유닛에 공격력·방어 숫자가 없으면 양을 그대로 |
| 2-2 조각 | 클래스·DB | 원본 클래스 + DB › 인스턴스. 판 데이터에는 **객체 목록**으로(고유 `id` + 원본 ID 필드 + 바뀌는 값: `OwnedJoker { id, joker, sell, mult }`). "쓰기" = 사용 기능 필드(`Usable`) + `Game.Use`. "가진 동안 +N" = 패시브 효과의 가진 동안 스탯 보정(조건부면 `modifierWhen`). 고정 값(등급·최대 레벨·태그)은 원본에 | 질문(종류 목록) |
| 2-2 키워드 | 고르는 값 | `[KeywordGroup]` 클래스 + `[Keyword(typeof(그룹))]` 필드 | 쓰지 않음 |
| 2-3 자리 | 목록·줄 길이 | 자리마다 판 데이터의 `List<T>` 하나(빈 칸 = null, 격자는 줄 길이 = 열 수, 보드는 편마다 목록 하나). 계산은 `Placement`, DB는 대상 '자리로 고르기'·조건 '자리 검사'. 순서·위치가 효과에 영향이면 패시브 효과 '놓인 것마다'(목록 순서로 발동 — 순서가 열 우선이면 목록을 열 우선으로 담는다). 칸이 늘어나면 목록 길이를 행동이 늘린다. 플레이어마다 따로면 `players[].칸` | 질문 |
| 2-4 자원 | 필드·비용 | 판 자원은 RunState, 남는 자원은 Profile 필드. 쓰는 곳은 `Game.Pay(키, 경로, 양, what: "자원.name", forId: 무엇을 위한)`, 틱 묶음 안에서 되면 내는 것은 `Game.TryPay` | 질문 |
| 3 핵심 동사 | 규칙 함수 | 동사마다 `Rules` 함수 + 행동 직전 이벤트(`~Intent`, 필드는 주체·대상 id·양·종류·횟수·`cancelled`) + 끝난 뒤 이벤트. 사용·비용·상태 효과 걸기·확률은 GBible 기본 행동 직전 이벤트(사용·비용 지불·상태 효과 걸기·확률)를 쓴다. "효과 수치 2배"는 기본 행동 직전 이벤트 '효과 배율'이라 동사마다 둘 필요가 없다(프로젝트 효과 Block이 `Use.Context.Power`를 곱한다) | 장르의 기본 동사(3절) |

## 3. 비었을 때의 추천

질문에 붙일 추천이다(진행 매뉴얼 1절 — 승인받아야 확정). 장르별 기본은 구현 가이드(BuildGuide) 07장 1절 표(Undo 방식·판 저장·구역·난수 흐름·더 쓰는 부품)를 따른다. 그 밖의 기본값:

- 고정 틱: 턴제 0, 실시간 30, 방치형 0(꺼 둔 시간 정산이 핵심이라 `Game.Now`로 잰다 — 07장 1절 방치형 줄이 이 목록보다 앞선다).
- Undo 보관 수 200. 사슬 한도 16.
- 피해 공식: 스탯 → 스킬 계수 → 피해 증폭(합) → 추가 피해, 방어 100/(100+방어), 같은 칸은 더하고 칸끼리는 곱한다.
- 기본 동사(3절이 비었을 때): 피해·회복·죽음·사용(카드·스킬·아이템)·비용·획득(보상). 카드 게임이면 뽑기·버리기, 보드·칸 맵이면 이동, 턴 순서가 있으면 차례(누가 다음인가). 실시간 이동·물리는 동사가 아니라 화면 쪽(판정 보고 행동)
- 조각 목록은 객체 목록, 놓인 순서가 결과를 바꾸면 패시브 효과 '놓인 것마다'.
- 슬롯 1개. 기본 설정 5개: 전체 음량·브금 음량·효과음 음량·언어·전체 화면.
- 대상 Block 기본: 자신·고른 대상, 적이 여럿이면 전체 적·무작위 적, 자리가 있으면 '자리로 고르기', 지니면 발동하는 종류가 있으면 주인공.
- 선택 기능: Steam 출시 대상이면 Steam 켬(Steamworks.NET 패키지 설치는 먼저 묻는다 — 부가 기능 표 Steam 줄), 나머지는 6절에 표시된 것만.

진행 매뉴얼 3절을 따른다(질문마다 정할 것 · 선택지 · 추천 · 이유 · 답이 없으면 · 뒤집기 비용). 단계 0에서 더 볼 것:

- 4-2에 표시가 없어도 자료·4-1·4-3의 효과에 그런 구조가 보이면(빌려 쓰기·여러 칸 …) 표시할지 묻는다. 나중에 나오면 메인 룰을 고쳐야 하기 때문이다.
- 이 게임에 해당하지 않는 칸은 `해당 없음 — 이유`로 채우고 묻지 않는다. 개발자에게 보이지 않는 구현 값(틱 수·저장 간격·Run In Background)은 AI가 정해 추천 승인 목록에 올린다. 반대로 구현 선택이 기믹을 줄이면(적을 화면 쪽에 두면 적에게 상태 효과를 못 건다) 기획 질문으로 올린다(진행 매뉴얼 3절).
- 답·승인은 결정 기록에 적고 명세서 칸도 고친다(`(답 D-n)`·`(추천 승인 D-n)`). 같은 것을 두 번 묻지 않는다. 답을 기다리는 추천은 결정 기록의 '확인 기다리는 것'에 둔다.

## 5. 시스템 목록(답을 받은 뒤 한 번 보여 줄 것)

한 페이지로:

1. 메인 룰: 조각 → 자리(목록·줄 길이) → 순서(행동·단계별 이벤트·계산 함수), 4-2에서 만들 자리.
2. 데이터: 판(RunState)·프로필(Profile)의 필드, 유닛 클래스, 조각 객체 클래스.
3. 조각 종류: 원본 클래스·DB 종류(패시브 효과·액티브 효과·상태 효과 — 선택 요소라 쓰는 것만 템플릿으로 들인다, Reference 4-1 · 인스턴스)·판 데이터 모양.
4. 핵심 동사: 함수 이름 · 행동 직전 이벤트(필드) · 이벤트.
5. 진행 흐름: 행동 목록(판 시작 → … → 판 끝), 반복 단위의 행동, 씬 흐름.
6. 재사용 Block: 효과·대상·조건.
7. DB 설정: Bootstrap(Undo·판 저장·Undo 끊는 이벤트·고정 틱·씬 흐름), 설정 항목, Steam.
8. 부가 기능.
9. 밸런싱 값·가중치 표 이름.
10. 개발자 몫: 에디터에 드러낼 밸런싱 값 목록 · 레벨 데이터 모양 · 대사 연결 · 테스트 씬과 첫 테스트 상황·명령.
11. 개발자 답으로 정한 것과 추천을 승인받은 것(결정 기록 번호). 확인 기다리는 것이 남았으면 시스템 목록을 보이기 전에 묻는다.

확인을 받으면 관례 16절 순서로 만들고, 끝에 진행 매뉴얼 13절 양식으로 보고한다.

## 6. 그다음: 콘텐츠·레벨 디자인 단계

진행 매뉴얼 7~9절. 콘텐츠(조각 하나하나의 효과 문장)는 기믹 목록 2절의 갈래로 쪼개 관례 0절 순서(DB 조합 → 재사용 Block → `[BindTo]` → 중간층 확장)로 만들고 DB 반영 스크립트로 넣는다. 레벨 배치·대사는 개발자가 하고, AI는 그 데이터 모양과 연결을 만든다.

단계 0에서 모든 콘텐츠를 다 볼 필요는 없다. 갈래마다 만드는 법이 정해져 있고, 핵심 동사마다 행동 직전 이벤트 자리가 있기 때문이다. 다만 메인 룰의 구조를 바꾸는 것(4-2)과 예외 잡기 표의 "예"는 단계 0에서 다 드러나야 한다.

## 7. 효과를 쪼개는 예(효과 문법)

- 쪼개고 남는 것이 "양이 규칙으로 정해짐"뿐이면 `[BindTo]`이고 문법 안이다.
- 시스템층이 할 일은 위 마지막 칸이다: 핵심 동사의 행동 직전 이벤트·이벤트에 필드를 미리 두고(주체·대상 id·양·종류·횟수), 대상 Block과 셀 이벤트를 준비한다. 개별 효과는 레벨 디자인 단계에서 DB로 조립한다.
- 마지막 칸이 화면이 정하는 것(물리 충돌 결과, 애니메이션이 끝나는 순간)이면 화면이 판정하고 결과를 판정 보고 행동으로 보낸다 — 문법 안이다(관례 3절). 규칙이 화면의 결과 없이 그것을 알아야 할 때만 문법 밖이다(관례 13절).
