## 1. 기획 명세서 — 들꽃마을 농장

`PlanningSpec.md` 양식을 기획자처럼 채운 것이다. [선택] 칸 몇 개는 일부러 비웠다.

### 0. 한 줄 소개

- [필수] 장르·참고 게임: 농장 생활 시뮬(Stardew Valley 비슷), 2D 탑뷰.
- [필수] 한 문장 소개: 할머니가 남긴 낡은 농장을 물려받아, 계절마다 작물을 키우고 마을 사람들과 친해진다.
- [필수] 멀티플레이: 없음. 나중에 2~4인 협동을 붙일 수도 있다.
- [선택] 플레이 한 판의 길이: 끝이 없다(한 세이브를 수십 시간). 게임 하루는 실제 약 1분 30초.

### 1. 한 판의 흐름

- [필수] 시간: 섞임. 하루 안의 시각은 실시간으로 흐른다(현실 0.7초 = 게임 10분, 아침 6:00 시작). 주인공은 실시간으로 걸어 다닌다. 대화 중에는 시각이 멈춘다.
- [필수] 한 판: 새 게임(주인공 이름·농장 이름) → 1년차 봄 1일 아침 6시, 집에서 → 하루 → 잠 → 밤사이 정산 → 다음 날 … 한 계절 28일, 봄·여름·가을·겨울, 해가 바뀌어도 계속.
- [필수] 반복 단위: 하루. 집을 나와 농장 일(괭이질·씨앗 심기·물 주기·거두기) → 마을(상점에서 씨앗 사기, 마을 사람과 대화·선물) → 숲·해변에서 채집·낚시 → 출하 상자에 팔 물건 넣기 → 밤에 침대에서 잠(새벽 2시가 되면 그 자리에서 쓰러진다) → 밤사이 출하 정산·작물 성장·날짜·날씨 → 다음 날 아침.
- [필수] 판이 끝나는 때: 없음(끝없이 계속). 패배도 없다.
- [필수] 판이 끝나도 남는 것: 없음(세이브마다 따로). Steam 도전과제만.
- [선택] 되돌리기(Undo): (비움)
- [선택] 이어 하기: 끄고 켜면 마지막으로 잔 다음 날 아침부터.

- [필수] 이 게임에서 가장 이상한 효과:
  1. 작물 성장: 물을 준 날만 하루 자란다. 계절이 바뀌면 그 계절 작물이 아니면 시든다.
  2. 게임 시각: 현실 0.7초 = 게임 10분. 새벽 2시가 되면 그 자리에서 쓰러져 다음 날 아침 집에서 깬다(골드 10% 잃음, 최대 1,000).
  3. 선물 반응: 아주 좋아하는 것 +80, 아주 싫어하는 것 −40, 생일이면 ×8, 한 사람에게 일주일에 2번까지(하루 1번).
  4. 날씨: 비 오는 날은 바깥 밭 전부에 물을 준 것으로 친다. 내일 날씨는 오늘 TV로 미리 본다.
  5. 마을 사람 일정: 요일·날씨·시각에 따라 다른 장소에 가 있다(비 오면 집, 금요일 밤엔 술집 …).
  6. 제작 해금: 농사 레벨 3이 되면 스프링클러 제작법이 생기고, 스프링클러 주변 8칸은 매일 아침 물을 준다.
  7. 출하 상자: 넣은 물건은 그날 밤 팔리고 다음 날 아침 정산 화면에 보인다.
  8. 음식 버프: 요리를 먹으면 그날 하루 이동 속도 +1, 운 +1.
  9. 온실: 온실 안 작물은 계절이 바뀌어도 시들지 않는다.
  10. 운: 매일 아침 그날의 운이 정해지고, 운이 좋을수록(운에 비례해) 채집에서 희귀품이 잘 나온다.
  11. 축제(봄 13일): 9시~14시 모든 마을 사람이 광장에, 상점은 닫힘, 그날 날씨는 늘 맑음. 축제 장소에 들어가면 시각이 멈추고 나오면 22시.
  12. 작물 품질: 거둘 때 농사 레벨에 따라 일반·은·금. 품질이 높으면 비싸고, 가방에서 품질이 다르면 다른 칸.

- 정하는 것: 플레이어 상태를 한 명(`run.farmer`)으로 둘지 목록으로 둘지, 시각을 흐르게 하는 자동 행동을 누가 보내는지.
- 추천값: 한 명. 시각 진행 행동(`AdvanceTime`)은 규칙 등록 함수 한 곳(`CalendarRules.Register`)에서만 보낸다.
- 이유: GBible 멀티는 보류 중이다. "모든 변경은 행동·static 없음"만 지키면 나중에 시각 진행을 호스트 한 곳으로 옮길 수 있고, 행동에는 이미 `actorId` 칸이 있다. 지금 플레이어 목록을 두면 모든 행동·화면에 "누가"가 붙는다.
- 답이 없으면: 추천값으로 진행.

**Q2. [데이터 구조] 가방을 GBible 인벤토리로 쓰나, 프로젝트 가방을 만드나**
- 정하는 것: 저장되는 가방 모양. GBible 인벤토리(`Optional/Inventory`)는 빼면 칸을 당겨 지우고(`Remove`가 빈 칸을 `RemoveAt`), 칸에 아이템·개수 말고 다른 정보(품질)가 없고, 칸 옮기기가 없다. 명세서는 "빈 칸 유지·끌어 옮기기·품질이 다르면 다른 칸"이다.
- 추천값: 프로젝트 가방 `Bag { List<BagSlot> slots }`(36칸 고정, `BagSlot { item, count, quality }`, 빈 칸은 `item = ""`)과 넣기·빼기·옮기기 규칙 함수. 인벤토리 모듈은 끈다.
- 이유: 저장 구조라 출시 뒤에 바꾸면 저장 변환이 필요하다. 품질을 아이템 ID로 나누면(`parsnip.gold`) 원본이 세 배가 된다.
- 답이 없으면: 추천값으로 진행.

**Q3. [데이터 구조] 맵 칸 정보(밭이 되는 땅·물·장애물)를 규칙이 확인하나**
- 정하는 것: "여기를 괭이질할 수 있나"를 누가 판단하나. GBible 규칙(Unity 없음)은 Tilemap을 읽지 못하고, 규칙이 읽을 지도 데이터 기능도 없다.
- 추천값: 화면(Tilemap)이 확인하고 행동은 칸 좌표만 받는다. 규칙은 칸 상태(이미 갈렸나·작물이 있나)만 본다.
- 이유: 규칙이 확인하려면 프로젝트 DB 종류(칸 표시 배열) + Tilemap에서 굽는 에디터 메뉴가 필요하다(4절 판정 C 하나 더). 싱글이면 화면 확인으로 충분하고, 협동을 붙일 때 굽기를 더해도 판 데이터 구조는 그대로다.
- 답이 없으면: 추천값으로 진행.

**Q4. [문법 밖] 마을 사람이 길을 걷는 것을 규칙이 아나**
- 정하는 것: 규칙이 아는 마을 사람의 위치.
- 추천값: 규칙은 "지금 머무는 곳"만 계산한다(일정 표에서 지금 시각 이전의 마지막 도착점, 저장하지 않는 함수 `Rules.WhereIs`). 걷는 모습은 화면이 길찾기로 보간하고, 다른 씬에 있을 때는 바로 그 자리로 친다. 말 걸기·선물은 규칙이 "같은 장소"만 보고 "옆 칸"은 화면이 본다.
- 이유: 실시간 이동은 화면 쪽 자유 영역이다(관례 10절). 걷는 중의 위치를 규칙에 두면 10분마다 모든 사람의 좌표가 판 데이터·저장·전송에 실린다.
- 비용: 화면 쪽 길찾기(GBible에 없음). 걷는 도중에는 "같은 장소" 판정이 한 칸 늦을 수 있다.
- 답이 없으면: 추천값으로 진행.

**Q5. [문법 밖] 낚시 미니게임을 어떻게 만드나**
- 정하는 것: 잡혔는지를 누가 정하나.
- 추천값: 물고기는 규칙이 먼저 뽑고(`StartFishing` 행동, 가중치 표 `fish.<장소>`, 판 데이터 `run.fishing`), 미니게임은 화면 코드가 판정하고, 결과만 행동으로 보낸다(`FinishFishing { caught, perfect }`).
- 이유: 판정이 화면 입력과 막대의 움직임(실시간)으로 정해져 규칙 밖이다(관례 13절).
- 비용: 미니게임 화면 하나. 결과를 화면이 정하므로 협동에서 서버가 검증하지 못한다.
- 답이 없으면: 추천값으로 진행.

**Q6. [효과의 폭] "운에 비례해 희귀품↑"를 어디까지**
- 정하는 것: 채집 확률이 운을 따르는 방식. GBible 가중치 표의 무게는 고정이고 줄마다 조건만 붙는다(30장 2-3).
- 추천값: 운을 세 구간(나쁨·보통·좋음)으로 나누고, 표에 조건이 붙은 희귀품 줄을 더한다(같은 항목·같은 무게 줄을 "운 좋음"일 때만 하나 더 → 정확히 ×2). DB만으로 되고 기획자가 고친다.
- 이유: 운에 정확히 비례하게 하려면 코드 풀(`Game.Roll(풀, …, stream: "forage")`)로 뽑아야 하고, 그러면 채집 표를 DB에서 고칠 수 없다.
- 답이 없으면: 추천값(세 구간)으로 진행.

## 3. 시스템 목록

질문에 추천값으로 답했다고 보고 만든 목록이다(Guide 5절 순서).

### 3-1. 데이터

- **판 = 한 세이브 전체**(세션 구역). 한 판이 끝나지 않으므로 판 끝 이벤트도 없다.
- **프로필(메타 구역)은 거의 비운다.** 슬롯마다 `profile.json`이 따로라(06장 2.1) "세이브 사이에 남는 것"을 둘 곳이 아니다. 도전과제·로그 기록만 저절로 들어간다.
- 플레이어 데이터 키를 넷으로 나눈다. 다시 그리기·binding-path가 **키 단위**로만 지켜보기 때문이다(32장 2-1). 10분마다 바뀌는 시각과 수천 칸의 밭을 같은 키에 두면 밭 그림이 0.7초마다 모두 다시 그려진다.

| 키(구역) | 형식 | 담는 것 |
|---|---|---|
| `run` (세션) | `RunState` | `farmer`(Farmer: `id = "farmer"`·name·farmName·gold·energy·maxEnergy·speed·luck·skills `List<SkillState{id, xp, level}>`) · `calendar`(Calendar: year·season·day·weekday·minute·nextStepAt·festival) · `weather`(today·tomorrow) · dailyLuck · `scene`(지금 장소 = 씬 이름) · entry(들어온 문) · shippingBin·lastShipped(`List<ItemStack>`) · learnedRecipes · fishing(낚시 중이면 물고기) |
| `world` (세션) | `WorldState` | `locations: Dictionary<string, LocationState>` — LocationState{`id`(장소 ID)·`plots: Dictionary<int, Plot>`·`objects: Dictionary<int, PlacedObject>`·`forage: Dictionary<int, ForageItem>`}. 정수 키 = 칸 키 |
| `npcs` (세션) | `NpcBook` | `list: List<NpcState{id(=원본 ID), points, talkedToday, giftedToday, giftsThisWeek}>` — 딕셔너리가 아니라 리스트(조건 '배열·리스트 항목 검사'로 "엘리 하트 4"를 DB에서 쓰려고, 5절 G7) |
| `bag` (세션) | `Bag` | 36칸 고정 `BagSlot{item, count, quality}` |

- 칸 하나: `Plot { id("x,y" — ViewList 열쇠), x, y, crop, daysGrown, stage, watered, dead, fertilizer, regrowIn }`.
- **행동에는 칸 객체 대신 (장소, x, y) 값을 넣는다.** `Game.Find(id)`는 그 키의 Sync + 데이터 나무 전체 훑기라 칸이 수천이면 비싸다(코드 `GameApi.Find` → `PlayerDataStore.SyncedMirror` → `Mirror.FindById`, 5절 G3). 규칙은 딕셔너리를 칸 키로 바로 찾는다.
- **날짜·시각은 `run.calendar`.** `minute`은 하루 시작부터의 분(360 = 6:00, 1560 = 다음 날 2:00). `weekday`는 `day`에서 계산되지만 DB 조건·대사 분기가 읽도록 저장한다.
- 넣지 않는 것: 주인공·마을 사람 위치, 걷는 길, 커서 칸, 고른 도구 줄 칸(화면 상태. 도구 쓰기 행동이 도구 ID를 넘긴다).

### 3-4. 진행 흐름

```
타이틀 → 슬롯 고르기(기본 슬롯 화면) → NewRun + StartRun { name, farmName } → StartDay
하루: AdvanceTime(자동, 10분마다)
      EnterLocation { location, entry } · UseTool { tool, location, x, y } · Plant · Harvest · PickUpForage
      PlaceObject { item, location, x, y } · TalkTo { npc } · GiveGift { npc, item, quality }
      BuyItem { shop, item, count } · SellToShop · Ship { slot, count } · Craft { recipe } · Eat(= Game.Use)
      MoveSlot { from, to } · StartFishing → FinishFishing { caught, perfect } · EnterFestival · LeaveFestival
      Sleep → EndDay { passedOut } → (같은 행동 안) StartDay
행동 밖: DayStarted를 받으면(SubscribeAfterAction) GBibleRuntime.SaveRun
```

- **EndDay 안 순서**: 출하 정산 → 물 준 칸 성장 → 물 표시 지우기 → `DayEnded` 쏨 → 날짜 +1(28일 넘으면 계절, `SeasonChanged` → 시듦) → 오늘 날씨 = 어제 본 내일 날씨, 내일 날씨 뽑기 → 운 뽑기 → 비면 바깥 밭 물 → 스프링클러 물 → 채집물 생김 → 일간·주간 값 초기화 → 에너지·6:00·`scene = FarmHouse` → `DayStarted` 쏨.
- **씬 흐름**: `run.scene`(장소 ID = 씬 이름), 빈 값이면 `Title`(32장 2-6).
- **시각 진행**: Rules의 `CalendarRules.Register(session)`이 `session.Ticked`에서 `Clock.Time ≥ run.calendar.nextStepAt`일 때만 `session.Do(new AdvanceTime())`(33장 5-1 모양). 연결은 Client `Bootstrap.Started` 한 줄(17장 2-6). 대화(`pauseGame`)·멈추는 화면(`GameTime.Pause`)이 열리면 `Time.deltaTime`이 0이라 틱도 시각도 멈춘다(07장 2.5).

### 3-5. 프로젝트 고유 기능

- 만들지 않는다. 원본은 인스턴스로 충분하다.
- 상시 규칙(생일 ×8·토요일 판매가)은 규칙 함수 안에서(5절 G8). 온실처럼 "그 장소에서만"인 규칙은 장소 객체에 건 영구 상태 효과로 DB 조립(4절).
- Q3을 "규칙이 확인"으로 답하면 DB 종류 '지도'(`LocationMapData`: 크기·칸 표시 배열) + Tilemap 굽기 메뉴를 더한다.

## 4. 기믹·효과 쪼개기

판정은 3절 시스템층이 있다고 보고 그 기믹을 넣는 데 드는 것이다: **A** = DB만, **B** = 코드 한 단위(규칙 함수 몸통·Block·`[BindTo]`·행동 하나), **C** = 중간층 확장(GBible에 없어 프로젝트가 하위 시스템을 새로 세우거나 모듈을 대신함), **D** = 문법 밖.

### 4-1. 먼저 따질 것 — 게임 안 시계

GBible의 시간은 `session.Clock`(초·틱)과 `GameTime`(일시정지·배속)뿐이고, 날짜·시각·요일·계절·하루 넘김은 없다(코드 `GameClock`은 `Tick`·`Time` 두 칸, 매뉴얼·코드에 calendar·season 없음).

| 방법 | 어떻게 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| ① 시계에서 계산 | `dayStartedAt`만 저장, 시각 = (`Clock.Time` − 그것) ÷ 0.7 × 10 | 행동이 없다 | 잠·쓰러짐·축제처럼 시각을 건너뛰거나 멈추는 일을 시계로 할 수 없다(게임 시계는 호스트가 `EndFrame`으로 흘리고, 규칙이 건너뛰게 하는 길이 없다). 플레이어 데이터가 아니라 HUD binding-path·다시 그리기·DB 조건이 못 본다 |
| ② 판 데이터 + 10분 행동(추천) | `run.calendar.minute`, 10분마다 `AdvanceTime` 행동 하나가 `TimeChanged`를 쏜다 | 데이터가 정답이라 저장·HUD·DB 조건(분 ≥ 1080)·상태 효과의 셀 이벤트(`DayStarted`)가 그대로 따라온다 | 행동이 1초에 1.4개. Undo가 없어 이력은 쌓이지 않지만 행동마다 Sync가 여러 번 돈다(5절 G4) |

- 하루 넘김은 `EndDay` 행동 하나 안에서 끝낸다(3-4). "그날 하루" 지속은 상태 효과 지속 '이벤트 횟수 1, 셀 이벤트 `DayStarted`'(29장 2-2).
- 2시 쓰러짐·축제 시각 멈춤은 `AdvanceTime`이 분을 더한 뒤 보는 분기다.

### 4-2. 먼저 따질 것 — 맵 칸(타일) 데이터

| 무엇 | 어디에 | 이유 |
|---|---|---|
| 바뀌는 칸(밭·설치물·채집물) | `world` 키, 장소별 `Dictionary<int, …>`(칸 키) | 플레이어 데이터라 저장·전송·Undo 길을 탄다. 칸 키로 바로 찾는다 |

| 칸을 가리키는 행동 필드 | (장소, x, y) 값 | 객체 참조는 실행 직전 `Game.Find`로 다시 찾는다(O(데이터 크기), 5절 G3) |

## 5. 빈틈 목록

### 5-1. 기능·성능

**G1. 게임 안 달력이 없다**
- 무엇: 날짜·시각·요일·계절, 시각 진행, 하루 넘김, "18:00~22:00" 같은 시각 조건, 시각 글("오전 6:10"). GBible 시간은 `GameClock`(초·틱)뿐이다.
- 왜(빈도): 이 장르는 모든 규칙(성장·일정·상점·쓰러짐·날씨)이 달력 위에 선다. AI가 매번 데이터 칸·자동 행동·틱 연결·하루 넘김 행동·이벤트 넷을 새로 짓고 이름을 정한다. DB 조건은 분(1080)으로 적어야 하고, HUD 시각은 binding-path로 안 돼 화면 코드가 된다.
- 다른 장르에도: 생활·경영·생존·RPG 낮밤·방치형(날짜 보상).
- 제안: 선택 기능 '달력'. DB › 달력 설정(하루 시작·끝 분, 10분당 게임 초, 계절 이름·일 수, 요일 이름) · 플레이어 데이터 `$calendar`(year·season·day·weekday·minute) · 행동 `AdvanceCalendar`(틱이 보냄)·`SkipToNextDay` · 이벤트 `TimeOfDayChanged`·`DayEnded`·`DayStarted`·`SeasonChanged` · 상태 효과 지속 '게임 일 수' · 조건 Block '시각 사이'·'요일'·'계절' · 텍스트 틀 `{value:clock}` · `Game.ScheduleAtGameTime(일, 분, 행동)`.
- 3요소: ① 평범한 이벤트·행동이라 래퍼 없음 ② 10분마다 숫자 하나의 변경, 협동이면 호스트만 보내도록 "자동 행동을 보내는 쪽" 표시가 필요 ③ 리플렉션 없음.

**G2. 규칙이 읽는 격자 지도가 없다**
- 무엇: 칸 단위 맵의 안 바뀌는 정보(갈 수 있음·밭 가능·물), 칸 키·이웃 칸·길찾기. 규칙은 Tilemap을 못 읽는다.
- 왜(빈도): 괭이질·물 채우기·설치·채집 자리·마을 사람 길찾기마다 "이 칸이 되나"가 나온다. 지금은 화면을 믿거나(협동에서 검증 불가), 프로젝트 DB 종류 + 굽기 메뉴를 매번 짓는다(Q3).
- 다른 장르에도: 전술·로그라이크·퍼즐·타워 디펜스·건설 생존.
- 제안: DB 종류 '격자 지도'(`GridMapData`: 크기·칸 표시 비트 배열) + 에디터 메뉴 'Tilemap에서 굽기' + Core 도우미 `Grid.Key(x, y)`·`Game.Grid(id).Has(x, y, "tillable")`·`Neighbors`·`Path(from, to)`. 판 데이터는 평범한 `Dictionary<int, T>`를 그대로 쓴다(감싸는 형식을 만들지 않는다).
- 3요소: ① 함수만 더함 ② 안 바뀌는 데이터라 DB에 있어 전송 없음 ③ 리플렉션 없음.

**G3. `Game.Find`·상태 효과 정리가 데이터 크기에 비례한다**
- 무엇: `Game.Find(id)`는 부를 때마다 그 키를 Sync하고 사본 나무 전체를 훑는다(`GameApi.Find` → `SyncedMirror` → `Mirror.FindById`). 행동의 객체 필드는 실행 직전 이것으로 다시 찾는다. 상태 효과가 하나라도 있으면 바깥 행동마다 한 번 더 Sync하고 가진 쪽마다 `Find`한다(`GameSession` 생성자의 `Committing` → `Statuses.PruneMissing`).
- 왜(빈도): 칸·설치물이 수천인 판에서 "설치물마다 상태 효과"(스프링클러·비료·허수아비)를 쓰면 10분 행동마다 가진 쪽 수 × 데이터 크기다. 문서에는 이 비용이 없어 AI가 객체 참조·상태 효과를 그대로 쓴다. 가정: 실제 시간은 재지 않았다.
- 다른 장르에도: 개체가 많은 RTS·콜로니·타워 디펜스·경영.
- 제안: Mirror가 Sync 때 id → 객체 색인을 갱신하고 `Find`·`PruneMissing`이 그것을 쓴다(O(1)). 그 전까지 관례·매뉴얼 02장에 "개체가 수천이면 행동 필드에 객체 대신 키·좌표" 한 줄.
- 3요소: ① 코드 변화 없음 ② 전송 무관 ③ 리플렉션 없음.

**G4. 프레임마다 모든 플레이어 데이터를 비교한다**
- 무엇: 프레임 끝(`GameSession.EndFrame` → `Data.Sync`)과 바깥 행동마다 여러 번(`Track` 끝·`GameSession.Do`, 상태 효과·Modifier가 있으면 `Committing`도) 모든 Mirror 키를 생성 코드로 비교한다. 아무것도 안 바뀐 프레임에도 비용이 데이터 크기다.
- 왜(빈도): 세이브가 커지는 장르(수십 시간)는 데이터가 계속 큰다. 이 게임은 프레임마다 + 1초에 1.4번의 행동마다 수천 칸을 비교한다. 가정: 생성 코드라 수천 개는 1ms 안이라고 보지만 재지 않았다.
- 다른 장르에도: RPG·경영·생존의 큰 세이브.
- 제안: 매뉴얼 01·33장에 "Sync 비용 = 데이터 크기 × (프레임 + 행동마다 2~3번)" 적기. 기능으로는 키마다 '행동 밖 변경을 받지 않음' 표시(그 키는 프레임 끝 Sync에서 뺌, 행동 밖 변경은 `Modify`로만) 또는 행동이 꺼낸 키만 비교.
- 3요소: ① 어트리뷰트나 DB 칸 하나 ② 전송 무관 ③ 리플렉션 없음.

**G5. 인벤토리가 고정 칸·칸 정보·옮기기를 못 한다**
- 무엇: `Inventory.Remove`가 빈 칸을 지워 칸 자리가 당겨지고, `InventorySlot`은 item·count뿐(품질 없음), 옮기기·바꾸기·나누기가 없다. DB에서 쓸 '인벤토리에 넣기·빼기' 결과 Block, '가지고 있음' 조건 Block, 얻음 이벤트도 없다(25장 5절: '플레이어 데이터에 주기'는 겹치기를 거치지 않는다).
- 왜(빈도): 도구 줄·끌어 옮기기·품질은 이 장르의 기본이라 모듈을 버리고 가방을 새로 짓는다(Q2, 판정 C). 모듈을 써도 Block 셋을 매번 짓는다.
- 다른 장르에도: RPG·생존·액션 RPG 거의 전부.
- 제안: `Inventory.fixedSlots`(빼도 빈 칸을 남김) · `Move(from, to)`·`Swap`·`Split` · `InventorySlot.tag`(품질 같은 글자 하나, item과 tag가 같을 때만 겹침) · 결과 Block '인벤토리에 넣기'·'인벤토리에서 빼기'(쓴 아이템 빼기 포함) · 조건 Block '인벤토리에 있음' · 이벤트 `ItemAdded`·`ItemRemoved`. Reference 2-4 "칸 있는 가방" 줄에 "칸 UI·장비 칸·옮기기 없음"을 적는다.
- 3요소: ① 평범한 클래스 필드·Block ② 칸 하나의 변경이라 작다 ③ 리플렉션 없음.

**G6. 판 저장에 "이벤트를 받으면 저장"이 없다**
- 무엇: Bootstrap '판 저장'은 끌 때·행동마다·저장하지 않음 셋(`RunSaveMode`)뿐이다. "하루 끝에만 저장"은 '저장하지 않음' + `SubscribeAfterAction<DayStarted>` → `GBibleRuntime.SaveRun` 코드다. 명세서 양식 1절에는 "체크포인트에서"가 있는데 기획 명세서 읽는 법 2절 표에는 그 줄의 GBible 대응이 없다.
- 왜(빈도): 하루·세이브 포인트·층 끝 저장은 흔하다. AI가 매번 저장 시점 코드를 쓰고, `NewRun`을 빠뜨리면 예전 `run.json`이 남는다(5-2 D3).
- 다른 장르에도: RPG 세이브 포인트, 로그라이트 층 끝, 액션 체크포인트.
- 제안: `RunSaveMode.OnEvent` + Bootstrap '판 저장 이벤트' 칸(이미 있는 `RunSaver`의 이벤트 받기·프레임 끝 저장 길을 쓴다).
- 3요소: ① DB 칸 하나 ② 무관 ③ 리플렉션 없음.

**G7. 필드 경로로 딕셔너리 키·id 한 항목을 집을 수 없다**
- 무엇: `npcs[elly].points` 같은 경로가 없다(11장 3-1, 코드 `FieldPaths.Resolve`는 딕셔너리를 값들로만 편다). 조건은 리스트 + '배열·리스트 항목 검사'(any, `id == elly` AND `points ≥ 1000`)로 되지만, binding-path(HUD·사람들 탭)와 텍스트 틀에는 그 길이 없다.
- 왜(빈도): "엘리 하트 4"는 대사·선택지 조건·화면 칸에 자주 나온다. 데이터를 딕셔너리로 두면 DB 조건이 막히는 것을 AI가 만들고 나서야 안다.
- 다른 장르에도: 퀘스트 상태·세력 평판·유닛별 값.
- 제안: 경로 문법 `npcs.list[#elly].points`(id로 한 요소)·`map[key]`(딕셔너리 키). 문서(11장 3-3)에 "id 하나 고르기 = 항목 검사 any + id 일치 AND" 예를 더한다(문서에서 찾기 어려움).
- 3요소: ① 경로 글자만 ② 무관 ③ 생성 코드(`FieldAccess`)로 읽어 리플렉션 없음.

**G8. 상시 규칙·개체마다 도는 트리거를 걸 주인이 없다**
- 무엇: 늘 켜진 가로채기·이벤트 반응(생일 ×8, 토요일 판매가 +10%)을 DB에서 조립할 종류가 없다. 도전과제는 한 번·Undo 밖, 상태 효과는 가진 쪽이 필요하다. "놓인 물건마다 아침에"도 같다. 지금은 주인공·장소에 건 영구 상태 효과로 우회하거나(29장 2-1이 허락하지만 문서에 이 쓰임이 없다) 17장처럼 DB 종류를 짓는다.
- 왜(빈도): 기획자가 "이번 주만 판매가 +10%" 같은 규칙을 DB로 더하고 싶을 때마다 AI가 호스트를 고민한다. 개체마다 상태 효과는 G3 비용이 붙는다.
- 다른 장르에도: 난이도 규칙·기간 이벤트 보너스·패시브 지형 효과 — 거의 전부.
- 제안: DB › '규칙'(`RuleData`: 켜짐 조건 + 트리거(이벤트·조건·가로채기) + 결과, 반복, 행동 안에서 돎) 기본 제공. 그 전까지 29장에 "상시 규칙 = 주인공에게 건 영구 상태 효과, 장소 규칙 = 장소 객체 + 가진 쪽 필드" 패턴과 비용을 적는다.
- 3요소: ① DB 종류 하나 ② 무관 ③ 등록은 시작할 때만.

**G9. 가중치 표 무게를 값에 따라 바꿀 수 없다**
- 무엇: 줄의 무게는 고정, 조건으로 켜고 끄기만 된다(30장 2-3). "운에 비례"는 구간 줄(Q6)이나 코드 풀이다.
- 왜(빈도): 운·레벨·호감도에 따라 확률이 바뀌는 표가 흔하다. 코드 풀로 가면 기획자가 DB에서 못 고친다.
- 다른 장르에도: 로그라이크(희귀 확률 +%), RPG 드롭률, 가챠 천장.
- 제안: 항목 줄 `weightScale`(밸런스 값 ID 또는 플레이어 데이터 경로 × 계수) 또는 뽑기 가로채기 자리 `RollIntent { table, entries(item·weight) }`.
- 3요소: ① DB 칸 ② 무관(난수 흐름은 그대로) ③ 생성 코드로 읽음.

**G10. 다시 그리기가 키 단위다**
- 무엇: `GameView.Redraw`·`ViewList`·binding-path는 플레이어 데이터 키가 바뀌면 다시 그린다(32장 2-1). 경로 단위로 지켜볼 수 없다. 그래서 시계와 밭을 다른 키로 나눠야 한다(3-1).
- 왜(빈도): 자주 바뀌는 값(시계·타이머)과 큰 목록이 같은 판 데이터에 있으면 큰 목록이 계속 다시 그려진다. AI가 키를 나누는 이유를 문서에서 찾지 못하면 `run` 하나에 몰아넣는다.
- 다른 장르에도: 실시간 HUD가 있는 경영·생존·RTS.
- 제안: 키에 경로 앞부분을 허락(`Redraw(draw, "run:calendar")`) — 저장소의 `DataChanged(key, changes)`가 이미 경로를 준다. 그 전까지 32장 6절에 "자주 바뀌는 값과 큰 목록은 키를 나눈다".
- 3요소: ① 글자 하나 ② 무관 ③ 리플렉션 없음.

**G11. 기본 화면에 글자 입력 창이 없다**
- 무엇: 확인·고르기·설정·슬롯·일시정지뿐이다. 이름 짓기는 프로젝트 화면(`TextField`)이다.
- 왜(빈도): 새 게임마다 한 번이지만 거의 모든 장르의 새 게임 화면에 있다.
- 다른 장르에도: RPG 이름 짓기, 세이브 이름, 길드 이름.
- 제안: `GameScreens.Prompt(안내, 기본값, done, 최대 길이)` 기본 화면.
- 3요소: ① 함수 하나 ② 무관(결과는 행동으로) ③ 리플렉션 없음.

**G12. "섞임"(실시간 시각 + 되돌리기 없음) 장르의 추천값 줄이 없다**
- 무엇: 기획 명세서 읽는 법 2절 "1 시간"은 턴제·실시간 두 줄이라 실시간이면 스냅샷 Undo가 추천된다. 가이드 07장 1절 장르 표에 생활·농장 시뮬 줄이 없다. 명세서 양식에도 "게임 안 시계(하루 길이·달력)"·"맵이 칸 단위인가" 칸이 없어 4·5절 문장에 섞여 들어온다.
- 왜(빈도): [선택] 되돌리기를 비우면 AI가 "가장 가까운 줄"을 골라야 하고, 실시간 액션 줄(스냅샷·체크포인트)과 RPG 접힌 칸 사이에서 매번 판단한다.
- 다른 장르에도: 경영·생존·방치형 일부.
- 제안: 가이드 07장 1절에 "생활·농장 시뮬 | 쓰지 않음 | 하루 끝 저장(G6) | 판 = 세이브 전체, 프로필 거의 없음 | `weather`·`luck`·`forage`·`fish` | 달력(G1)·격자(G2)·다이얼로그·가방" 줄. 양식 1절에 [선택] "게임 안 시계", 6절에 [선택] "맵이 칸(타일) 단위인가". 읽는 법 2절 "1 시간"에 "섞임" 줄.
- 3요소: 문서만.

## 6. 하루 안에 되나

**시스템층(규칙·DB·테스트)과 UI Toolkit 화면은 된다. 2D 탑뷰 월드 쪽까지 AI 혼자 하루 안에 끝내기는 어렵다.**

되는 이유:
- 질문이 6개이고 모두 추천값으로 갈 수 있다. 데이터 구조(키 넷·칸 키·리스트 NPC)와 흐름(`EndDay` 한 행동, 하루 시작 뒤 저장)이 명세서와 관례로 정해진다.
- 행동·Undo 끔·판 저장·씬 흐름·다이얼로그(대화·선물 반응·TV 분기)·밸런스 값·가중치 표(날씨·채집·물고기)·상태 효과(음식·온실)·기본 화면(확인·슬롯·설정·일시정지·알림)이 GBible에 있어 그대로 쓴다. 기믹 19줄 중 A 5·B 11이 그 위에서 끝난다.
- GBible에 없는 셋(달력 G1, 가방 G5, 하루 끝 저장 G6)은 한 번 정하면 프로젝트 코드로 닫히는 크기다. 화면 8개는 35장의 UXML + `GameScreen` + binding-path 흐름 그대로다.

어려운 이유:
- 월드 화면이 GBible 범위 밖이다. 주인공 이동·칸 커서·도구 휘두르기·밭과 작물 그리기(Tilemap 좌표)·마을 사람 길 걷기(길찾기)·문으로 장소 옮기기·낚시 미니게임을 AI가 처음부터 짓는다. 32장은 데이터 → 오브젝트 연결(`ViewList`)까지만 준다.
- 그 화면은 씬·Tilemap·프리팹이 있어야 돈다. 관례 6절대로 AI는 프리팹·인스펙터 연결을 만들지 않으므로 사람이 Unity에서 씬을 짠 뒤에야 확인된다.
- 칸 데이터가 커지면 G3·G4의 비용이 이 장르에서 먼저 드러난다. 측정하지 않았으므로 "설치물마다 상태 효과" 같은 DB 조립을 쓰기 전에 확인해야 한다.

하루 목표를 지키려면 G1(달력)·G2(격자 지도·길찾기)·G5(가방)를 GBible에 넣는 것이 가장 크다. 셋 다 다른 장르(경영·전술·RPG)에서도 매번 다시 짓는 부분이다.
