### 1. 한 판의 흐름

- 시간: 실시간. 집(허브)·상점·축복 고르기 창에서는 시간이 멈춘다.
- 한 판: 집에서 무기를 고르고 출발 → 1구역(방 10개 안팎. 대부분 전투 방, 중간에 상점 1·샘 1, 끝에 중간보스) → 2구역 → 3구역(끝에 보스) → 탈출. 방을 깨면 문이 2~3개 열린다. 문마다 다음 방 보상(축복·금화·최대 체력·잿빛 조각·회복)이 그림으로 보이고, 플레이어가 문을 고른다.
- 반복 단위: 방. 방에 들어서면 적 웨이브가 1~3번 나온다(웨이브의 적을 다 잡으면 다음 웨이브). 마지막 웨이브까지 다 잡으면 방 보상이 나온다. 전투 중에는 이동·일반 공격(3타 콤보)·특수기·대시(2칸, 칸마다 다시 참)·스킬(쿨다운)·소모품(1칸)을 쓴다.
- 판이 끝나는 때: 주인공 체력이 0이고 죽음 무시가 남지 않았으면 패배(집으로). 3구역 보스를 잡으면 승리(탈출).
- 판이 끝나도 남는 것: 잿빛 조각(죽어도 남음), 거울 강화 단계, 해금한 무기, 최고 구역, 탈출 횟수.
- [선택] 되돌리기(Undo): 
- [선택] 이어 하기: 체크포인트에서. 방에 들어설 때 저장하고, 끄고 켜면 그 방 처음부터.

| 4 | 떨어진 금화의 규칙상 모양 | 처치 순간 판 데이터 금화에 바로 더한다. 바닥 동전과 자석은 연출만 | 바닥 동전을 판 데이터에 두면 위치와 '주움' 판정을 화면이 보고해야 하고, 방을 떠날 때·이어 하기 때의 처리가 생긴다 | 추천값으로 진행 |
| 5 | 무적이 막는 것, 피할 수 없는 피해 | 무적은 피해 의도를 막는다 → 그 피해에 딸린 상태 효과·"맞으면" 발동도 없다. 피해 종류에 `unavoidable`(용암·보스 즉사기)을 두고 무적은 그것만 막지 않는다 | 피해 의도의 `kind` 필드를 시스템층에서 정해야 나중에 효과가 붙는다(관례 4절) | 추천값으로 진행 |
| 6 | 쿨다운 감소의 단위 | 특수기 한 번(휘두름 하나)에 한 번, 피해가 실제로 들어간 적이 1 이상일 때. 0 아래로 내려가지 않는다. 대상은 스킬 칸 하나 | "적 다섯을 맞히면 −5초"인지에 따라 이벤트 모양(맞힘마다 / 휘두름마다)이 달라진다 | 추천값으로 진행 |
| 7 | 죽음 무시의 기준 | 최대 체력(보정 포함)의 30% 올림. 버틴 뒤 1초 무적. 남은 횟수는 주인공에게 걸린 상태 효과의 중첩(거울 강화 '불굴'이면 판 시작 중첩 2). HUD에 중첩 수가 보인다 | "판마다 한 번"이 거울 강화로 "N번"이 된다. 플래그가 아니라 횟수로 둬야 한다 | 추천값으로 진행 |
| 8 | 시너지를 얻은 뒤 조건이 깨지면 | 유지한다. 조건은 후보에 나올 때만 본다 | 같은 자리 교체로 불 축복이 1개로 줄 수 있다. 유지하지 않으면 축복을 잃는 규칙(되돌림)이 따로 필요하다 | 추천값으로 진행 |
| 9 | 잔불 폭발의 대상과 연쇄 | 리아는 맞지 않는다. 잔불로 죽은 적도 잔불을 터뜨린다(연쇄). 한 적이 여러 폭발에 맞으면 폭발마다 따로 맞는다 | 연쇄는 1초씩 늦게 이어져 사슬 한도(16)와 상관없다. 한계는 방의 적 수다 | 추천값으로 진행 |
| 10 | 잔불의 위치와 범위 판정 방법(문법 밖) | 폭발 자리 = 처치 순간 그 적 그림의 위치(화면이 기억). 1초 타이머는 규칙의 예약. 1초 뒤 그 순간 범위 안의 적을 화면 물리로 찾아 행동으로 보고 | 규칙은 위치를 모른다. 대안(타이머까지 화면에)은 되감기·이어 하기에서 빠진다. 추천안은 폭발 하나가 행동 둘(터짐·맞음)이 된다 | 추천값으로 진행 |
| 11 | 밀치기와 벽 충돌(문법 밖) | 밀치기는 화면 물리만(규칙에는 세기 값만 의도에 싣는다). 벽 충돌 피해는 넣지 않는다. 넣는다면 화면이 피해 종류 `wallSlam`으로 보고 | 밀려난 거리·벽은 물리가 정한다(관례 13절) | 추천값으로 진행 |
| 12 | 투사체 반사(문법 밖) | 투사체는 규칙 데이터에 두지 않는다(매 프레임 바뀌는 위치·속도). 반사 창(대시 직후 0.3초)만 규칙의 상태 효과, 되돌리기·되돌린 투사체의 맞음은 화면이 판정해 보고. 되감기·이어 하기 때 날아가던 투사체는 사라진다 | 투사체를 규칙 데이터로 옮기면 매 프레임 기록이 쌓인다(01장 5절) | 추천값으로 진행 |

**질문 12개.** 답을 받으면 명세서 4·5절 옆에 적어 두라고 권한다.

묻지 않고 정한 것(정하고 보고만 한다):

- 멀티 없음 → 세션 하나. 모든 변경은 행동, static 상태 없음.
- 고정 틱 30. Undo는 개발용 스냅샷(0.5초 × 20). 출시 빌드는 '없음'(Bootstrap에 빌드별 칸이 없어 `Configuring` 한 줄, 빈틈 5-3-4).
- 판 저장: '저장하지 않음' + 화면 코드가 `RoomEntered`를 받은 뒤 `GBibleRuntime.SaveRun`(Bootstrap에 '이벤트 때 저장'이 없다, 빈틈 5-3-3). 판 끝 이벤트 `RunEnded`. '프로필도 행동마다 저장'은 끈다(실시간이면 행동이 있는 프레임마다 파일을 쓴다).
- 피해 공식: 방어 능력치가 없으므로 "공격력 × 계수 × (1 + 피해 증폭 합) + 추가 피해", 주인공이 받을 때만 `× damageTaken`.
- 대시: 2칸, 칸마다 0.8초 뒤 하나씩 다시 찬다. 쿨다운·재충전은 게임 시계 기준 시각으로 판 데이터에.
- 적 접촉 피해는 적의 공격 판정 하나에 한 번(겹쳐 있는 동안 매 프레임이 아님).
- 축복 고르기 창: 같은 ID(`momoi.choice`)의 프로젝트 화면(시간 멈춤·설명·등급·바뀔 축복). '고르기 창 저절로'는 끈다.
- 연출: 피격·피해 숫자·죽음은 연출 대기열 밖에서 바로 튼다. 대기열은 보스 등장·판 결과만.
- 설정: 기본 5개 + 화면 흔들림·피해 숫자(켜기/끄기). 입력(키 바꾸기) 켬, Steam 켬(App ID 480으로 시작), 리치 프레즌스.
- 난수 흐름: `crit`(치명타), `loot`(처치 금화), `room`(방 보상·웨이브), `target`(무작위 적). 가중치 표는 표마다 흐름이 따로다(30장 2-3).
- 슬롯 3개(기본 슬롯 화면).

**판·프로필**(DB › 플레이어 데이터: `run` = 세션, `profile` = 메타)

```csharp
[Serializable] public class RunState
{
    public string scene;                                   // 씬 흐름(빈 값 = 타이틀)
    public int zone, roomIndex;
    [DataRef(typeof(InstanceData))] public string weapon;  // 무기 원본
    public Hero hero = new Hero();
    public Room room;                                      // 집이면 null
    public List<Door> doors = new List<Door>();
    public List<OwnedBlessing> blessings = new List<OwnedBlessing>();
    public int gold, shards, hourglass, potions;
}
[Serializable] public class Fighter { public string id; public int hp; public double maxHp, attack; }
[Serializable] public class Hero : Fighter    // id는 늘 "hero"(영구 Modifier 대상, 28장 5-2)
{ public double specialPower, critChance, damageTaken = 1, moveSpeed; public int dashMax = 2, dashes = 2; public double dashRefillAt, skillReadyAt; }
[Serializable] public class Enemy : Fighter { [DataRef(typeof(InstanceData))] public string monster; public double attackInterval, moveSpeed; public int spawnPoint; }
[Serializable] public class Room { public string id, kind, encounter, reward; public int wave; public bool cleared; public List<Enemy> enemies = new List<Enemy>(); public List<Blast> blasts = new List<Blast>(); }
[Serializable] public class Door { public string id, reward, god; }
[Serializable] public class OwnedBlessing { public string id; public int rarity; }   // id = 축복 원본 ID(한 판에 하나씩이라 겹치지 않는다)
[Serializable] public class Blast { public string id, victimId; public double at, radius; public int amount; }
[Serializable] public class Profile { public int shards, escapes, runs, bestZone; public Dictionary<string, int> mirror = new Dictionary<string, int>(); public List<string> weapons = new List<string>(); }
```

- 죽음 무시 남은 횟수는 필드가 아니라 상태 효과 `deathDefiance`의 중첩이다(질문 7).
- 판에서 얻은 잿빛 조각은 `run.shards`에 모았다가 `EndRun`이 이기든 지든 프로필로 옮긴다.

| 규칙 함수 | 의도(필드) | 끝난 뒤 이벤트 |

| `Rules.StartCooldown`·`ReduceCooldown(game, user, slot, seconds)` | `CooldownIntent { userId, slot, seconds, cancelled }` | `CooldownChanged { userId, slot, readyAt }` |

| `Rules.Gain(game, resource, amount)` | `GainIntent { resource, amount, cancelled }` | `ResourceGained` |
| 비용 | `Game.Pay`(기본 `CostIntent`) | — |
| `Rules.GainBlessing(game, id, rarity)` | — | `BlessingGained { blessing, rarity, replaced }` |

- 주인공 id는 `"hero"`로 고정해 의도 조건(`sourceId 일치 hero`)과 영구 Modifier가 판마다 맞게 한다.
- 이동은 규칙 동사가 아니다(관례 10절). PlanningSpecGuide 3절의 "이동이 있으면 이동"은 따르지 않는다(5-5 문서 오류 6).

### 3-4. 진행 흐름

- 집: `BuyMirror { upgrade }`(`Game.Pay(profile, "shards", …)`) → `StartRun { weapon }`(시작 체력·거울 강화·죽음 무시 중첩·`scene = "Zone1"`·첫 방).
- 방: `EnterRoom { door }`(문 보상 확정, 웨이브 구성 뽑기, 웨이브 1 소환, `RoomEntered`를 쏜다 → 화면이 받아 `SaveRun`) → 전투 → 마지막 적이 쓰러지면 그 행동 안에서 `Rules.SpawnWave` 또는 `Rules.ClearRoom`(`RoomCleared`, 문 2~3개를 방 보상 표에서 뽑는다) → `TakeRoomReward`(보상 오브젝트를 만지면. 축복이면 고르기 요구) → `EnterRoom { door }` …
- 전투 입력(화면 → 행동): `Strike { hero, kind, combo, hits }`(휘두름·특수기·스킬의 판정 하나 = 행동 하나), `EnemyHit { sourceId, monster, kind }`(적 공격·투사체가 리아를 맞힘. 쏜 적이 이미 죽었을 수 있어 참조 필드가 아니라 id 글자), `BlastHit { blast, targets }`, `ReflectHit { monster, targets }`, `Dash { hero }`, `CastSkill { hero }`, `Game.Use(소모품, hero)`.
- 틱 규칙(`session.Ticked`에서 시각을 보고 그때만 행동): `RefillDash`, `Pulse`(0.5초마다 `Pulsed`를 쏜다 — 화상용, 3-6), 라이브러리의 "상태 효과 만료"·"예약 실행".
- 판 끝: `EndRun { won }` → `RunEnded`(판 끝 이벤트), 조각을 프로필로, `scene = "Home"`.
- 반복 단위는 방이다. "이번 방 동안" 같은 효과의 셀 이벤트는 `RoomCleared`.
- 씬 흐름: `run.scene`(Title·Home·Zone1~3), 빈 값 = Title.

### 3-5. 프로젝트 고유 기능 — 축복

- `[Database("축복", Group = "콘텐츠", IdPrefix = "blessing")] class BlessingData : GameData { [Keyword(typeof(God))] god; [Keyword(typeof(BlessingSlot))] slot; trigger(TriggerSlot Event·Condition·Intercept); outcomes(OutcomeSlot PlayerData·Coded·Targeted·Intent) }`.
- 등록: `BlessingRules.Register(session, 축복들)` — 축복마다 `session.Triggers.Register`, 발동 순간 `run.blessings`에 그 ID가 있을 때만 `RunOutcomes`(17장 2-6·2-8, `BoundOutcomes` 확인 포함). 연결은 `Client/Bootstrap.Started` 한 곳.
- 등급: 컨텍스트에는 등급 칸이 없다. 효과 Block이 `Rules.RarityOf(c)`(`run.blessings`에서 `c.Owner`의 등급을 찾음)로 읽어 `rarityScale`을 곱한다(질문 3, 5-2-1).
- 새 개념 이름 '축복'·'거울 강화'는 명세서에 있으므로 묻지 않는다.

### 5-1. 실시간 구조

**1. 연출 대기열이 하나뿐이고, 기본값이 "연출을 기다림"이다**
- 왜: `GameView.Present`는 넣은 순서대로 하나씩 돈다(32장 2-2, 코드 `GameView`에 동시 재생 없음). 실시간은 피격 번쩍임·피해 숫자·죽음이 한 프레임에 수십 개다. 게다가 (a) `Redraw`·`ViewList`·'데이터 연결'·`GameScreen`(`WaitForPresentation` 기본 참)·씬 흐름이 대기열이 빌 때까지 미뤄진다 — 연출이 끊이지 않는 전투에서 HUD·적 목록이 늦게 그려진다. (b) `GameView.Busy`가 계속 참이라 `OnClick`·`GameScreens.Do`가 버튼 행동을 무시한다(코드 `GameScreens.Do`). (c) `ViewList`·`ElementList`의 `OnRemove`(죽는 모습)도 대기열에 들어가 적 열이 한꺼번에 죽어도 하나씩 쓰러진다. 그런데 관례 6절·PlanningSpecGuide 2절(6 연출)·Reference 2-4는 연출 경로로 `SubscribeAfterAction → Present`만 적고 실시간의 예외를 말하지 않는다. 모든 피격마다 걸린다.
- 다른 장르: 실시간 전부(디펜스·뱀서류·액션 RPG). 턴제 광역기에서도 동시 연출이 필요하다.
- 제안: `GameView.Play(연출)`(대기열 밖, 동시 재생, 속도·건너뛰기는 따르고 다시 그리기를 막지 않음) · `ViewList.RemoveInParallel`(죽는 모습을 동시에) · DB › 화면 설정 '실시간 연출: 다시 그리기가 연출을 기다리지 않음'(고정 틱이 켜져 있으면 기본 켬) · `Busy`를 선택 대기만으로 보는 칸(`OnClick`이 연출 중에도 돈다). 문서: 관례 6절·가이드 7장 6절에 "실시간은 피격 연출을 `Play`로, 순서가 필요한 것(보스 등장·결과)만 `Present`".
- 3요소: ① API 하나·칸 하나 ② 무관 ③ 무관.
- 해결 가능 여부: 가능. 지금은 프로젝트가 `SubscribeAfterAction`에서 바로 VFX를 만들고, `waitForPresentation: false`·`WaitForPresentation => false`를 화면마다 적고, `OnRemove`를 비워 직접 처리하는 방식으로 우회한다(코드 단위, B).

**2. 쿨다운·충전이 없다**
- 왜: DB › 능력(16장)에도 코어에도 쿨다운 칸이 없다(코드 검색 결과 없음). 대시 칸·스킬·소모품·적 공격까지 프로젝트가 매번 준비 시각 필드 + 사용 조건 Block + 실패 글 + 줄이기 효과 + HUD 남은 시간을 만든다. 가이드 7장의 `Dash` 예는 실패를 `InvalidOperationException`으로 던진다(5-5 문서 오류 1). 판마다·입력마다.
- 다른 장르: 턴제 RPG(3턴 쿨다운)·MOBA·카드(턴당 한 번)·방치형.
- 제안: DB › 능력에 `cooldown`(지속과 같은 모양: 게임 시간 초 / 이벤트 횟수) · `charges`(칸 수·칸마다 재충전) 칸. 런타임 `Game.CooldownLeft(사용자, 능력)` · `Game.ChargesOf` · `Game.ReduceCooldown(사용자, 능력 또는 태그, 양)` · 효과 Block '쿨다운 줄이기' · `FailureKeys.OnCooldown`("{ability}은(는) {seconds}초 뒤에 쓸 수 있습니다") · 저장 `$cooldowns`(세션). 읽기 API라 화면이 `CanDo`를 매 프레임 부르지 않고 남은 시간을 그린다.
- 3요소: ① 칸·API ② 작은 목록 하나 ③ 없음.
- 해결 가능 여부: 지금은 프로젝트 코드(C). 라이브러리 기능이 되면 A.

**3. "N초마다" 주기 트리거가 없다**
- 왜: 상태 효과·프로젝트 기능의 트리거는 이벤트 받기·조건 충족·가로채기·사용뿐이다(29장 3-1, 28장 3-6). 화상(0.5초마다)·재생·오라 펄스·"3초마다 가장 가까운 적에게 번개"를 DB로 만들 수 없다. 조건의 `PollInterval`은 도전과제 감시용 시간 조건이다. 그런데 가이드 7장 6절·Reference 2-2는 "독·화상은 상태 효과(지속 = 게임 시간 N초)"라고만 써서 DB로 될 것처럼 읽힌다(5-5 문서 오류 4). 실시간 게임의 지속 피해 전부.
- 다른 장르: 실시간 전부, 방치형(초당 생산), 타워 디펜스.
- 제안: 상태 효과에 `pulse`(주기 초) 칸 + 라이브러리 이벤트 `StatusPulsed { status, holderId, stacks }`(트리거 '이벤트 받기'로 받고 가진 쪽 필드로 거름). 프로젝트 기능용 트리거 잎 '주기(초)'(`TriggerKinds.Interval`). 같은 틱에 맞은 주기는 행동 하나로 묶는다(적 40마리가 화상이어도 주기마다 행동 하나).
- 3요소: ① DB 칸 ② 행동 묶음 ③ 없음.
- 해결 가능 여부: 지금은 공통 부품 하나(`Pulse` 틱 규칙 → `Pulsed` 이벤트)로 우회(C). 그 뒤 축복·상태 효과는 A.

**4. 부분 시간(적만 멈춤·느려짐)이 없다**
- 왜: 게임 시계는 세션에 하나(`session.Clock`)이고 상태 효과·예약이 모두 그 시계를 본다. `GameTime`은 `Time.timeScale` 전체다(07장 2.6~2.10). 시간 정지·감속 장판·"적 50% 느리게"에서 규칙 시간 일부를 멈출 수 없고, 화면 쪽 '적 시간 배율'도 프로젝트가 만든다(`GameView.DeltaTime`은 연출 속도용).
- 다른 장르: 액션·RTS(유닛별 감속)·퍼즐(시간 조작).
- 제안: (가) 문서: 가이드 7장 6절에 "부분 시간 정지 = 화면 시간 배율 + 규칙 시간은 흐름(근사)"을 정해 두기. (나) 라이브러리: 상태 효과·예약에 `clock` 칸(기본 / 이름 있는 묶음) + `Game.PauseClock("enemy", 초)` · `Game.SetClockScale("enemy", 배율)`. 묶음 시계는 세션 시계에서 파생해 저장·되감기에 함께 들어간다.
- 3요소: ① 칸 하나 ② 시계 값 몇 개 ③ 없음.
- 해결 가능 여부: 근사는 가능(A + 화면). 규칙 시간까지는 지금 문법 밖(D).

**5. 실시간 입력의 "지금 되나" 확인이 비싸다**
- 왜: 대시를 쿨다운 중에 누르면 `Game.Do`가 실패 → 예외 + 행동 기록 + Journal 오류 줄("행동 실패, 변경 취소")이 남는다(코드 `ActionDispatcher.Execute`). 미리 보려면 `Game.CanDo`가 행동 전체를 미리보기로 돌린다(33장 2-2). 버튼을 누르고 있는 동안 매 프레임이면 타임라인이 실패로 찬다.
- 다른 장르: 실시간 전부.
- 제안: 5-1-2의 읽기 API로 대부분 해결. 문서(33장·가이드 7장): "실시간 입력은 읽기 전용 확인(쿨다운·자원) 뒤 `Do`, 실패를 흐름 제어로 쓰지 않는다". 라이브러리: `GameFailure`로 실패한 행동은 Journal '정보' 수준으로, 같은 실패가 이어지면 한 줄로 묶기.
- 3요소: ① 문서·옵션 ② 무관 ③ 무관.
- 해결 가능 여부: 가능(문서 + 작은 라이브러리 수정).

**6. 규칙이 시작하는 범위 효과의 위치와 판정 요청**
- 왜: 위치는 화면에만 있다(가이드 7장 6절). 플레이어 입력으로 시작하는 범위(휘두름)는 화면 판정 결과를 `Picked`·`hits`로 넘기면 되지만, 규칙이 시작하는 범위(처치 1초 뒤 폭발, 주기 오라, 장판)는 규칙이 위치도 맞은 대상도 모른다. 프로젝트마다 "폭발 지점 목록 + 판정 요청 이벤트 + 판정 보고 행동" 짝과 "사라진 적의 마지막 위치 기억"을 새로 만든다. `ViewList`가 오브젝트를 지우면 `GameView.Find(id)`는 `null`이다(32장 2-3). PlanningSpecGuide 7절의 "2초 뒤 폭발(실시간)" 줄도 누가 맞는지를 말하지 않는다(5-5 문서 오류 8). 범위 효과가 있는 축복·스킬마다.
- 다른 장르: 실시간 전부. 그리드 전술은 위치가 규칙 데이터라 괜찮다.
- 제안: 관례 10절·가이드 7장에 패턴을 적는다 — "한 번 정해지는 위치(처치 지점·장판 중심)는 판 데이터에 넣어도 된다(매 프레임이 아니다)", "규칙이 시작하는 범위 = 규칙이 판정 요청 이벤트를 쏘고 화면이 결과를 행동으로 답한다". 라이브러리: `GameView.LastPosition(id)`(ViewList가 지울 때 위치를 남김) · 판정 요청 규약 `AreaRequested { requestId, centerId, radius, ability }` + 화면이 `Game.Use(ability, user, 맞은 것들)`로 답.
- 3요소: ① 패턴·이벤트 하나 ② 답은 id 목록이라 작다. 멀티에서는 판정 권한 문제(서버가 위치를 모름)라 멀티 설계와 함께 정해야 한다 ③ 없음.
- 해결 가능 여부: 지금은 C(프로젝트 패턴). 문서로 정해 두면 B.

**7. 판정 결과를 보고하는 행동의 모양이 정해져 있지 않다**
- 왜: 가이드 7장·33장 5-1의 예는 `HitHero { foe, amount = 3 }` 한 줄이다. 휘두름 하나에 맞은 적 목록과 대상별 판정 정보(백어택·밀치기 방향·콤보 순번)를 어디에 싣는지, 접촉 피해를 얼마나 자주 보내는지 정해져 있지 않다. 그리고 예처럼 피해 양을 화면이 정하면 규칙 계산이 화면으로 샌다. 쏜 적이 이미 죽은 투사체는 참조 필드(`Enemy shooter`)로 넣으면 실행 직전 다시 찾기에서 "찾을 수 없습니다"로 실패한다(02장, 코드 `ActionReferences.Live`). 모든 맞음.
- 다른 장르: 실시간 전부.
- 제안: 가이드 7장 6절에 판정 행동 예 — `Strike { hero, kind, combo, List<HitInfo { target, backstab }> hits }`(대상 목록 + 대상별 플래그, 피해 양은 규칙이 계산), "적 40마리를 한 번에 맞혀도 행동 하나", "접촉 피해는 판정 시작 때 한 번", "쏜 쪽이 사라질 수 있으면 id 글자 + 원본 ID".
- 3요소: ① 문서 ② 묶으면 패킷이 작다 ③ 무관.
- 해결 가능 여부: 가능(문서 수정).

**8. 실시간 성능 기준과 조절 칸이 없다**
- 왜: 행동 하나마다 모든 데이터 Sync 두 번(시작·끝) + 상태 효과·이번 판 Modifier가 있으면 끝나기 직전 한 번 더(`Committing`) + 참조 필드마다 `Game.Find`(데이터 나무 훑기, 매번 새 목록) + `Describe()` 두 번(LINQ·문자열) + Journal 줄들이 든다. 이벤트·가로채기마다 `ToList`·`OrderBy` 할당과 `_entries.Contains`(목록 선형 검색)가 있고, 상태 효과 트리거는 가진 쪽마다 `Game.Find`(코드 `TriggerSystem`·`StatusSystem.HoldersFor`). 매 프레임 끝에도 모든 데이터 Sync. Journal은 출시 빌드에서도 켜져 바뀐 곳마다 문장을 만들고(`DescribeChanges` 기본 참, Bootstrap 칸 없음), 4096줄이면 실시간으로 십여 초 분량이다. 33장은 "틱 규칙은 가볍게"만 말하고, PlayerDataStore.md 12절의 수치(행동 한 번 5ms)는 Mirror 이전 값이다(5-5 문서 오류 9). 가정(측정 안 함): 적 40·축복 15·초당 행동 30이면 프레임당 1ms 안쪽일 것이다. 다만 할당이 쌓여 GC가 튈 수 있다.
- 다른 장르: 실시간·뱀서류(적 수백)는 특히.
- 제안: 33장에 '실시간 예산' 절(행동 한 번 비용, 초당 행동 수·적 수 기준, 묶는 법, 적 수백 마리면 규칙 데이터를 무리로 묶는 법). 모니터 머리에 '이번 초 행동 수·Sync 시간'. Bootstrap 고급에 '출시 빌드에서 변경 문장 끄기'(`DescribeChanges`)·'Journal 출시 빌드 보관 줄 수'. 라이브러리 안쪽: 가로채기 순서를 등록 때 한 번 정렬, `_entries`를 HashSet으로, `Find`에 id 색인.
- 3요소: ① 칸 ② 무관 ③ 무관.
- 해결 가능 여부: 문서·칸은 가능. 안쪽 정리는 라이브러리 수정(AI는 하지 않고 알린다, 관례 0절).

### 5-2. 효과 문법

**1. 효과 Block의 숫자를 등급·레벨로 키울 수 없다**
- 왜: Block 숫자 칸은 상수다(밸런스 값·등급 참조 없음, 코드 검색 결과 없음). 컨텍스트(`TriggerContext`)에도 등급·레벨 칸이 없다. 축복 등급·스킬 레벨·카드 강화마다 항목을 따로 만들거나 Block마다 등급 코드를 넣어야 한다. 축복 전부.
- 다른 장르: 카드(강화)·RPG(스킬 레벨)·수집형(별)·방치형(업그레이드 단계).
- 제안: `[Scalable]` 어트리뷰트를 붙인 숫자 칸이 DB에서 '값 출처'(상수 / 밸런스 값 / 밸런스 값(단계 = 컨텍스트의 `Level`))를 고르게 하고, 컨텍스트에 `Level`을 둔다(프로젝트 기능의 `RunOutcomes`가 넣는다). 또는 문서에 "등급별 항목 따로" 규칙을 명시.
- 3요소: ① 어트리뷰트라 OK ② 무관 ③ 칸 해석은 초기화 때.
- 해결 가능 여부: 지금은 C(Block마다 `useRarity`). 라이브러리 기능이면 A.

**2. 상태 효과 길이를 걸 때 바꿀 수 없다**
- 왜: `ApplyStatus(대상, id, 중첩, 출처)`에 길이 인자가 없고(코드 `StatusSystem.Apply`), DB 길이는 숫자 상수다. 대시 무적 = 대시 동작 시간(밸런스 값)인데 상태 효과 길이가 따로 놀아 기획자가 두 곳을 고친다. 거울 강화로 무적이 0.8초가 되면 상태 효과를 하나 더 만든다. 시간 지속 효과 전부.
- 다른 장르: 모든 장르(스킬 레벨에 따른 지속 턴).
- 제안: `Game.ApplyStatus(…, length: 값)` + 효과 '상태 효과 걸기'에 `length` 칸(비우면 DB 값) + DB `duration.lengthFrom`(밸런스 값 ID).
- 3요소: ① 인자·칸 ② 무관 ③ 없음.
- 해결 가능 여부: 지금은 우회 불가(값마다 상태 효과를 따로). 라이브러리 수정 필요.

**3. "가진 것의 원본 필드로 세기" 조건이 없다**
- 왜: 판 데이터는 원본 ID만 둔다(관례 1절). 그런데 '배열·리스트 항목 검사'는 판 데이터 항목의 필드만 본다(11장). "불 축복 2개 이상"·"희귀 유물 3개"·"덱의 불 카드 수"마다 프로젝트 조건 Block을 만든다.
- 다른 장르: 덱빌딩·로그라이크 전부.
- 제안: '배열·리스트 항목 검사'에 '항목이 DB ID면 원본에서 읽기' 켜기(경로 `$source.god`), 또는 기본 조건 Block '원본 필드로 세기'(목록 경로·원본 필드·값·개수).
- 3요소: ① 칸 ② 무관 ③ 원본 값 읽기는 생성 FieldAccess(인스턴스 값 클래스는 `[Serializable]`)로 리플렉션 없음 — 가정.
- 해결 가능 여부: 지금은 B(조건 Block 하나). 라이브러리 기능이면 A.

**4. 고르기 후보에 덧붙일 값이 없고, 기본 고르기 창은 이름만 그린다**
- 왜: `ChoiceCandidate { id, label }`이고 '가중치 표에서 고르기' 후보는 원본 ID뿐이다(29장 4-11, 30장 3-3). "축복 셋, 각각 등급이 다름"·"상점 품목과 가격"·"보상 셋 중 하나(양 포함)"는 코드 `Game.Ask` + 이어서 할 행동에 후보별 값을 따로 담아야 한다. 기본 고르기 창은 이름 버튼만 그린다(코드 `ChoiceWindow`, 설명·아이콘·등급 없음). 로그라이크의 보상 고르기 전부.
- 다른 장르: 거의 모든 로그라이크·RPG 보상.
- 제안: `ChoiceCandidate.data`(글자 사전: `rarity`·`amount`)와 `[Chosen]` 옆의 `[ChosenData]` 칸, '가중치 표에서 고르기'에 '후보마다 붙일 표'(등급 표) 칸, 기본 고르기 창이 `<id>.desc`(5-2-5)와 `data`를 함께 그림.
- 3요소: ① 칸·어트리뷰트 ② 작은 사전 ③ 없음.
- 해결 가능 여부: 지금은 B(코드 `Ask` + 프로젝트 고르기 화면).

**5. 설명 글 규약이 없다**
- 왜: 이름은 `<id>.name`이 규약인데(23장) 설명은 없다. 축복·카드·유물의 플레이어용 설명(수치 포함, 번역)을 프로젝트마다 키·틀을 정한다. Block의 `Sentence`는 DB 요약(한국어, 번역 안 됨)이다. 콘텐츠마다.
- 다른 장르: 카드·로그라이크·RPG.
- 제안: 규약 `<id>.desc` + `Texts.Describe(id)`(그 항목의 Block 칸 값을 `{필드}`로 넘김, 5-2-1의 등급 배율 반영) + 메뉴 'DB 설명 키 채우기'.
- 3요소: ① 규약·API ② 무관 ③ Block 칸 읽기는 생성 FieldAccess.
- 해결 가능 여부: 지금은 프로젝트가 규약을 정해 쓴다(B).

### 5-3. 화면·저장·설정

**1. `GameScreen`에 매 프레임 훅이 없다**
- 왜: 쿨다운 원·무적 깜빡임·시간 정지 남은 막대는 시간에 따라 바뀌지만, binding-path와 `Draw`는 데이터가 바뀔 때만 돈다(35장 2-2·2-3, 코드 `GameScreen`의 훅은 `OnOpen`·`Draw`·`OnClose`). 가이드 06장은 "쿨다운 표시는 준비 시각 − 게임 시계"라고만 한다. 화면마다 `schedule.Every`나 MonoBehaviour를 따로 쓴다.
- 다른 장르: 실시간 전부, 방치형(남은 시간).
- 제안: `GameScreen.Tick(float dt)`(열린 동안 매 프레임) 또는 binding-path 틀 `run:hero.skillReadyAt@countdown`(시각 필드 → 남은 초, `TickAlpha` 보간) · ProgressBar용 `momoi-countdown` 클래스.
- 3요소: ① 훅·틀 ② 무관 ③ 없음.
- 해결 가능 여부: 가능(작은 라이브러리 기능). 지금은 화면 코드 우회(B).

**2. 기본 화면 바꾸기의 "시간 멈춤" 방법이 문서에서 찾기 어렵다**
- 왜: 기본 고르기 창은 시간을 멈추지 않는다(코드 `BuiltInSpec`). 같은 ID(`momoi.choice`)로 DB › 화면 항목을 만들고 '열린 동안 게임 시간 멈춤'을 켜면 코드 없이 기본 창이 멈춘 채 뜬다(코드 `MakeController`가 `[BindTo]`가 없으면 기본 창을 쓴다). 35장 2-5 '바꾸기'는 USS 바꾸기만 설명한다.
- 다른 장르: 실시간 전부.
- 제안: 35장 2-5에 "같은 ID 항목의 칸(층·시간 멈춤·아래 입력 막기)이 기본 화면에도 먹는다"를 한 줄. 더 나아가 DB › 화면 설정에 '고르기 창 열린 동안 시간 멈춤'(고정 틱이 켜져 있으면 기본 켬).
- 3요소: ① 문서 ② 무관 ③ 무관.
- 해결 가능 여부: 기능은 있다(문서에서 찾기 어려움).

**3. 판 저장에 "이벤트 때"가 없고, 실시간의 "행동마다"가 위험하다는 경고가 없다**
- 왜: 명세서 양식은 이어 하기·저장 시점에 "체크포인트에서"를 선택지로 주는데(PlanningSpec 1절·9절), PlanningSpecGuide 2절 표와 Bootstrap '판 저장'(끌 때·행동마다·저장 안 함)에는 대응이 없다(5-5 문서 오류 7). 가이드 7장 6절만 "저장하지 않음 + 체크포인트에서 `SaveRun`(행동 밖)"이라 화면 코드가 한 곳 생긴다. 또 '행동마다 저장'·'프로필도 행동마다 저장'은 행동이 있는 프레임마다 파일을 쓴다(코드 `RunSaver.FrameEnd`) — 실시간에서는 초당 수십 번인데 문서에 경고가 없다(가이드 7장 '프로필 저장 시점'은 "진행이 프로필에 있으면 켠다"고만 한다 — 이 게임의 잿빛 조각처럼 판 중에 프로필 값이 생기면 AI가 켜기 쉽다).
- 다른 장르: 액션·RPG(세이브 포인트)·메트로배니아.
- 제안: Bootstrap '판 저장'에 '이 이벤트를 쏜 행동이 끝날 때'(이벤트 고르기, 판 끝 이벤트와 같은 칸 모양). 고정 틱이 켜져 있는데 '행동마다'를 고르면 Bootstrap 화면에 경고. PlanningSpecGuide 2절 '1 이어 하기'·'9 저장 시점'에 "체크포인트 → 저장 이벤트" 줄.
- 3요소: ① 칸 ② 무관 ③ 무관.
- 해결 가능 여부: 가능. 지금은 화면 코드 한 곳(B).

**4. Undo 방식을 빌드별로 정할 수 없고, 되감기는 화면 상태를 돌리지 않는다**
- 왜: 실시간은 개발 중엔 스냅샷 되감기가 쓸모 있지만 출시엔 플레이어용 Undo가 없다. 스냅샷은 0.5초마다 판·프로필 전체를 사전 나무로 내보낸다(코드 `CaptureSnapshot` → `Data.Export`, 생성 FieldAccess라 리플렉션은 없지만 할당). Bootstrap에는 값이 하나라 `Configuring` 코드가 필요하다(관례 1절 "코드가 필요 없는 설정은 DB"와 어긋남). 되감기는 규칙 데이터만 돌리므로 적 위치·투사체는 그대로다 — 문서에 없다.
- 다른 장르: 실시간 전부.
- 제안: Bootstrap '출시 빌드 Undo 방식'(같음 / 없음). 가이드 7장 6절에 "되감기는 화면 상태(위치·투사체)를 돌리지 않는다 → 개발용".
- 3요소: ① 칸 ② 무관 ③ 무관.
- 해결 가능 여부: 가능.

**5. "항상 켜진 기본 규칙"을 DB에 두는 자리가 문서에 없다**
- 왜: "맞으면 0.5초 무적을 건다"는 장르 기본 규칙이지만 기획자가 DB에서 고칠 만하다. 주인공에게 판 시작 때 거는 영구 상태 효과(트리거 + 결과)로 두면 코드 없이 되지만, 관례·가이드에 이 패턴이 없어 AI가 매번 `Rules.Damage` 안에 코드로 쓸지 고민한다.
- 다른 장르: 모든 장르(턴 시작 드로우 보정, 전역 규칙).
- 제안: 29장 5절에 "기본 규칙 = 주인공(또는 진영)에게 거는 영구 상태 효과" 예.
- 3요소: 문서만.
- 해결 가능 여부: 기능은 있다(문서에서 찾기 어려움).

**6. 뺄 목록에 객체 목록의 원본 ID 경로를 쓰는 예가 없다**
- 왜: 30장 3-2의 뺄 목록 예는 ID 글자 목록(`run › relics`)뿐이다. 가진 축복을 `OwnedBlessing { id, blessing, rarity }`처럼 두면 `blessings[].blessing` 경로가 되는지 문서로 알 수 없다(코드 `IdsAt`는 `FieldPaths.Resolve`로 경로를 따라가므로 될 것 — 가정). 이번 설계는 `OwnedBlessing.id = 원본 ID`로 피했다.
- 제안: 30장 5-10에 객체 목록 경로 예 한 줄.
- 해결 가능 여부: 문서에서 찾기 어려움.

### 5-4. 3요소에 걸리는 것 요약

- ① 코딩 쉬움: 래퍼 형식이 필요한 제안은 없다. 제안은 모두 DB 칸·API·어트리뷰트(`[Scalable]`·`[ChosenData]`)다.
- ② 멀티 패킷: 판정을 화면이 하므로(질문 1) 실시간 멀티를 붙일 때 판정 권한을 다시 정해야 한다(5-1-6). 판정 결과를 휘두름마다 묶으면(5-1-7) 패킷은 작다.
- ③ 런타임 리플렉션: 이번 설계에서 새로 생기는 것은 없다. 원본 필드 읽기(5-2-3)·Block 칸 읽기(5-2-5)는 생성 FieldAccess를 전제로 한다(가정).

## 6. 하루 안에 되나

**판단**: 규칙층(데이터·핵심 동사·축복 기능·상태 효과·표·진행 흐름)과 UI 화면(HUD·축복 고르기·상점·거울·결과·타이틀)은 하루 안에 된다. 단 질문 12개에 답이 왔고, 5-1의 빈틈(동시 연출·쿨다운·주기·판정 요청)을 프로젝트 코드로 어떻게 메울지 위 시스템 목록대로 정해 둔 상태일 때다. 전투의 화면 쪽(조작·대시 이동·콤보 입력 창·적 AI·투사체·히트박스·시간 배율·밀치기)까지 넣으면 하루 안에는 "규칙대로 돌지만 손맛은 자리 표시" 수준까지다. 그래서 "레벨 디자인을 뺀 모든 시스템과 UI"를 글자 그대로 보면 이 장르는 하루를 넘긴다.

**이유**

1. **시스템의 절반이 화면 쪽이다.** 턴제(카드 던전)는 규칙이 시스템의 거의 전부라 GBible이 대부분을 받친다. 실시간 액션은 이동·판정·AI·투사체가 화면 쪽 "자유 영역"(관례 10절)인데, GBible에는 이 영역의 부품·규약이 없고 가이드도 한 줄 설명이다. AI가 판정 보고 모양부터 새로 정한다(5-1-6·5-1-7).
2. **실시간 공통 부품을 매번 새로 만든다.** 쿨다운·충전, 주기 실행, 동시 연출, 규칙이 시작하는 범위 효과의 판정 요청, 부분 시간 배율, 매 프레임 HUD 갱신은 실시간 게임이면 늘 필요한데 모두 GBible 밖이다(5-1-1~4, 5-3-1). 각각은 작지만 모양을 정하는 판단이 들어가고, 정한 모양이 축복 수십 개의 DB 조립 방식을 묶는다.
3. **질문 다섯 개가 판정 경계다.** 12개 중 5개(1·2·10·11·12)가 문법 밖이거나 규칙과 화면의 경계라, 답에 따라 데이터 모양(폭발 지점·투사체·시간)이 갈린다. 답이 추천값과 다르면(예: 시간 정지가 규칙 시간까지 멈춤) 시계 설계부터 다시 한다.
4. **실시간 성능 기준이 없다.** 적 40마리·초당 행동 수십 개에서 Sync·`Find`·Journal·할당이 어디까지 괜찮은지 문서가 말하지 않아(5-1-8), 만든 뒤 프로파일러로 확인하고 고치는 단계가 따로 생긴다.
5. **문서의 실시간 예가 관례와 어긋난다.** 가이드 7장·02장·33장의 실시간 예를 그대로 따르면 관례 위반(예외 종류·상수·Unity API·연결 자리)이 생겨(5-5의 1·2), AI가 예와 관례 중 무엇을 따를지 판단해야 한다.

하루 목표에 가까워지려면, 5-1-1(동시 연출)·5-1-2(쿨다운)·5-1-3(주기)·5-3-3(저장 이벤트)을 라이브러리 기능으로, 5-1-6·5-1-7(판정 요청·보고 패턴)과 5-5의 오류를 문서로 먼저 정리하는 것이 가장 효과가 크다. 그러면 4절의 C 3개 중 2개(잔불·화상)가 A·B로 내려가고, 질문 10·12는 정해진 패턴을 따르는 확인 질문이 된다.
