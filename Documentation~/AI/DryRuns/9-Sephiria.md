# 콘텐츠 시험 9 — 세피리아 아티팩트 276개 · 콤보 20개

세피리아(실시간 액션 로그라이트)의 아티팩트 시트(276개)와 콤보 효과 시트(20콤보, 85단계)를 GBible로 옮긴다고 놓고, 코드를 쓰지 않고 "어떻게 만들지"만 판정한 기록이다. 먼저 메인 룰(가방 배치 계산기)을 세우고, 그 위에서 아티팩트 효과 문장을 분류했다.

- 읽은 것: `ProjectConventions.md`·`Reference.md`·`GimmickCatalog.md`, 매뉴얼 11·12·16·17·28·29·33·37장(1·2·6절 위주), `PlanningSpecGuide.md` 7절.
- 문서로 판단이 안 돼 코드를 본 곳: `Runtime/Core/Passives.cs`(레벨 0·`byLevel`·`modifierTarget`의 레벨 합·대상 하나만), `Runtime/Core/Placement.cs`(`Pattern`이 줄을 넘는 칸을 버리는지), `Runtime/Core/Attributes.cs`(`Apply`). 5절에 적었다.
- 이 기록의 새 이름(행동·이벤트·행동 직전 이벤트·Block·데이터 클래스)은 관례 2절대로 지은 가칭이다.

## 1. 한 줄 결론

**문법 밖 0개, 아티팩트 쪽 예외 4개(최대 중첩 늘리기 3 · 화상 틱 속도 1)와 메인 룰 쪽 예외 4건이다.** 가장 큰 빈틈은 **세피리아의 "같은 아티팩트 여러 개 · 0레벨부터"를 패시브의 '가진 동안 능력치 보정'이 그대로 받지 못한다**는 것이다. 보정 받을 대상을 주인공으로 두면 레벨이 "모든 사본의 레벨 합"이 되어 값이 틀린다(사본마다 값을 더해야 하고, [고유]는 가장 높은 하나만이어야 한다). 0레벨은 GBible에서 "가지지 않음"이다. 그래서 능력치 줄이 있는 아티팩트 약 170개가 모두 계산 함수의 우회(사본마다 Modifier 붙이기, 저장 레벨 = 세피리아 레벨 + 1)를 거친다.

## 2. 메인 룰 — 가방 배치 계산기

기믹 목록 1절의 세피리아 줄 그대로다. 조각 = 가방의 아티팩트·석판, 자리 = 가방 목록 + 줄 길이 6, 순서 = 배치가 바뀌는 행동의 끝에서 계산 함수 한 번. 전투 중 발동은 계산 결과(켜진 아티팩트 목록·콤보 딕셔너리)를 가진 목록으로 삼는 패시브가 한다.

### 2-1. 데이터

```csharp
// 판 데이터(run)
[Serializable] public class BagPiece { public string id; public string item; public int baseLevel; public int turns; public int count; }
//   item = 원본(인스턴스) ID — 아티팩트면 ArtifactData, 석판이면 SlateData. count = 진화 횟수·쌓는 값(4절 예외 5)
[Serializable] public class LitArtifact { public string id; public string artifact; public int level; }
//   켜진 아티팩트. id = 가방 조각의 id, artifact = 패시브 ID(위치 변형 포함), level = 세피리아 레벨 + 1(4절 예외 2)
public List<BagPiece> bag = new List<BagPiece>(new BagPiece[34]);   // 6열, 마지막 줄 4칸, 빈 칸 null. 칸이 늘면 Add(null)
public List<int> slotBonus = new List<int>(new int[34]);             // 칸 레벨(친타마니 +3)
public List<int> mysticSlots = new List<int>();                      // 신비 콤보가 고른 칸
public List<LitArtifact> lit = new List<LitArtifact>();
public Dictionary<string, int> combos = new Dictionary<string, int>(); // 콤보 패시브 ID → 개수
public string weapon;                                                // 무기 종류(무기 전용 아티팩트)
public bool inBattle;
```

{

    public List<Cell> pattern;        // 무늬(화면 기준 상대 칸)
    public int bonus;                 // +n / −n

### 2-2. 계산 함수 `Bag.Recalculate` — 차례

1. **칸 보너스** = `slotBonus` + `mysticSlots`.
2. **석판**(칸 순서): `hasSpot`이면 `Placement.Is(bag, i, 6, spot)`가 거짓일 때 건너뛴다. 덮는 칸 = 무늬면 `Placement.Pattern(i, n, 6, pattern, turns)`, 같은 줄·열이면 `Placement.Indices(…, SameRow/SameColumn)`(돌리면 줄 ↔ 열), 대각선 끝까지면 거리 1~(줄 수)의 대각선 무늬 네 갈래를 `Pattern`에 넣는다(목록 밖·줄 밖은 `Pattern`이 버린다). `ignore`면 그 칸을 무시 표시, 아니면 `bonus[at] += bonus`.
3. **아티팩트**(칸 순서): 레벨 = `clamp(baseLevel + bonus[i], 0, maxLevel)`. 무시 칸 · `<제약>` 불충족(`Placement.Is`) · 무기 불일치 · '꺼짐' 상태 효과(반딧불이)면 켜지 않는다.
4. **태그 정하기**: `variants`로 패시브 ID·콤보를 바꾼다(캘세더니 열쇠 = 줄 y, 대립의 천칭·영원의 식 = `x < 3` 왼편).
5. **[고유]**: 같은 원본 중 레벨이 가장 높은 하나만 남긴다.
6. **`lit` 다시 쓰기**: 칸 순서로 `{ id = 조각 id, artifact = 패시브 ID, level = 세피리아 레벨 + 1 }`.
7. **콤보 세기**: 켜진 것의 콤보 → 개수. 하얀 종이(양옆 아티팩트가 같은 콤보면 그 콤보 +1). `combos`에 쓰고, 단계가 바뀐 콤보마다 이벤트 `ComboTierChanged { combo, from, to }`.
8. **보정 모으기**(4절 예외 1): `Game.RemoveModifiers("bag", hero)` 뒤, 켜진 것마다 `session.Passives.Find(artifact).Modifiers`의 줄을 `At(level)`로 `Game.AddModifier(hero, …, "bag")`.
9. 이벤트 `BagRecalculated`.

부르는 행동(모두 끝에서 `Bag.Recalculate`): `MovePiece`(칸 바꾸기) · `RotatePiece`(`rotatable`이 아니면 `Game.Fail`) · `AddPiece`(얻기) · `RemovePiece`(팔기·파괴 = `null`) · `ChangeWeapon` · `EnterRoom`(신비 칸을 `Game.Random("mystic")`으로 다시 고를 때). 화면의 "돌리면 어떻게 되나"는 `Game.Preview(new RotatePiece { … }, g => g.Data().Run.lit…)`.

### 2-3. 패시브의 모양

| 패시브 | 가진 목록 | 칸 |
|---|---|---|
| 아티팩트(276) | `run › lit` | `matchField`(일치 필드) `artifact`, `perElement`(놓인 것마다) 켬, `levelField`(레벨 필드) `level`. `modifiers`(가진 동안 능력치 보정)의 `byLevel`(레벨별 값)에 **시트 값을 그대로**(첫 칸 = 0레벨). `modifierTarget`(보정 받을 대상)은 **비운다**(주인공은 계산 함수 8단계가 받는다) |
| 콤보(20) | `run › combos`(딕셔너리, 레벨 = 개수) | 패시브 ID = 딕셔너리 키. `modifierTarget` `hero`. `byLevel`은 개수마다 한 칸(견고 물리 피해 = 0, 2, 2, 4, 4, 6, 6, 8, 8, 8 …). 가진 쪽이 `run` 하나라 레벨 합 문제가 없다 |

- 전투 중 발동은 시스템층 이벤트를 받는다: `WeaponHit`·`DamageDealt`·`CritHit`·`Dashed`·`DashAttackHit`·`GuardSucceeded`·`PerfectGuard`·`Evaded`·`HitTaken`·`EnemyKilled`·`SpellCast`·`MpSpent`·`PotionDrunk`·`RoomEntered`·`BattleStarted`·`ArtifactHit`·`MerchantTraded`.
- **사본마다 쿨다운** = 켜진 아티팩트(사용자)에 건 숨긴 상태 효과 + 조건 '상태 효과 검사'(사용자 ≤ 0). 켜진 아티팩트 id = 조각 id라 다시 계산해도 걸린 것이 남는다.
- **"N초마다"는 상태 효과의 주기(`pulse`)로 만들지 않는다.** 주기는 아티팩트가 꺼져도(조각 id가 가방에 남아) 계속 돌고, 레벨마다 다른 간격을 못 쓴다. 대신 패시브의 **쿨다운 고리**: 발동 = `|| OR`(이벤트 받기 '상태 효과 끝남'(status = 그 쿨다운) · '전투 시작' · `BagRecalculated`) `&& AND` '상태 효과 검사'(사용자 쿨다운 ≤ 0) `&& AND` '플레이어 데이터 검사'(`inBattle` 참) → 결과 + 쿨다운 다시 걸기(B2, 길이 `{level:5/4/3/2.5}`).
- **자기 투사체·동료·행성의 맞음** = 화면이 판정 보고 `Strike { hits }`(맞은 쪽 id · 종류 · `sourceArtifactId` = 조각 id · 거리 · 마지막 연격 · 근처에 적 있음) → 이벤트 `ArtifactHit` → 패시브 `holderField`(가진 쪽 필드) `sourceArtifactId`로 그 사본만 발동.

### 2-5. 명세서 4-2에 표시할 것 · 기획에 물을 것

4-2 표시: **놓인 순서·위치가 효과를 바꾼다**(가방 6열, `perElement`) · **위치로 태그·속성이 바뀐다**(2-2의 4·7단계) · **판정 규칙이 바뀐다**(`Game.Owned` 스위치: 얼음구름 나비·영원의 식·명상 서적·운철 귀걸이·쥐 마법사의 펜던트·이각수 관) · **효과가 반복 발동한다**(얼음무구·태양검·마법서 추가 발동 = 시스템 행동 직전 이벤트의 `times`) · 칸 레벨 목록(친타마니·신비). 빌려 쓰기·여러 칸 조각은 없다.

시트로 정해지지 않는 것(틀리면 계산 함수를 크게 고친다):

1. 같은 아티팩트를 둘 가질 수 있나, [고유]의 뜻(중복 시 가장 높은 하나만?). → 추천: 둘 가능, [고유]는 가장 높은 레벨 하나. 어느 쪽이든 2-2의 5·8단계 한 곳.
2. 콤보 개수에 꺼진 것(제약 불충족·무기 불일치)·[고유] 중복을 세나. → 추천: 켜진 것만, 같은 원본은 하나. 7단계 한 곳.
3. 콤보 단계 값은 바뀌나(4개 = +4) 쌓이나(+2 +4). 10단계의 다른 능력치(견고 증폭 15%)는 8단계 값에 더해지나. → 추천: 바뀜 + 10단계는 더함. `byLevel`만 다르다.
4. 신비 콤보 "무작위 1칸/2칸"의 뜻(그 칸 레벨 +1?)과 다시 고르는 때. → 추천: 방에 들어갈 때 다시 고름(배치마다 고르면 옮길 때마다 바뀐다). `EnterRoom` 한 곳.
5. 석판 '무시' 칸의 뜻(그 칸 아티팩트를 끔 / 석판 보너스를 받지 않음)과 −n 석판으로 레벨이 0 아래일 때. → 추천: 0에서 멈춤. 2·3단계.
6. "최하단·가장 아래 칸"이 덜 찬 마지막 줄(30~33번)인가. → 추천: 그렇다(`PlaceSpot` 맨 아래 줄). 위 줄 오른쪽 두 칸은 아니다.

## 3. 분류 표

판정 기호는 공통 지시 그대로다. 한 아티팩트에 문장이 여럿이면 가장 무거운 쪽(예외 > BindTo > 메인 룰 > Block > DB)으로 묶었고, 나머지 문장은 "만드는 법"에 적었다. "화면"은 판정을 화면이 하는 것이고 주 분류와 겹친다. 모든 아티팩트는 2-3의 패시브 하나 + 2-1의 `ArtifactData` 하나이며, 능력치 줄은 `byLevel`에 시트 값 그대로다.

## 4. 예외 · 문법 밖

**문법 밖: 없음.** 위치·거리·주변 적·충돌은 모두 판정 보고 행동으로 문법 안이다.

| # | 무엇이 · 왜 | 우회 | 있으면 없어지는 것(라이브러리) |
|---|---|---|---|
| 1 | **같은 아티팩트 여러 개의 가진 동안 보정.** `modifierTarget`(보정 받을 대상)을 정하면 레벨 = 모든 가진 쪽의 레벨 합이고 값은 그 합의 `byLevel` 칸이다. 세피리아는 사본마다 값을 더해야 하고([고유]가 아니면), [고유]는 가장 높은 하나다. 0레벨 사본 둘(저장 레벨 1·1, 예외 2)이면 세피리아는 "0레벨 값 × 2"인데 GBible은 "저장 레벨 2(= 세피리아 1레벨)의 값 하나"를 준다. 능력치 줄이 있는 아티팩트 약 170개(그중 [고유]가 아닌 37개는 사본마다 더해야 하고, [고유]는 중복을 빼야 한다) | 계산 함수 8단계: `modifierTarget`을 비우고(보정은 켜진 아티팩트 객체가 받아 무해), 켜진 것마다 패시브의 `modifiers`를 `At(level)`로 주인공에 Modifier(출처 `bag`)로 붙인다. 매 계산마다 떼고 다시 붙이므로 남지 않는다. 읽을 때마다 사본을 모두 훑어 더하는 방법(`Rules.Stat`)은 실시간·멀티에서 능력치를 읽을 때마다 `lit` × 패시브를 돌아 무거워(3요소 2 성능) 고르지 않았다 | `PassiveData`에 "여럿일 때" 칸: 레벨 합(지금) · 가진 쪽마다 값 합 · 가장 높은 하나 → 8단계와 [고유] 5단계가 없어지고 `modifierTarget hero`만으로 끝난다 |

| 6 | **아티팩트 하나 = 패시브 하나 = 발동 하나.** 가진 목록의 키·일치 필드가 곧 패시브 ID라 한 아티팩트에 패시브를 둘 둘 수 없다. 서로 다른 순간이 둘인 효과는 `OR`로 묶으면 결과가 두 순간 모두에 돈다(21·137·162·201·207) | `[BindTo]`에서 `c.Event` 형식으로 나눈다(그래서 BindTo로 셌다). 콤보는 한 패시브에 능력치 + 발동 하나라 걸리지 않았다 | `PassiveData`에 규칙 여러 줄(17장 2-4의 `List<TriggerRule>`처럼 발동 → 결과 줄마다) |

조각으로 센 예외는 3·4의 4개다. 1·2는 메인 룰 전체, 5·6은 BindTo 12개의 이유다.

함께 있으면 Block·BindTo가 줄어드는 것(예외는 아니다):

- 틀(`{level:…}`)을 '상태 효과 걸기'의 중첩·길이, 조건 '확률', '이벤트 쏘기'의 값(`{user}`도)에 → B2·B3·B6이 없어진다(그 셋만 쓰는 Block 줄이 DB가 된다).
- 조건 '자리 검사'에 "이벤트의 개체가 사용자의 (방향)에 있다" → B7이 없어진다.
- `PassiveModifier`에 "요소의 숫자 필드에 비례"(`perField`) → 계산 함수가 개수를 `lit` 요소에 써 두면 119·166·236이 DB가 된다.

## 5. 문서 빈틈

1. **레벨 0**(코드를 봤다: `Passives.cs`의 `At`·`ModifiersFor`): 17장·28장은 "레벨 0 = 가지지 않음 / 값 0"이라고만 하고, 37장 5-5는 `level = 1 + bonus[i]`로 +1을 조용히 쓴다. 0레벨부터 세는 시트를 어떻게 옮기는지(저장 +1, 시트 값 그대로)가 어디에도 없다.
2. **여러 사본의 레벨 합**: 17장 0-1·37장 5-5는 "불씨 둘(레벨 1·2)이면 레벨 3"이라고만 한다. 사본마다 값을 더하는 게임(세피리아)·가장 높은 것만 쓰는 게임에서 틀린다는 말과 우회가 없다(4절 1).
3. **아티팩트의 칸은 어디에**: 기믹 목록 1절·37장 5-5는 가방 조각의 원본 ID를 "아티팩트 = 패시브 ID"로 둔다. 그러나 등급·최대 ★·콤보·제약·무기·[고유]를 둘 곳이 패시브에 없고(17장 0-5), DB ID는 종류를 넘어 하나뿐이라(17장 1절) 인스턴스와 패시브를 다른 ID로 두고 `DataRef`로 잇는 모양을 스스로 정해야 했다.
4. **기믹 목록 2-4(능력치 함수) ↔ 관례 3절**: 2-4는 변환의 서·날개·베루트의 낫을 "능력치 함수 한 곳"에 쓰라고 하고, 관례 3절은 "조각 하나하나의 효과는 메인 룰 코드에 쓰지 않는다"고 한다. 능력치에 기여하는 코드를 붙일 `[BindTo]` 자리가 없어 둘이 부딪힌다(3절 '능력치 함수' 10개).
5. **기믹 목록 2-4·2-7(쌓기·진화 = 필드 바꾸기 사용자 자신) ↔ 37장 5-5(`lit`을 매번 다시 만듦)**: 둘을 같이 따르면 쌓은 값이 사라진다(4절 5).
6. **"N초마다 = 상태 효과의 주기"**(기믹 목록 2-7): 아티팩트가 꺼져도 주기가 돈다(꺼진 조각도 같은 id로 가방에 남아 걸린 것이 정리되지 않는다). 레벨마다 다른 간격도 못 쓴다. 패시브의 쿨다운 고리(2-3)가 맞는데 문서에 없다.
7. **제약을 어디서 거나**: 37장 5-4는 은접시·차가운 자물쇠·용골 파편을 패시브 발동의 '자리 검사'로 예시하고, 마지막 줄에서야 "늘 붙는 능력치는 계산 함수에서 켜고 끈다"고 한다. 세피리아의 `<제약>`은 아티팩트 전체(능력치 + 발동)를 끄므로 계산 함수 쪽 하나로 정해야 한다. 기믹 목록 2-1 "자리 조건 → 조건 '자리 검사'"도 같은 예를 든다.
8. **틀이 되는 칸이 좁다**: 값 틀은 '행동 직전 이벤트 고치기'·'필드 바꾸기'뿐이다. 레벨마다 다른 확률·쿨다운·중첩·발사 수가 세피리아의 대부분인데, 기믹 목록 2-5 "N% 확률 → 조건 '확률'", 2-10 "중첩·지속"에는 레벨 변형이 없다.
9. **`modifierTarget`은 객체 하나**(코드를 봤다: `FieldPaths.Resolve(…).FirstOrDefault()`): "모든 동료의 최대 HP +25%"를 동료 목록에 줄 수 없다는 말이 17장에 없다.
10. **'비용 지불' 행동 직전 이벤트에 누가 내는지가 없다**: 28장 4-14·기믹 목록 2-6. "왼쪽 칸 마법서의 MP 소모 −30%"는 거를 수 없어 프로젝트 행동 직전 이벤트를 따로 둬야 한다.
11. **자리 관계**: 37장의 자리 Block은 "고르기"와 "한 개체의 자리 검사"뿐이다. "이 피해를 낸 아티팩트가 내 윗 칸인가"(북향의 금빛 침·거대 망원경·헌신의 휘장)는 없다(B7).
12. **`Placement` 작은 것**(코드를 봤다: `Placement.cs`): `Pattern`이 줄 밖(x < 0, x ≥ 열 수)을 다음 줄로 넘기지 않고 버린다는 것이 2-5에 직접 적혀 있지 않다. `Indices`의 `includeSelf` 인자가 4-1 표에 없다. 왼편/오른편 절반·끝까지 가는 대각선(석판)은 자리·방향에 없어 코드로 쓴다.
13. **기믹 목록 2-4 "먹구름 → 눈보라 구름"**을 `statusId` 바꾸기로 들었지만 세피리아의 먹구름은 상태 효과가 아니라 자원 + 공격자다. 하위 시스템 스위치(`Game.Owned`)가 맞다.
14. **이름**: "레벨"이 셋이다(세피리아 ★ 0부터, GBible 패시브 레벨 1부터 = 가진 수, 콤보 개수를 레벨로). "증폭"(0 기준 능력치에 플랫)과 "피해량 +%"(퍼센트)의 구분은 28장 6절 한 줄에만 있다.
