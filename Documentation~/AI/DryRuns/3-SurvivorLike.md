## 2. AI의 질문 목록

기획 명세서 읽는 법 1·4절대로 바꾸기 비싼 것부터 모았다. 멀티는 "없음"이라 묻지 않는다. **질문은 7개**다.

**Q1. 적·보석·줍는 것을 어디에 두나, 이어 하기를 하나** (데이터 구조)
- 정하는 것: 적(체력)·보석(값·떨어진 자리)·줍는 것을 플레이어 데이터(판)에 두는지, 화면 쪽 오브젝트 풀에만 두는지. 끄고 켜면 판을 잇는지.
- 추천값: 판 데이터의 따로 키 `field`(세션 구역)에 적 `{ id, monster, hp }`·보석 `{ id, exp, x, y }`·줍는 것 `{ id, kind, x, y }`. 위치·속도·투사체는 화면 쪽 오브젝트 풀. 이어 하기는 Bootstrap '판 저장' = 끌 때 저장(다시 켜면 적은 Q3의 다시 놓기로 화면 밖 둘레에, 주인공은 맵 가운데).
- 이유: 적이 판 데이터에 있어야 피해·처치가 규칙 함수·행동 직전 이벤트·상태 효과·로그·도전과제를 그대로 탄다. 수백 개의 Sync는 측정값(가이드 09장 6절: 객체 2,500개 약 0.06ms)으로 보면 Sync 한 번에 0.02ms 안팎이다(3-0). 화면 쪽에만 두면 더 가볍지만 적에게 거는 효과(감속·빙결)를 DB로 못 만들고, 이어 하기·멀티 확장이 막힌다. '행동마다 저장'은 고르지 않는다(초당 30번 파일을 쓴다, 빈틈 16).
- 답이 없으면: 추천값으로 진행.

**Q2. 맞음·닿음·주움을 누가 정하나** (문법 밖)
- 정하는 것: 명중·접촉·줍기 판정의 자리.
- 추천값: 화면(물리 충돌)이 정해 틱마다 묶음 행동 하나(`TickRun { hits, contacts, pickups, visible }`, 대상은 id 글자)로 보낸다. 규칙은 그 목록으로 피해·처치·줍기를 계산한다. 무기 발사 시각도 화면이 게임 시계(`session.Clock.Time`)와 `Game.Attribute`(쿨다운·수·범위)로 정한다.
- 이유: 위치가 화면에 있다(Q1). 맞을 때마다 행동 하나면 초당 수백 행동이 되고 행동마다 Sync 2번·기록·참조 다시 찾기가 붙는다.
- 비용: 무기 동작 종류(6)마다 화면 코드, 충돌 수집기 하나. 판정이 기기마다 조금 다를 수 있다(멀티 없음이라 괜찮다).
- 답이 없으면: 추천값으로 진행.

**Q3. 화면 밖 적 다시 놓기** (문법 밖)
- 정하는 것: 다시 놓기를 규칙에 둘지 화면에 둘지, 보스도 하는지.
- 추천값: 화면 쪽만(데이터는 그대로, 행동 없음). 주인공과의 거리가 밸런스 값 `relocateDistance`를 넘으면 진행 방향 앞쪽 화면 밖 둘레에 놓는다. 보스 포함.
- 이유: 위치가 규칙 밖이고 규칙은 알 필요가 없다. 멀티로 가면 위치 권한이 필요해진다(빈틈 18).
- 답이 없으면: 추천값으로 진행.

**Q4. 화면 기준 효과(로자리오 '화면 안 전부', 반딧불 병 '가장 가까운 적', 번개 씨앗 '무작위 적')** (문법 밖)
- 정하는 것: 공간으로 정해지는 대상을 어떻게 규칙에 넘기나.
- 추천값: 화면이 후보 id 목록을 묶음 행동에 넣는다(`visible`). 로자리오는 그 목록 전부를 처치, 번개 씨앗은 규칙이 그 목록에서 `Game.Roll(목록, n, unique: true, stream: "lightning")`. 가장 가까운 적은 화면이 고르고 명중만 보낸다.
- 이유: '화면 안'·'가장 가까운'은 위치가 있어야 정해진다.
- 답이 없으면: 추천값으로 진행.

**Q5. "처치 100마다 다음 보석 2배(10초 동안)"의 뜻** (모호)
- 정하는 것: (a) 다음 보석 하나인가 10초 동안 줍는 모든 보석인가, (b) 10초 안에 다시 100을 채우면 4배인가 시간만 새로인가, (c) 처치 수는 판 처치 수인가.
- 추천값: 10초 동안 줍는 모든 보석 ×2, 다시 걸리면 시간만 10초로(겹치지 않음), 판 처치 수(사신 제외). 성장(+%)과는 곱이라 순서가 상관없다.
- 이유: 상태 효과 하나(게임 시간 10초 · 다시 걸 때 '지속 갱신')로 그대로 만들어진다.
- 답이 없으면: 추천값으로 진행.

**Q6. 레벨이 한 번에 여러 번 오를 때, 다시 뽑기·지우기의 모양** (흐름)
- 정하는 것: 쌓인 레벨업을 어떻게 묻나, 다시 뽑기는 몇 장을, 지우기 뒤에는 어떻게 채우나.
- 추천값: 쌓인 레벨 수만 기억하고 하나씩 묻는다(다음 후보는 앞 선택을 반영해 그때 뽑는다). 다시 뽑기 = 보이는 선택지 전부 새로. 지우기 = 고른 하나를 그 판의 풀에서 빼고 그 자리만 새로 채움(다시 뽑기 횟수는 쓰지 않음). 지운 것은 보물 상자에서도 안 나옴. 풀이 비면 금화 25 / 치킨(체력 30) 중 고르기.
- 이유: 후보를 한꺼번에 뽑으면 둘째 창에 이미 최대가 된 무기나 칸이 찬 뒤의 새 무기가 나온다(빈틈 9).
- 답이 없으면: 추천값으로 진행.

**Q7. 진화의 모양** (데이터)
- 정하는 것: 진화 무기의 칸·레벨, 짝 패시브 조건, 진화할 무기가 여럿일 때.
- 추천값: 진화 무기는 원래 무기 자리를 대신한다(칸 수 그대로), 최대 1레벨, 짝 패시브는 남는다. 짝 패시브는 레벨 1 이상이면 된다. 상자 하나에 진화 하나(먼저 얻은 무기부터), 진화한 상자는 레벨업을 주지 않는다. 진화 무기는 레벨업 풀에 나오지 않는다.
- 이유: 무기 칸 목록의 모양과 상자 결과 창이 이것으로 정해진다.
- 답이 없으면: 추천값으로 진행.

**추천값으로 정하고 알리는 것(묻지 않음)**

- Undo: 쓰지 않음(실시간이고 위치가 화면 쪽이라 스냅샷 되감기는 규칙 값만 돌아가 화면과 어긋난다 — 5-2 문서 부족 5).
- 고정 틱 30, 판 끝 이벤트 `RunEnded`, 시작할 때 이어 하기 끔(타이틀에 이어 하기 버튼), 슬롯 1개.
- 피해 공식: 적이 받는 피해 = 무기 레벨 피해 × (1 + 공격력), 방어 없음. 주인공이 받는 피해 = 접촉 피해 − 방어(최소 1). 명세서 2-1의 방어 정의를 따랐고 기본 공식(100/(100+방어))은 쓰지 않는다.
- 저주의 '적 수'는 스폰 수와 최대 적 수 둘 다에 곱한다.
- 설정: 기본 5개 + 피해 숫자 보이기·화면 흔들림(켜기/끄기). 키 바꾸기 켬(실시간). Steam 켬(App ID 480으로 시작).
- 고리: 사슬 한도 16.

### 3-0. 수백 개의 개체를 무엇으로 두나

| 개체 | 판 데이터(플레이어 데이터) | 화면 쪽 오브젝트 풀 | 고른 것 |
|---|---|---|---|
| 적(최대 300 × 저주) | `field.foes { id, monster, hp }` | 위치·속도·넉백·다시 놓기·애니메이션 | 나눠서 둘 다 |
| 투사체(수백, 수명 0.3~3초) | 넣지 않는다(매 프레임 바뀌고 짧게 산다 — 01장 5절 "매 프레임 바뀌는 값") | 전부 | 화면 쪽만 |
| 보석(≤ 400) | `field.gems { id, exp, x, y }`(자리는 떨어질 때 한 번 적고 안 바뀜) | 끌려옴(자석)·반짝임 | 나눠서 둘 다 |
| 줍는 것·화로 | `field.pickups { id, kind, x, y }` | 그림 | 나눠서 둘 다 |
| 주인공 | `run.hero`(체력·능력치) | 위치·이동 | 나눠서 둘 다 |

- **다른 것**(Unity ECS·Jobs·GPU 인스턴싱)은 화면 쪽 구현을 무엇으로 하느냐의 문제라 GBible과 부딪히지 않는다. 적이 1,000을 넘으면 화면 쪽만 바꾼다.
- **성능**(가정, 가이드 09장 6절 측정값을 객체 수에 비례시켜 본 것): 판 데이터 객체는 최대 약 800개 → Sync 한 번 약 0.02ms(Mono). 틱 30에서 행동이 초당 30개 → 행동 시작·끝 Sync 60번 + 프레임 끝 Sync 60번 ≈ 초당 2.4ms(프레임당 0.04ms). 이 정도는 문제가 아니다. 문제는 Sync가 아니라 **행동·이벤트·결과마다 붙는 기록 글과 할당**(빈틈 6), **행동 필드의 객체 목록 다시 찾기**(빈틈 3), **ViewList의 다시 그리기**(빈틈 5)다.
- **Undo**: 쓰지 않음. 스냅샷을 켜면 `field`가 되감겨 적 목록이 바뀌는데 위치는 화면에 있어 어긋난다.
- **저장**: 끌 때 저장. `field`가 저장되므로 적 체력·보석·상자가 이어진다. 위치는 다시 놓기로 복구(저장 직전에 위치를 담을 자리가 없다 — 빈틈 15).
- **멀티**(지금은 없음, 3요소 ②만 본다): 묶음 행동 하나 = ChangeSet 하나 = 패킷 하나. 명중 50개짜리 틱은 약 1.8KB(가이드 09장 "50유닛 광역기 약 1.8KB")라 초당 최대 약 50KB, 보통 10~20KB. 위치는 따로 보내야 한다(빈틈 18).

### 3-4. 진행 흐름(행동)

`StartRun { character }` → (틱마다) `TickRun { hits, contacts, pickups, visible }` → (레벨업이면) `TakeLevelUp { [Chosen] pick, shown }` → … → `EndRun { won }`(죽음·포기, 판 끝 이벤트 `RunEnded`). 타이틀: `BuyPowerUp { powerUp }` · `RefundPowerUps`.

```
프레임: 화면 쪽 Update — 이동·다시 놓기·무기 발사·투사체·충돌 → 수집기에 명중·접촉·주움·화면 안 적을 쌓는다
LateUpdate(GBibleRuntime): session.EndFrame → 틱마다 session.Ticked (33장 2-1)
  └ Ticked: 수집기를 비워 Game.Do(new TickRun { … })          ← 틱마다 행동 하나
       TickRun.Run: 스폰(시각이 됐으면) → 명중마다 Rules.Damage → 접촉 → 줍기 → 회복(1초마다)
       레벨이 오르면 pendingLevelUps++ → 기다리는 선택이 없으면 Rules.AskLevelUp → Game.Ask
  └ 레벨업 창(같은 ID momoi.choice, '열린 동안 게임 시간 멈춤') → 시간이 멈춰 틱도 멈춘다
  └ 프레임 끝 Sync · 다시 그리기(HUD = run, 적·보석 풀 = field)
```

- 씬 흐름: `run.scene`(빈 값 = 타이틀, `Garden` = 정원), DB › Bootstrap '씬 흐름'(32장 2-6).

### 3-5. 프로젝트 고유 기능

- 만들지 않는다. 트리거가 있는 패시브(부활초)는 상태 효과로, 판 규칙(처치 100마다)은 규칙 함수로 둔다. 명세서 읽는 법 2절은 "지니면 발동 = 프로젝트 고유 기능"이라 하지만, 레벨 = 중첩인 상태 효과가 같은 일을 DB만으로 한다(문서에 없는 방법, 빈틈 12).

### 3-10. 가중치 표·풀(레벨업 선택지 풀)

**레벨업 선택지 풀 = 코드 풀**(30장 4-4 `Game.Roll(풀, 개수, unique, stream)`, 5-10 "규칙이 계산한 후보").

```
Rules.LevelUpPool(game) → (원본 ID, 무게)들
  가진 무기  : 진화 무기가 아니고 level < Weapon.levels.Count        → (weapon, Weapon.weight)
  새 무기    : run.weapons.Count < weaponSlots, 해금, 안 가짐, !evolvedOnly → (id, Weapon.weight)
  가진 패시브: level < Passive.maxLevel                             → (passive, Passive.weight)
  새 패시브  : run.passives.Count < passiveSlots, 해금, 안 가짐        → (id, Passive.weight)
  빼기       : run.banished
뽑기: Game.Roll(풀, 3 + (운으로 1), unique: true, stream: "levelUp")
비면: DB 가중치 표 levelUpFallback(금화 25 · 치킨)에서 Game.Roll → 같은 창에
```

- 왜 DB 가중치 표가 아닌가: 줄 조건이 "이 줄의 항목을 가졌나·최대인가"를 모르고(조건이 컨텍스트 없이 `Evaluate(session)`만 받는다 — `WeightTables.cs`), '칸 6개가 찼으면 새것 빼기'를 줄마다 같은 조건으로 적어야 한다(빈틈 10). 무게는 원본(`Weapon.weight`)에 있어 기획자가 DB·CSV에서 고친다.
- 다시 뽑기는 같은 흐름(`levelUp`)에서 다시 뽑는다. 흐름이 앞으로 갔으므로 다른 결과가 나온다.
- 그 밖의 표(DB › 가중치 표): `levelUpFallback` · `brazierDrop`(금화 60·치킨 20·자석 10·로자리오 5·모래시계 5) · `eliteDrop`(보물 상자) · 웨이브마다 나올 적 표(`wave.m00` …). 상자 개수는 코드 풀(밸런스 값 무게, 빈틈 17).
- 난수 흐름(07장): `spawn` · `drop`(표는 `table:<ID>`가 따로) · `levelUp` · `chest` · `chestItem` · `crit` · `lightning`.

## 4. 기믹·효과 쪼개기

가이드(기획 명세서 읽는 법) 7절의 "언제 + 누구에게 + 무엇을 + 안전장치"로 쪼갰다. 판정은 3절의 시스템층이 있다고 보고 정했다.

**0. 명중·접촉·줍기(전투 전체의 바탕) — D**
- 언제: 화면 충돌(틱마다 모아서) · 누구에게: 화면이 준 id · 무엇을: 피해·처치·줍기.
- 부품: `session.Ticked`(33장 2-1·4-1) → `Game.Do(new TickRun { … })`, `Rules.Damage`·`Rules.Kill`·`Rules.Pickup`, `DamageIntent`(28장 4-7·4-8), `DamageDealt`·`EnemyKilled`(10장).
- 문법 밖인 것은 "맞았는가"뿐이고, 그 뒤는 모두 문법 안이다. 묶음의 대상은 id 글자 목록(객체 목록이면 요소마다 다시 찾는다 — 빈틈 3).

**1. 무기 진화 — B**(짝 하나 더하기는 A)
- 언제: 상자를 줍는 틱의 `TickRun` 안 `Rules.OpenChest` · 누구에게: 가진 무기 중 조건이 맞는 첫 무기 · 무엇을: 바꾸기(그 칸의 `weapon`을 진화 ID로, `level` 1) + `WeaponEvolved`를 쏜다.
- 조건(코드 `Rules.TryEvolve`): `level == Weapon.levels.Count` AND `evolvesTo` 있음 AND `run.passives`에 `evolvePassive`(레벨 1 이상) AND 진화 무기를 아직 안 가짐.
- 부품: 원본 칸 `evolvesTo`·`evolvePassive`(`[DataRef]`, 관례 8절), 상자 창(`SubscribeAfterAction<ChestOpened>` → `GameScreens.Open`, 35장 4-1). 도전과제 `firstEvolution`.
- 가정: `[DataRef(typeof(InstanceData))]`가 `Weapon` 인스턴스만 고르게 거르는지는 확인하지 못했다.

**2. 다시 뽑기(3회)·지우기(3회) — B**
- 언제: 레벨업 선택 대기 중 · 무엇을: 선택 요구를 고쳐서 다시.
- 부품: `Game.Ask(안내, ChoiceCandidate들, new TakeLevelUp { shown }, min: 1, max: 1, source: "levelUp")`(29장 4-8·4-11). 후보 = 보이는 선택지 + 조작 후보 `reroll`(남았을 때) + `banish.<id>`(선택지마다, 남았을 때). `TakeLevelUp`의 `[Chosen] string pick`(4-9)이 `reroll`이면 `run.rerolls--` 후 다시 `Rules.AskLevelUp`, `banish.<id>`면 `run.banished.Add(id)`·`run.banishes--` 후 그 자리만 새로 뽑아 다시 `Game.Ask`(이어서 할 행동 안의 `Ask` = 이어 고르기, 5-8 끝). 원본 ID면 `Rules.TakeItem` 후 `pendingLevelUps--`, 남았으면 다음 `Ask`.
- 화면: DB › 화면 `momoi.choice`(같은 ID로 바꿈, 35장 2-5) + `[BindTo]` 화면 코드, 버튼은 `Game.Answer(choice.id, "reroll")`. `OnClick(…, () => 행동)`은 선택 대기 중 `Busy`라 무시되므로 쓸 수 없다(빈틈 8).
- 가정: 조작 후보 id(`banish.whip`)가 `Answer`의 후보 검사를 그대로 지난다(후보 id는 글자라 된다고 봄).

**3. 처치 100마다 10초 동안 보석 경험치 2배 — C**
- 언제: 발동(처치 수가 100의 배수가 된 순간) + 지속(게임 시간 10초) · 누구에게: 주인공 · 무엇을: 경험치 행동 직전 이벤트 고치기 ×2.
- 부품: `Rules.Kill`에서 `run.kills % Balance(killMilestone) == 0`이면 `KillMilestone`을 쏘고 `Game.ApplyStatus(hero, GameIds.Status.ExpFrenzy)`(29장 4-1) — **처치 동사에 이정표를 넣는 중간층 확장**이다. DB로 못 하는 이유: 조건에 "N의 배수"가 없고(빈틈 11), 늘 켜진 판 규칙을 둘 DB 종류가 없다(빈틈 12).
- 상태 효과 `expFrenzy`(29장 3-1): 최대 중첩 1, 다시 걸 때 '지속 갱신', 지속 '게임 시간(초)' 10, 트리거 '행동 직전 이벤트 받기'(행동 직전 이벤트 '경험치'), 가진 쪽 필드 `targetId`, 결과 '행동 직전 이벤트 고치기' `amount` 곱하기 2(28장 3-4). HUD 남은 시간 = `ActiveStatus.remaining − Clock.Time`(29장 4-2).
- 가정: 레벨업 창으로 게임 시간이 멈추면 10초도 멈춘다(시간 지속은 게임 시계, 07장 2.10).

**4. 화면 밖 적 다시 놓기 — D**(화면 쪽으로 해결)
- 부품: 화면 쪽 적 이동 코드 + `Game.Balance(GameIds.Balance.RelocateDistance)`(행동 밖 읽기, 30장 2-1). 데이터·행동 없음.

**5. 자석(맵의 모든 보석) — B**
- 언제: 줍기 · 무엇을: `Rules.Pickup(magnet)` → `MagnetPicked`를 쏜다 → 화면이 모든 보석 오브젝트를 끌어온다 → 닿은 보석은 다음 틱들의 `TickRun.pickups`로.
- 부품: `PickupItem.kind`(키워드), `SubscribeAfterAction<MagnetPicked>`(32장 1절), 보석 오브젝트 풀.
- 가정: 끌려오는 중에 끄고 켜면 보석은 떨어진 자리로 돌아간다(끌려옴은 화면 상태).

**6. 저주받은 꽃잎(적 수 +10%, 받는 경험치 +10%) — A**
- 지속(가진 동안) · 주인공 · 능력치 보정 `curse` 플랫 +0.1, `growth` 플랫 +0.1(레벨마다).
- 부품: `Passive.perLevel` → `Rules.TakeItem`이 `Game.RemoveModifiers(passiveId, hero)` 뒤 레벨 × 값으로 `Game.AddModifier`(28장 4-3·4-4). `Rules.SpawnTick`이 `Game.Attribute(hero, "curse")`를 스폰 수·최대 적 수에, `Rules.GainExp`가 `growth`를 곱한다(28장 4-2). 시스템층이 둘을 읽어 두면 패시브는 DB만.

**7. 보물 상자 1·3·5개 — B**
- 부품: `Game.Roll(new[] { ("1", w1), ("3", w3), ("5", w5) }, 1, stream: "chest")`(30장 4-4), 무게 = `chestWeight1/3/5` + 운 보정. 올릴 무기는 가진 것 중 최대가 아닌 것에서 `Game.Roll(…, stream: "chestItem")`. DB 표로는 같은 더미 항목 세 줄 + 개수 1·3·5(30장 3-2 `minCount`) 꼼수가 된다(빈틈 17).

**8. 30:00 사신 — B**
- 부품: `Rules.SpawnTick`이 `minute >= reaperMinute`이면 `run.cleared = true`, `RunCleared`를 쏘고 사신을 스폰. 주인공이 죽으면 `EndRun { won = run.cleared }` → 판 끝 이벤트 `RunEnded`(Bootstrap, 20장 3절) → 판 저장 지움·프로필 저장.

**9. 보석 400개 상한 — B**
- `Rules.DropGem`: `field.gems.Count >= maxGems`면 `field.bigGemExp += exp`, 아니면 `Game.NewId("gem")`으로 보석 추가(빈틈 13).

**10. 영구 강화 가격 — B**(강화 하나 더하기는 A)
- 행동 `BuyPowerUp`: 가격 = `Rules.PowerUpPrice` = `baseCost × (1 + priceStepPerRank × rank) + pricePerPurchase × profile.purchases`, `Game.Pay(GameIds.PlayerData.Profile.Id, "gold", 가격, what: "gold.name")`(28장 4-12), `Game.AddModifier("hero", attribute, kind, value, "power." + id, permanent: true)`(28장 5-2). 되돌려 받기 = `Game.RemoveModifiers` + 금화. 화면은 같은 `Rules.PowerUpPrice`로 표시만(30장 5-3 끝).

**11. 운 → 4번째 선택지 — B**
- `Rules.AskLevelUp`: 개수 = 3 + (`Game.Random("levelUp").Chance(fourthChancePerLuck × Game.Attribute(hero, "luck"))` ? 1 : 0)(07장 2.2).

**12. 햇살 비료(공격력 +10%/레벨) — A**
- `Passive.perLevel` 한 줄 `might` 플랫 +0.1(합이 되게 플랫으로 — 28장 5-3·6절 "증폭은 플랫"). 무기 피해 = 레벨 피해 × (1 + `Game.Attribute(hero, "might")`).

**13. 부활초(부활 1회, 체력 50%) — A**
- 상태 효과 `revival`: 최대 중첩 0, 영구, 트리거 '행동 직전 이벤트 받기'(행동 직전 이벤트 '죽음'), 가진 쪽 필드 `unitId`, 결과: 행동 직전 이벤트 고치기 `막기` → 행동 직전 이벤트 고치기 `reviveHpRatio` 값으로 바꾸기 0.5 → 대상에게 효과(대상 비움 = 가진 쪽) → 상태 효과 풀기(`revival`, 1)(29장 3-1·3-2, 28장 3-4). 패시브 원본 `status = revival`이면 `Rules.TakeItem`이 레벨마다 한 중첩. `Rules.Kill(hero)`이 `DeathIntent`를 거친다(28장 5-3·5-5).
- 가정: 상태 효과 한 줄의 결과 목록이 위에서부터 차례로 돈다(행동 직전 이벤트를 고친 뒤 자기를 풂).

**14. 모래시계(10초 모든 적 정지) — B**
- 상태 효과 `timeFreeze`(게임 시간 10초, 트리거 없음 — 표시만)를 줍기 결과로 주인공에게 건다(A). 화면 쪽 적 이동이 `Game.HasStatus(hero, GameIds.Status.TimeFreeze)`를 읽고 멈춘다(B, 화면 코드 한 번). 적 수백에게 따로 걸지 않는다(`$statuses`가 수백 줄이 된다).

**15. 로자리오(화면 안 적 전부 처치) — D**(공간 대상)
- `TickRun.pickups`의 로자리오 + 화면이 넘긴 `visible` id 목록 → 그 적마다 `Rules.Kill`. 규칙은 목록을 믿는다.

**16. 물뿌리개(주변 오라: 0.5초마다 주변 적 피해) — B**(오라 무기 더하기는 A)
- 화면 동작 '오라'(`WeaponBehaviour.Aura`) 한 번 → 원본 수치(`levels`)로 오라 무기를 더한다. 넉백은 화면 몫.

**17. 번개 씨앗(무작위 적 n명에게 낙뢰) — B**
- 화면 동작 '낙뢰'가 `visible`을 넘기고, 규칙이 `Game.Roll(visible, n, unique: true, stream: "lightning")`(30장 4-4)로 고른 적에게 `Rules.Damage`. 결정론이 필요 없으면 화면이 고르고 명중만 보내도 된다.

**18. 엘리트 → 보물 상자, 화로 → 드롭 — A**
- `Monster.dropTable`(가중치 표 ID) → `Rules.Kill`이 `Game.Roll(dropTable, 1)`(30장 4-4·5-4) 결과를 `field.pickups`에. 표는 DB(무게·꽝·줄 조건 `run.minute` 이상).

**19. 피격 뒤 0.5초 무적 — B**

## 5. 빈틈 목록

제안에 적은 기능·API·칸 이름은 모두 안이다(넣기 전에 이름을 확인한다).

### 5-1. 빈틈

**빈틈 1. 장르 추천값에 '대량 실시간' 줄이 없다**
- 무엇: 가이드 07장 1절 표와 기획 명세서 읽는 법 2절 '1 시간'은 실시간이면 "고정 틱 30, Undo 스냅샷"뿐이다. 개체 수백일 때 Undo·판 저장·개체를 어디 둘지·묶음 행동·연출 방식의 추천이 없어 Q1·Q2를 매번 묻는다.
- 왜(얼마나 자주): 이 장르의 첫 결정이고, 틀리면 데이터 구조를 다시 짠다. 대량 실시간 프로젝트마다.
- 다른 장르: 타워 디펜스·탄막·RTS·실시간 로그라이트.
- 제안: 07장 1절에 줄 '대량 실시간'(Undo 쓰지 않음 · 판 저장 끌 때 또는 저장하지 않음 · 고정 틱 30 · 규칙 값만 플레이어 데이터, 위치·투사체는 화면 쪽 오브젝트 풀 · 틱마다 묶음 행동 · 연출은 대기열 밖 · 흐름 `spawn`·`drop`·`levelUp`). 기획 명세서 읽는 법 2절 '1 시간'에 "개체가 수백이면 이 줄" 갈래, 기획 명세서 2-1에 [선택] "한 화면의 최대 개체 수".
- 3요소: 문서만, 걸리는 것 없음. 해결: 가능(문서 수정).

**빈틈 2. 틱마다 결과를 묶어 보내는 행동 패턴이 없다**
- 무엇: 33장 5-1·관례 10절은 "규칙에 필요한 결과만 행동으로"까지만 말한다. 맞을 때마다 `Game.Do`하면 행동마다 Sync 2번·행동 기록·난수 상태 보관·Journal 한 줄·참조 다시 찾기가 붙는다.
- 왜: 서바이버는 초당 명중이 수백이다. 이 패턴을 AI가 매번 지어낸다.
- 다른 장르: 실시간 액션·디펜스·RTS·리듬 게임.
- 제안: 33장 5절에 예제 "틱마다 결과 묶음"(`TickRun { List<HitReport> hits }`, 수집기를 `Ticked`에서 비움, 대상은 id 글자) + 관례 10절 한 줄 "실시간의 결과는 틱당 행동 하나로 묶는다".
- 3요소: ②에 유리(한 묶음 = ChangeSet 하나 = 패킷 하나). 해결: 가능(문서 수정).

**빈틈 3. 행동 필드의 객체 목록은 요소마다 다시 찾는다**
- 무엇: `ActionReferences.Resolve`가 목록 필드의 요소마다 `Game.Find`를 부르고, `Find`는 키마다 Sync 뒤 사본을 훑는다(03장 2절). `Describe()`도 참조 id를 전부 글로 만든다(행동마다 두 번). 문서(관례 3절, 참조 2-1)는 "행동 필드에 객체를 넣어도 된다"만 말한다.
- 왜: 묶음 행동에 적 객체 50개를 넣으면 틱마다 50번 찾는다.
- 다른 장르: 광역기가 많은 전술·RTS(여러 유닛 명령).
- 제안: 문서 — 02장·관례 3절에 "요소가 많으면 id 글자 목록으로 받고 행동 안에서 한 번 훑어 찾는다". 라이브러리 — `Resolve`가 행동 하나에 id → 객체 색인을 한 번 만들어 쓰기(`DataIdentity`의 색인 재사용), `Describe`는 목록이면 "외 n개"로 줄이기.
- 3요소: 걸리는 것 없음(색인은 생성 코드 위). 해결: 가능.

**빈틈 4. 연출 대기열이 실시간과 맞지 않는다**
- 무엇: `GameView.Present`는 하나씩 차례로 돈다(32장 2-2). 남아 있으면 `Busy`라 `OnClick(…, 행동)`·`GameScreens.Do`가 무시되고, `Redraw`·`ViewList`·화면 `Draw`(기본 `WaitForPresentation` 참)가 미뤄진다. `ViewList.OnRemove`도 대기열이다. 피격·사망 이펙트를 문서대로(참조 2-4 "피해 숫자·죽는 모습을 차례로 → Present") 넣으면 HUD가 멈추고 사망 연출이 줄을 선다. 가이드 06장 실시간 칸은 "피격 이펙트는 이벤트를 받아 튼다"뿐이라 문서에서 찾기 어렵다.
- 왜: 실시간 장르의 모든 이펙트.
- 다른 장르: 실시간 액션·디펜스.
- 제안: 문서 — 32장 6절·가이드 06장·07장 6절에 "실시간 이펙트는 `SubscribeAfterAction`에서 바로 띄우고 `Present`를 쓰지 않는다, 화면은 `waitForPresentation: false`". 라이브러리 — `GameView.PlayNow(코루틴/done)`(대기열 밖·`Busy`에 안 셈·속도는 따름) 또는 DB › 화면 설정 '연출 기다리기 기본값'.
- 3요소: 걸리는 것 없음. 해결: 가능.

**빈틈 5. ViewList가 수백 개를 감당하지 못한다**
- 무엇: `ViewList`는 풀이 없고(`Instantiate`·`Destroy`), 다시 그릴 때마다 모든 항목에 `SetSiblingIndex`·`bind`, `ToList`·`HashSet`·`Dictionary`를 새로 만든다(`ViewList.cs`). `field`가 틱마다 바뀌면 초당 30번 × 300개.
- 왜: 적·보석·줍는 것 오브젝트를 데이터에 맞춰 그리는 자리라 AI가 늘 손으로 풀을 다시 만든다.
- 다른 장르: RTS·디펜스·방치형(유닛 수천)·탄막.
- 제안: `ViewList` 옵션 `pool: true`(꺼 두고 다시 씀) · `keepOrder: false`(순서 맞추기 끔) · `bindChanged: true`(ChangeSet 경로로 바뀐 항목만 bind) · `removeInParallel`(OnRemove를 대기열 밖에서) + 프리팹 대신 만들기 함수(`Func<TView>`) 생성자(빈틈 19).
- 3요소: ① 옵션이라 래퍼 아님, ③ 리플렉션 없음. 해결: 가능(라이브러리).

**빈틈 6. 기록(Journal) 글을 그 자리에서 만든다**
- 무엇: 이벤트를 쏠 때마다 `EventBus.Describe(evt)`(StringBuilder·박싱) + 받는 목록 `ToArray()`, 결과마다 `RunOutcomes`의 `outcome.Natural(session)`, Sync마다 키당 최대 12줄 `DescribeNatural`. `DescribeChanges`는 코드(`session.Data.DescribeChanges`)로만 끄고, 이벤트·결과 글은 끌 길이 없다.
- 왜: 명중 이벤트가 초당 수백이면 글·할당이 그만큼(가정: 초당 수십 KB의 가비지). 명중마다 DB 결과(사용 기능·상태 효과 결과)를 돌리면 더 커진다.
- 다른 장르: 모든 실시간·시뮬레이션·서버.
- 제안: `SessionOptions.JournalDetail`(`Full`·`Warnings`) + DB › Bootstrap 고급 '기록 자세히(개발 빌드만)', 또는 기록에 이벤트·결과 객체만 담고 모니터가 읽을 때 글을 만드는 게으른 기록. 가이드 09장 6절에 "초당 이벤트 수 기준" 한 줄.
- 3요소: ③ 생성 코드(`FieldAccess`)를 그대로 써 리플렉션 없음. 해결: 가능.

**빈틈 7. 선택을 기다리는 동안 게임 시계가 규칙 쪽에서 멈추지 않는다**
- 무엇: 멈춤은 화면의 '열린 동안 게임 시간 멈춤'(`GameTime` = `timeScale`)뿐이고 기본 고르기 창은 멈추지 않는다(`GameScreens.BuiltInSpec`의 `Choice` pause 거짓). `GameSession.EndFrame`은 `Choices.IsWaiting`을 보지 않는다. 화면이 없는 세션(테스트·서버)에서는 멈출 길이 없고, 창이 뜨기 전 한 프레임은 틱이 더 돌 수 있다(가정: 창은 다음 프레임에 `IsWaiting`을 보고 열린다).
- 왜: 실시간 게임의 레벨업·보상 고르기마다.
- 다른 장르: 실시간 로그라이트·RTS의 보상 선택·액션 게임의 상점.
- 제안: `SessionOptions.PauseClockWhileWaiting` + DB › Bootstrap '선택을 기다리는 동안 게임 시계 멈춤'(EndFrame이 기다리는 동안 틱·예약·시간 지속을 돌리지 않음).
- 3요소: ② 방장 시계가 멈춰 결정론에 맞다. 해결: 가능.

**빈틈 8. 선택 대기 중 선택을 고치는 입력(다시 뽑기·지우기)이 막힌다**
- 무엇: `GameView.Busy`가 `IsWaiting`을 포함해 `OnClick(…, 행동)`·`GameScreens.Do`가 선택 대기 중 행동을 보내지 않는다. 후보는 요구한 순간 `PendingChoice.options`에 고정된다. 우회는 조작 후보(`reroll`·`banish.<id>`)를 같은 `Ask`에 넣고 이어서 할 행동이 다시 `Ask`하는 것인데, 문서에 없고 다시 묻는 선택은 줄의 맨 뒤로 간다.
- 왜: 서바이버·덱빌딩(카드 보상 다시 뽑기)·로그라이트의 상점 새로고침.
- 다른 장르: 위와 같음.
- 제안: (a) 29장 5절 예제 "다시 뽑기·지우기·건너뛰기 횟수". (b) `Game.Reask(choiceId, 후보)` — 같은 id·같은 자리에서 후보만 바꿈(행동 안). (c) 행동 클래스 어트리뷰트 `[WhileChoosing]`가 붙으면 `GameScreens.Do`가 선택 대기 중에도 보낸다.
- 3요소: ① 어트리뷰트라 괜찮다. 해결: 가능.

**빈틈 9. 쌓인 선택은 후보가 미리 정해진다**
- 무엇: `Game.Ask`는 요구하는 순간 후보를 뽑는다. 큰 보석으로 3레벨이 오를 때 세 번 `Ask`하면 둘째·셋째 후보가 앞 선택을 모른다(최대가 된 무기·칸이 찬 뒤의 새 무기가 후보). 우회("쌓인 수만 저장하고 이어서 할 행동이 다음을 묻는다")가 문서에 없다.
- 왜: 레벨업이 겹치는 판마다.
- 다른 장르: 덱빌딩의 연속 보상, RPG의 연속 레벨업 스킬 선택.
- 제안: 29장 5절에 "차례로 묻기" 예제(`pending` 수 + 이어서 할 행동 끝에서 다음 `Ask`). 라이브러리로는 결과 '가중치 표에서 고르기'에 '앞 선택이 끝난 뒤 뽑기'(`deferRoll`).
- 3요소: 걸리는 것 없음. 해결: 가능(문서로 충분).

**빈틈 10. 가중치 표의 줄 조건이 "이 줄의 항목"을 모른다**
- 무엇: `WeightEntry.condition.Evaluate(session)`에 컨텍스트가 없어, "이 항목을 가졌고 최대가 아닐 때", "칸 6개가 찼으면 새것 빼기"를 줄마다 그 항목 id를 손으로 넣은 조건으로 적어야 한다. 목록 줄·뺄 목록에 요소 조건이 없어 "가진 무기 중 레벨 < 최대"를 고르지 못한다. 그래서 레벨업 풀을 코드 풀로 만들었다(3-10).
- 왜: 레벨업 풀은 이 장르의 핵심 표이고 기획자가 가장 자주 만지는 곳이다.
- 다른 장르: 덱빌딩 카드 보상(강화 안 된 카드만), RPG 상점(가진 장비 빼기), 가챠(천장).
- 제안: (1) 줄 조건에 `Context.Item`(그 줄의 항목 ID)을 주고 기본 조건 Block '이 항목이 목록에 있음(키 · 경로)'. (2) 목록 줄과 뺄 목록에 요소 조건 `listFilter`·`exclude[].filter`(ValueFilter, 요소마다). 원본 값(최대 레벨)과의 비교가 필요하면 데이터에 `maxed` 같은 값을 두는 방법을 예제로.
- 3요소: ③ 필드 경로·생성 코드 위라 리플렉션 없음. 해결: 가능.

**빈틈 11. "N마다(배수)" 조건이 없다**
- 무엇: `FieldOp`에 나머지 비교가 없고(`FieldPaths.cs`), 로그 '비교'도 이상·이하뿐이다. "처치 100마다"를 DB로 못 만들어 처치 동사에 넣었다(C).
- 왜: 이정표형 기믹은 흔하다.
- 다른 장르: "5층마다 상점", "10콤보마다", "3턴마다".
- 제안: `FieldOp.MultipleOf`(값이 N의 배수) + 로그 '비교'에 같은 연산. 또는 로그에 '구간 이벤트'(값이 N의 배수를 넘을 때마다 `StatCrossed { stat, value }`를 쏜다).
- 3요소: 걸리는 것 없음. 해결: 가능.

**빈틈 12. 늘 켜진 판 규칙·"지니면 발동(레벨)"을 둘 기본 DB 종류가 없다**
- 무엇: 도전과제는 한 번·Undo 밖, 로그는 기록만, 상태 효과는 누군가 걸어야 하고, 유물식 기능은 프로젝트가 만든다(17장). "처치 100마다 주인공에게 상태 효과"는 코드로 갔다. 레벨이 있는 패시브는 "레벨 = 중첩인 영구 상태 효과"로 DB만으로 되지만, 그 방법이 문서에 없다(문서에서 찾기 어려움). 대상 Block도 기본은 '사용자 자신'뿐이라 '주인공'을 프로젝트마다 만든다.
- 왜: 유물·패시브·판 규칙은 로그라이크 계열 모든 프로젝트에 있다.
- 다른 장르: 덱빌딩(유물), 액션 로그라이트(축복), RPG(패시브 스킬), 모든 장르의 난이도 규칙.
- 제안: 기본 DB 종류 '지니는 것'(가칭 `PerkData`): 가진 목록(플레이어 데이터 경로, 비우면 늘 켜짐 = 판 규칙) · 레벨 경로 · 레벨별 능력치 보정 · 트리거(이벤트·조건·행동 직전 이벤트 받기) → 결과 · 반복. 기본 대상 Block '플레이어 데이터의 개체'(키 · 경로)·'목록에서 무작위 n'(흐름 이름)·'목록 전부'. 그 전에 29장에 "영구 상태 효과를 패시브로" 예제.
- 3요소: 결과 실행은 지금의 `Triggers.Register`·`RunOutcomes` 그대로. 해결: 가능.

**빈틈 13. `Game.NewId`가 부를 때마다 데이터를 쓴다**
- 무엇: `NewId`는 `$id.<접두>`를 `Set`한다(그 키 Sync·기록 한 줄·`Changed`, 메타 구역). 초당 적 수십·보석 수십이면 기록과 알림이 그만큼이고, 키 없이 보는 `Redraw`가 다시 그린다.
- 왜: 대량 스폰마다.
- 다른 장르: 탄막·RTS·디펜스.
- 제안: `Game.NewIds(prefix, n)`(한 번에 n개), `$id.*` 내부 키는 기록 줄을 남기지 않기.
- 3요소: 걸리는 것 없음. 해결: 가능.

**빈틈 14. 게임 시계·시간 형식·막대 최댓값을 binding-path로 못 보인다**
- 무엇: 게임 시계는 플레이어 데이터가 아니라 binding-path(`키:경로`)로 못 읽는다. 틀 서식에 초 → mm:ss가 없다(`TextFormat`의 `time`은 `DateTime`만). ProgressBar의 `high-value`는 연결되지 않는다(35장 2-2). 화면 `Draw`는 데이터가 바뀔 때만이라 타이머는 `schedule.Every`를 쓰는 화면 코드가 된다.
- 왜: HUD의 남은 시간·경험치 막대·버프 남은 시간, 매 프로젝트.
- 다른 장르: 실시간 액션·방치형·스피드런 기록·쿨다운 표시.
- 제안: 예약 키 `clock:time`(프레임마다 다시 그림) · 틀 서식 `{value, duration}`(mm:ss / h:mm:ss) · `high-binding-path`(ProgressBar 최댓값) · 상태 효과 남은 시간 `status:<ID>.remaining`.
- 3요소: 걸리는 것 없음. 해결: 가능.

**빈틈 15. 판을 저장하기 직전에 화면 상태를 담을 기회가 없다**
- 무엇: '끌 때 저장'은 끌 때 바로 `SaveRun`한다. `GBibleRuntime`의 이벤트는 `Configuring`·`Started`·`Stopped`뿐이라 주인공 위치를 행동으로 담을 자리가 없다. 이어 하면 위치가 처음으로 돌아간다.
- 왜: 위치를 화면에 두는 실시간 게임의 이어 하기마다.
- 다른 장르: 실시간 액션·탐험.
- 제안: `GBibleRuntime.Saving`(판 저장 직전, 행동 밖 — 받는 쪽이 `Game.Do(new CapturePositions { … })`).
- 3요소: 걸리는 것 없음. 해결: 가능.

**빈틈 16. 판 저장 '행동마다'가 실시간에서 초당 수십 번이 된다**
- 무엇: `RunSaver`는 바깥 행동이 끝날 때마다 프레임 끝에 저장한다. 틱마다 행동이면 초당 30번 파일을 쓴다. 기획 명세서 읽는 법 2절은 "한 판이 길면(1시간 이상) 행동마다"를 권한다.
- 왜: 실시간 프로젝트가 이 추천을 따르면 바로 걸린다.
- 다른 장르: 모든 실시간.
- 제안: 문서 — 2절 그 줄에 "실시간이면 행동마다를 고르지 않는다". 라이브러리 — Bootstrap '행동마다 저장 최소 간격(초)'.
- 3요소: 걸리는 것 없음. 해결: 가능.

**빈틈 17. 가중치 표 항목이 DB 항목만이라 값(개수)을 뽑지 못한다**
- 무엇: 항목은 DB 항목 고르기다(30장 3-2). "상자 1·3·5개", "웨이브 크기"는 코드 풀이나 더미 항목 + 개수 꼼수가 된다.
- 왜: 보상 개수·등급 같은 값 뽑기.
- 다른 장르: 로그라이크 보상 개수, 가챠 등급.
- 제안: 줄 종류 '값'(글자·숫자 항목, `Game.Roll`이 그 글자를 돌려줌).
- 3요소: 걸리는 것 없음. 해결: 가능.

**빈틈 18. 대량 개체의 멀티: 위치 채널이 설계에 없다**
- 무엇: 가이드 11장·`TestMultiplayer.md` 유형 B는 "위치·속도는 별도 동기화(보간)"라고만 한다. 다시 놓기·충돌 판정·화면 안 목록이 모두 위치에 기대는데 그 권한·전송이 정해져 있지 않다. 규칙 값 ChangeSet은 틱마다 1~2KB(명중 50 기준)라 방장 한 명이 셋에게 보내면 초당 수백 KB까지 갈 수 있다(가정).
- 왜: 지금은 멀티 없음이라 이 프로젝트에는 걸리지 않는다. 협동 서바이버를 하면 첫 결정.
- 다른 장르: 실시간 협동 전부.
- 제안: 유형 B 설계(보류 중)에 "규칙 값 ChangeSet 20Hz 묶음 + 위치 스냅샷 채널(보간) + 판정 권한은 방장"을 명시. 대량 개체는 체력만 묶어 보내고 위치는 묶음 단위(떼)로.
- 3요소: ②가 정면이다. 지금 설계로는 규칙 값만 다룬다. 해결: 설계 문서로 가능(구현은 보류).

**빈틈 19. AI가 씬 오브젝트 원형(프리팹)을 만들 수 없다**
- 무엇: 관례 6절은 "프리팹·인스펙터 연결은 쓰지 않는다", `ViewList`는 프리팹이 있어야 한다. 서바이버는 적·투사체·보석·줍는 것 원형이 여럿이라, 사람이 프리팹을 만들기 전까지 화면을 못 띄운다. 코드로 `GameObject` + `SpriteRenderer` + 콜라이더를 만드는 길은 되지만 문서에 없다.
- 왜: 씬 오브젝트가 많은 장르마다.
- 다른 장르: 액션·디펜스·퍼즐(타일).
- 제안: 관례 6절에 "씬 오브젝트는 코드로 만들고(스프라이트는 DB 원본의 칸), 사람이 나중에 프리팹으로 바꿀 수 있게"를 허용. `ViewList`·제안한 풀에 `Func<TView>` 생성자.
- 3요소: ① 생성자 하나 더라 괜찮다. 해결: 가능.

### 5-2. 문서 오류·부족

1. **참조 6절 "Undo 보관 수(행동 단위) 200(Bootstrap)"** — 코드 기본값은 0(제한 없음)이다(`GameDatabase.historyLimit` 기본, 매뉴얼 20장 3절 표도 0). 200은 카드 던전의 값·추천값이다. → "기본 0, 추천 200"으로.
2. **35장 2-5 "고르기 창을 따로 만들었으면 '고르기 창 저절로'를 끈다"** — 같은 ID(`momoi.choice`)로 바꾸면 저절로가 그 DB 항목을 연다(`GameScreens`가 `Open(Choice)` → DB 항목). 끄면 안 열린다. → "같은 ID로 바꾸면 켜 둔다, 다른 ID로 따로 만들면 끈다. 실시간이면 그 항목의 '열린 동안 게임 시간 멈춤'을 켠다".
3. **"물리 충돌 결과 = 문법 밖"(기획 명세서 읽는 법 7절 마지막 줄·관례 13절) ↔ 33장 1절 "물리·이동은 화면, 결과만 행동"** — 모순이다. 서바이버는 거의 모든 피해가 충돌이라 문서대로면 전투 전체를 문법 밖으로 묻게 된다. → "물리·공간이 정한 사실(맞음·닿음·화면 안)을 행동의 입력으로 받으면 문법 안, 규칙이 그 사실을 스스로 계산해야 하면 밖".
4. **33장 5-1 예제 `ArenaRules`** — 규칙 클래스에 `using UnityEngine`·`[RuntimeInitializeOnLoadMethod]`·`GBibleRuntime.Started +=`가 있다. 관례 1절(Rules에 화면 API 없음, 서버·테스트에서도 같은 코드)·17장 2-6(연결은 Client의 `Bootstrap.Started` 한 곳)과 어긋난다. Rules 어셈블리가 `GBible.Unity`·UnityEngine을 참조하므로(`StartSetup.ReferencesOf`) 컴파일은 되어서, AI가 그대로 옮겨도 아무도 막지 않는다. → 틱 규칙은 `ArenaRules.Tick(session)`만 Rules에, 연결은 `Bootstrap.Started`에.
5. **기획 명세서 읽는 법 2절 '1 시간 | 실시간 → Undo 스냅샷'**(가이드 07장 6절도) — 위치를 화면에 두라는 규칙과 함께 쓰면 되감은 뒤 규칙 값과 화면이 어긋난다(목록이 되감기면 화면 오브젝트가 처음 자리로)는 말이 없다(부족). → "위치를 화면에 두고 개체가 생기고 사라지는 실시간이면 Undo 쓰지 않음".
6. **참조 2-4 "피해 숫자·죽는 모습을 차례로 → Present"·32장** — 실시간이면 쓰지 말라는 말이 없다(부족, 빈틈 4).

## 6. 하루 안에 시스템층 + 화면을 끝낼 수 있나

**판단: 조건부로 된다.** 질문 7개에 추천값으로 답을 받고, 무기 동작 종류를 처음에 3~4개(베기·투사체·오라·궤도)로 줄이면 하루 안에 된다. 6개를 모두 넣고 손맛까지 맞추려면 빠듯하다.

- **GBible이 거의 다 주는 것(규칙층)**: 데이터·행동·고정 틱·상태 효과(2배·무적·정지·부활)·Modifier(패시브·영구 강화)·밸런스 곡선·가중치 표(드롭)·선택 대기(레벨업)·로그·도전과제·저장·씬 흐름·설정·Steam. 규칙층은 문법 안에서 막힘 없이 나온다(C 1개, A·B가 대부분).
- **GBible 밖이라 처음부터 짜는 것(화면 쪽 실시간 층)**: 적·투사체·보석 오브젝트 풀, 이동·다시 놓기, 충돌 수집기와 틱 묶음 보내기, 무기 동작 종류별 스크립트, 자석 끌기, 카메라, 대기열 밖 이펙트. `ViewList`·`Present`는 이 장르에 맞지 않아 대신 짜야 한다(빈틈 4·5). 이것이 하루를 가르는 곳이다.
- **화면(UI)**: HUD·레벨업 창(같은 ID 교체)·상자 창·결과·타이틀·캐릭터 고르기·영구 강화. binding-path와 기본 화면(일시정지·설정·확인·알림)이 받쳐 줘서 막히지 않는다. 타이머·막대 최댓값은 화면 코드(빈틈 14).
- **사람이 해야 하는 것**: 그림·프리팹(빈틈 19 — 코드로 만든 임시 오브젝트로 대신할 수 있다), Unity에서 실제 프레임 시간 확인(적 300·투사체 수백). AI는 성능을 직접 볼 수 없으므로 5-3의 가정이 맞는지는 플레이로 확인해야 한다.
- **하루를 넘기게 하는 위험**: 묶음 행동·차례로 묻기·조작 후보 같은 패턴을 AI가 문서 없이 지어내는 동안 생기는 되돌림(빈틈 2·8·9). 이 셋이 문서에 들어가면 위험이 크게 준다.
