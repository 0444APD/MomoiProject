# 장르 시험 5 — 방치형 클리커 (모모이 베이커리)

GBible의 목표("정해진 양식의 기획 명세서 + GBible 문서·규칙 → AI가 레벨 디자인을 뺀 시스템·UI를 하루 안에, 질문 20개 이하로")를 방치형 클리커 하나로 시험해 **빈틈**을 찾은 기록이다. 코드는 고치지 않았다. 문서와 코드가 다른 곳은 코드를 기준으로 적고, 그 차이도 빈틈으로 적었다.

이 문서에서 쓰는 말:

| 말 | 뜻 |
|---|---|
| BigNum (임시 이름) | double(약 1.8e308까지, 유효 숫자 15~17자리)로 모자란 수를 담는 값 형식. 가수(double, 1 이상 10 미만) + 지수(long). 이 시험에서는 GBible에 없어서 프로젝트 코드로 만든다고 본다 |
| 정산 (Settle) | 지난 정산 뒤 흐른 시간만큼 초당 생산을 쿠키에 더하는 행동. 가이드 07장 6절이 쓰는 말 |
| 현실 시각 | 컴퓨터 시계의 UTC 시각. 게임 시계(`session.Clock`, 게임이 켜져 있는 동안만 흐르고 판을 불러오면 저장한 시각으로 돌아간다)와 다르다 |
| 판 / 프로필 | 세션 구역(`run`) / 메타 구역(`profile`). 이 게임에서 판 = 환생 한 주기 |
| 빵집 | 전체 배율·클릭 힘을 가진 객체(`id = "bakery"`). 상태 효과·Modifier가 붙는 쪽 |
| 천상칩 | 환생할 때 얻는 영구 재화. 하나마다 생산 +1% |
| 판정 A~D | A = DB만, B = 코드 한 단위(Block·`[BindTo]`·행동 하나), C = 중간층 확장(규칙 함수·행동 직전 이벤트 자리·DB 종류), D = 문법 밖 |

새로 제안한 이름(BigNum, `Game.UtcNow`, `GBibleRuntime.RunLoaded` …)은 모두 임시 이름이다.

## 1. 기획 명세서 — 모모이 베이커리

### 0. 한 줄 소개

- 장르·참고 게임: 방치형 클리커(Cookie Clicker, Adventure Capitalist).
- 한 문장 소개: 모모이가 큰 쿠키를 눌러 쿠키를 굽고, 건물을 사서 저절로 굽게 하고, 환생해서 더 빨리 굽는다.

- 플레이 한 판의 길이: 환생 한 번까지 몇 시간~하루(꺼 둔 시간 포함).

### 1. 한 판의 흐름

- 시간: 실시간. 켜 두면 초마다 쿠키가 늘고, 꺼 둔 시간도 일부 계산한다(5절).
- 한 판: 쿠키 0에서 시작 → 큰 쿠키를 눌러 쿠키 → 건물을 사서 초당 생산 → 업그레이드로 배율 → 가끔 황금 쿠키 → 쿠키가 충분히 쌓이면 환생(천상칩을 받고 쿠키·건물·업그레이드·버프가 처음으로) → 다시.
- 반복 단위: 따로 없다(초마다 생산). 플레이어는 큰 쿠키 누르기·건물과 업그레이드 사기·황금 쿠키 누르기·환생을 한다.
- 판이 끝나는 때: 플레이어가 환생을 고를 때(얻을 천상칩이 1 이상일 때만 버튼이 켜진다). 패배는 없다.
- 판이 끝나도 남는 것: 천상칩, 전체 누적 생산, 도전과제, 통계(클릭 수·황금 쿠키 누른 수·환생 수).

## 2. AI의 질문 목록

명세서·관례·참조 문서로 정해지지 않고 나중에 바꾸기 비싼 것만 묻는다(PlanningSpecGuide 4절, 바꾸기 비싼 순서). **질문 3개**, 그리고 시스템 목록 확인 1번(3절)이다.

### 2-1. 질문

**Q1. 판과 프로필을 어떻게 나누나** (데이터 구조)
- 정하는 것: 쿠키·건물·업그레이드·버프를 판(세션 구역)에, 천상칩·누적·도전과제를 프로필에 둘지, 판 저장을 켤지.
- 추천값: 판 = 환생 한 주기. `run`(세션): 쿠키·이번 판 누적·건물·산 업그레이드·시너지·황금 쿠키. `profile`(메타): 천상칩·전체 누적·환생 수. 판 저장 켬('끌 때 저장' + 30초마다), 판 끝 이벤트 = 환생(`Ascended`), 시작할 때 이어 하기 켬.
- 이유: 가이드 07장 1절 표의 방치형 기본(모두 프로필·판 저장 안 함)으로 가면, 상태 효과(`$statuses`)·예약(`$schedule`)·이번 판 Modifier(`$modifiers`)가 세션 구역이라 껐다 켜면 버프·황금 쿠키 예약이 사라지고, 환생 초기화를 필드마다 손으로 써야 한다. 판으로 두면 환생 = `GBibleRuntime.NewRun` 한 줄이고, 업그레이드 보정·버프·예약이 저절로 비워진다.
- 답이 없으면: 추천값으로 진행.

**Q2. 1e308을 넘는 값은 어디까지인가** (문법 밖 — 큰 수)
- 정하는 것: BigNum을 쓸 값의 범위. GBible의 숫자 칸(플레이어 데이터에 주기·비용 내기·플레이어 데이터 검사·스탯·Modifier·밸런싱 값·로그·행동 직전 이벤트 고치기·binding-path·CSV)은 모두 double이라, BigNum 값에는 그 DB Block을 쓰지 못하고 프로젝트 Block으로 바꾼다.
- 추천값: BigNum = 쿠키·이번 판/전체 누적 생산·초당 생산·건물과 업그레이드 가격. double = 배율(업그레이드·버프·천상칩·우유), 개수, 천상칩 수, 비율. 대신 만드는 Block: '쿠키 주기'·'쿠키 검사'·'N초분 생산', 비용은 규칙 함수 `Rules.Spend`.
- 이유: 배율이 1e308 안이면 스탯·Modifier·상태 효과 보정(DB 조립)이 그대로 산다. 가격을 double로 두면 1e300을 넘는 쿠키를 쓸 곳이 없다.
- 답이 없으면: 추천값. 배율도 1e308을 넘는다고 하면 스탯·Modifier를 쓰지 못하고 배율 계산이 모두 코드로 간다(되돌리기 비싸서 묻는다).

**Q3. 꺼 둔 시간을 무엇으로 재나** (문법 밖 — 현실 시간)
- 정하는 것: 오프라인 시간의 근거와 시계 조작 대책.
- 추천값: 컴퓨터 시계(UTC). 정산 행동마다 현실 시각을 행동 필드로 받고(화면 쪽이 `DateTime.UtcNow.Ticks`를 넣는다), "현실 경과 − 게임 시계 경과"를 꺼 둔 시간으로 본다. 0 미만(시계를 뒤로 돌림)은 0, 8시간에서 자른다. 시계를 앞으로 돌리는 조작은 8시간 상한까지 그대로 둔다.
- 이유: 규칙은 `DateTime`을 쓰지 않고(관례 3절) 게임 시계는 켜져 있는 동안만 흐른다(07장 2.5). 행동 필드로 받으면 기록·이어 하기·나중의 서버 판정과 맞는다. 차이로 재면 끄기 직전 훅이 없어도(빈틈 7) 끄기·튕김·창 내림·일시정지가 모두 같은 규칙으로 처리된다.
- 답이 없으면: 추천값. Steam 서버 시각 같은 조작 막기가 필요하면 별도 시스템(문법 밖)이다.

### 2-2. 묻지 않고 정해서 알릴 것

| 정한 것 | 값 | 근거 |
|---|---|---|
| Undo 방식 | 쓰지 않음 | 가이드 07장 1절(명세서 1절 빈칸) |
| 고정 틱 | 초당 10 | 시간 규칙이 초 단위. PlanningSpecGuide 2절의 실시간 기본 30보다 낮게 |

### 3-1. 데이터

```csharp
// Rules/Data/IdleData.cs (BigNum은 Rules/Numbers/BigNum.cs — 프로젝트 코드)
[Serializable] public class RunState                 // 플레이어 데이터 run(세션)
{
    public BigNum cookies, bakedThisRun, cps;          // cps = 마지막 정산 때 초당 생산(화면 보간·오프라인용)
    public double lastSettledAt, nextSettleAt;         // 게임 시계 기준
    public long lastUtc;                               // 마지막 정산의 현실 시각(행동 필드로 받은 UTC ticks)
    public Bakery bakery = new Bakery();
    public List<Building> buildings = new List<Building>();      // 처음 산 때 만든다
    public List<string> upgrades = new List<string>();           // 산 업그레이드 원본 ID
    public List<Synergy> synergies = new List<Synergy>();
    public List<GoldenCookie> goldens = new List<GoldenCookie>();
}
[Serializable] public class Bakery { public string id = "bakery"; public double mult = 1, clickBase = 1, clickCpsRatio, milkPower = 1; }   // 숫자 필드 = 스탯
[Serializable] public class Building { public string id; public int count; public double mult = 1; }    // id = 건물 원본 ID
[Serializable] public class Synergy { public string from, to, source; public int per = 100; public double percent = 0.01; }
[Serializable] public class GoldenCookie { public string id; public double x, y, expiresAt; }
[Serializable] public class Profile { public double chips; public BigNum bakedAllTime; public int ascensions; }   // profile(메타)
```

> **초당 생산을 매 프레임 플레이어 데이터에 더하지 않는다.**
> - 행동 단위: 정산 한 번 = 행동 하나(`Settle`), 클릭 한 번 = 행동 하나. 쿠키를 쓰는 행동(사기·황금 쿠키·환생)은 그 행동 안에서 먼저 `Rules.Settle`을 부른다. 사기가 실패하면 그 정산도 함께 취소되지만, 다음 정산이 같은 구간을 다시 계산하므로 잃는 것은 없다.
> - Undo: 쓰지 않음. 행동마다 이전 값을 보관하지 않는다. 실패 취소·미리보기(`Game.Preview`)는 트랜잭션으로 되돌리므로 그대로 된다(Actions.cs `Preview`).
> - 저장: '행동마다 저장'은 쓰지 않는다. 정산마다(1초), 클릭하는 동안은 프레임마다 `run.json`·`slot.json`을 쓰게 된다(RunSaver는 행동이 있었던 프레임 끝마다 저장). '끌 때 저장' + 30초마다 저장. 튕기면 마지막 저장 뒤 진행을 잃고, 그 시간은 다음 정산이 오프라인(50%)으로 메운다.
> - 화면: 쿠키 수는 `run.cookies + run.cps × (Clock.Time − run.lastSettledAt)`로 매 프레임 보간해 그린다(화면 코드, 데이터는 바꾸지 않는다).
> - `Update`에서 직접 더하면 행동 밖 변경이다(관례 3절·10절). 매 프레임 행동으로 더하면 4-2(3)의 비용이 든다.

- 유닛 클래스: 없음. 스탯을 가진 객체는 `Bakery`(mult·clickBase·clickCpsRatio·milkPower)와 `Building`(mult).

### 3-3. 핵심 동사

| 동사 | 규칙 함수 | 행동 직전 이벤트(필드) | 끝난 뒤 이벤트 |

- BigNum 필드는 '행동 직전 이벤트 고치기'가 고치지 못하므로(숫자 형식만, Intercepts.cs) 행동 직전 이벤트에는 double `multiplier`를 둔다. 이벤트의 BigNum은 트리거 필터가 읽지 못하므로 double `log10`을 함께 넣는다.
- `Game.Pay`는 쓰지 않는다(double만 낸다). 가격 행동 직전 이벤트 자리는 `PriceIntent`가 맡는다.

### 3-4. 진행 흐름

- 행동: `StartRun`(새 판 행동: 빵집, 첫 황금 쿠키 예약, `nextSettleAt`) → `Settle { utc }`(1초마다) · `Click` · `BuyBuilding { building, count }`(1·10·-1 = 최대) · `BuyUpgrade { upgrade }` · `SpawnGolden` · `DespawnGolden { golden }`(예약) · `ClickGolden { golden }` → `Ascend`(판 끝 이벤트 `Ascended`) → 화면이 `GBibleRuntime.NewRun` + `StartRun`.
- 반복 단위의 행동: `Settle`. 셀 이벤트는 없다(시간 지속만).
- 씬 흐름: 없음(씬 하나).
- Client `Bootstrap.Started` 연결: `session.Ticked += _ => IdleRules.Tick(session, DateTime.UtcNow.Ticks)`(시각이 되면 `Settle`을 `Do`), 30초마다 저장, `SubscribeAfterAction` 연출(떠오르는 숫자는 `GameView.Present` 없이 `GameScreens.Overlay`에 바로 — 빈틈 11), `OfflineRewarded` → 오프라인 창, `AchievementUnlocked` → 알림.

### 4-2. 따로 따진 것

**(1) 큰 수 — double 한계.**
- double은 약 1.8e308에서 무한대가 되고 유효 숫자는 15~17자리다. GBible에서 double로 묶인 곳(코드 확인):
  - `Game.Pay`·`CanPay`: 원시 숫자 형식·decimal 필드만 받고 double로 읽고 쓴다(GameApi.cs `ReadNumber`). 실패 글의 `{have}`·`{need}`도 `"0.##"`.
  - '플레이어 데이터에 주기'(`PlayerDataReward.amount` double, `TypeResolver.IsNumeric` 형식만), '플레이어 데이터 검사'(FieldPaths `Compare` → `TryNumber`), '행동 직전 이벤트 고치기'(Intercepts.cs, 숫자 형식만).
  - 스탯·Modifier(Attributes.cs `BaseOf` → `Convert.ToDouble`), 밸런싱 값·곡선(double), 로그(`Stats` double, 저장 스키마 `Double`).
  - binding-path(ScreenBinding `Format`: double은 `"0.##"`, 그 밖에는 `IFormattable.ToString(null, Invariant)`), 텍스트 서식(`FormatNumber(double)`).
- BigNum 구조체는 저장·Sync에는 들어간다(MirrorWeaver가 `[Serializable]` 구조체 비교 코드를 만든다 — Unity에서 확인 안 함, 가정). DB Block·CSV·DB 입력 칸은 숫자로 다루지 않는다.
- binding-path에 BigNum을 걸면 BigNum의 `ToString`이 쓰인다. 설정의 표기를 따르게 하려면 BigNum이 전역 설정을 읽어야 하는데, 규칙 어셈블리의 static 상태라 관례 3절에 걸린다 → 화면 코드로 그린다.
- 정밀도: 가수가 double이라 큰 쿠키에 작은 생산을 더하면 사라진다(1e20 + 0.1). 생산이 쿠키와 함께 커지는 장르라 보통 드러나지 않는다(가정).

**(2) 현실 시간 — 오프라인.**
- 게임 시계는 켜져 있는 동안만 흐르고, 판을 불러오면 저장한 시각으로 돌아간다(07장 2.5·3절). 시간 예약은 영구로 둘 수 없다(29장 2-5). 규칙은 `DateTime`을 쓰지 않는다(관례 3절).
- `GBibleRuntime.Stopped`는 저장이 끝난 뒤 불린다(20장 4절, GBibleRuntime.cs `Stop`) → 끄기 직전에 "마지막 접속 시각"을 행동으로 남길 자리가 없다.
- `slot.json`의 `savedAt`은 `DateTime.Now`(지역 시각, GBibleRuntime.cs `WriteSlotInfo`)라 시간대·여름 시간이 바뀌면 틀린다 → 쓰지 않는다.
- 그래서 Q3의 방식: 정산 행동마다 `utc`를 받아 `run.lastUtc`에 적고, 다음 정산에서 (utc − lastUtc) − (Clock.Time − lastSettledAt)를 꺼 둔 시간으로 본다.

**(3) 매 프레임 생산의 비용.**
- 60fps에서 프레임마다 행동이면 초당 행동 60개다. 행동마다 기록(Journal, 기본 4096줄)이 쌓여 타임라인이 1분 남짓에 밀리고, 행동 시작·끝의 Sync와 조건 다시 평가(쿠키를 읽는 도전과제 조건 수십 개)가 매 프레임 돈다. '행동마다 저장'·'프로필도 행동마다 저장'이면 프레임마다 파일을 쓴다(RunSaver `FrameEnd`). Undo 쓰지 않음이라 기록 메모리는 들지 않는다.
- 1초 정산이면 위가 모두 초당 한 번이다. Sync 자체는 행동과 상관없이 매 프레임 한 번 돈다(GameSession `EndFrame`) — 데이터가 작아 가볍다.
- 클릭은 행동 하나씩이다(초당 10~20번). 저장을 '끌 때 + 30초마다'로 두면 문제 없다.

### 4-3. 가정

1. BigNum `[Serializable] struct`가 플레이어 데이터·저장·Sync에서 그대로 돈다(코드상 구조체 생성 코드가 있다).
2. DB 인스턴스 편집기에서 BigNum 필드는 가수·지수 두 칸으로 보인다(한 칸 "1.5e320" 입력은 안 된다).
3. 배율(업그레이드 곱·천상칩·우유)의 곱은 1e308 안이다(Q2).
4. 프렌지가 시간으로 끝날 때, 보정이 끝날 때 결과보다 먼저 떨어지고(Statuses.cs `Expire`: `Drop` → `Run`) 끝남 이벤트가 없어서, 마지막 정산 뒤 끝나기까지의 몫(정산 간격 이하)은 ×1로 계산된다. 기획자가 알아채지 못할 크기로 본다.
5. Run In Background는 프로젝트 설정에서 켠다(GBible은 건드리지 않는다).
6. `SimpleCondition`이 읽은 키를 감시기가 모으므로(11장 4-4), 쿠키 검사 도전과제 수십 개가 정산마다 다시 평가돼도 가볍다.

## 5. 빈틈 목록

### 5-1. GBible에 없는 것

**빈틈 1. 큰 수 형식이 없고, 모든 숫자 칸이 double이다**
- 무엇: 1.8e308을 넘는 값을 담을 형식이 없다. 비용 내기·주기·검사·스탯·밸런싱 값·로그·행동 직전 이벤트 고치기·CSV·DB 입력·binding-path·텍스트 서식이 모두 double(4-2(1)).
- 왜: 방치형이면 쿠키·가격·누적이 모두 여기 걸려 매 프로젝트 BigNum과 대체 Block을 새로 만든다. 1e15를 넘으면 정수 정밀도도 잃는다.
- 다른 장르에도: 수집형 후반 피해 인플레, 경영 시뮬의 돈, 증분 게임 전부.
- 제안: 코어 `BigNum`(임시) `[Serializable] struct { double mantissa; long exponent; }` + 연산자(`+ − × ÷`, 비교, double과 섞기)·`Pow`·`Log10`·`Root`·`Parse("1.5e320")`·`IFormattable`("sci"·"short"). `TypeResolver.IsNumeric`류 "숫자로 보는 형식"에 넣어 '플레이어 데이터에 주기'·'비용 내기'(`Game.Pay(키, 경로, BigNum)` 오버로드)·'플레이어 데이터 검사'·로그(`StatData` 값 형식)·'행동 직전 이벤트 고치기'(곱하기)·CSV 한 칸·DB 입력 칸이 받게 한다. 그 전까지 문서(참조 6절 "정해진 숫자")에 "숫자 칸은 double, 1e308·정밀도 15자리"와 "큰 수 행동 직전 이벤트에는 double `multiplier`를 둔다"를 적는다.
- 3요소: ① 새 형식이지만 필요한 필드만 쓰고 연산자로 평소처럼 계산한다(기존 숫자를 감싸라고 강요하지 않는다) ② 16바이트 값 형식, Mirror 생성 코드로 비교·전송 ③ 리플렉션 없음(형식 등록은 시작 때).
- 해결: 가능 · 코어에 값 형식 하나 + 숫자 Block들의 형식 분기.

**빈틈 2. 현실 시각이 없다**
- 무엇: 규칙은 `DateTime` 금지, 게임 시계는 켜져 있을 때만 흐른다. 규칙이 "지금 몇 시인가"를 아는 길이 없어 행동 필드로 받는 관례를 매번 만든다.
- 왜: 오프라인 보상이 있는 게임은 모두. 정산마다 쓴다.
- 다른 장르에도: 수집형(일일 보상·출석·스태미나 충전), 이벤트 기간, 시즌 패스.
- 제안: 호스트가 행동마다 `tick`처럼 UTC를 찍고(`GameAction.utc`, 임시) 규칙은 `Game.UtcNow`로 읽는다. 판 저장·프로필 저장에 `savedUtc`를 남기고 `Game.OfflineSeconds`(마지막 저장 ~ 지금)를 준다. 멀티면 서버가 찍는다. 가이드 07장 6절에 "현실 경과 − 게임 경과" 방식 예를 둔다.
- 3요소: ① 프로젝트 코드가 준다 ② 행동마다 8바이트 ③ 없음.
- 해결: 가능 · 행동 기록에 칸 하나 + API 하나.

**빈틈 3. 주기 저장이 없다**
- 무엇: 판 저장은 끌 때 / 행동마다 / 안 함뿐이다. 행동마다는 행동이 있었던 프레임마다 쓴다(클릭 연타 중이면 프레임마다). 튕기면 '끌 때'는 돌지 않는다.
- 왜: 방치형은 몇 시간씩 켜 두므로 늘 필요하다. 지금은 Client 코드로 타이머를 쓴다.
- 다른 장르에도: 실시간 액션(가이드 10장도 "행동마다는 낭비"라 적음)·시뮬·수집형.
- 제안: Bootstrap '판 저장'에 "N초마다"(칸 `autosaveInterval`, 프로필도 함께) 선택지.
- 3요소: 문제없음(행동 밖 프레임 끝에서 저장).
- 해결: 가능 · RunSaver에 시각 확인 하나.

**빈틈 4. 판 끝 이벤트와 같은 프레임에 `NewRun`하면 프로필 즉시 저장이 빠진다** (코드)
- 무엇: 판 끝 이벤트를 받으면 RunSaver가 프레임 끝에 판 저장을 지우고 프로필을 저장하려고 표시한다. 그런데 같은 프레임에 `GBibleRuntime.NewRun`을 부르면 `_runSaver.Reset()`이 그 표시(`_endPending`)를 지워 프로필이 저장되지 않는다(GBibleRuntime.cs `NewRun`, RunSaver.cs `Reset`). '프로필도 행동마다 저장'이 꺼져 있으면 끌 때까지 저장되지 않는다.
- 왜: 환생 확인 버튼 한 번에 `Do(Ascend)` → `NewRun` → `Do(StartRun)`을 하므로 환생할 때마다. 그 사이 튕기면 천상칩을 잃는다.
- 다른 장르에도: 로그라이크의 "바로 다시 하기"를 판 끝 행동과 같은 입력에서 할 때.
- 제안: `Reset`이 남은 프로필 저장을 먼저 하거나(`NewRun` 안에서 `_endPending`이면 `SaveProfile`), 06장 3.2에 "판 끝 이벤트를 쓰면서 같은 프레임에 새 판을 열면 `SaveProfile`을 직접 부른다"를 적는다.
- 3요소: 문제없음.
- 해결: 가능 · 몇 줄.

**빈틈 5. 쌓이는 값(정산형)의 패턴이 없다**
- 무엇: 문서는 "매 프레임 바뀌는 값은 플레이어 데이터에 넣지 않는다"까지만 말한다. 초당 생산처럼 시간에 따라 쌓이는 값을 어떻게 넣는지(N초 정산 + 쓰기 전 정산 + 화면 보간 + 시각 기록)는 없어 AI가 매번 설계한다.
- 왜: 방치형의 중심. 정산을 빠뜨린 행동이 있으면 쿠키가 모자라다고 잘못 실패한다.
- 다른 장르에도: 경영(수입), 생존(배고픔·체온), 실시간 재생, 농장 성장.
- 제안: 33장 5절에 "정산" 예(1초 정산·쓰기 전 정산·보간)와 가이드 07장 6절 연결. 도우미 `Accrual`(임시: `lastAt` + `Settle(game, rate)`)은 선택.
- 3요소: 문제없음.
- 해결: 가능 · 문서(+ 작은 도우미).

**빈틈 6. 상태 효과가 끝나는 순간을 규칙이 잡지 못한다** (코드)
- 무엇: 시간 만료에서 보정을 먼저 떼고 끝날 때 결과를 돌린다(Statuses.cs `Expire`: `Drop` → `Run`). 걸림·끝남 이벤트도 없다. 그래서 "버프 동안만 더 쌓이는 값"을 끝 순간까지 정산할 수 없다.
- 왜: 프렌지·클릭 프렌지가 끝날 때마다(오차 ≤ 정산 간격).
- 다른 장르에도: 실시간 지속 피해 정산, 버프 끝 연출, "버프 유지 시간" 로그.
- 제안: 끝날 때 결과를 보정 떼기 전에 돌리고 그 순서를 29장 2-2에 적거나, 이벤트 `StatusApplied`·`StatusEnded { status, holder, reason }`(임시)를 쏜다.
- 3요소: 문제없음(이벤트 하나).
- 해결: 가능.

**빈틈 7. 이어 하기 뒤·끄기 직전 훅이 없다**
- 무엇: '시작할 때 이어 하기'는 `Started` 뒤에 판을 불러온다(GBibleRuntime.cs `Start`) → 불러온 뒤 할 일(오프라인 정산·창)을 걸 이벤트가 없다. `Stopped`는 저장 뒤라 끄기 직전 행동을 남길 수 없다.
- 왜: 방치형은 켤 때마다. 지금은 첫 `Ticked`에서 우회한다.
- 다른 장르에도: 이어 하기 뒤 "지난 이야기" 연출, 끌 때 정리 행동.
- 제안: `GBibleRuntime.RunLoaded`(이어 하기·새 판 행동 뒤)·`Stopping`(저장 전, 행동 가능) 이벤트.
- 3요소: 문제없음.
- 해결: 가능.

**빈틈 8. 규칙에서 원본 목록을 얻지 못한다**
- 무엇: `session.Instances`는 ID → 원본 찾기만 한다. 같은 클래스 원본 전부(DB 순서)를 규칙이 모른다. GameIds도 클래스별 목록이 없다. 그래서 판 시작에 모든 건물을 만들 수 없고(지금은 처음 살 때 만든다), "모든 건물" 효과는 가진 건물만 본다. 상점 목록은 Client가 `GameDatabase`로 모은다.
- 왜: 원본 종류가 있는 게임은 거의 다. 우회(가중치 표를 목록으로 쓰기, GameIds를 손으로 배열)는 기획자가 DB에 더해도 코드를 고쳐야 한다.
- 다른 장르에도: 카드 전체·도감·상점 진열·몬스터 목록.
- 제안: `Game.Originals<T>()`(임시, 시작 때 만든 표, DB 순서) + GameIds에 클래스별 `All` 배열.
- 3요소: ③ 시작 때 표를 만든다(런타임 리플렉션 없음).
- 해결: 가능.

**빈틈 9. 필드 경로로 목록 원소(id)·딕셔너리 키를 고르지 못한다**
- 무엇: 경로는 `items[].level`(하나라도)뿐이다(FieldPaths). "커서 25개 이상"·"건물 cursor의 mult" 같은 조건·주기를 DB에서 쓰려면 프로젝트 조건 Block이 필요하다.
- 왜: 해금 조건·도전과제마다.
- 다른 장르에도: "인벤토리의 포션 개수", "유닛 hero의 레벨", "퀘스트 q3 진행".
- 제안: 경로 문법 `list[id=값].field`·`dict[키]` — '플레이어 데이터 검사'·'주기'·binding-path가 함께 쓴다.
- 3요소: ③ 경로 해석은 처음 한 번 캐시(FieldPaths `TypeCache`), 값 읽기는 생성 코드.
- 해결: 가능.

**빈틈 10. 숫자 표기 서식이 없다**
- 무엇: binding-path 숫자는 `"0.##"` 고정(1e45는 46자리), 텍스트 서식은 .NET 문자열만(`{n, number, 0.00E+0}`은 된다). "1.23 Qa" 같은 단위 약자, 설정으로 바꾸는 표기가 없다.
- 왜: 모든 큰 숫자 칸.
- 다른 장르에도: RPG 큰 피해 숫자, 경영 돈, 한국식 단위(만·억·조).
- 제안: 텍스트 서식 `{n, number, short}`·`{n, number, sci}` 기본 제공 + `TextFormat.RegisterNumberStyle("이름", 함수)` + binding-path 서식 꼬리(`run:cookies#short`, 임시) + 설정 적용 대상 '숫자 표기'.
- 3요소: 문제없음.
- 해결: 가능.

**빈틈 11. 입력을 막지 않는 연출이 없다**
- 무엇: `GameView.Present`가 하나라도 돌면 `Busy`라 `OnClick`이 무시된다. 35장 5-4의 피해 숫자 예도 `Present`라, 그대로 따라 하면 클릭마다 떠오르는 숫자가 다음 클릭을 씹는다.
- 왜: 클리커는 클릭마다.
- 다른 장르에도: 실시간 액션 타격 숫자, 리듬.
- 제안: `GameView.Play(연출)`(임시, 대기열 밖·`Busy`를 켜지 않음) 또는 35장 5-4에 "막지 않는 연출은 `Overlay`에 바로 붙인다" 예.
- 3요소: 문제없음.
- 해결: 가능.

**빈틈 12. 화면 칸을 매 프레임 그릴 자리가 없다**
- 무엇: `GameScreen.Draw`는 데이터·언어가 바뀔 때만 돈다. 보간되는 쿠키 수·버프 남은 초·쿨다운 막대는 화면마다 `schedule.Execute(...).Every(...)`를 직접 쓴다.
- 왜: HUD 하나, 그리고 시간 표시마다.
- 다른 장르에도: 실시간 쿨다운·웨이브 타이머.
- 제안: `GameScreen.Tick(double dt)`(임시, 열린 동안 매 프레임) 또는 35장에 예.
- 3요소: 문제없음.
- 해결: 가능.

**빈틈 13. 곡선의 묶음 계산(합·역산)이 없다**
- 무엇: `Curve`는 한 단계 값만 준다. "10개 사기"(합)·"살 수 있는 만큼"(역산)은 프로젝트가 닫힌 식을 쓰는데, 기획자가 곡선을 '표'로 바꾸면 그 식이 틀린다. BigNum 가격에는 곡선 자체를 못 쓴다.
- 왜: 방치형 상점마다.
- 다른 장르에도: 경영(대량 구매), 수집형(레벨 여러 번 올리기 비용).
- 제안: `Curve.Sum(base, from, count)`·`Curve.MaxCount(base, from, budget)`(비율로·일정하게는 닫힌 식, 그 밖에는 반복) + BigNum 판.
- 3요소: 문제없음.
- 해결: 가능.

**빈틈 14. 창이 내려간 동안 계속 돌지 정할 곳이 없다**
- 무엇: GBible·문서에 Run In Background 언급이 없다. 꺼져 있으면 창을 내린 동안 시계가 멈춘다(이 시험에서는 Q3의 차이 계산이 오프라인으로 메운다).
- 왜: 방치형은 늘 정해야 한다.
- 다른 장르에도: 멀티(꺼져 있으면 끊김), 실시간.
- 제안: 시작 설정 또는 Bootstrap에 '창이 내려가도 계속'(`Application.runInBackground`) 칸, 20장에 한 줄.
- 3요소: 문제없음.
- 해결: 가능.

### 5-2. 문서 오류 · 부족

1. **가이드 07장 1절 표의 방치형 줄**(Undo 쓰지 않음 · 판 저장 저장하지 않음 · `Meta`)이 환생이 있는 방치형과 맞지 않는다: 상태 효과·예약·이번 판 Modifier가 세션 구역이라 판을 저장하지 않으면 껐다 켤 때 사라지고, 환생 초기화도 손으로 써야 한다. 같은 장의 "프로필도 행동마다 저장"을 켜라는 말(가이드 10장 2절 표도)은 1초 정산이면 매초, 클릭 중이면 프레임마다 파일을 쓴다. → 환생이 있으면 "판 = 환생 주기, 판 저장 켬, 판 끝 이벤트 = 환생"으로.
2. **가이드 07장 6절 방치형**의 `Game.Pay(…, (int)Game.Balance(…))`: 방치형 가격은 곧 int 범위(약 2.1e9)를 넘어 넘친다. `Game.Pay`·밸런싱 값이 double이라는 한계(1e308·정밀도)도 참조 문서·관례 어디에도 없다.
3. **가이드 07장 6절**의 "마지막 정산 시각을 `DateTime` 필드로": 관례 3절은 규칙에서 `DateTime`을 쓰지 말라 한다. 현실 시각을 행동 필드로 받는 법, 켜져 있는 동안에도 시각을 갱신해야 한다는 것(아니면 켜 둔 시간도 보상), 끄기 직전 훅이 없다는 것이 빠져 있다.
4. **PlanningSpecGuide 2절**: '1 시간' 줄(실시간 → 고정 틱 30·Undo 스냅샷)이 가이드 07장 방치형(Undo 쓰지 않음)과 부딪친다. '9 키 바꾸기'의 "실시간이면 켬"은 마우스만 쓰는 방치형에 맞지 않는다.
5. **Reference.md 2-1**의 Undo 방식 "행동 단위·스냅샷·없음": 화면 이름은 "쓰지 않음"(BootstrapPage `HistoryNames`). 참조 문서는 "이름은 화면에 보이는 그대로"라고 한다.
6. **매뉴얼 35장 5-2 상점 예**가 `new BuyCard { source = item.card, price = item.price }`로 화면이 가격을 행동에 넣는다. 30장 5-3은 "가격은 행동 안에서 계산, 화면이 넣으면 속일 수 있다"이고 그 `BuyCard`에는 `source`만 있다.
7. **매뉴얼 33장 5-1 `ArenaRules`**: 이름은 Rules인데 `UnityEngine`·`[RuntimeInitializeOnLoadMethod]`·`GBibleRuntime.Started +=`를 쓴다. 17장 2-6("기능마다 자기 `Started +=`를 두지 않는다, 연결은 Client `Bootstrap.Started` 한 곳")과 어긋난다.
8. **가이드 09장 '다른 장르라면'·12장**의 "계산으로 얻을 수 있는 값(누적 생산량 등)은 저장하지 않고": 환생 게임에서 누적 생산은 천상칩의 근거라 다시 계산할 수 없다. 예가 오해를 부른다.
9. **매뉴얼 29장 2-2·2-3**: 시간 만료 때 보정을 떼고 나서 끝날 때 결과가 돈다는 순서(코드 `Drop` → `Run`)가 적혀 있지 않다. 끝날 때 결과에서 그 보정을 읽으려는 사람이 틀린다.
10. **기획 명세서 양식(PlanningSpec.md)**: 2-1이 전투를 전제(유닛·피해 공식)하고, 1절 '시간'에 "꺼 둔 시간도 흐름"이 없다. 방치형·경영 기획자는 칸을 억지로 채운다. → 2-1에 "핵심 공식(피해·생산 …)", 1절에 "현실 시간(꺼 둔 시간 포함)" 선택지.
11. **매뉴얼 35장 5-3 타이틀 예**의 '새 게임'이 `new StartRun()`만 한다. 06장 3.1·20장은 `GBibleRuntime.NewRun`을 먼저 부른다(아니면 세션 구역의 상태 효과·예약·Modifier가 남는다).

## 6. 하루 안에 끝낼 수 있나

**된다.** 세 질문의 답(또는 추천값)이 먼저 와야 한다.

- 되는 쪽: 씬이 하나이고 흐름이 짧다(새 판 → 정산·클릭·사기 → 환생). 효과 대부분이 DB 조립으로 떨어진다 — 버프는 상태 효과(게임 시간 지속 + 스탯 보정), 클릭 프렌지·할인은 상태 효과의 행동 직전 이벤트 + 행동 직전 이벤트 고치기, 황금 쿠키 효과는 가중치 표 + 액티브 효과, 업그레이드는 인스턴스 사용 기능 + 스탯 보정. 환생 초기화는 판 끝 이벤트 + `NewRun`이 맡는다. 설정·확인·알림·일시정지는 기본 화면, 도전과제·로그·Steam은 있는 기능이다.
- 무거운 쪽: GBible에 없어 프로젝트가 직접 만드는 것 — BigNum과 그것을 받는 대체 Block·서식·쓰기 함수(빈틈 1·10), 현실 시각을 행동 필드로 받는 정산(빈틈 2·5), 주기 저장(빈틈 3), 이어 하기 뒤 훅 우회(빈틈 7), 매 프레임 보간 칸과 입력을 막지 않는 연출(빈틈 11·12). 모두 문법 안에서 우회되지만, 다음 방치형 프로젝트도 똑같이 다시 만든다.
- 틀리기 쉬운 곳: 쿠키를 쓰는 행동에서 정산을 빠뜨리는 것, BigNum 필드에 기본 숫자 Block(플레이어 데이터 검사 등)을 붙이는 것(숫자로 읽지 못해 조건이 늘 거짓), 환생 버튼에서 같은 프레임 `NewRun`으로 프로필 저장이 빠지는 것(빈틈 4).
- 빈틈 1·2·3·5가 GBible에 들어가면 이 장르의 시스템층은 거의 DB 조립과 규칙 함수 몇 개로 줄어든다.
