# 08. 시험과 디버깅

버그를 보면 같은 판을 다시 만들고, 모니터에서 원인을 거슬러 올라가고, Undo로 앞뒤를 오가며 고친다. 바뀌지 않아야 할 규칙은 테스트로 묶어 둔다.

누가 무엇을: 테스트 씬·테스트 명령·테스트 상황·규칙 테스트는 AI가 만든다(관례 19절 — 테스트 씬은 반영 스크립트의 `TestSceneSetup.Ensure`, 명령은 DB 반영 스크립트). 개발자는 그것으로 플레이하며 상황을 저장하고 버그를 알린다. AI는 Unity 창을 누를 수 없으므로 규칙 테스트·플레이 확인을 요청 파일로 돌린다(6절, 매뉴얼 [38장](../../Manual/38-Testing.md) 2-4·2-5).

> [!note]- 이 장에서 쓰는 말
> | 말 | 뜻 |
> |---|---|
> | 모니터 | 메뉴 `MomoiProject › 모니터`. 플레이 중인 세션을 보고 조작하는 창. 탭은 타임라인 · 데이터 · 도전과제 · 로그 · 이벤트 · 행동 · 명령. |
> | 통합 기록(Journal) | 세션에서 일어난 모든 일(행동·이벤트·값 변경·달성·경고)을 원인과 함께 한 줄씩 남긴 기록. 타임라인 탭이 보여 준다. |
> | Undo | 마지막 행동이 바꾼 값을 행동 전으로 되돌리는 것. 난수도 함께 돌아간다. |
> | 시드 | 결정론 난수의 씨앗. 같은 시드에서 같은 행동을 하면 같은 결과가 나온다. |
> | 테스트 씬 | `Assets/MomoiProject/Scenes/Test.unity`. 게임 씬을 복사하고 컴포넌트 `TestScene`(시작할 테스트 상황 · 시드 · 따로 슬롯 · 시간 배속 · 멀티)을 붙인 씬. 플레이하면 그 상황으로 바로 시작하고 테스트 패널(F1)이 뜬다. |
> | 테스트 상황 | 지금 판·프로필·난수·게임 시각을 이름 붙여 저장한 파일(`Assets/MomoiProject/Data/Tests/<이름>.json`, `TestScenarios`). 모니터 명령 탭·테스트 패널에서 저장·불러오기. |
> | 테스트 명령(개발 명령) | 버튼 하나로 도는 개발용 동작. DB › 개발 › 개발 명령의 항목 하나가 버튼 하나다(모니터 명령 탭·테스트 패널). 개발 빌드에만 있다. |
> | 이벤트 호출 | 모니터 이벤트 탭에서 이벤트 값을 채워 직접 쏘는 도구. |
> | 시뮬레이션 | 값을 덮어쓰지 않고 실제 이벤트를 쏴서 게임과 같은 경로(이벤트 → 로그 → 도전과제 → 보상)로 움직이는 것. 쏜 이벤트 묶음은 행동 하나로 기록된다. |

## 1. 같은 판 다시 만들기

- **고정 시드**: DB › 시작 파일 › Bootstrap의 **개발 빌드에서 시드 고정**을 켜 둔다([01장](01-StartProject.md) 4절). 같은 순서로 하면 같은 판이 나온다. 모니터 머리 줄에 "시드 20261003 · …"이 보이면 된다.
- **테스트 상황**: 버그 직전에 모니터 › **명령** › 테스트 상황(또는 테스트 패널)에서 이름을 붙여 저장한다. 다시 열면 그 순간(판·프로필·난수·게임 시각)으로 돌아오고, 테스트 씬의 시작 상황으로 고르면 플레이하자마자 그 순간이다. 파일이 프로젝트(`Assets/MomoiProject/Data/Tests/`)에 남으므로 AI가 같은 상황을 읽어 규칙 테스트로 재현한다(관례 19절).

버그 보고에는 상황 이름(없으면 시드와 판 저장 파일)을 붙인다.

> [!note]- 시드 자세히
> - 고정되면 덱 섞기·전리품·무작위 대상이 같게 나온다. 에디터 플레이는 개발 빌드로 친다. 출시 빌드는 늘 지금 시각을 시드로 쓴다.
> - 난수를 쓰임마다 흐름으로 나누면([07장](07-GenreRecipes.md) 4절) 코드를 고쳐 한 흐름의 뽑는 횟수가 달라져도 다른 흐름은 그대로라 재현이 덜 흔들린다.
> - Bootstrap의 `Configure`에서 `options.Seed`를 바꾸면 코드가 이긴다. 그때 모니터 **타임라인**에 "코드(Configuring)가 DB › Bootstrap의 세션 옵션을 바꿨습니다: 시드 … → …"가 남는다.

> [!note]- 판 저장으로 다시 만들기
> - 모니터 › **명령** › 저장 › **판 저장** / **판 불러오기**. 파일은 `GBibleRuntime.RunSavePath`(`…/MomoiProject/run.json`)이고 판 데이터·난수 상태·게임 시계가 들어간다. 테스트 씬은 '따로 슬롯'이 켜져 있으면 'test' 슬롯을 써서 실제 저장을 건드리지 않는다.
> - Bootstrap의 판 저장이 "행동마다 저장"이면 `run.json`은 늘 마지막 행동 뒤로 덮인다. 버그 직전을 남기려면 테스트 상황으로 저장한다.
> - 같은 묶음의 **새 판**은 `GBibleRuntime.StartNewRun(session)`이다: 판 데이터를 처음 값으로(Undo 기록도 비운다), 판 저장을 지우고, Bootstrap의 '새 판 행동'을 돌린다. **프로필 삭제**는 다음 플레이부터 적용된다.
> - 개발 중에 데이터 구조를 바꾸면 맞지 않는 저장이 초기화된다([10장](10-SaveAndRelease.md) 5절).

## 2. 개발 명령

시험 준비(골드 넣기, 적 모두 처치 …)는 버튼 하나로 만든다. AI가 DB 반영 스크립트로 DB › **개발** › **개발 명령**에 항목을 만들면(새 항목은 저절로 적용 — 관례 15절) 모니터 **명령** 탭과 테스트 패널에 버튼이 생긴다. 로직 샘플·요청으로 더한 조각마다 얻기·쓰기·걸기 명령을 만들고 **분류**(`category`)로 묶는다(관례 19절).

- 항목의 **결과** 칸에 결과 Block을 쌓아 무엇을 할지 조립한다. 대부분 코드가 없고, 문장 안의 값(어느 인스턴스·몇 개)은 개발자가 드롭다운으로 바꾼다.
- 누르면 결과 전체가 행동 하나로 실행된다. 타임라인에 "[개발] 버튼 이름"으로 남고, 게임 행동처럼 Undo된다.
- 출시 빌드에서는 등록되지 않는다(버튼이 없다). 따로 감쌀 것이 없다.

카드 던전의 명령:

| 버튼(ID) | 결과 |
|---|---|
| 골드 +100 (`goldPlus100`) | **플레이어 데이터에 주기**: `run` › `gold` 증감 100 |
| 한 턴 30 피해 (`turnDamage30`) | **이벤트 쏘기**: 턴 끝, `turn` = 1, `damage` = 30(5절) |
| 적 모두 처치 (`killAll`) | 코드(`[BindTo]`, 아래) |

규칙 함수를 거쳐야 하는 명령은 결과 Block 대신 코드로 쓴다. DB 항목을 만들고, 그 ID에 `[BindTo]`를 붙인 함수를 Rules에 둔다(`GameIds` 상수는 반영 스크립트가 돌고 Unity가 다시 컴파일한 뒤에 생긴다 — 관례 15절).

```csharp
[BindTo(GameIds.DebugCommand.KillAll)]
static void KillAll(TriggerContext c)
{
    var game = c.Game;
    foreach (var enemy in Rules.LivingEnemies(game).ToArray()) Rules.Damage(game, game.Data().Run.hero, enemy, 9999);
}
```

> [!note]- 왜 적 모두 처치는 코드인가
> 적의 체력을 0으로 덮어쓰면 적은 전투에서 빠지지 않고, 처치 이벤트(`EnemyKilled`)도 쏘지 않아 로그 `kills`가 반응하지 않는다. 피해 규칙(`Rules.Damage`)을 거쳐야 게임에서 적을 잡을 때와 같은 길(전투에서 빼기 → 처치 이벤트 → 로그)로 돈다. 이런 "규칙을 부르는" 명령만 코드로 쓴다.

> [!note]- 항목의 칸
> | 칸 | 뜻 |
> |---|---|
> | 버튼 이름 | 명령 탭에 보일 이름. 비우면 ID |
> | 분류 | 명령 탭에서 묶이는 이름. 기본 "개발" |
> | 설명 | 버튼에 마우스를 올리면 보인다 |
> | 결과 | 결과 Block 목록: 플레이어 데이터에 주기 · 이벤트 쏘기 · 로그에 기록 · 대상에게 효과 · 코딩한 결과. ID에 `[BindTo]`가 있으면 그 함수가 결과다 |
>
> 명령 탭에는 기본 묶음이 이미 있다. **저장**(프로필 저장·프로필 삭제·판 저장·판 불러오기·새 판), **시간**(일시정지 / 재개·1프레임 진행·배속). 선택을 기다리는 중이면 맨 위에 **선택 대기** 패널이 생긴다(5절).

> [!note]- 이벤트 쏘기 Block
> - 이벤트를 고르고, 값 줄(필드 경로 = 값)을 적고, 횟수를 정한다. 값은 숫자·글자·참거짓·enum 필드만 적는다(`a.b`로 안쪽 필드도). 적지 않은 필드는 이벤트 클래스의 기본값이다.
> - 그 이벤트를 받는 로그·도전과제·트리거가 게임에서처럼 반응한다.
> - 개발 명령 말고도 종류 제한이 "모두"인 결과 칸(도전과제 보상 등)에서 쓸 수 있다.

> [!note]- 왜 행동 하나로 실행하나
> 결과 전체를 `DeveloperEditAction` 하나 안에서 실행한다. 그래서 바꾼 값이 기록(행동 탭의 "[개발] 골드 +100", 공개 범위 "개발자")에 남고 Undo된다. 명령 안에서 값을 행동 밖에서 고치면 Undo되지 않고, 그 뒤 Undo하면 덮어쓰기 경고가 난다.

> [!note]- 수치는 플레이 중에 DB에서 바로 — 밸런싱 값 · 가중치 표
> 개발자가 플레이 중에 DB › 밸런싱 값·가중치 표를 고치면 저장(Ctrl+S) 전이라도 0.5초 안에 실행 중인 게임에 반영된다. 보상 골드 곡선·드롭 무게를 바꿔 가며 같은 판을 바로 다시 해 본다(4절의 Undo와 함께 쓰면 같은 난수에서 비교된다). 정했으면 Ctrl+S로 저장한다. 표 계산기에서 고친 값은 그 탭의 **CSV › CSV 가져오기**로 넣는다([04장](04-AddingContent.md) 10절).

> [!note]- 코드로 등록하기
> DB 항목으로 안 되는 것(행동 밖에서 할 일 — `CaptureSnapshot` 등)만 `session.Debug.Register(분류, 이름, 실행, 설명)`으로 등록한다. 세션마다 등록되므로 `Bootstrap.RegisterRules`(`GBibleRuntime.SessionCreated` — 모든 세션, [01장](01-StartProject.md) 4절)에서 한다. 멀티 클라이언트에서 누른 명령은 서버 세션의 같은 분류·이름 명령으로 돌므로 서버 세션에도 있어야 한다. 화면에만 쓰는 명령(시간 배속처럼 이 화면만 바꾸는 것)은 `Bootstrap.Started`에. 출시 빌드에서는 `Register`가 아무것도 하지 않으므로 `if (Debug.isDebugBuild)`로 감싸지 않는다. 값을 바꾸는 명령은 직접 `DeveloperEditAction`으로 감싼다(DB 항목처럼 저절로 감싸지지 않는다).
> ```csharp
> session.Debug.Register("카드 던전", "골드 +100", () => session.Do(new DeveloperEditAction
> {
>     label = "골드 +100",
>     Edit = () => session.Game.Data().Run.gold += 100,
> }));
> ```

## 3. 모니터로 원인 찾기

"턴을 넘겼더니 체력이 생각보다 많이 줄었다"를 예로 든다.

1. **타임라인** 탭의 **모든 값 ▾**에서 `run`을 고르고 **묶어 보기**를 켠다. "턴 끝" 행동 줄을 펼치면 그 행동이 쏜 이벤트와 바뀐 값(`hero.hp` …)이 차례로 보인다.
2. `hero.hp`가 바뀐 줄을 고르면 오른쪽 **인과 관계**에 뿌리 행동부터 그 줄까지가 보인다. 피해 이벤트를 **열기**하면 `sourceId`·`amount`로 어느 적이 얼마를 줬는지 나온다.
3. **데이터** 탭 › 판 데이터에서 그 적의 `intentIndex`를 보고 몬스터 원본의 `attackPattern`과 비교한다.
4. **행동** 탭에서 실패한 행동이 있었는지 본다.

**Alt**를 누르고 있으면 문장이 코드식으로 바뀌어 필드 경로가 정확히 보인다.

> [!note]- 무엇을 어디서 보나
> | 알고 싶은 것 | 볼 곳 |
> |---|---|
> | 이 값이 왜 바뀌었나 | 타임라인 › **모든 값 ▾**에서 값 고르기 → **묶어 보기** → 줄 고르기 → 오른쪽 **인과 관계** |
> | 지금 값이 무엇인가, 바꿔 보고 싶다 | 데이터 탭(**판 데이터**·**프로필 데이터**). 고친 값은 개발자 행동 하나로 기록되어 Undo된다 |
> | 내 행동이 실행됐나, 왜 실패했나 | 행동 탭(상태 **실행** · **Undo됨** · **실패**, 실패 줄에 마우스를 올리면 오류) |
> | 이 이벤트를 받으면 무엇이 반응하나 | 이벤트 탭(**이벤트 호출**, 아래 "반응하는 로그") |
> | 도전과제가 제대로 달성되나 | 도전과제 탭 **트리거로 달성**(실제 이벤트로), 안 되면 **강제 달성** |
> | 로그가 제대로 쌓이나 | 로그 탭 **이벤트로 더하기**·**이벤트로 기록**(실제 이벤트로) / **직접 수정**(값만) |
> | 몇 판을 해야 나오는 상황을 지금 보고 싶다 | 명령 탭의 개발 명령(DB › 개발 › 개발 명령, 2절) |
> | 선택을 기다리고 있나, 답해 보고 싶다 | 명령 탭 맨 위 **선택 대기** 패널(5절) |
> | 이 카드를 내면 얼마나 들어가나(실제로 내지 않고) | 미리보기 `Game.Preview`·`Game.CanDo`([06장](06-Presentation.md) 2절). 아무 기록도 남지 않는다 |
> | 걸린 상태 효과·예약이 무엇인가 | 데이터 탭의 `$statuses`(누구에게·`stacks`·`remaining`)·`$schedule` |

> [!note]- 실패한 행동
> 행동 안에서 예외가 나면 그 행동이 바꾼 것이 모두 취소된다. 화면에 보인 연출과 값이 다르다면 여기부터 의심한다. 에너지 부족처럼 예상된 실패는 정상이다.

## 4. Undo로 앞뒤 보기

모니터 머리의 **Undo**는 마지막 행동을 되돌린다. 난수도 행동 전으로 돌아가므로 같은 카드를 다시 내면 같은 결과가 나온다.

"카드를 낸다 → 결과를 본다 → Undo → 값을 바꾸거나 다른 대상으로 다시 낸다"를 반복해 같은 난수 조건에서 결과를 비교한다.

> [!note]- Undo 자세히
> - 게임 코드의 `session.Undo()`와 같다.
> - 다시 하기(Redo)는 없다. 앞으로 가려면 같은 행동을 다시 한다.
> - 도전과제 달성과 그 보상은 Undo해도 남는다. 다시 시험하려면 데이터 탭 › **도전과제 달성**에서 거짓으로 바꾸거나 도전과제 탭의 **초기화**를 쓴다.

## 5. 이벤트로 반응 보기

반응을 시험할 때는 값을 덮어쓰지 말고 이벤트를 쏜다. 같은 이벤트를 받는 다른 기능(유물·다른 로그)도 게임처럼 함께 반응한다.

예: 도전과제 `bigTurn`("로그 `maxTurnDamage`가 30 이상")을 한 턴 30 피해 덱 없이 확인한다.

- **이벤트** 탭에서 "턴 끝"을 고르고 `damage`에 30을 넣고 **이벤트 호출**. `maxTurnDamage`가 30이 되고 `bigTurn`이 달성된다.
- 또는 **도전과제** 탭에서 `bigTurn`을 고르고 **트리거로 달성**. 모자란 로그를 채울 이벤트를 계획해 쏜다.

> [!note]- 자주 하는 시험은 개발 명령으로
> 같은 이벤트를 자주 쏜다면 DB › 개발 › 개발 명령에 **이벤트 쏘기** 결과로 만들어 둔다(2절). 카드 던전의 "한 턴 30 피해"가 이것이다. 누르면 턴 끝(`turn` = 1, `damage` = 30)을 쏘고, `maxTurnDamage`와 `bigTurn`이 반응한다.
>
> 도전과제 하나를 트리거로 달성해 보는 일은 도전과제 탭의 **트리거로 달성** 버튼이 이미 하므로 명령으로 만들지 않는다.
>
> 시험 코드에서는 `session.SimulateEvents`(이벤트 목록을 행동 하나로 쏜다)와 `session.TrySimulateAchievement`(트리거로 달성)를 쓴다.

> [!note]- 고르기를 시험한다 — 명령 탭의 선택 대기 패널
> 결과 `선택 요구`나 `Game.Ask`로 선택을 기다리는 중이면 명령 탭 맨 위에 "선택 대기 · 안내 글" 패널이 생긴다. 게임 화면에 고르기 창이 아직 없어도 여기서 고른다.
> - 후보 버튼을 누르면 ✓가 붙는다(하나만 고르는 선택은 바꿔 고른다). **답하기**를 누르면 답이 행동 하나로 실행되어 타임라인에 "선택: …"으로 남고 Undo된다.
> - 개수가 틀리거나 후보가 아니면 알림이 뜨고 아무것도 바뀌지 않는다(선택도 그대로 기다린다).
> - 후보 이름은 텍스트 `<id>.name`, 없으면 id다. 예: [04장](04-AddingContent.md) 9절 투척 단검.

> [!note]- 시뮬레이션 자세히
> - 쏜 이벤트는 행동 하나("[테스트] …")로 기록된다. Undo하면 로그는 돌아가고 달성은 남는다.
> - 이벤트 호출 아래 "반응하는 로그"에 이 이벤트를 받는 로그가 미리 보인다.
> - "턴 끝을 받는 유물이 엉뚱하게 발동한다" 같은 문제도 여기서 드러난다.
> - 모니터에서 이벤트를 쏘려면 이벤트 클래스에 매개변수 없는 생성자가 있어야 한다. 필드만 있는 클래스면 된다.

## 6. 규칙 테스트

카드 내기·실패 취소·Undo처럼 지켜야 할 규칙은 EditMode 테스트로 묶는다.

- `Assets/MomoiProject/Code/Tests`에 테스트 파일을 둔다. asmdef는 시작 설정이 이미 만들었다. 규칙(행동·규칙 함수·Block)을 만들거나 고치면 하나 이상 둔다(관례 12절).
- AI가 돌린다: `Logs/MomoiProject/RunTests.request`를 만들면 열린 Unity가 새로 읽고(방금 쓴 코드를 컴파일) EditMode 테스트를 돌려 `Logs/MomoiProject/TestResults.txt`에 쓴다(첫 줄 `상태: 모두 통과 — …` 또는 `상태: 실패 n · 통과 m …`). 요청 파일이 남아 있으면 아직 돌지 못한 것이다(플레이 중·모달 창). 매뉴얼 38장 2-4.
- 개발자는 Test Runner 창(`Window › General › Test Runner` › EditMode)에서 돌린다(이 실행은 결과 파일에 쓰지 않는다).

테스트는 DB 없이 세션을 손으로 만든다. 플레이어 데이터는 `Define`으로, 밸런싱 값은 `session.Balance.Define`으로, 카드·몬스터 원본은 `session.Instances`에 함수로 넣는다.

```csharp
[SetUp]
public void SetUp()
{
    _session = new GameSession(new SessionOptions { Seed = 7 });
    _session.Data.Define(GameIds.PlayerData.Run.Id, DataZone.Session, new RunState(), "판");
    _session.Data.Define(GameIds.PlayerData.Profile.Id, DataZone.Meta, new Profile(), "프로필");

    // DB › 밸런싱 값 대신 코드로 넣는다.
    _session.Balance.Define(GameIds.Balance.StartHp, 70);
    _session.Balance.Define(GameIds.Balance.StartGold, 99);
    _session.Balance.Define(GameIds.Balance.WinGold, 15, new Curve { kind = CurveKind.Linear, step = 3 });

    // DB › 인스턴스 대신 원본을 코드로 넣는다(시험에 필요한 수치만).
    var originals = new Dictionary<string, object>
    {
        [GameIds.Instance.Strike] = new Card { cost = 1 },                                       // 이름은 원본 칸이 아니라 텍스트 <ID>.name(02장 2절)
        [GameIds.Instance.Goblin] = new MonsterData { maxHp = 20, attackPattern = new List<int> { 6 } },
        // … 수비·화염구·슬라임·회복 물약
    };
    _session.Instances = id => originals.TryGetValue(id, out var value) ? value : null;
}
```

테스트는 게임과 똑같이 행동을 실행하고 값을 확인한다.

```csharp
[Test]
public void 에너지가_모자라면_아무것도_바뀌지_않는다()
{
    Game.Do(new StartRun());
    var battle = Game.Data().Run.battle;
    battle.energy = 0;                                   // 시험 준비(행동 밖 변경)
    var hand = new List<string>(battle.hand);
    Assert.Throws<GameFailure>(() => Game.Do(new PlayCard { card = Rules.CardOf(Game, hand[0]) }));   // Game.Pay가 던지는 플레이어용 실패
    CollectionAssert.AreEqual(hand, Game.Data().Run.battle.hand);
}
```

`Assert.Throws<T>`는 형식이 정확히 같아야 통과한다. 플레이어용 실패(`Game.Fail`·`Game.Pay`)는 `GameFailure`, "어떤 실패든"이면 `Assert.Catch<InvalidOperationException>`이다.

> [!note]- 왜 DB 없이 만드나
> - 게임은 덱의 한 장(`DeckCard`)이 든 원본 ID로 `Rules.CardData`·`MonsterOf`·`PotionOf`를 거쳐 원본을 읽는다. 테스트에 필요한 수치만 넣어 두면 개발자가 DB 수치를 바꿔도 테스트가 흔들리지 않는다.
> - `Define`은 DB가 없을 때만 쓴다. 게임에서는 DB › 플레이어 데이터가 정의한다([01장](01-StartProject.md) 3절).
> - 위 코드의 `Game`은 `GameApi Game => _session.Game;` 속성이다.

> [!note]- 카드의 사용 기능 넣기
> 카드를 내면 `Game.Use(card.card, …)`가 같은 ID의 액티브 효과를 찾는다. 테스트에서는 DB의 사용 기능 대신 액티브 효과(`AbilityDefinition`)를 코드로 정의한다.
> ```csharp
> void DefineCard(string id, TargetSelector target, Effect effect)
> {
>     var ability = new AbilityDefinition { Id = id };
>     if (target != null) ability.Targets.Add(target);
>     ability.Effects.Add(effect);
>     _session.Abilities.Define(ability);
> }
>
> // SetUp 안에서
> DefineCard(GameIds.Instance.Strike, null, new DealDamage { amount = 6 });
> DefineCard(GameIds.Instance.Defend, new SelfTarget(), new GainBlock { amount = 5 });
> ```

> [!note]- 카드 던전의 다른 테스트
> - **같은 시드면 첫 핸드가 같다**: 같은 시드로 세션을 둘 만들어 `StartRun` 뒤 핸드의 원본 ID를 비교한다.
> - **카드를 내고 Undo하면 전부 돌아온다**: 카드를 내고 `_session.Undo()` 뒤 에너지·적 체력·핸드를 확인한다.
> - **버그 재현**: 개발자가 저장한 테스트 상황과 같은 판을 `SetUp`·행동으로 다시 만들고, 고치기 전에 실패하는지 본다(매뉴얼 38장 5-2).

> [!note]- 테스트 자세히
> - `GBibleRuntime` 없이 만든 세션은 프레임이 흐르지 않는다. 프레임 끝 처리(시간 예약·시간 지속 상태 효과·고정 틱)가 필요하면 `session.EndFrame(0.016)`을 직접 부른다.
> - "이 행동을 하면 이렇게 된다"만 보고 상태를 그대로 두고 싶으면 `Game.Preview(행동, g => 읽기)`. 되돌릴 필요 없이 다음 줄에서 같은 상태로 다른 행동을 시험한다.
> - 상태 효과를 쓰는 규칙을 시험하려면 DB 대신 `session.Statuses.Define(new StatusDefinition { … })`로 정의를 넣는다(매뉴얼 [29장](../../Manual/29-Statuses-Schedules-Choices.md)).
> - Tests asmdef(`MomoiProject.Tests`)는 Rules·`GBible.Core`·`GBible.Unity`·켠 데이터 모듈(`GBible.Inventory` 등)·Test Runner·NUnit을 참조하고, 에디터에서 테스트를 돌릴 때만 컴파일된다. 화면 코드(Client)는 부를 수 없다. 규칙이 Rules에 있어야 하는 이유다.
> - 화면은 규칙 테스트로 보지 않는다. AI는 플레이 요청(`Logs/MomoiProject/Play.request` → `PlayResults.txt`·`Captures/*.png`, 매뉴얼 38장 2-5)으로 열고 누르고 찍어 본다.

타임라인·콘솔의 `[MomoiProject]` 경고는 쌓아 두지 않는다. 보이면 그때 아래 표로 고친다.

## 8. 체크리스트

- [ ] DB › 시작 파일 › Bootstrap에서 개발 빌드 시드를 고정했다.
- [ ] 테스트 씬(`Assets/MomoiProject/Scenes/Test.unity`)이 있고, 플레이하면 시작 상황(없으면 새 판)으로 열리며 테스트 패널이 뜬다.
- [ ] 시험 준비용 테스트 명령이 DB › 개발 › 개발 명령에 분류별로 있고, 누르면 행동 하나로 기록·Undo된다. 규칙을 거쳐야 하는 명령만 `[BindTo]` 코드다.
- [ ] 버그는 테스트 상황(이름)으로 받아 규칙 테스트로 재현한 뒤 고친다.
- [ ] 타임라인에서 값 하나의 변경 원인을 따라갈 수 있다.
- [ ] 도전과제·로그·유물의 반응을 이벤트 호출·트리거로 달성으로 확인했다. 고르기는 명령 탭의 선택 대기 패널로 확인했다.
- [ ] 밸런싱 값·가중치 표는 플레이 중에 DB에서 고쳐 보며 맞췄다.
- [ ] 지켜야 할 규칙(실패 취소, Undo, 같은 시드 같은 결과)이 `Assets/MomoiProject/Code/Tests`에 테스트로 있고, `RunTests.request` → `TestResults.txt`가 모두 통과다.
- [ ] 타임라인·콘솔(`Logs/Editor.log`)에 `[MomoiProject]` 경고가 남아 있지 않다.

> [!note]- 다른 장르라면
> - **실시간 액션**: 행동 단위가 아니라 스냅샷으로 되감는다(Bootstrap의 Undo 방식 "스냅샷"). 모니터 머리에 "되감기 스냅샷 n (n초 간격)"이 보이고, **Undo**는 마지막 스냅샷으로 되감는다. 버그 직전으로 돌아가 보려면 `session.CaptureSnapshot()`을 부르는 개발 명령(`session.Debug.Register`)을 만들어 두고 그 순간 근처에서 누른다. 빠른 장면은 모니터의 **일시정지**·**1프레임**·배속(0.25× …)으로 늦춰 본다.
> - **턴제 전술**: AI처럼 판단이 복잡한 코드는 AI가 고른 행동의 `Describe()`를 읽기 쉽게 쓴다("오크1 → 영웅 공격"). 행동 탭·타임라인만으로 AI의 선택을 따라갈 수 있다.
> - **수집형·방치형**: 프로필이 오래 쌓이므로 명령 › 저장 › **프로필 삭제**(다음 플레이부터)와 **새 판**으로 처음 상태를 자주 시험한다. 오래된 프로필 파일을 몇 개 보관해 두었다가 출시 전 저장 변환을 시험한다.
> - **멀티**: 테스트 씬 › 멀티플레이를 시험 모드(지연 0.1 이상)로 돌려 화면이 결과를 기다리는지 본다. 모니터 머리에서 세션(서버 · 이 화면 · 방마다)을 골라 서버 쪽 타임라인을 본다. 클라이언트일 때 Undo·새 판·테스트 상황은 서버 쪽에서 한다([11장](11-MultiplayerReady.md), 매뉴얼 40장 2절).
