## 0. 철학

1. **일반인도 개발에 참여할 수 있는 UX.** 요소 추가·조건·보상은 전용 에디터에서 메뉴 선택과 숫자 입력만으로 만든다. 사용자는 저장 형식(SO, JSON)을 보지 않는다.
2. **실수는 사람의 주의가 아니라 도구가 막는다.** 타이핑하는 문자열을 최소화하고, 검증기·계약 테스트가 저장 시점과 빌드 직전에 오류를 차단한다.
3. **정보 전달이 뚜렷해야 한다.** 모든 조건·보상은 사람이 읽는 문장으로 보이고, 모든 상태 변화는 원인과 함께 기록된다.
4. **독립성.** 어느 프로젝트에 넣어도 동작한다. 의존이 없으면 에러 없이 비활성화되고 설치를 안내한다.
   **Odin Inspector와 DOTween은 가급적 사용하지 않는다.** 신규 기능은 Unity 기본 기능(UI Toolkit·IMGUI 에디터, `[SerializeReference]`, 자체 트윈·보간)으로 구현한다. 기존 사용처는 점진적으로 제거한다 (§10).
5. **구축 비용보다 사용 편의.** 프레임워크 구축 비용은 감수한다. 판단 기준은 이후 사용 편의성이다.

## 1. 현황 진단 (현재 코드의 문제)

| 영역 | 문제 |
|---|---|
| 확장 방식 | 도전과제·로그 조건이 C# 람다(델리게이트). 에디터가 내용을 볼 수 없어 표시·검색·검증 불가. |
| 등록 | `AddDefinition` → `Initialize`를 수동 호출. 누락 시 에러 없이 미동작. |
| 식별 | 키가 직접 타이핑하는 문자열. 오타·중복 미검출. |
| 수치의 기준 | Logs와 `ProgressAchievement`가 같은 이벤트에서 각자 누적 → 두 개의 기준. |
| 재사용 | 조건·보상이 도전과제 안에 갇혀 퀘스트·해금 등에서 재사용 불가. |
| Events 역할 혼합 | 알림과 값 수정 파이프라인(`ref` 수정)이 한 시스템. 수정 순서 제어 장치 없음. |
| 싱글 전제 | `static` 클래스 + 전역 `SaveData`. 플레이어별 상태·테스트 격리 불가. |
| 소급 달성 | 이벤트 구독 방식이라, 이미 조건을 넘은 상태에서 추가된 도전과제는 달성되지 않음. |
| 이름 충돌 | 라이브러리에 예제 클래스(`PlayerStats`, `Equipment`, `MyLogs`, `MyAchievements`)가 전역 네임스페이스로 포함. |
| 소스 손상 | 24개 파일의 한글이 U+FFFD로 손상(주석·인스펙터 라벨·로그). 원본 확보 필요. |

## 2. 층 구조

```
① Events            이벤트 전달 (코드 층, 프로그래머)
② Modifiers         값 수정 파이프라인 — 우선순위 있는 수정자 (Events에서 분리, 후순위)
③ Stats             이벤트를 숫자로 바꾸는 유일한 곳 (현 Logs 확장)
④ Conditions        공용 조건 블록 라이브러리
   Rewards          공용 보상 블록 라이브러리
⑤ Achievements      얇은 층: 정의 목록 + 달성 상태 + 달성 알림
   (Quests / Unlocks / Tutorial 도 ④를 그대로 재사용)
⑥ Save              모든 층의 상태 저장
⑦ Observability     모든 층을 가로지르는 관찰 계약·기록·모니터
⑧ Network Adapter   멀티플레이어 연동 (핵심 로직과 분리)
```

의존 방향은 위→아래가 아니라 **아래 층이 위 층을 모른다**가 원칙이다. Achievements는 이벤트를 직접 구독하지 않고 **관찰 대상(Observable)**만 본다.

## 3. 데이터 저장

### 3.1 형식: ScriptableObject를 원본으로

- 정의(도전과제·수치·블록 조합)는 SO 에셋으로 저장한다. Force Text 직렬화로 YAML 텍스트 → git diff·머지 가능.
- 채택 이유: 에셋 참조(아이콘·사운드·프리팹)를 GUID로 안전하게 유지, 사용처 검색, Undo, 다중 편집, `[SerializeReference]` 다형성 지원.
- JSON/CSV 내보내기·가져오기는 **옵션 기능**으로 제공한다(엑셀 일괄 편집, 서버 밸런싱 대비). 원본은 항상 SO.
- 항목당 에셋 1개 → 동시 작업 시 머지 충돌 최소화.

### 3.2 사용자는 SO를 직접 다루지 않는다

- 시스템별 **전용 데이터베이스 창**(표 형태)이 목록·추가·편집·검색·검증을 모두 제공한다.
- 에셋 생성·이름·폴더 배치는 창이 자동으로 처리한다.

### 3.3 ID 규칙

- 모든 항목은 저장·분석용 **ID**와 **표시 이름**을 분리한다. 사용자가 입력하는 것은 표시 이름뿐.
- ID는 생성 시 자동 부여, 이후 **변경 불가**(세이브 호환). 변경이 꼭 필요하면 마이그레이션 도구를 통한다.
- ID 중복은 검증기가 차단한다.
- 코드 참조용 **ID 상수 클래스를 자동 생성**한다(예: `AchievementIds.MonsterHunter`). 항목 삭제 시 코드 쪽은 컴파일 에러로 드러난다.
- 미결: ID 형식(자동 연번 vs 영문 슬러그) — §13.

## 4. 블록 계약 (Conditions / Rewards)

프로그래머는 블록 **타입**을 C#으로 만든다. 사용자는 블록을 메뉴에서 고르고 값만 입력한다. 새 블록 타입은 메뉴·역색인·대시보드·검증기에 자동으로 등록된다.

### 4.1 조건 블록 계약

| 멤버 | 필수 | 설명 |
|---|---|---|
| `Evaluate(ctx)` | ✔ | 현재 충족 여부 |
| `Dependencies()` | ✔* | 의존하는 관찰 대상 키 목록 |
| `PollInterval` | ✔* | 시간 기반 조건일 때 명시적 확인 주기 |
| `Describe()` | ✔ | 사람이 읽는 문장 ("처치 수 ≥ 100") |
| `Validate()` | ✔ | 설정값 검사 (빈 참조, 범위 등) |
| `State` | 선택 | 스스로 기억하는 값 + 초기화 규칙(판마다/영구) — 연속·순서 조건용 |

\* `Dependencies()`와 `PollInterval` 중 **최소 하나는 반드시** 있어야 한다. 둘 다 없으면 "조용한 미동작"이므로 계약 테스트가 실패시킨다.

복합 조건(AND / OR / NOT)도 블록이며, 의존 대상은 하위 블록의 합집합이다.

### 4.2 보상 블록 계약

| 멤버 | 필수 | 설명 |
|---|---|---|
| `Grant(ctx)` | ✔ | 보상 지급 (Observability에 원인과 함께 기록) |
| `Describe()` | ✔ | "골드 500 지급" |
| `Validate()` | ✔ | 설정값 검사 |

### 4.3 블록 설계 원칙

- **블록은 적게, 복잡한 조건은 새 블록 클래스로.** 블록 조합으로 스크립트 언어를 만들지 않는다.
- 기본 조건 블록 초안: 수치 비교(≥, ≤, 범위), 비율, 다른 요소 달성 여부, 플래그, 인벤토리 보유, AND/OR/NOT.
- 블록 클래스 이름 변경·삭제 시 `[MovedFrom]` 사용. 끊긴 데이터는 검증기가 찾아 보여준다.

## 5. 관찰 대상과 평가 흐름

### 5.1 관찰 대상(Observable) 규격

조건은 수치에만 의존하지 않고 **관찰 대상 키**에 의존한다.

```
stat:처치수
inventory:전설무기
achievement:몬스터사냥꾼
flag:튜토리얼완료
```

값을 가진 시스템(Stats, Inventory, Achievements, Flags …)은 "이 키의 값이 바뀌었다" 알림을 보내는 공용 규격을 구현한다. 새 시스템도 이 규격만 구현하면 모든 조건 블록에서 쓸 수 있다.

### 5.2 평가 흐름 (폴링 없음)

1. **역색인 구성**: 시작 시 `관찰 대상 키 → 그 키를 보는 조건 목록`. 이미 달성한 항목은 제외.
2. **변경 수집**: 관찰 대상이 바뀌면 "바뀐 키 목록"에 모은다.
3. **프레임 끝 일괄 평가**: 바뀐 키에 연결된 조건만 한 번씩 평가. 중복 평가·순서 문제 없음.
4. **달성 처리**: 달성 → 보상 지급 → 달성 알림 → 역색인에서 제거.
5. **로드 직후 전체 평가**: 이미 조건을 넘은 상태에서 추가된 항목도 소급 달성.
6. **시간 조건**: `PollInterval`을 선언한 블록만 스케줄러가 주기 평가.

### 5.3 Stats 범위

수치는 범위를 가진다: **누적 / 이번 판 / 최고치(Max) / 최저치(Min)**, 멀티플레이어에서는 추가로 **플레이어 / 팀 / 매치 / 전체**.
"한 방 10,000 피해"는 최고치 범위, "60초 내 보스 처치"는 최저치 범위, "한 판에 50 처치"는 이번 판 범위로 표현한다.

Stats 정의도 블록으로 만든다: "이벤트 [적 처치 ▾] 발생 시 필드 [수량 ▾]를 수치 [처치 수 ▾]에 더함". 이벤트 필드 목록은 에디터가 구조체에서 읽어 제시한다. **필드 이름 기반 접근은 이 한 곳만 허용**하고, 필드가 사라지면 검증기가 표시한다.

## 6. 에디터 UX

### 6.1 요소 추가 흐름 (도전과제 예)

```
[+ 새 도전과제]
 이름: 몬스터 사냥꾼          ← 유일한 텍스트 입력 (ID 자동)
 아이콘: [선택 ▾]
 조건: [+ 조건 추가 ▾] → 수치 이상
        수치 [처치 수 ▾]  ≥  [100]
 보상: [+ 보상 추가 ▾] → 재화 지급
        재화 [골드 ▾]  수량 [500]

 미리보기: "처치 수가 100 이상이면 달성 → 골드 500 지급"
 ✔ 검증 통과 / ✖ 빨간 글씨로 즉시 오류 표시
```

### 6.1A 에디터 디자인 시스템 (2026-09-28 합의)

- 모든 커스텀 에디터는 **UI Toolkit**(UXML·USS·Flexbox, Painter2D, SVG)으로 만든다. Unity 기본 인스펙터 모양을 쓰지 않고 앱·웹 수준의 자체 디자인으로 그린다. IMGUI·Odin은 사용하지 않는다.
- 창마다 따로 만들지 않고 **라이브러리 전용 디자인 시스템**을 먼저 만든다.
  - 디자인 토큰: 색상·여백·글꼴 크기·모서리를 USS 변수로 한 곳에서 정의, 에디터 라이트/다크 테마 자동 대응
  - 컴포넌트: 버튼, 카드, 검색창, 블록 선택 드롭다운, 검증 표시, 진행 바 등을 한 번 만들어 모든 창에서 재사용
  - 모션 토큰: 애니메이션 시간·이징 곡선 통일. USS 트랜지션 + 자체 트윈(스프링·순차 등장·관성)
- 같은 디자인 시스템을 런타임 UI(플레이어 행동 로그 등)에도 사용한다.
- 6.3+ 기능 활용 후보: USS 필터(blur, drop-shadow 등), Shader Graph UI 재질, SVG 기본 지원.
- 한계: Flexbox만(Grid 없음), CSS식 box-shadow·linear-gradient 없음(필터·Painter2D로 대체), Lottie 미지원. USS 필터·Shader Graph UI 재질의 **에디터 창 동작 여부는 미확인** → 시험 창으로 검증.
- **첫 작업: 시험 창 프로토타입** — 에디터 창 안에서 블러·그림자 필터, 트랜지션, 스프링 애니메이션, 커스텀 카드 디자인 동작 확인. (사용자가 데스크탑에서 확인 가능할 때 진행)

### 6.1B 디자인 언어 (2026-09-28 사용자 지정)

참고 이미지: `Documentation~/design-references/ref-01-metric-dashboard.jpg`, `ref-02-crypto-dashboard.jpg` (어두운 대시보드). 포인트 컬러는 참고 이미지의 주황 대신 **핫핑크 rgb(253, 93, 131) #FD5D83** (2026-09-28 변경).

**재사용 원칙: 커스텀 UI는 패널 단위로 재활용한다.** 시트(`GsSheet`), 상세 패널(`GsDetailPanel`), 확인 창(`GsDialog`), 변경 표시(`GsChangeView`), 드롭다운(`GsDropdown`)은 한 번 만들어 모든 창이 같이 쓴다.

**드롭다운**: 모든 선택 목록은 `GsDropdown`을 쓴다(Unity 기본 메뉴·DropdownField 사용 금지). 항목이 8개 이상이면 검색창이 생기고 이름·캡션·그룹·**한글 초성**(`ㅊㅊ` → 처치 수)으로 찾는다. 그룹 머리글, 현재 값 표시(✓), 설명 줄, 비활성 항목, 키보드(↑↓ Enter Esc) 지원.

**톤**
- 다크 테마. 배경은 거의 검정, 패널은 배경보다 한 단계 밝은 짙은 회색.
- 패널 외곽선은 **보일 듯 말 듯한** 얇은 선(흰색 저불투명도). 둥근 모서리. 모던한 형태.
- 텍스트는 흰색. 덜 중요한 정보는 **작고 옅게**(회색·낮은 불투명도)로 위계를 만든다.
- **포인트 컬러는 한 가지.** 선택 상태·주요 버튼·강조 수치·그래프 강조에만 사용. 포인트 요소에 은은한 발광 허용.
- **분류용 팔레트**: 요소 분류(카테고리·태그·시스템 구분)를 위한 **약 10여 가지 동일 톤 컬러**. 쨍한 파스텔톤 — 명도·채도를 맞추고 색상(hue)만 달리한다. 포인트 컬러와 구분되어야 한다. 배지는 해당 색의 옅은 배경 + 진한 글자.

**여백과 공간**
- 간격·여백을 넉넉하게. 공간 분리를 빼곡하게 하지 않는다.
- 구분은 선보다 **여백과 패널 명도 차이**로 한다.

**상호작용 원칙 (정보 우선)**
- 처음 보이는 화면은 **깔끔한 정보 UI**다. "나는 드롭다운이야, 눌러" 같은 인상(화살표, 입력칸 테두리, 버튼 모양)을 기본 상태에서 드러내지 않는다.
- 값은 평소 일반 텍스트로 표시된다. 마우스를 올리면 은은한 강조로 상호작용 가능함을 알리고, **클릭해야 편집 UI(드롭다운·입력칸·선택기)로 전환**된다. 편집이 끝나거나 Esc·포커스 해제 시 다시 정보 표시로 돌아간다.

**시트형 패널** (2026-09-28 개정)
- 좌상단에 타이틀, 그 아래 시트(표) 형태. 헤더는 작고 옅게, 행 구분은 옅은 선 또는 여백.
- **셀은 읽기 전용이다.** 한 번 클릭으로 값이 바뀌는 위험을 없애고, 좁은 칸에서 잘리는 정보는 상세 패널에서 본다.
- 행을 더블클릭하면 상세 패널을 그 셀의 필드로 스크롤해 연다(2026-09-28: `···` 버튼 제거). 칸보다 긴 글자는 끝이 행 배경색 그라데이션으로 흐리게 가려진다.
- 머리줄 경계를 끌어 열 폭을 조절하며, 폭은 탭(타입)마다 보기 설정에 저장된다. 기본값은 설명처럼 긴 글 열을 넓게, ID 열을 좁게.

**카드형 패널 (상황·정보에 따라 선택)**
- **세로형(A)**: 적당히 큰 스프라이트가 위쪽을 꽉 채우고, 아래 패널 공간에 텍스트. 정사각형보다 약간 세로로 긴 비율.
- **가로형(B)**: 스프라이트가 좌측을 꽉 채우고, 우측이 텍스트 영역. 16:9 패널.
- **바형(C)**: 좌측에 작은 스프라이트, 우측에 한두 줄 텍스트. 얇은 막대 형태.
- 카드 A·B의 이미지 영역은 **정사각형**. 카드 C는 이미지 상·하·좌 여백이 같다(10px).
- 카드 종류는 하나의 카드 컴포넌트 + 레이아웃 변형으로 제공하고, 표시할 정보의 양·중요도에 따라 고른다.
- 카드는 읽기 전용이다. **클릭하면 모든 카드가 같은 상세 패널을 연다.**

**상세 패널** (모든 카드·시트 공용, 2026-09-28 합의)
- 배치(2026-09-28 개정): 위쪽에 정사각형 이미지(좌·상 여백 동일)와 그 오른쪽 제목·정보·요약, 그 아래는 전체 폭 정보 영역, 맨 아래 되돌리기·저장. 세로로 넉넉한 크기.
- 이미지는 클릭해서 바꾼다(Unity 오브젝트 선택 창, 끌어다 놓기 가능). 이미지 필드는 정보 영역에 따로 나오지 않고, 되돌리기·저장 확인 창에서만 전후 이미지로 보여준다.
- 도전과제 요약은 두 줄: `조건  처치 수 (누적) 1 이상 달성 시` / `보상  골드 50 획득`.
- 조건·보상 블록은 문장처럼 한 줄로 조립한다: `[처치 수 (누적)] [1] [이상]`, `[골드] [50] 획득`. 대괄호 단어마다 클릭해 바꾼다(블록의 `BlockInfo.Sentence` 템플릿).
  - 문장 블록은 겉패널 없이 한 줄이며 줄 사이는 간격으로만 나눈다. 단어는 외곽선만 있는 패널(여백 넉넉), 주어(첫 단어)와 뒤 내용 사이는 더 띄운다. 바꾸기·삭제는 줄에 마우스를 올리면 오른쪽 끝에 나타난다.
  - 묶음 블록(모두 만족 등)만 이름 한 줄을 두고 하위 문장을 들여쓴다.
- 제목 아래 요약은 `[머리말] 내용` 줄로 나눈다(도전과제: 조건 / 보상, 수치: 방식 / 반영).
- 내용은 필드마다 **헤더 · 내용** 순서로 쌓고, 길어지면 내용 영역만 스크롤한다. 맨 위에 요약 문장(예: 조건 → 보상)과 검증 결과.
- **편집은 이 패널 안에서만**, 원본이 아닌 사본에 한다. 바뀐 필드는 헤더가 포인트 컬러로 바뀌고 위에 이전 값, V자 화살표, 아래에 현재 값으로 표시된다(긴 내용은 줄바꿈, 조건 블록은 문장 단위).
- **되돌리기**: 확인 창(변경 목록 포함) 후 사본을 원본으로 되돌린다. **저장**: 변경 목록(이전 → 현재, 위아래 배치)을 나열한 확인 창 후 원본에 반영(Undo 가능).
- 저장하지 않고 닫으면 계속 편집 / 버리고 닫기 / 저장하고 닫기를 묻는다.

### 6.1C 데이터–화면 연결 (2026-09-28 합의)

타입별 하드코딩 없이 모든 데이터 타입을 같은 카드·시트로 보여준다.

**슬롯**: 카드는 데이터 타입을 모르고 슬롯만 안다 — 이미지(Sprite만), 제목, 부제목, 배지(enum·태그 → 분류 팔레트 색), 수치 목록. 카드 A·B·C는 같은 슬롯의 배치 변형. 시트는 열(column)이 슬롯 역할.

**기본 흐름: 어트리뷰트 불필요**
1. `GameData` 상속 클래스를 만들면 데이터베이스 창에 나타나고 **자동 추론**으로 표시된다 (첫 Sprite → 이미지, `name`/`displayName` → 제목 등).
2. 원하는 부분만 **화면 설정(보기 설정 에셋)**에서 메뉴로 바꾼다: 레이아웃, 슬롯별 필드. 슬롯에 맞는 타입의 필드만 목록에 표시.
3. 게임별 데이터 클래스에는 데이터 필드 외의 코드를 쓰지 않는다.

**필드 이름 변경 대응**: 화면 설정은 필드를 이름으로 기억한다. 필드가 사라지면 검증기가 끊긴 연결을 표시하고, 같은 타입의 비슷한 필드를 후보로 제안해 클릭 한 번으로 재연결한다.

**어트리뷰트 (선택, 라이브러리 내장 타입 전용)**: `[CardImage]` `[CardTitle]` `[CardBadge]` `[CardStat]` `[SheetColumn]` `[SheetHidden]`, 클래스에 `[CardLayout]`. 화면 설정 에셋은 프로젝트마다 따로 생기지만 어트리뷰트는 코드와 함께 이동하므로, 도전과제처럼 **공용 라이브러리가 제공하는 타입**이 어느 프로젝트에서든 처음부터 잘 보이게 하는 기본값으로만 사용한다.

**우선순위**: 화면 설정 > 어트리뷰트 > 자동 추론.

**편집·모니터링**
- 값 수정은 SerializedProperty 경로 → Undo·다중 편집·검증 자동 적용.
- 플레이 중에는 같은 카드가 상태 저장소(§9A.4)의 런타임 값에 연결되어 변경 알림으로 즉시 갱신.

### 6.1D 데이터베이스 등록 판별 (2026-09-28 합의)

**정의 데이터와 런타임 상태를 구분한다.**
- 정의 데이터(아이템 정의, 캐릭터 정의, 도전과제 …) → **데이터베이스 창**
- 런타임 상태(플레이 중 캐릭터의 현재 체력 등) → **모니터 창** (관찰 계약 §9)

**등록 기준: 명시적 참여(opt-in)**
- 데이터베이스 항목은 공용 베이스 클래스 `GameData`(ScriptableObject)를 상속한다. 상속하면 코드 추가 없이 창에 자동으로 나타난다.
- `GameData`가 제공하는 필수 계약: 자동 ID(변경 불가), 표시 이름, 태그, 검증 훅, 관찰 계약.
- 선택 메타데이터: `[Database("아이템", Group = "인벤토리", Icon = …)]` — 창의 표시 이름·분류·아이콘. 없으면 클래스 이름 사용.
- 제외: 추상 클래스, 제네릭 정의, `[HideInDatabase]`, 테스트·샘플 어셈블리.
- 탐색은 Unity `TypeCache`(컴파일 시 캐시되는 타입 목록)로 한다 → 프로젝트가 커져도 빠르고, 컴파일 직후 자동 갱신.
- 항목 안에 들어가는 일반 C# 클래스(예: 아이템의 효과 목록)는 독립 표가 아니라 항목 내부 필드로 표시된다.

**놓침 방지**
- `GameData`를 상속하지 않은 ScriptableObject 데이터 타입이 프로젝트에 있으면 창 하단에 "등록되지 않은 데이터 타입"으로 옅게 알린다.
- 새 타입이 등장하면 기존 에셋을 자동으로 찾아 목록에 포함하고, 새 항목 생성 시 폴더 배치·파일 이름은 창이 처리한다.
- 같은 등록 기준이 서버용 JSON 내보내기(§8.2) 대상도 결정한다.

### 6.1E 설정 흐름과 도움말 (2026-09-29 사용자 지정, 이후 모든 기능에 적용)

목표: 비프로그래머 개발자도 모든 기능을 다룰 수 있게 한다.

- **시작하기**(도감 사이드바 맨 위): 새 프로젝트 설정 단계를 순서대로 보여 준다. 단계마다 자세한 설명, 자동 판정한 현재 상태, 바로 하기 버튼(해당 종류 열기·만들기 등), 도움말 연결을 둔다. 자동 판정이 없는 단계는 직접 '완료로 표시', 선택 단계는 '건너뛰기'. 진행 표시는 `ProjectSettings/GameSystems/Setup.json`(팀 공유). 필수 단계가 남아 있으면 도감을 처음 열 때 시작하기가 먼저 보인다.
- **도움말**(메뉴 Game Systems › 도움말): 모든 창·탭·도감 종류·블록의 설명을 분류별로 모으고 검색한다. 도감 제목, 상세 패널, 모니터 탭 제목, 배치 편집의 블록, 시작하기 단계 옆 `?` 버튼이 해당 항목을 연다(툴팁은 요약).
- **등록**: 도움말은 `IHelpProvider`, 설정 단계는 `ISetupProvider` 구현 클래스를 TypeCache로 수집한다. 기본 항목은 `Editor/Help/BuiltInHelp.cs`, `SetupSteps.cs`. 조건·보상·필터 블록과 배치 블록은 어트리뷰트의 `Description`으로 항목이 자동 생성된다.
- **강제**: `HelpCoverageTests`가 기본 도감 종류·모니터 탭의 직접 쓴 도움말, 블록 `Description`, 도움말의 제목·요약·본문·연결, 설정 단계의 설명·도움말 연결, 기본 도감 종류가 시작하기에서 이어지는지를 검사한다.
- **문체**: 매뉴얼보다 약간 친절한 정도. 비유·지나친 풀이 없이 가독성 우선(첫 문장에 핵심, 짧은 문단, 소제목·목록).

## 8. 멀티플레이어

1. **정의와 상태 분리**: 정의는 공유 읽기 전용. 달성 상태·수치·진행도는 **플레이어별 컨텍스트**.
2. **static 제거**: 시스템을 인스턴스 기반으로. 싱글 게임은 `Default` 인스턴스로 기존처럼 간편하게 사용. 테스트는 독립 인스턴스로 격리.
3. **범위**: 수치에 플레이어 / 팀 / 매치 / 전체 범위.
4. **판정 권한**: 달성 판정은 서버. 클라이언트는 결과·상태를 받아 표시. 이벤트는 발생 주체(플레이어 ID)를 가진다.
5. **네트워크 무관 핵심**: 핵심 로직은 순수 C#. Netcode for GameObjects / Mirror / Fish-Net / Photon 등은 **어댑터 층**으로만 연결.
6. **플랫폼 동기화**: Steam·콘솔 도전과제도 어댑터로 연결.

### 8.2 엔진 무관 코어 (유형 A 필수 조건)

- 유형 A의 서버는 Unity 없이 .NET으로 게임 로직을 실행한다. 헤드리스 Unity 서버보다 한 프로세스가 훨씬 많은 매치를 처리한다.
- 따라서 로직 층(Events, Stats, Conditions/Rewards, Achievements, Action, 상태 저장소, 난수)은 **UnityEngine을 참조하지 않는 순수 C# 어셈블리**로 만든다(asmdef `noEngineReferences`). Unity 전용 부분(에디터, 표현, SO 작성 도구)은 별도 어셈블리.
- 정의 데이터: 작성은 SO, **빌드 시 엔진 무관 런타임 데이터(JSON)로 내보내** 클라이언트와 서버가 같은 데이터를 읽는다.

### 8.3 유형 A 보안 원칙

- 클라이언트는 행동(Action)만 보낸다. 서버가 모든 행동을 검증·실행하고 결과만 돌려준다.
- 재화·인벤토리·구매 내역은 서버 DB에만 존재한다. 클라이언트 값은 표시용.
- 숨겨진 정보(상대 패, 시야 밖 정보)는 클라이언트로 보내지 않는다 (§9A.4의 공개 수준 사용).
- 경쟁 매치의 난수 시드는 서버만 보유하고, 매치 종료 후 리플레이용으로 공개한다.
- 결제 아이템 지급은 Steam 서버 측 확정을 받은 뒤에만, 주문 ID 기준 중복 지급 방지.

### 8.4 유형 A 안정성 원칙

인프라(AWS 관리형 서비스, Steam API)는 업계 표준으로 안정적이다. 위험은 직접 작성하는 로직에 있다.

- **매칭은 직접 구현하지 않는다.** AWS GameLift FlexMatch를 매칭 전용(standalone)으로 사용하고, 매칭 결과 알림을 받아 .NET 서버가 매치를 시작한다. (Nakama는 서버 로직 언어가 C#이 아니어서 코드 공유 구조와 맞지 않음)
- 매칭이 반드시 보장해야 하는 성질:
  - 한 유저는 동시에 하나의 매치에만 속한다 (티켓 상태의 원자적 전이)
  - 전원 수락 후에만 매치를 확정한다. 이탈 시 매치 취소, 남은 인원은 대기 시간을 유지한 채 재대기
  - 대기 시간에 따라 허용 실력 범위를 확장하고, 최대 대기 시간을 넘기면 대안 처리
  - 신호가 끊긴 티켓은 자동 만료
  - 서버는 전원 접속을 확인한 뒤에만 첫 턴을 시작
- **멱등성**: 모든 행동과 결제에 고유 번호. 같은 번호의 재전송은 무시.
- **복구**: 매치 상태는 턴 확정마다 DB 저장, 재접속 시 이어서 진행. 결제 확정과 지급 내역을 주기적으로 대조해 누락분 보정.
- **검증**: 가상 유저 부하 테스트(무작위 이탈·거절·재접속) + 불변식 자동 검사("한 유저 두 매치 없음", "모든 매치 정원 충족", "최대 대기 시간 준수"). 매칭 서버도 관찰 계약(§9)을 따른다.

## 9. 관찰성 (Observability)

모든 시스템은 런타임이든 아니든 모든 상태를 확인할 수 있어야 한다. 개별 패널이 아니라 **공통 계약**으로 보장한다.

| 항목 | 내용 |
|---|---|
| 스냅샷 | 현재 상태 전체를 트리로 제공 |

| 디버그 명령 | 값 설정, 강제 달성, 초기화 등 테스트 조작 |

### 9.2 통합 기록 (Journal)

모든 기록은 **원인 기록 ID**를 가진다 → 인과 사슬 추적.

```
#1310  [Event]         적 처치 (player 1, 고블린)
  └ #1311  [Stats]        처치 수 99 → 100
      └ #1312  [Achievements] 몬스터 사냥꾼 달성
          └ #1313  [Rewards]      골드 +500 (1200 → 1700)
              └ #1314  [Save]         슬롯 0 저장
```

이벤트 발동 내역, 세이브 입출력, 수치 변화, 달성·보상이 모두 같은 기록에 들어간다. 링 버퍼로 크기 제한.

## 9A. 행동 기록과 되돌리기 (Action / Undo / Rewind / Replay)

> 당장 구현하지 않는다. 그러나 **1단계 기반부터 이 요구를 전제로** 만든다. 되돌리기를 고려하지 않은 구조에 나중에 추가하는 것은 사실상 재작성이다.

### 9A.1 목표

- 모든 플레이어 행동을 기록한다. 플레이어는 UI로, 개발자는 모니터로 확인한다.
- 행동을 되돌릴 수 있다: 턴제의 **수 Undo**, 실시간의 **되감기·역재생**, 그리고 **리플레이·관전**.

### 9A.2 Action 층

- 행동은 메서드 호출이 아니라 **직렬화 가능한 데이터**다: 주체(플레이어 ID), 종류, 파라미터, 틱/턴.
- 모든 플레이어 행동은 **행동 처리기(Action Dispatcher)**를 거친다.
- 이 한 경로가 멀티플레이어(클라이언트 전송 → 서버 검증·실행), 행동 로그, 되돌리기, 리플레이를 함께 담당한다.
- 행동은 통합 기록(§9.2) 인과 사슬의 **뿌리**다.

```
[Action] #88  플레이어 1: 고블린 공격 (턴 12)
  └ [Event] 적 처치
      └ [Stats] 처치 수 99 → 100
          └ [Achievements] 몬스터 사냥꾼 달성
              └ [Rewards] 골드 1200 → 1700
```

### 9A.3 되돌리기 방식

| 방식 | 사용처 |
|---|---|
| 변화 기록 역적용 (Journal의 이전값을 거꾸로 적용) | 수 Undo |
| 스냅샷 (체크포인트마다 전체 상태) | 되감기의 기준점, 리플레이 시작점 |
| 결정론적 재실행 (스냅샷 + 행동 기록 재실행) | 되감기, 리플레이, 롤백 넷코드 |
| ~~행동마다 역연산 코드 작성~~ | **사용 금지** — 부수효과 누락 시 조용히 상태가 어긋남 |

### 9A.4 지금 기반에 넣는 제약 (필수)

1. **상태 저장소**: 모든 게임 상태는 프레임워크가 추적하는 저장소에 둔다. 변경은 추적 API로만 하며 `이전값 → 새값`이 자동 기록된다. 직접 필드 대입·숨은 `static` 상태 금지. 관찰성 기록과 되돌리기 기록은 **같은 데이터**다.
2. **트랜잭션**: 행동 하나로 발생한 모든 변화는 한 트랜잭션. 되돌리기 단위 = 트랜잭션.
3. **값 기록 형식**: 증분(+500)이 아니라 이전값과 새값을 모두 기록. 기록 값은 복사본(불변).
4. **효과 분류**: 모든 보상 효과는 `게임 상태 안 / 게임 밖(결제·플랫폼 전송)` 중 하나를 선언한다. 도전과제 달성·보상은 어느 쪽이든 Undo 이력에 넣지 않는다(State.Permanent). 선언 누락은 계약 테스트가 실패시킨다. (2026-09-29: 확정 단계를 없애며 '확정 후 실행' 분류 삭제)
5. **결정론 기반**: 게임 로직은 `UnityEngine.Random`·`System.Random`·`Time`을 직접 쓰지 않고 프레임워크의 **시드 난수 스트림**과 **게임 시계**를 쓴다. 난수 상태는 스냅샷에 포함.
   - 난수는 프레임워크 자체의 **정수 기반 알고리즘** → 같은 시드면 어느 기기·플랫폼에서든 같은 순서 (기기 간 세션 공유).
   - 난수는 **용도별 스트림**(맵 생성 / 드롭 / 전투 …)으로 분리 → 한 시스템에 난수 호출을 추가해도 다른 시스템의 결과는 바뀌지 않는다.
6. **로직·표현 분리**: 되감기는 로직 상태를 되돌리고, 화면(트윈 연출·파티클·대화 타임라인)은 **상태로부터 재동기화**된다. 역재생 연출은 표현 층의 선택 기능.
7. **행동 로그 표시**: 행동마다 `Describe()` (TextTable 다국어 키). 공개 수준: 플레이어 공개 / 개발자 전용 / 멀티플레이 상대에게 비공개.
8. **상태 구역 분리**: 상태 저장소는 두 구역으로 나뉜다.

   | 구역 | 예 | 되감기 |
   |---|---|---|
   | 세션 상태 | 맵, 유닛, 체력, 인벤토리, 이번 판 수치 | 되감긴다 |
   | 메타(프로필) 상태 | 도전과제, 누적 수치, 계정 보상, 해금 | 되감기지 않는다 |

9. **행동은 즉시, Undo는 이력 (2026-09-29 개정)**: 행동은 실행되는 즉시 끝나며 대기·확정 단계가 없다. 실행한 행동은 이력에 쌓여 언제든 뒤에서부터 되돌린다(이력 한도 HistoryLimit, 기본 무제한). 실시간 게임은 행동별 기록 대신 일정 간격 스냅샷(HistoryMode.Snapshots)으로 되감으며, 게임 코드는 어느 방식이든 `session.Undo()` 하나를 쓴다. 되돌리면 행동이 바꾼 값·난수(스냅샷은 시간까지)가 돌아가고, 도전과제 달성과 보상은 유지된다(스냅샷 되감기는 되감은 구간의 달성·보상을 다시 적용). 값이 돌아가므로 같은 진행을 되풀이해도 쌓이지 않는다 → 파밍 차단.

### 9A.5 결정 사항 (2026-09-28)

- **결정론 수준**: 난수 결정론(기기 간 동일)은 필수. 전체 시뮬레이션 결정론(고정소수점·물리 배제)은 채택하지 않는다 — 필요한 장르(롤백 넷코드·락스텝)에서 게임별로 선택.
- **되감기·리플레이는 재계산이 아니라 기록된 상태(변화 기록 + 스냅샷)로 수행** → 어느 기기에서 재생해도 동일. 세션 공유 = 시드 + 행동 기록 + 스냅샷 전달.
- **되감기 범위**: 행동이 바꾼 값(세션·메타 구역 모두). 도전과제 달성과 보상은 되감지 않는다.
- **도전과제 달성 시점 (2026-09-28, 2026-09-29 개정)**: 달성과 보상은 조건을 만족하는 즉시 일어나고 Undo·되감기로 취소되지 않는다. 값(골드 등)만 되돌아간다.

### 9A.6 정책 (게임별로 정함)

- 멀티플레이어 되돌리기는 서버만 수행하며, 허용 조건(합의·규칙)은 게임별 정책.
- 되돌리기 방식(행동 단위 / 스냅샷 / 없음), 이력 한도, 스냅샷 간격·보관 개수.
- 기록 보존: 링 버퍼 크기, 스냅샷 간격, 오래된 기록 압축.

**구현 중 확정한 세부 결정**
- Undo 단위는 행동 하나. 상태를 바꾸지 않은 행동(빗나감 등)도 Undo 단위에 포함한다.
- Undo하면 난수 상태도 행동 직전으로 되돌린다 → 같은 행동은 같은 결과(결정론, "좋은 결과 나올 때까지 Undo" 차단).
- 값 변화의 원인은 그 변화를 만든 행동이다 → 기록이 `행동 → 상태 → 달성 → 보상`으로 이어진다.
- ID 형식은 임시로 `접두어_0001` 자동 연번(`EditorDatabase.NextId` 한 곳만 바꾸면 된다). 미결 유지.
- 카드 슬롯용 어트리뷰트(`[CardImage]` 등)는 아직 만들지 않았다. 라이브러리 내장 타입은 자동 추론으로 충분히 표시된다.
- 식별자 기능 정리(2026-09-29 사용자): 태그와 선택지를 **키워드**로 합쳤다. 키워드 그룹(부모) 아래 키워드. 식별 기능은 플레이어 데이터(구 상태 키, StateKeyData) · 키워드 · 필드 규칙 세 가지. 필드 형식이 개수를 정한다(string = 하나, string 목록 = 여러 개). 주 흐름은 `키워드 연결` 창(왼쪽 필드 · 오른쪽 그룹, 필드 규칙 자동 생성), 도감 탭은 확인·유지보수용. 규칙은 필드를 선언한 클래스에 건다. GameIds: `PlayerData`, `Keyword.그룹.키워드`.
- 키워드 탭(2026-09-29 사용자): 키워드와 키워드 그룹을 도감 사이드바의 한 탭(`[Database(Page = "keywords")]`, 그룹은 `Hidden`)에서 다룬다. 전용 화면은 `CodexPage`(TypeCache 수집). 그룹 순서·키워드 순서는 숨긴 `order` 필드, 끌어 놓기로 바꾸고 키워드를 다른 그룹으로 옮긴다.
- 도감 변경 모아 두기(2026-09-29 사용자): 도감의 모든 변경은 `CodexStaging`(작업본·새 항목·삭제 목록)에 모이고, 탭을 옮길 때 변경 목록(전후 값)을 보여 주고 적용/되돌리기. `EditorDatabase.All`은 적용 대기 변경을 덮어씌운 모습, `Committed`는 실제 에셋(GameIds·런타임 목록 동기화용). 적용 순서: 삭제 → 수정 복사 → 새 에셋 → ID 바꾸기(참조·파일 이름·변경 이력). 플레이·창 닫기·종료 때 확인, 재컴파일 때 SessionState로 보존. 예외: 프리팹 컴포넌트 수정·스프라이트 베이크는 즉시.
- ID·이름(2026-09-29 사용자): 도감 항목은 ID로만 식별한다(표시 이름 필드 없음, DisplayName = ID). ID 형식은 lowerCamelCase(`playerGold`, `player.inventory`), 대소문자만 다른 ID는 중복으로 막는다. 새 항목 제안 ID는 접두어+연번(`keyword3`).
- 그룹 탭(2026-09-29 사용자): 키워드·스프라이트 규격은 `GroupedCodexPage`(그룹 카드 + 항목 칩, 왼쪽 옅은 세로선 손잡이로 그룹 순서, 칩 끌어 순서·그룹 이동). 순서·소속은 `IOrderedData`·`IGroupedData`, 만들기는 `CodexGroups`. 기본 테두리(적용 대기는 배지로만).
- 입력 칸(2026-09-29 사용자): 탐색기·상세 패널·대화 상자의 값 칸은 `GsField`(둥근 상자 안 위 이름표·아래 값, 비어 있음/편집 중 밑줄/오류 빨강+문구/비활성). 긴 값은 5줄까지 늘고 그 이상은 칸 안 스크롤. 상세 패널은 좁고 긴 모양(폭 480 이하), 블록은 한 줄씩(SingleColumn).
- 수치 → 로그(2026-09-29 사용자): StatData 탭 이름을 '로그'로. 플레이 중 쌓이는 기록(처치 수, 최고 콤보)만 로그에 두고, 골드처럼 쓰고 줄어드는 자원은 플레이어 데이터로 두는 방향(샘플 골드 이전·플레이어 데이터 보상 블록은 미정).
- ScriptableObject는 파일 이름과 클래스 이름이 같아야 에셋이 스크립트를 찾는다 → 도감 종류마다 파일 하나(TemplateData.cs, PrefabData.cs, SpritePreset*.cs, SpriteSpecDatabase.cs, Keyword*.cs, FieldRuleData.cs).
